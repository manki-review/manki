# Manki — Agent & Contributor Guide

Manki is a GitHub Action that runs a multi-agent LLM code review on pull requests. This file captures the repo conventions that both human contributors and coding agents (Claude Code, Codex, Cursor, Aider, Continue, etc.) should follow. It's read natively by all of those tools — one file, all agents.

See `README.md` for what manki does and `docs/getting-started.md` for installing it in a repo. This file is strictly about conventions for working on manki itself.

## Pipeline order

The review stages are listed in this order: **planner, reviewer, judge, dedup**. Per-stage config keys (`models.{planner,judge,second_refuter,dedup}`), logs and docs follow it, so keep new per-stage items in the same order. The reviewer stage has no key in `models`: the finders are the entries of `review.groups`. `second_refuter` is the second refuter's model and sits next to `judge`. `fallback` is not a stage and comes last.

At run time, `runReview` in `src/review.ts` calls dedup before the judge:

1. **Planner** triages the change (`trivial`, `subtle`, `paired`) and picks the judge effort. `selectTeam` sorts the PR into a review class (`classifyPr` in `src/routing.ts`) and runs the class's review group: the trivial verifier alone, one finder, or two finders on different models. Every finder gets the same `buildFinderAgent` checklist, so a pair differs only in its models. Security-sensitive, CI or dependency, and data contract paths are floor classes that force two finders.
2. **Finders** run in parallel and produce findings. A failed finder is retried once, unless it reached a limit or ran out of time, and only with the time the round has left (`ROUND_TIME_MS`, enforced through `withSignal`). A finder that still fails makes the round incomplete. A finder with tools that opens none of the files listed for it outside the changed files is asked once more (`askAgain` in `runReview`), and its first answer stays when that second ask fails. A finder that reads in slices is asked on the slice the unopened files pick and on each slice with a unit left without a line, and the findings of its slices stay. Each finder also gives a line per unit of the change that `listUsesOutsideDiff` lists, a changed function or condition, at most 20 per call (`dealUnits`), and the same second ask names a unit it left without a line. Alongside them, the sibling comparisons (`runComparisons` in `src/compare.ts`) ask one small call per sibling field or sibling implementation that `listUsesOutsideDiff` found, and add their findings to the finders'. So do the related repo checks (`runRelatedChecks` in `src/compare.ts`): one small call per counterpart that `listRelatedUses` found in a related repo, which keeps a finding only with a cited line on both sides. So do the claim checks (`runClaimChecks` in `src/pr-claims.ts`): one small call per statement of the PR text that the change relies on, which never reads the PR description and reports only a statement the code disproves. A claim can add a check and never remove one, so no other stage reads a claim or its status. So do the pattern checks (`runPatternChecks` in `src/compare.ts`): one small call per piece of structure the change adds, which `listUsesOutsideDiff` lists, that compares it with at least two existing places doing the same kind of thing and reports only a difference it can cite. So do the fix checks (`runFixChecks` in `src/fixes.ts`): `listFixes` lists the fixes of the diff without the PR text, and one small call per fix follows its problem to the cause and reports only a workaround that cites a line outside the fix. The scope reader (`runScopeReader` in `src/scope.ts`) also runs alongside them: one call on the judge's client that says whether the PR is useful and whether it should be split. It adds no finding for the judge, and its answer is listed in the review body. With `review.scope_blocks` it becomes warnings after the judge and the refuter, which skip the judge's grading and only add a hold. A doubt needs the refuter's confirmation first (`confirmDoubt`). Each warning goes to the one thread of its kind by its fixed title (`placeScopeWarning`), never through dedup. Once the finders and these checks are done, a second read (`readAgain` in `runReview`) runs on a first complete review or after a push that changed more than half of the diff (`getsSecondReads`): the finder that found the fewest repeats its call with the location and title of each finder's finding, at most twice while a read adds a blocker or warning. Its findings go through dedup and the judge, where a read's copy never changes a finder's grade (`bySecondReadsOnly`), and a read that fails leaves the round complete.
3. **Dedup** drops findings matching resolved findings from earlier rounds, first statically, then with the `dedup` model. A thread Manki settled by agreeing with an answer that accepted no fix drops a repeat in its own file only while the push left the lines the thread, its findings, Manki's answer and the repeat cite alone (`citedCodeUnchanged` in `src/review.ts`). While it does, the judge may also link a finding to that thread's finding, which drops the finding after the judge. A thread whose agreed answer names a tracking issue that is open, was opened by a writer and names the code the thread cites (`deferredThreadIds` in `src/review.ts`, read by `findRelatedWork`) skips that line check for the judge's link, so a linked repeat not graded above the thread is dropped whatever the push changed. The ratchet and the in-PR suppression drop a repeat of an agreed thread only while `citedCodeUnchanged` finds the lines the thread and the repeat cite unchanged, read from the push or from GitHub's comparison since the round that raised the thread (`diffsSinceRaised`).
4. **Judge** evaluates the rest, and is skipped when nothing is left to judge: no finding, no open thread and no carried warning it is asked about, with the open threads and every earlier round record read. It merges same-round duplicates and states each finding's severity table cell, from which `mapJudgedToFindings` works out the grade. When the judge's `grade`, the verdict of its reasoning, is lower than a blocker cell gives, the finding is held at a warning like a doubted one, with its `consequence` doubt the judge's own or, without one, that the row's damage happens and normal operation does not undo it (`damageDoubt`). A finding every finder filed as a blocker, a security finding and one another doubt already holds keep their path. For a blocker cell it doubts, the judge also states the grade the finding earns once its doubts hold (`gradeIfConfirmed`), and `warning` there keeps a confirmed finding a warning. A blocker cell whose trigger the judge marks not realistic (`rareTrigger`) gets the premise that its trigger happens in realistic use as a doubt, so it blocks only once the refuter confirms that trigger, unless it is a security finding. A doubt holds no security finding down, except one whose `securityClass` is a cost or an input form that gets past a check (`DOUBT_HELD_CLASSES` in `src/judge.ts`), which only a confirmation of every doubt makes a blocker. A judge with repository tools then tries to refute the blockers and the findings it doubted (`refuteBlockers` in `src/refute.ts`). A check confirms a defect only when it cites lines for both the trigger normal use produces and the wrong result someone can observe (`parseRefutation`). The scope reader's doubt, a finding graded by the rule it breaks and an answer about a premise need neither (`statesNoFailure`). When the judge drops a finder's blocker for a reason about code outside the diff, it states that premise and the cell the finding earns without it (`dropRestsOn`), and the refuter checks the premise as a `drop` doubt. The finding comes back at that cell only when the check disproves the premise. A confirmation of every doubt gives a blocker cell its blocker when every finder that reported the finding filed it as a blocker, on a security finding, or when the finding restates an earlier blocker. When two or more finders ran, a finding only one of them reported, with no other check beside it, counts as not filed by every finder (`soleFinder`): a second read counts as the finder whose call it repeated, only on a finding no finder reported, and a sweep as the reporters of the finding it started from (`countedReporters` in `src/types.ts`), so neither is a second reporter, and any other check is. When a refuter runs, such a blocker cell is held like a doubted one even without a doubt, with `damageDoubt` as its consequence unless the judge named one. Any other such finding needs every check to confirm the defect and the consequence the judge names as a premise, and without that premise it stays a warning (`keepsWarning`). Beside the refuter, each blocker and warning the location does not settle gets an origin check (`checkOrigins` in `src/origin.ts`), at most `MAX_ORIGIN_CHECKS` a round: one small call that reads the merge base and answers `introduced`, `worsened`, `pre_existing` with the failing lines on both sides, or `unsure`. The code reads every cited line. On a flagged line the PR left unchanged it requires that line at its base place with the same text, and on any other line a line of the finding's own file at the base. The second refuter's model gives a second answer where one does not settle it. A blocker the judge raised above every finder's grade stays one only when the stored checks agree that the defect is confirmed, and otherwise goes back to the highest finder grade (`capUnconfirmedRaise` in `src/refute.ts`), unless it is a security finding, a tool alert, an open lead or restates an earlier blocker, and a broken rule keeps the grade `review.rules` gives. The judge's own pre-existing call never lowers a grade. Memory suppressions then hide matching findings, never a blocker, a security finding or a tool alert. Then `markPreExisting` in `src/review.ts` tags the findings the PR did not cause: by location, or by the origin answers (`foundOnBase` in `src/types.ts`). A blocker, a finding that would block, a security finding, the warning of a disproved blocker and any finding on a changed line need two `pre_existing` answers on different known models (`sameOnBase`). A warning or note on an unchanged line needs one, with no answer against it (`oneCheckOnBase`). On a blocker, one passing answer changes no grade and only adds a note that the finding may be older than the PR. It posts only the security findings among them, a blocker as a warning except on code the PR did not touch, whatever the origin checks found. Every other pre-existing finding is kept in the round record only, whatever its grade. Any other finding the origin checks made pre-existing is posted as a note when an answer names a line the PR added or changed that fixes the same failure on another path (`fixedElsewhere`). A warning that neither its cited lines nor a tool check proves is kept in the round record only (`hideUnprovenWarnings`), unless the judge graded it a blocker or would once its doubts hold (`wouldBlockIfTrue`). The grade a finder filed does not count. So is a warning without a realistic trigger, on any row (`unpostedForTrigger` in `src/refute.ts`). One that would be a blocker if true needs a check that disproves its trigger first. When two finders ran and fewer than two of them reported such a warning on the `degraded` row, the refuter also checks its trigger (`doubtTrigger` in `src/judge.ts`). It also checks the trigger of such a warning that would be a blocker if true and the judge named no trigger for, and leaves that warning out for its trigger only when the check disproves it (`disprovedTrigger`). Each posted blocker and warning gets its `checkStatus` there (`checkStatus` in `src/refute.ts`). A blocker that restates an open thread after the push applied that thread's own suggested fix is posted in that thread as a warning once the refuters confirm the fix from lines the push added, or the judge's refuter alone when no second refuter is set (`restatedAfterOwnFix` in `src/review.ts`). `determineOutcome` then decides whether any finding blocks.
5. **Other finder's vote** runs after the refuter, on a round with two or more finders, for each blocker and warning one finder alone reported (`soleFinder`) or only second reads reported, unless it is a security finding, `gradedByRule` or restates an earlier thread (`otherFinderVotes` in `src/other-finder.ts`). One call without tools on the model of a finder that did not report it, without a fallback model, and for a second read's finding on another model than the read's, sees the lines the finding cites and those its checks cite as trigger and result, without the checks' answers, and names a `trigger` line and a `result` line, each quoted, `none` or `not_shown`, in the refuter's words for the two (`TRIGGER_MEANING` and `RESULT_MEANING` in `src/writing-rules.ts`). Only both lines held by the head with their code within 3 lines back the finding. Any other answer declines it: a blocker is posted as a warning that `DISPROVED_TAG` guards, with its cell kept as `judgeCell`, and a warning as a note that no step leaving notes out removes (`votedDown` in `canLeaveOut`), also a warning the judge held in a blocker cell. A `not_shown`, for code the call does not show, changes no grade. A line in a file the head cannot read gives no vote. A call that times out is asked once more. `withVote` ignores the vote on a blocker the refuter disproved and on a finding `gradedByRule` once the refuter is done. A failed call, or one without the time for its own timeout plus `MIN_JUDGE_MS`, changes nothing and never stops the round.
6. **Importance** runs last of the grading steps, once the round is down to what it posts (`src/importance.ts`). One call on the judge's client, without tools, rates every posted warning that `getsScore` in `src/review.ts` accepts, from 1 to 10. The call shows no grade, reporter or check. A warning whose `trigger` is below `review.min_warning_trigger` and whose `matters` is below `ALWAYS_POSTED_MATTERS` is not posted: it goes to `unposted` with `rare_trigger`, its scores and the cut-off. `mayBeLeftOut` keeps every guarded finding (`isGuardedFinding`), tool alert, finding `gradedByRule`, finding that `wouldBlockIfTrue`, pre-existing finding, scope warning and open lead posted, and `getsScore` one an earlier thread or review body carries or that restates an earlier blocker or a finding of an open thread. A warning that restates one an earlier round rated takes those scores (`withEarlierImportance`), read from the posted entries and the `rare_trigger` ones of the round records, and stays left out or posted as that round had it. A failed call, one without the time for its own timeout plus `MIN_JUDGE_MS` and a finding without a usable entry after one retry change nothing.
7. **Verdict reader** runs only when nothing blocks. It reads the whole diff cold on the judge's client and returns `READY` or `ADDRESS_FIRST` (`src/verdict.ts`).
8. **Tracking issues**: once the grades are final, one call on the `dedup` model matches the findings to the open issues and PRs of related work that a person with write access opened (`linkTrackingIssues` in `src/related-work.ts`). A match only adds "Tracked in #N" to the finding and changes no grade.

## Commit messages

- Short, imperative, with backtick highlighting for identifiers (function names, types, file paths, etc.)
- Example: `` fix: handle `None` case in `parseConfig` for missing `models` field ``

## Changelog

- Never edit `CHANGELOG.md` in a feature or fix PR. CI rejects it. The release PR writes the changelog from the merged PRs, so put what users need to know in the PR title and body.

## Docs

- A change to behavior, config, action inputs or review output updates the docs it affects in the same pull request. [Where to look](#where-to-look) says which file covers what.

## Code style

- Imports at the top of the module. No `import` inside functions, methods, or blocks.
- Remove dead code rather than suppressing warnings (no `// eslint-disable` for unused code). Git history is the archive.
- Prefer the most restrictive visibility that compiles. Default to non-exported; only widen when required.
- Don't introduce emojis to the codebase. Don't add comments that narrate the change ("now returns...", "fixed X").

## Testing

- Before adding a new `test()`/`it()`, search for an existing test that fits the context and extend it with a new case.
- Before creating a test helper, search for existing utilities — test helpers typically live next to the code they exercise in `src/*.test.ts`.
- Never ignore or skip failing tests. Fix the root cause. If the fix is genuinely out of scope, open an issue first and link it from the skip.
- Never open, search or quote the benchmark's hold-out cases in `bench/holdout/` while working on Manki. Exclude that directory from every search. Develop and debug against `bench/cases` only, since the hold-out score decides releases.

## Architecture quick reference

- `src/providers/` holds the LLM integration. Every model call goes through the `LLMClient` interface (`types.ts`), built per stage by `createLLMClient` (`factory.ts`). `anthropic.ts`, `openai.ts` and `gemini.ts` implement it over each provider's SDK or CLI.
- `src/config.ts`: config schema, defaults, validation (`DEFAULT_CONFIG`, `KNOWN_KEYS`, `validateConfig`).
- `src/review.ts`: planner (`runPlanner`), team selection (`selectTeam`), parallel finder loop, dedup and judge calls, round outcome (`runReview`, `determineOutcome`).
- `src/agents.ts`: the finder prompt (`buildFinderAgent`) and the trivial verifier.
- `src/routing.ts`: review classes, groups and floors (`classifyPr`).
- `src/judge.ts`: judge agent (`runJudgeAgent`).
- `src/refute.ts`: the refuter (`refuteBlockers`).
- `src/origin.ts`: the origin check (`checkOrigins`), whether the PR caused a blocker or warning.
- `src/verdict.ts`: verdict reader (`runVerdictReader`).
- `src/other-finder.ts`: the other finder's vote on a blocker or warning one finder alone reported (`otherFinderVotes`, `withVote`).
- `src/importance.ts`: the importance rating of the posted warnings (`rateWarnings`, `mayBeLeftOut`, `withImportance`).
- `src/compare.ts`: sibling comparisons (`runComparisons`) on the questions `listUsesOutsideDiff` (`src/symbol-uses.ts`) finds, related repo checks (`runRelatedChecks`) on the counterparts `listRelatedUses` finds, and pattern checks (`runPatternChecks`) on the added structure `listUsesOutsideDiff` lists.
- `src/pr-claims.ts`: the claims of the PR text (`extractPrClaims`) and the check of each one (`runClaimChecks`), on the loop of checks with repository tools (`checkEach`).
- `src/fixes.ts`: the fixes of the diff (`listFixes`) and the root cause check of each one (`runFixChecks`).
- `src/scope.ts`: the scope reader (`runScopeReader`), the code checks of its answer and the warnings `review.scope_blocks` posts (`scopeWarnings`).
- `src/dependency-sources.ts`: reading a dependency's published source at the version the PR uses (`dependencyLoader`), with one module per registry in `src/registries/` and unpacking with node-tar in `src/archive.ts`.
- `src/sweep.ts`: with `review.sweep`, one search of the diff per kept finding the setting names (`startsSweep`) for other instances of its defect class (`runSweeps`).
- `src/recap.ts`: prior-round state from review threads, and dedup (static and LLM) against earlier findings.
- `src/github.ts`: GitHub API helpers (diffs, progress comments, posting reviews).
- `src/interaction.ts`: comment commands and replies in review threads.
- `src/reply-check.ts`: the code checks on a thread reply's structured answer (`checkReply`): its outcome's proof, the statements it lists, and a fix it places in another pull request (`checkFixedElsewhere`).
- `src/state.ts`: the approval check after a thread or review changes.
- `src/index.ts`: top-level orchestration per dispatched event (`src/dispatch.ts`).
- `action.yml`: action inputs/outputs.

The `effort` level maps to provider-specific thinking or reasoning settings inside each client's `sendMessage`.

## Where to look

- Config schema + defaults: `src/config.ts`
- Config reference: `docs/configuration.md`. A new or changed setting needs its entry in `scripts/config-reference.ts`, then `npm run config-reference`, and its line in `.manki.yml.example`.
- Action inputs/outputs: `action.yml`
- User-facing docs, by what each covers:
  - `README.md`: overview, commands, local review. `docs/index.html`: the homepage.
  - `docs/getting-started.md`: setup, the workflow, action inputs and outputs, events, the settings block.
  - `docs/how-reviews-work.md`: pipeline, review groups, severity, review output, CI results, analyzers, related repositories, round records.
  - `docs/memory.md`: review memory. `docs/security.md`: tokens, untrusted content, reviewer tools.
  - `RELEASE.md`: release steps. This file: pipeline order and architecture.
- Convention changes or open design questions: GitHub issues
