# Judge grading fixture corpus

Each `*.json` file holds one reviewer finding, which claims a `blocker` in all but `own-proposal-objection`, `refuted-by-shown-guard`, the three warning fixtures, the three note fixtures, the four doubted fixtures, the seven notice fixtures, the five fixtures that set `posted`, the three doubted security fixtures and `cell-against-reasoning`, the PR diff it sits in, and the grades the judge may return (`allowed`). Every fixture without `blocker` in `allowed` breaks exactly one rule of the blocker definition, except the three warning fixtures, the three note fixtures, the four doubted fixtures, the three `unnoticed-` fixtures, `rare-window-minor`, `doc-promise-only`, the two doubted security fixtures a doubt holds down, `misuse-no-caller`, `rare-odds-collision`, `double-failure-hold` and `cell-against-reasoning`. The others cover cases a rule could wrongly clear.

The three warning fixtures also set `proven`. A warning is posted only when it is proven, so the judge must tell a warning the code shown proves from one that rests on code it cannot see. With `proven: true` the graded finding has to cite proving lines and name no doubt whether the defect exists. With `proven: false` it has to name such a doubt or cite no lines, so that a tool check runs before it is posted. In `cut-list-note` the only open question is how a model reads the text the code builds. No code read can settle that, so it is no doubt, and the finding is proven by the removed lines.

Two of the note fixtures hold the same kind of note, a comment that states a number the code does not have. The judge keeps the one whose number the diff shows. It drops the one whose number sits in a file it cannot see, since a note it cannot check is not worth a reader's time, while `unproven-warning` shows that a warning in the same position stays.

The judge is shown the diff of a file only when the finding sits on it or cites it in a proving line or an evidence line. The third note fixture is a missing test as a finder reports it: no proving line, and evidence lines that start with the test file's `file:line`. Those lines put the test file in front of the judge, so it can check the note and keeps it.

The four doubted fixtures set `ifConfirmed`. Each finding rests on code the diff does not show, so without tools the judge holds it at a `warning` and lists the unseen code as a doubt. `ifConfirmed` is the grade the finding earns once a check confirms that doubt. With `blocker` the judge must leave the finding able to rise: a wrong invoice total and lost data are serious damage. With `warning` it must not: a wrong figure in a heading or a status text is a real defect that damages nothing else, so the judge states `warning` as its `gradeIfConfirmed`, or a cell that gives no blocker.

The seven notice fixtures are findings a finder filed as a `warning`, on the line between a warning and a note. A warning needs a consequence someone would notice in realistic use. The three `unnoticed-` fixtures describe a real cost that nobody would notice, and state the realistic scale, as the finders are told to for a cost, and the diff itself shows that scale. The finder still filed each as a `warning`, so the judge must lower it to `note`. The judge lowers a warning only when the code shown confirms the small scale, never on the finding's word alone. The four `noticed-` fixtures have the same shape, a size, a temporary file, a slowdown or memory, with a consequence someone does notice, so they stay a `warning` or above. `unnoticed-extra-pass` and two of the `noticed-` ones come from findings of `bench/cases` runs. The others are constructed, with no outside input and no stated budget, so nothing but the scale decides the grade.

The three trigger fixtures set `posted`. A `degraded` warning needs a realistic trigger, a sequence of events normal use produces, or it is kept in the round record only. `rare-window-minor` is a lost wake-up in a few nanoseconds between two lines while each job takes seconds, and the job still runs, up to a second late: the judge keeps it on the `degraded` row with no trigger, or drops it, and never posts it. `rare-trigger-severe` needs two saves to overlap in a few milliseconds, but then the settings file is corrupt, so it stays posted however rare the trigger is. `noticed-common-slowdown` costs only one round trip, but on every page change, so its trigger is common and it stays a warning.

The two doc promise fixtures each add a function whose docstring promises an atomic replace that the code does not do. A broken public contract is one existing callers already rely on, so a new promise the code does not keep is no such contract, and the judge grades the failure the code itself causes. In `doc-promise-only` that failure is a cache that gets rebuilt, so the finding is a `warning` at most. In `doc-promise-lost-data` the code loses the user's settings on every sync, so it stays a `blocker`.

The three doubted security fixtures are security findings a finder filed as a `warning` on code the diff does not show: a caller that passes outside input, or a view that serves the file. A doubt holds a security blocker down only when it rests on a cost or an edge case being reached. `doubted-security-cost` is a quadratic loop over a request body, and `doubted-security-check-gap` is a filter that misses one spelling of an extension it blocks. The judge holds each at a `warning` with the doubt listed, and a check that confirms the doubt makes it a blocker. `doubted-security-injection` is a file name that reaches a shell, which stays a `blocker` with the same kind of doubt open.

Two more trigger fixtures set `posted` and share one Dialer class. In `misuse-no-caller` the warning needs `start` called twice for one address, and the only caller calls it once in a constructor, so no realistic trigger leads to it and it is never posted. In `misuse-real-caller` a Reconnect handler calls `start` again, so the same warning is posted.

Four fixtures check that a trigger that is not realistic keeps a blocker cell at a warning, and that a realistic failure does not. `rare-odds-collision` loses a report only when two 128-bit random names collide, and `double-failure-hold` only keeps a pull request held a while longer when a record update and its retry both fail, so neither may block. `realistic-failure-loss` loses a stored file when one upload breaks off, and in `single-failure-approval` one failed API call approves a pull request with open blockers, so both stay blockers.

`cell-against-reasoning` repeats a warning of an earlier round on unchanged code. A Python block scanner backfills an account from a match taken before its address window is extended, so an output past the window is missing from the balance until a rescan delivers the block again. The finder and the earlier round graded it a `warning`, so Grade Stability asks for a cell that gives one. A judge can still state a `wrong` cell while its reasoning concludes `warning`. Manki then holds the blocker cell at a `warning` until a check with tools confirms the damage of the row, and no such check runs here.

`judge.test.ts` checks that the corpus covers every case once and that each finding points at a line of its diff. A live replay, gated on `RUN_JUDGE_LIVE_FIXTURES=1` and signed in with `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`, sends each fixture through `runJudgeAgent` against a real model and checks the grade is allowed. CI does not run it. Run it after changing the judge prompt or model.
