# Security model

Manki handles untrusted PR content and cross-repo tokens. The security model rests on these guarantees:

- **Prompt injection**: PR diffs are untrusted content passed into LLM prompts. All findings, thread replies and answers to questions are sanitized before posting to GitHub so that embedded HTML, scripts, links, `@mention` strings, `suggestion` blocks and Manki's own hidden markers cannot be used to inject content, trigger notifications or pass as Manki's state. Manki adds its own markers after sanitizing. The finders get the PR title and description, linked issues, file contents or code windows, and the diff in fenced blocks that no text inside can close, each labelled as untrusted data, and are told never to follow instructions in them. The judge gets the PR title and description in the same kind of fence, and the rest of that content labelled as untrusted. The verdict reader gets file contents and the diff the same way, and never the PR title, description or linked issues. A [claim check](how-reviews-work.md#claims-of-the-pr-text) gets one statement of the PR text, kept only when the text holds it word for word, in such a fence, with the diff. It may also get lines of the related repositories that a search for names guessed from the statement found, fenced and labelled as untrusted. No other call gets them. A claim can add a check and never remove one: no other call's input and no grade depends on a claim or on its status. The one effect beyond its check is that a claim fetches the related repositories, so the judge can read the cited code of one where it would otherwise be told the repository was not fetched. Only the defect a check reports for a statement it disproved is added, and the judge and the refuter check it like a finder's. The titles and descriptions of other open PRs and issues, which the `dedup` model reads to flag related work and to match findings to the ones that track them, are passed the same way and cut short, and the note posts only their sanitized titles with links. Only an issue or PR a person with write access opened can track a finding, and the match is only shown. A reply in a review thread quotes a developer's statement only when the words are in the reply itself, and a search for a statement such as "nothing calls `backup`" is run by Manki as plain text, never as a pattern or a command. The reply's model gets the PR's title and description as they are when it answers, in the same kind of fence and labelled as untrusted. A statement about the description is listed as checked only when Manki itself finds the cited text in the description it read, or finds that it does not hold a text the reply says is gone. What the model read in a related repository is posted as a place only, never as text. The Codex CLI reports the model's reply and its own errors as separate JSON events, and Manki reads a limit, a retry or the session only from Codex's own events, so a PR that steers the model into writing error lines cannot make its call pass for a limit or a retry.
- **Token handling**: Manki masks every token it mints or decodes in the workflow logs via `core.setSecret()`, and GitHub masks the secrets you pass as inputs. The App's review token covers only the reviewed repo and only reads its code. GitHub lets only a token with `contents: write` resolve a review thread, so Manki resolves and reopens its threads through the token service's `/resolve`. The service checks that the request comes from the run it dispatched, and that the thread is Manki's and on that run's PR. Then it changes the thread with a token it mints for that one call. Manki holds no token for the central memory repository. The token service reads and writes it for the run it started, and lets each run write only its own repo's folder (see [Review memory](memory.md)). Only your own memory repository in `memory.repo` uses a token, the `memory_repo_token` input. Your own App's private key needs more care, see [Your own GitHub App](getting-started.md#your-own-github-app). The provider CLIs get only the variables they need to run (`PATH`, `HOME`, `USER`, `LOGNAME`, temp folders, locale, `XDG_*`, the proxy settings including `ALL_PROXY` and `NODE_USE_ENV_PROXY`, and the CA settings), their own configuration and their own credential. The Claude CLI gets `ANTHROPIC_*`, `CLAUDE_CODE_*`, `DISABLE_*`, `VERTEX_REGION_*`, `API_TIMEOUT_MS`, `MAX_THINKING_TOKENS`, `MCP_TIMEOUT`, `MCP_TOOL_TIMEOUT`, `CLOUD_ML_REGION`, and the AWS region, profile, config file, login cache, role and web identity variables. Its `HOME` and `CLAUDE_CONFIG_DIR` are a folder of its own, see [Claude on a self-hosted runner](#claude-on-a-self-hosted-runner). The Codex CLI gets `OPENAI_*` and `CODEX_*`, and with repository tools `GITHUB_API_URL` for `repo_info`. Its `HOME` and `CODEX_HOME` are a folder of its own, see [Codex on a self-hosted runner](#codex-on-a-self-hosted-runner). The Gemini CLI gets `GEMINI_*`, `GOOGLE_*` and `VERTEX_*`. Its `HOME` and `GEMINI_CLI_HOME` are a folder of its own, see [Gemini on a self-hosted runner](#gemini-on-a-self-hosted-runner). For every CLI, the other variables that name the user's folders point into that folder too: `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` for Windows, and `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME`. `HOMEDRIVE` and `HOMEPATH` never pass. A variable with a secret word as one of the underscore-separated parts of its name (`TOKEN`, `KEY`, `SECRET`, `PASSWORD`, `CREDENTIALS`, `AUTH`, `HEADERS` and similar, as in `OPENAI_API_KEY_PROD` or `GOOGLE_CREDENTIALS_JSON`) never reaches a CLI, so no other variable of the Manki step does either, whatever its name, and neither do the action inputs and the OIDC endpoint. Six such names hold a file path, an endpoint or a switch and do pass: `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, `AWS_CONTAINER_CREDENTIALS_FULL_URI`, `CLAUDE_CODE_SKIP_BEDROCK_AUTH` and `CLAUDE_CODE_SKIP_VERTEX_AUTH`. There are two exceptions. The first is the credentials of a Claude setup that is on: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and `AWS_BEARER_TOKEN_BEDROCK` with `CLAUDE_CODE_USE_BEDROCK`, `GOOGLE_APPLICATION_CREDENTIALS` with `CLAUDE_CODE_USE_VERTEX`, `ANTHROPIC_AUTH_TOKEN` with `ANTHROPIC_BASE_URL`, and `ANTHROPIC_CUSTOM_HEADERS` with `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL` or `ANTHROPIC_VERTEX_BASE_URL`. Without one of those gateways Manki warns that it drops `ANTHROPIC_CUSTOM_HEADERS`. They go to the Claude CLI only, and Manki redacts their values from everything it posts. The second is the key of an [OpenAI-compatible endpoint](getting-started.md#openai-compatible-endpoint): with `openai_base_url`, the Codex CLI gets `openai_api_key` as `OPENAI_API_KEY` and sends it to that endpoint only. Manki's tool server, which the Codex CLI starts, does not get the key, and Manki redacts it from everything it posts. Manki writes no Codex config file and no login file for the endpoint. The base URL goes to the Codex CLI on its command line, so put no credential in it. Every secret value is also redacted from the action outputs, such as `findings_json`. Manki deletes the OAuth files it wrote when the run ends, so no token stays on a persistent runner. The Codex and Gemini login files are in the run's own home of that CLI, which Manki deletes too. OpenAI's guide says to use the Codex login (`openai_oauth_token`) only on a trusted private runner and not for a public or open-source repository, see [Codex CLI OAuth Token](getting-started.md#codex-cli-oauth-token-subscription-experimental). Manki reads its own state only from comments and reviews by `manki-review[bot]`, or by your own App's bot, so no other account, such as `github-actions[bot]`, can forge it.
- **Reviewer tools**: Reviewers that run on the Claude CLI (`claude_code_oauth_token`) or the Codex CLI (`openai_oauth_token`, or `openai_api_key` with `openai_base_url`) can read the PR beyond the diff. Manki fetches the head commit with 500 commits of history into a fresh folder that holds no credential. It also keeps the merge base the PR's diff starts from in that folder. The 500 commits usually hold it. When they do not, Manki fetches that one commit with the same token, kept out of the folder as for the head. Manki's `read_file` with `ref` set to `base` reads a file there as it was before the PR, through git's objects, so a symlink is its text. It refuses a path that `exclude_paths` names or `closed_paths` closes, `.git` and any path outside the repository, and each read takes a tool step like any call. A merge base Manki cannot find or fetch leaves the tools with the head alone. A Claude reviewer gets Read, Grep and Glob limited to that folder (`--restricted`) without its `.git`, which the CLI refuses by the deny rules Manki passes, and a Codex reviewer gets `read_file`, `grep` and `glob` from Manki's own tool server. The `homes` job of the `Codex tools` workflow checks those rules on the pinned Claude CLI on every pull request. A Claude reviewer reads the head with its own Read, so Manki's `read_file` reads only the base or a related repository there. Codex waits for that server before its first request, and a call whose server does not start fails instead of reviewing without it. Both also get three tools of Manki's own: the git history of a file or lines, ast-grep structural search, and `repo_info`, which tells whether a GitHub repository given as `owner/name` exists and is public, archived or a fork, and names its default branch. `repo_info` makes unauthenticated reads of public repository metadata from the GitHub API, so no token reaches the CLI. It returns no contents, a private repository reads as "not publicly visible: private, or doesn't exist", and its answer reaches the model fenced as untrusted data. Each repository is asked once per run. A rate limit answers that it cannot tell, and the repository is asked again after five minutes. The reviewer has no shell and no other web access. A Claude reviewer has no other tool, and a Codex reviewer keeps the few tools of Codex's own listed in [Codex reviewer tools](#codex-reviewer-tools). Manki's tools refuse any path outside the folder, also through a symlink. Every stage with these tools, which includes the refuter, a judge with `judge.tool_steps` and the reply in a review thread, reads a [related repository](how-reviews-work.md#related-repositories) only through Manki's own tools, confined to that repository's checkout the same way. Its content is other people's text: each of those stages is told to treat it as untrusted data and never to follow an instruction in it, and a line of it can confirm a finding but never lift one alone. Symlinks in the PR are checked out as plain files that hold their target. Each reviewer gets a budget of tool calls by risk: 8 for the quick check of a trivial PR, 30 for a single finder and 40 when two finders read the PR or it touches a security, supply chain or data contract path. Three calls before the end, Manki tells the reviewer to wrap up, and after the last one it refuses every further call, so the reviewer answers with what it checked. It marks a finding it could not finish checking as not checked yet, and reports what it was still looking into as open leads: the judge settles a lead graded `blocker`, and with tools also one graded `warning`, and the review body lists the others, and the ones it could not settle, under "Not finished checking". A 15-minute limit per reviewer is only a safety net. The Codex CLI runs in its read-only sandbox with approvals off and every built-in tool turned off that Codex lets Manki turn off. A call on an OpenAI-compatible endpoint that resumes its Codex session after a failed answer runs the CLI again with the same sandbox, the same settings and the same tool server, and its budget of tool calls counts across the runs. Reviewers on an Anthropic or OpenAI API key, or on Gemini, review the diff without tools. The Gemini CLI gets a policy that denies every tool, so it cannot search or fetch the web either. A judge on the Claude or Codex CLI gets the same tools. With `judge.tool_steps` above 0, it reads the PR with them while it grades, up to that many calls. In every case it tries to refute each blocker and each open lead it keeps, the verdict reader's blockers included, and each finding it lowered for want of proof or would grade higher if a premise it doubts holds, with 15 calls each. The refuter reads PR content, so its answer never clears a blocker on its own. A disproved blocker becomes a warning that only a fix or someone allowed to clear it clears, never the PR author's answer alone, and is posted with the refuter's reason. With a second refuter on `models.second_refuter`, a blocker only one of them disproves keeps its grade, posted with both reasons. The one exception is a blocker the judge alone raised, which no finder graded a blocker: a disproof sends it back to the highest grade a finder gave it, the same place a check that settles nothing leaves it. A security finding, an open lead the judge graded blocker and a finding that restates an earlier blocker or an open thread that blocks never go back. Neither does a tool alert that names a security problem. Any other tool alert goes back only when two refuters on different models both disprove it, which posts it as a guarded warning (see [Severity tiers](how-reviews-work.md#severity-tiers)). A disproof drops only a finding graded below blocker, such as an open lead or a finding capped at warning for want of proof, and only when it cites a line of the finding's own file or of the PR's diff. Its reason is shown in the review body, under "Disproved by a check of the code". A confirmed finding is posted with the lines that prove it, and one the refuter cannot settle keeps its grade, except an open lead below blocker, which is listed as not finished instead of posted. A security finding changes only when confirmed. The outcome is stored with the finding, so a later round reuses it while the files it rests on are unchanged. A finding whose higher grade the judge left to the tools is checked afresh each round, since the code or caller it rests on can sit in any file. The planner and dedup stages get no tools.
- **Closed paths**: `closed_paths` names paths no review stage may read, such as a hidden test set whose content must stay out of every review. A closed file is left out of the diff that every stage and analyzer reads. Before any stage runs, Manki also deletes it, and each folder that leaves empty, from the checkout the reviewer tools read, and drops it from the checkout's git index, so no tool that lists the tracked files names it. Neither Manki's tools nor the Claude CLI's own read the checkout's `.git`. So the search for uses outside the diff, the sibling comparisons, the claim checks, the sweeps, every reviewer, judge and refuter tool call and the reply in a review thread find nothing there, whatever tool they use. Manki keeps the list of the paths it removed, so the dependency tool refuses every package when one of them could decide which code the PR runs. A file the PR moves out of a closed path holds the closed file's text, so its new path is closed the same way. A file the PR moves into a closed path held that text at the base, so its old path is closed too, and a read at the base finds nothing there. An open thread on a closed file shows no code, a warning the review body carries over is never checked against one, and an instruction file never pulls one in through a link. A call of Manki's own tools on a closed path is answered that the repository's config closes the path, and the round record counts those calls as `usage.closedCalls`. The closed files stay in the git history of the checkout, but no reviewer can run git: the Claude CLI gets only Read, Grep and Glob, and the Codex CLI has its shell turned off. Git keeps that history compressed in `.git`, and Manki's tools and the Claude CLI's own refuse any path there. Manki's `read_file` at the PR's base reads that history, so it refuses a closed path there, answers it as it does at the head and counts it the same way. A Codex reviewer can still use Codex's own `apply_patch` to learn whether a file exists and whether a line it guesses is in it (see [Codex reviewer tools](#codex-reviewer-tools)). In the checkout there is nothing for it to probe, since Manki deleted the closed files there before any stage ran, and `.git` holds their history only compressed. A copy of a closed file outside the checkout, such as another checkout of the repository on a self-hosted runner, is a separate matter that `closed_paths` does not cover. Manki's own git history tool follows no line across a rename while a path is closed, and shows no line history at all for a file that was ever at a closed path, since a later commit's diff would show the lines it replaced there. It still lists that file's commits. While `closed_paths` is set, Manki does not check a reply's claim that [another pull request fixes a finding](how-reviews-work.md#a-fix-in-another-pull-request). That check reads GitHub's merge of the PR, which holds what other pull requests changed, and which of its files are open is not certain. Manki's own reads through the GitHub API skip closed files too: the PR diff that a thread reply and `/manki explain` read, the file lists of the other open PRs that the related work check reads, and the lines a review quotes from a finding's file or from the files its checks cite. So a finding on a closed file, or one that cites it, shows no code, no fix as a diff and no link to its lines, since GitHub shows a link to lines as their code. A symlink is never read as its target, since its target can be a closed file. GitHub answers a symlink to a file with the target's content, but under the blob id of the link itself, so Manki drops content whose blob id differs from the one GitHub names, for every file it reads as code or analyzer input. A lockfile is read as the blob GitHub names for its path, which is the link itself for a symlink, and is skipped when its size differs from the size GitHub reports for the path. While paths are closed, an instruction file that is a symlink is not read either, the checkout keeps no symlink, as it already holds each one as a plain file with the link's text, and Manki's tools refuse a path that goes through one. When the base branch's `.manki.yml` cannot be read on a second try, or its YAML does not parse while its text names `closed_paths`, or its `closed_paths` is not a list of paths, Manki cannot tell which paths are closed. A review round then fails before it reads any code, with the reason in its progress comment, and a thread reply, `/manki explain` or a free-form question gets that reason in place of an answer. A base config that parses but does not load still closes the paths its `closed_paths` names, and one whose YAML does not parse and never names `closed_paths` closes nothing.
- **Dependency sources**: The finders, the claim checks and the refuters can read the published source of one of the PR's [dependencies](how-reviews-work.md#dependency-sources) through Manki's own tools, and so can a judge with tools, which shares the refuter's. A model never chooses the package or its version alone. The package must be one that the PR's own lockfiles or manifests name: `Cargo.lock` or `Cargo.toml` for a Rust crate, and `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml` or `package.json` for an npm package, that git tracks, and for a crate outside `target`. The version is the one a committed lockfile locks, never one a workspace member's `Cargo.lock` locks, which Cargo ignores. Only a package no lockfile locks gets a version through its requirement, and only when the manifests state one. Manki reads a package only when it is certain which code the PR runs, and otherwise the round record lists it as `refused` with the reason. So a package is not read when any manifest, install script, hook, Yarn plugin, patch or setting of the checkout can change it or the lockfile an install reads, when the lockfiles lock several versions or the manifests state several requirements, when any lockfile locks it from a git repository, a path, another registry or another package's archive, or with a patch applied, when a registry setting of the PR may take it from another registry, whatever host the lockfile names, when the checkout holds a committed `node_modules` or an install file Manki does not read, when a fresh install may pick another version than the newest a requirement allows, when a lockfile, manifest or setting does not parse, when the checkout holds a git submodule or a symlink an install could follow to a file Manki does not see, when the runner's file system does not tell apart names that differ only in case, when `closed_paths` removed a file that can decide a package, or when the listing of the checkout passed its cap. Cargo files are read with the `smol-toml` parser. Settings files are read line by line with plain string search, so no line can make a pattern slow. [Dependency sources](how-reviews-work.md#dependency-sources) lists each case. Neither is one whose locked version holds characters a version does not have. Manki contacts only `index.crates.io` and `static.crates.io` for crates and `registry.npmjs.org` for npm packages, over HTTPS, without a token, and follows no redirect. It checks each archive against the checksum its lockfile states, or the registry states when no lockfile does, and reads nothing of an archive that does not match: the round record marks the package `mismatch`, and the round does not fetch it again from anywhere. Manki unpacks an archive with node-tar, the reader npm itself uses, in strict mode, and writes only plain files and folders, never a link and never a file that can run. It refuses the whole archive when it holds anything else, such as a link or a device, or a path that is absolute or has a `..` part, and when node-tar finds it broken. Nothing in a package runs: no build script and no install step. Each resource an archive, a registry's answer or the PR's checkout can make Manki spend has a cap, and passing one leaves the package unread:
  - an archive as downloaded: 50 MB, and as unpacked, headers included: 200 MB;
  - files and folders an archive creates: 20,000, counting each folder a file's path implies;
  - a path in an archive: 32 levels deep and 1,024 bytes, never absolute, and canonical, so with no `.`, `..` or empty segment and no leading `./`;
  - a crate's index file: 20 MB, and an npm package's version list: 30 MB, counted as received after decompression;
  - the time to resolve one package: 60 seconds, and to fetch its archive another 60 seconds, each within the limit of the tool call. A fetch starts only when the call has its whole time left, and one that runs out of time or meets an error that may pass, such as an HTTP 503, is tried again by a later call;
  - the lockfiles, manifests and registry settings of the PR's checkout: 20,000 such files, and 50 lockfiles of one registry, where passing either refuses every package, and the bytes read: 10 MB per file and 40 MB per call, the caps of every lockfile read;
  - packages per round: 10.

  A package's text is other people's text, under the same rule as a related repository: each stage is told to treat it as untrusted data and never to follow an instruction in it, and a line of it can confirm a finding but never lift one alone.
- **Downloaded tools**: Manki downloads the Claude CLI and its analyzers at pinned versions and checks each download against a digest fixed in Manki's code before it unpacks it. On a self-hosted runner it keeps the checked download, never the unpacked files, in the `manki-pinned` folder of the runner's tool cache (`RUNNER_TOOL_CACHE`), so later runs on that runner need no download. A later run reads the kept file, checks those bytes against the pinned digest again and unpacks them into the job's temp folder, which the runner empties after the job. So what a run executes always comes from bytes that run checked, also when another job on the same runner, under the same user, changed the kept file. A kept file that fails the check is not used: the run downloads the tool and replaces the file. Manki uses and writes the folder only when the folder and the tool cache are real folders that the runner's user owns and no one else can write. Otherwise it downloads as on any other runner and the run log says why. It reads no link and no file that is not a regular file there. A kept download no run used for 14 days is removed. GitHub-hosted runners and Windows runners keep nothing.
- **Who can command Manki**: Only people with write access to the repository, and accounts a maintainer put on the repository's allow list, can start Manki from a comment, settle a finding with a reply or tick Manki's boxes. Manki asks the GitHub API about each one, and asks the token service about an account without write access. Only a `workflow_dispatch` run asks. The service answers only a run it dispatched, checked with the run's OIDC token, and only for the repository that run belongs to, so a run started by hand gets a refusal. Any failure counts as not allowed. An allowed account gets everything write access gives: one that is not the PR author clears a blocking or security thread with a reply, the same as anyone with write access. An allowed PR author still clears one on its own PR only with the role `author_clear_role` names. Every check that needs a role, such as changing the list, which takes the `maintain` or `admin` role, or `author_clear_role`, reads only the role GitHub reports, so an allowed account never passes one (see [Allowing an account without write access](getting-started.md#allowing-an-account-without-write-access)).
- **Memory access control**: Only people with write access to the repository, or allowed accounts, can use `/manki remember`, `/manki forget`, and `/manki dismiss`. A global learning (`/manki remember global:`) is never stored by a run: global learnings reach every repo that shares the memory, so the owner of the memory repository edits `_global/` by hand. Commands from anyone else are ignored so memory cannot be poisoned by drive-by PRs. In the central memory repository, a run cannot write another repo's folder or `_global/`, so a suppression added in one repo never hides findings in another. That repository holds only public repos' memory, only the token service writes it, and Manki redacts its own secret values from everything it writes there. A private repo uses only a memory repo of its own, and on every run Manki checks with the API that this repo is private and has the same owner. Otherwise memory is skipped, and the review body says why.
- **Judge trust model**: The judge agent grades every finding and can lower any of them, from `blocker` down to `ignore`. This is intentional: a single precise judge produces fewer false positives than trusting individual reviewers.
- **OIDC authentication**: When using the GitHub App identity, token service requests are authenticated via GitHub Actions OIDC tokens. The request is cryptographically proven to come from a legitimate workflow run, so no shared secret is exchanged between your workflow and the token service.
- **Manki's own repository**: Manki reviews its own PRs with the build of the PR head (`.github/workflows/manki.yml`). Only a head in the same repository is built, and a fork's head gets the default branch. The build and the review run that head's code with every secret of the job and `id-token: write`, so this is safe only while everyone who can push a branch to the repository is trusted. Your own workflow runs the released action and never builds a PR.

## Codex reviewer tools

This list was measured with Codex CLI 0.166.0 on an [OpenAI-compatible endpoint](getting-started.md#openai-compatible-endpoint). A stand-in endpoint on the same machine recorded the tools in each request Codex sent, and called the tools to see what each one does. The `Codex tools` workflow repeats the measurement for the pinned Codex version on every pull request, and fails when a model is offered a tool that is not on the list in `scripts/fixtures/codex-tools.json`. On `gpt-5.5` that list is not complete. No request Codex sends names the tools it holds back, and `tool_search` returns only those whose description shares a word with the query. An empty, `*` or stop-word query returns none. The check searches for `agent spawn send wait close resume input goal file read write edit grep glob history repo search web image shell command exec patch resource mcp time clock sleep plugin app install user message list task skill memory`, and also compares the sources of held-back tools that the `tool_search` description names, today only `manki`. So a held-back tool from a new source fails the check. A new one from a listed source, or one the description names no source for, is not seen when its description has none of these words. Manki's own six tools are in every list. The models measured are `gpt-6.1-sol`, `gpt-5.6-sol`, `gpt-5.6-luna`, `gpt-5.5` and `gpt-5.4`, and Codex's list gives every other `gpt-6` and `gpt-5.6` model the same tool settings as one of these.

Which Codex tools a model gets depends on its entry in Codex's built-in list of models:

- `gpt-6.x` and `gpt-5.6-*`: a script host, `exec`, and `wait` for a script that is still running. A script runs JavaScript with no file system, no network and no shell, and can only call the tools the host holds: Manki's six tools, `apply_patch`, the three MCP resource tools and, on `gpt-6.x`, `clock__curr_time`.
- `gpt-5.5`: `apply_patch`, the three MCP resource tools and `tool_search`. Codex holds Manki's six tools back until `tool_search` finds them.
- A model Codex does not list, such as `gpt-5.4`: the three MCP resource tools.

What each of them can do in the read-only sandbox:

| Tool | What it can do |
|---|---|
| `exec`, `wait` | Run a script that calls the tools above. Nothing else. |
| `apply_patch` | Edit files, which the sandbox refuses every time. Before the refusal, Codex reads the file the patch names with the rights of the runner's user, anywhere on the machine. So its answer tells the model whether a file exists and whether a whole line the model guesses is in it. On a self-hosted runner that reaches the home folder, such as `~/.ssh`, and the checkouts of other repositories. It never shows a line the model did not guess, so it cannot reveal a secret the model does not already know. |
| `list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource` | Read the resources of the MCP servers Codex runs. Manki's tool server is the only one and has none, so each returns an empty list or an error. |
| `tool_search` | Search the descriptions of the tools Codex holds back. It reads no file. |
| `clock__curr_time` | Return the current time. |

Manki turns these off, and each switch was shown to remove the tools named with it:

- `features.shell_tool=false`: `exec_command` and `write_stdin`, the shell.
- `features.view_image=false`: `view_image`.
- `web_search=disabled`: `web_search`, offered on `gpt-5.5`.
- `agents.enabled=false`: `spawn_agent` and the other tools that start and message subagents. `features.multi_agent=false` alone leaves them on `gpt-6.x` and `gpt-5.6-*`.
- `features.goals=false`: `create_goal`, `get_goal` and `update_goal`.
- `features.sleep_tool=false`: `sleep`.
- `tools.experimental_request_user_input.enabled=false`: `request_user_input` and `request_user_input_async`.

Manki also sets `features.apps=false`, `features.plugins=false`, `features.multi_agent=false` and `features.image_generation=false`. On an endpoint none of them removes a tool once the switches above are set. They stay for the ChatGPT login (`openai_oauth_token`), whose tools were not measured, because Codex reads that login's model list from OpenAI's servers.

Codex has no switch for the rest. The script host, `apply_patch`, `tool_search` and the clock come with the model's entry in Codex's list, and the MCP resource tools come with any MCP server, so with Manki's own. Of these, only `apply_patch` reaches outside the repository, as described above.

Two more settings keep a review to what it needs. Both were measured the same way, and Manki sets them on the endpoint and on the ChatGPT login:

- `analytics.enabled=false`: without it, Codex sends usage metrics to `ab.chatgpt.com` on every run, also on an endpoint. On the ChatGPT login it also posts analytics events to `chatgpt.com`. With it, a run tries to reach no host but the endpoint, and the login posts no analytics events. Codex's source switches both off with this one setting.
- `skills.bundled.enabled=false`: without it, Codex writes its built-in skills into `$CODEX_HOME/skills/.system` and lists them in every request, about 4,700 characters. A PR text that names a skill as `$imagegen` added that skill's whole text. With it, no request carries skill text. Skills a self-hosted runner keeps in its own Codex home or in `~/.agents/skills` stay out as well, see [Codex on a self-hosted runner](#codex-on-a-self-hosted-runner).

The `Codex tools` workflow also fails when a request carries skill text, or when Codex tries to reach any host but the stand-in. It sees the connections that use the proxy settings, as Codex's analytics did.

## Codex login file on a self-hosted runner

With `openai_oauth_file`, the ChatGPT login stays in a file on a self-hosted runner, and Manki writes the tokens Codex renews back to it (see [Codex login file on a self-hosted runner](getting-started.md#codex-login-file-on-a-self-hosted-runner)). Unlike the OAuth files Manki writes for a run, this file stays on the runner. What the file grants and who can read it:

- The file holds the refresh token of your ChatGPT account. Whoever reads it can use your Codex subscription as you until you sign that session out at [platform.openai.com/account/sessions](https://platform.openai.com/account/sessions).
- Every job on the runner runs as the runner's user, so each one can read the file, whatever its mode. That includes the workflow steps of any pull request the runner runs. So use the file only on a runner that runs only workflows you trust, and never on a runner that runs pull requests from forks.
- Manki refuses a file or folder that another user owns or can read or write, so another account on the machine cannot read the login or put its own in place. It refuses a symbolic link, so the path cannot be pointed at another file. It refuses a file in the workspace, the runner's temp folder or the working folder, where the checked-out code is, and in the runner user's own Codex home, where a Codex the user runs would renew it outside Manki's lock. It reads the file without following a link and checks owner and mode again on the open file.
- Codex is not told the path. Manki copies the file into the run's own Codex home before a call and deletes that home when the run ends. The reviewer's tools still run as the runner's user, so what [`apply_patch`](#codex-reviewer-tools) can tell about a file applies to this one as it does to the copy in Codex's home: whether a line the model guesses is in it, never a token the model does not already know. A renewal is written back through a new file with mode 600 in the same folder and a rename. It is never written over a file that changed since the review read it, so the file never goes back to a refresh token that was used.
- The two locks next to the file, `auth.json.lock` for a renewal and `auth.json.writing` for a write-back, name the host and the process that holds them. They hold no token.

Measured with Codex CLI 0.166.0 and a stand-in on localhost that issued, expired and renewed made-up tokens: Codex renews before a request once the access token expires within 5 minutes, and after a request the server refuses. It has no lock of its own that keeps two processes from renewing at once, and a second copy of the login in another home failed once the first had renewed. So Manki takes its lock only to renew. Before a call that Codex could renew during, it has `codex app-server` renew the login once with the lock held, and every other call runs without the lock.

## Codex on a self-hosted runner

Codex reads its setup from its home folder, `~/.codex` or the folder `CODEX_HOME` names, and skills from `~/.agents/skills` as well. So Manki runs every Codex call with a home of its own: a new folder in the runner's temp folder that only the runner's user can open, set as both `HOME` and `CODEX_HOME`. It holds only what Manki and Codex write during the run. That is the login file from `openai_oauth_token` or a copy of the file `openai_oauth_file` names on the ChatGPT login, and Codex's session files. The calls of a run share the folder, so a token Codex refreshes in one call is there for the next. Manki deletes the folder when the run ends. It never reads the runner user's `~/.codex`, a `CODEX_HOME` set on the runner, or a login stored there, and refuses an `openai_oauth_file` inside them.

This was measured with Codex CLI 0.166.0 and the stand-in endpoint of the `Codex tools` workflow. A runner home held one marked item at a time, and the requests Codex sent were searched for the mark. With the runner's own home, as Manki ran Codex before, these reached a review:

| In the runner's home | What happened |
|---|---|
| A skill in `~/.codex/skills` or `~/.agents/skills` | Every request listed it with its description. |
| `AGENTS.md` or `AGENTS.override.md` in `~/.codex` | Every request carried its text as instructions. |
| An MCP server in `~/.codex/config.toml` | Codex started it and offered the model its tools. |
| `developer_instructions` in `config.toml` | Every request carried it. |
| A feature switched on in `config.toml` | With `memories`, the model got a script host and the request named the sandbox `workspace-write`. A setting Manki passes itself, such as the sandbox mode, the approval policy or the shell, kept Manki's value. |
| An `otel` exporter in `config.toml` | Codex sent its logs to that host. |
| `model_provider` or `chatgpt_base_url` in `config.toml` | On the ChatGPT login, Codex sent the login's token to the URL they name. On an OpenAI-compatible endpoint, Manki's own provider applied. |
| `OPENAI_API_KEY` in `~/.codex/.env` | Codex sent that key to the endpoint instead of Manki's. |
| A hook in `hooks.json` or `config.toml` that the runner's user had trusted | Codex ran its command and added its output to the request. A hook not yet trusted did not run. |
| `profile` in `config.toml` | Codex refused to start, so every Codex call failed. |

`AGENTS.md` in `~/.agents`, `instructions` in `config.toml`, a file in `~/.codex/rules` or `~/.codex/prompts`, and memories while the `memories` feature is off reached no request. A `notify` program did not run.

With Manki's own home, none of these reached a request or ran. The login's token went only to OpenAI's hosts, and the endpoint's key only to the endpoint. Setting `CODEX_HOME` alone is not enough: a skill in `~/.agents/skills` still reached the request until `HOME` pointed at the new folder too. The `Codex tools` workflow plants a skill in both folders, an `AGENTS.md`, a key in `.env`, and a `config.toml` with an MCP server, an `otel` exporter, a provider and ChatGPT URL that point elsewhere and a trusted hook in a runner home on every pull request. It fails when any of them reaches Codex, on an endpoint or on the ChatGPT login. The same runs on the runner's own home must still show each one, so a Codex version that reads one from elsewhere fails the check instead of passing it.

What a home folder does not change:

- The reviewer's tools run as the runner's user, so [Codex reviewer tools](#codex-reviewer-tools) still applies. `apply_patch` can tell whether a file the model names exists anywhere that user can read, and whether a line the model guesses is in it.
- Codex's source also reads settings that the machine's administrator sets for every user, in `/etc/codex` and, on macOS, in managed device profiles. These were not measured, and Manki does not keep them out.
- The variables of the Manki step that pass to the Codex CLI, listed under Token handling above, still reach it.
- These runs were on macOS, and the `Codex tools` workflow checks its planted items on Linux. Windows was not measured. There, Codex's source asks Windows for the user's profile folder without reading `HOME` or `USERPROFILE`, so a skill in `~/.agents/skills` may still reach a review.

## Claude on a self-hosted runner

The Claude CLI reads its setup from `~/.claude`, or the folder `CLAUDE_CONFIG_DIR` names, and from `~/.claude.json`. Manki runs every Claude call with a home of its own: a new folder in the runner's temp folder that only the runner's user can open, set as `HOME`, with `CLAUDE_CONFIG_DIR` in it. Manki writes no file there, since the login comes from `claude_code_oauth_token` as `CLAUDE_CODE_OAUTH_TOKEN`, and the CLI wrote no login file in the measured runs. The folder holds only what the CLI writes during the run, such as the transcript of each call, which carries the whole prompt. Manki deletes the folder when the run ends. It never reads the runner user's `~/.claude`, `~/.claude.json` or a `CLAUDE_CONFIG_DIR` set on the runner.

This was measured with Claude CLI 2.1.318 on Linux, against a stand-in endpoint on the same machine that `ANTHROPIC_BASE_URL` pointed at. Every other host went to a proxy that recorded and refused it. A runner home held these items, each with its own mark, and the requests were searched for the marks. The CLI with its own defaults (`claude -p`) on that home:

| In the runner's home | What happened |
|---|---|
| `CLAUDE.md` in `~/.claude`, or a file in `~/.claude/rules` | The request carried its text. |
| A skill in `~/.claude/skills`, a command in `~/.claude/commands`, an agent in `~/.claude/agents` | The request listed it. |
| A plugin installed and enabled in `~/.claude/plugins` and `settings.json` | The request listed its skill. |
| An MCP server in `~/.claude.json` | The CLI started it and offered the model its tools. |
| A `SessionStart` hook in `~/.claude/settings.json` | The CLI ran its command and added its output to the request. |
| `ANTHROPIC_BASE_URL` or `ANTHROPIC_CUSTOM_HEADERS` in the `env` of `settings.json` | The request and its token went to the URL it names, with the extra header. |
| `apiKeyHelper` in `settings.json` | The CLI ran it and sent the key it printed instead of Manki's token. |

A skill in `~/.agents/skills` and a `model` in `settings.json` reached no request.

With Manki's arguments, none of these reached a request or ran, on a call with repository tools and on one without, also on the runner's own home. The token sent was always Manki's, also with a login in `~/.claude/.credentials.json`. But the CLI wrote its transcripts and `.claude.json` into the runner's home. Without `--setting-sources ''`, `--strict-mcp-config` and `--restricted`, the runner's own home again gave the request `CLAUDE.md`, the rule, the MCP server, the hook, the `env` and the `apiKeyHelper`. With Manki's own home, none of them reached a request, also without those three arguments.

### Bedrock and Vertex credentials

On Bedrock (`CLAUDE_CODE_USE_BEDROCK`) and Vertex (`CLAUDE_CODE_USE_VERTEX`), the Claude CLI reads its cloud credentials from files that are in the user's home by default. Manki's own home does not have them, so Manki names the runner's own files by their variables while that setup is on: `AWS_CONFIG_FILE` (`~/.aws/config`), `AWS_SHARED_CREDENTIALS_FILE` (`~/.aws/credentials`) and `AWS_LOGIN_CACHE_DIRECTORY` (`~/.aws/login/cache`) on Bedrock, and `GOOGLE_APPLICATION_CREDENTIALS` (`~/.config/gcloud/application_default_credentials.json`, on Windows `%APPDATA%\gcloud\application_default_credentials.json`) on Vertex. It names only a file that exists and a variable the Manki step does not set itself. A variable set in the step's `env:` always wins. The AWS SDK reads the token of `aws sso login` from `~/.aws/sso/cache` of the home it runs with, and no variable names another folder. So on Bedrock Manki links that one folder of the runner, when it exists, into the CLI's own home as `.aws/sso/cache`. It links nothing else of `~/.aws`. When the link cannot be made, Manki warns once and the calls still run, so only a profile that needs the SSO login fails. It makes no link when the step sets `AWS_BEARER_TOKEN_BEDROCK` or `CLAUDE_CODE_SKIP_BEDROCK_AUTH`, since the CLI then reads no AWS credentials. An access key in the step's `env:` still gets the link, because a profile named by `AWS_PROFILE` wins over it, and that profile can be an SSO one. The rest of the runner's home stays out.

A `credential_process` in the AWS config or credentials file runs its command with the CLI's own home too, never the runner's. A helper with an absolute path that keeps nothing under `~` works. A helper that reads files under `~` or keeps its login there, as many single sign-on helpers do, finds nothing and the call fails. So when Bedrock reads AWS credentials and one of those files has a `credential_process`, Manki warns once and names the alternative: give the helper absolute paths and no state under `~`, or set `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` in the Manki step's `env:`.

This was measured with fake credentials and the same stand-in as the Bedrock and Vertex endpoint. It recorded the key each Bedrock request was signed with, and served Google's token endpoint, where it recorded the token a Vertex login refreshed with. The runner's home held one credential source at a time, in the files and format the cloud's own tool writes, next to the planted Claude setup above. With Manki's arguments:

| Credential source | Runner's own home (before) | Manki's own home |
|---|---|---|
| Access key in the step's `env:` (`AWS_ACCESS_KEY_ID`) | Reached the request | Reached the request |
| `aws configure` profile in `~/.aws/credentials`, as `default` or named by `AWS_PROFILE` | Reached the request | Reached the request |
| `credential_process` in `~/.aws/config`, with a helper at an absolute path that keeps nothing under `~` | Reached the request | Reached the request |
| `aws login` session in `~/.aws/login/cache` | Reached the request | Reached the request |
| SSO profile in `~/.aws/config`, signed in with `aws sso login` | Reached the request | Reached the request |
| `gcloud auth application-default login` in `~/.config/gcloud` | Reached the request | Reached the request |
| Key file named by `GOOGLE_APPLICATION_CREDENTIALS` in the step's `env:` | Reached the request | Reached the request |

No part of the planted Claude setup reached a request in any of these runs. With Manki's own home but without the variables and the link, every source in `~/.aws` or `~/.config/gcloud` failed. With the SSO profile and an access key in `env:` as well, the profile's SSO login still signed the request, and without the link the call failed. With `AWS_BEARER_TOKEN_BEDROCK` the CLI sent that key, and with `CLAUDE_CODE_SKIP_BEDROCK_AUTH` it signed nothing. The Claude CLI's `awsAuthRefresh`, `awsCredentialExport` and `gcpAuthRefresh` settings live in its settings files, which `--setting-sources ''` already turned off before Manki had a home of its own. Credentials from the metadata service of a cloud machine, an ECS task or a web identity token file use no home folder and were not measured.

## Gemini on a self-hosted runner

The Gemini CLI reads its setup from `~/.gemini`, or `.gemini` in the folder `GEMINI_CLI_HOME` names, and skills from `~/.agents/skills` as well. Manki runs every Gemini call with a home of its own: a new folder in the runner's temp folder that only the runner's user can open, set as both `HOME` and `GEMINI_CLI_HOME`. It holds only what Manki and the CLI write during the run. That is `.gemini/oauth_creds.json`, which Manki writes from `gemini_oauth_token`, and the CLI's own files. When the access token has expired, the CLI gets a new one from Google and writes it back to that file, keeping the refresh token. The calls of a run share the folder, so a token refreshed in one call is there for the next. Manki deletes the folder when the run ends. It never reads the runner user's `~/.gemini`, a `GEMINI_CLI_HOME` set on the runner, or a login stored there.

This was measured with Gemini CLI 0.66.0 on Linux. A stand-in on the same machine served Google's login checks and Code Assist calls with a certificate the CLI was told to trust, and refused every other host. A runner home held these items, each with its own mark. With the runner's own home, as Manki ran the Gemini CLI before:

| In the runner's home | What happened |
|---|---|
| `GEMINI.md` in `~/.gemini` | The request carried its text. |
| A skill in `~/.gemini/skills` or `~/.agents/skills` | The request listed it. |
| An extension in `~/.gemini/extensions` | The request carried its context file, and the CLI started its MCP server. |
| An MCP server in `~/.gemini/settings.json` | The CLI started it. Manki's policy kept its tools from the model. |
| A `SessionStart` hook in `settings.json` | The CLI ran its command and added its output to the request. |
| A telemetry endpoint in `settings.json` | The CLI sent its logs, metrics and traces there. |
| `CODE_ASSIST_ENDPOINT` in `~/.gemini/.env` | Every Code Assist call, with the login's token, went to the URL it names. |
| A login in `~/.gemini/oauth_creds.json` | The CLI used it instead of `gemini_oauth_token`, since Manki wrote its own only where no file was. |

A policy in `~/.gemini/policies` that allows every tool, an agent in `~/.gemini/agents`, a command in `~/.gemini/commands` and a `model` in `settings.json` changed no request.

With Manki's own home, none of these reached a request or ran, and the token sent was always the one from `gemini_oauth_token`.

The Gemini CLI also loads the first `.env` or `.gemini/.env` it finds in its working folder or a folder above it, before the one in its home. Manki's working folder for Gemini is a new folder in the system temp folder, and it holds an empty `.env` and an empty `.gemini/.env`, so the search stops there. Without them, a `CODE_ASSIST_ENDPOINT` in `/tmp/.env` or `/tmp/.gemini/.env` sent every Code Assist call and the login's token to the URL it names, also with Manki's own home. With them, neither changed a request. Any job or user on a shared runner can write `/tmp`. Even without those empty files, no other file in the folder above the working folder reached a request. For Gemini that was a `GEMINI.md`, an `AGENTS.md`, a `.gemini/settings.json` with an MCP server and a hook, and a skill in `.gemini/skills` or `.agents/skills`. For Claude, run as Manki runs it, it was a `CLAUDE.md`, a `CLAUDE.local.md`, a `.claude/CLAUDE.md`, a rule, a skill, a `.claude/settings.json` with a hook and a base URL, a `.mcp.json` and an `AGENTS.md`.

The `homes` job of the `Codex tools` workflow plants these items in a runner home on every pull request: for Claude all of the first table but `ANTHROPIC_CUSTOM_HEADERS`, for Gemini all of the second, and a `.env` in the temp folder above Gemini's working folder. It runs the pinned versions of both CLIs as Manki does and fails when any item reaches a request or runs, or when a CLI tries to reach a host it does not always reach. Control runs must still show each item: Claude with its defaults on the runner's own home, Gemini as Manki ran it before, and Gemini in a working folder without Manki's empty `.env` files. So a CLI version that reads an item from elsewhere fails the check instead of passing it. The job also runs Claude on Bedrock with an `aws configure` profile and with an `aws sso login` profile, and on Vertex with a `gcloud` login in the runner's home, and fails when that credential no longer reaches the request or any planted item does. A control run of the SSO profile on the runner's own home must sign in too, so a failure there points at Manki's link and not at the planted login.

What a home folder does not change, for both CLIs:

- Settings that the machine's administrator sets for every user, such as the Claude CLI's managed settings and `/etc/gemini-cli/settings.json`. These were not measured, and Manki does not keep them out.
- The variables of the Manki step that pass to a CLI, listed under Token handling above, still reach it.
- Windows and macOS were not measured. On Windows, Node's `os.homedir()` reads `USERPROFILE` and ignores `HOME`, which is why Manki sets `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` as well. A program in a CLI that asks Windows for the user's profile folder directly, without these variables, would still find the runner's.
