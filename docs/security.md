# Security model

Manki handles untrusted PR content and cross-repo tokens. The security model rests on these guarantees:

- **Prompt injection**: PR diffs are untrusted content passed into LLM prompts. All findings, thread replies and answers to questions are sanitized before posting to GitHub so that embedded HTML, scripts, links, `@mention` strings, `suggestion` blocks and Manki's own hidden markers cannot be used to inject content, trigger notifications or pass as Manki's state. Manki adds its own markers after sanitizing. The finders get the PR title and description, linked issues, file contents and the diff in fenced blocks that no text inside can close, each labelled as untrusted data, and are told never to follow instructions in them. The judge gets the PR title and description in the same kind of fence, and the rest of that content labelled as untrusted. The verdict reader gets file contents and the diff the same way, and never the PR title, description or linked issues. The titles and descriptions of other open PRs and issues, which the `dedup` model reads to flag related work, are passed the same way and cut short, and the note posts only their sanitized titles with links.
- **Token handling**: Manki masks every token it mints or decodes in the workflow logs via `core.setSecret()`, and GitHub masks the secrets you pass as inputs. The App's review token covers only the reviewed repo and only reads its code. GitHub lets only a token with `contents: write` resolve a review thread, so Manki resolves and reopens its threads through the token service's `/resolve`. The service checks that the request comes from the run it dispatched, and that the thread is Manki's and on that run's PR. Then it changes the thread with a token it mints for that one call. Manki holds no token for the central memory repository. The token service reads and writes it for the run it started, and lets each run write only its own repo's folder (see [Review memory](memory.md)). Only your own memory repository in `memory.repo` uses a token, the `memory_repo_token` input. Your own App's private key needs more care, see [Your own GitHub App](getting-started.md#your-own-github-app). The provider CLIs get only the variables they need to run (`PATH`, `HOME`, `USER`, `LOGNAME`, temp folders, locale, `XDG_*`, the proxy settings including `ALL_PROXY` and `NODE_USE_ENV_PROXY`, and the CA settings), their own configuration and their own credential. The Claude CLI gets `ANTHROPIC_*`, `CLAUDE_CODE_*`, `DISABLE_*`, `VERTEX_REGION_*`, `CLAUDE_CONFIG_DIR`, `API_TIMEOUT_MS`, `MAX_THINKING_TOKENS`, `MCP_TIMEOUT`, `MCP_TOOL_TIMEOUT`, `CLOUD_ML_REGION`, and the AWS region, profile, config file, role and web identity variables. The Codex CLI gets `OPENAI_*` and `CODEX_*`, and with repository tools `GITHUB_API_URL` for `repo_info`. The Gemini CLI gets `GEMINI_*`, `GOOGLE_*` and `VERTEX_*`. A variable with a secret word as one of the underscore-separated parts of its name (`TOKEN`, `KEY`, `SECRET`, `PASSWORD`, `CREDENTIALS`, `AUTH`, `HEADERS` and similar, as in `OPENAI_API_KEY_PROD` or `GOOGLE_CREDENTIALS_JSON`) never reaches a CLI, so no other variable of the Manki step does either, whatever its name, and neither do the action inputs and the OIDC endpoint. Six such names hold a file path, an endpoint or a switch and do pass: `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, `AWS_CONTAINER_CREDENTIALS_FULL_URI`, `CLAUDE_CODE_SKIP_BEDROCK_AUTH` and `CLAUDE_CODE_SKIP_VERTEX_AUTH`. The one exception is the credentials of a Claude setup that is on: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and `AWS_BEARER_TOKEN_BEDROCK` with `CLAUDE_CODE_USE_BEDROCK`, `GOOGLE_APPLICATION_CREDENTIALS` with `CLAUDE_CODE_USE_VERTEX`, `ANTHROPIC_AUTH_TOKEN` with `ANTHROPIC_BASE_URL`, and `ANTHROPIC_CUSTOM_HEADERS` with `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL` or `ANTHROPIC_VERTEX_BASE_URL`. Without one of those gateways Manki warns that it drops `ANTHROPIC_CUSTOM_HEADERS`. They go to the Claude CLI only, and Manki redacts their values from everything it posts. Every secret value is also redacted from the action outputs, such as `findings_json`. Manki deletes the Codex and Gemini OAuth files it wrote (`~/.codex/auth.json`, `~/.gemini/oauth_creds.json`) when the run ends, so no token stays on a persistent runner. A file that was there before the run stays. Manki reads its own state only from comments and reviews by `manki-review[bot]`, or by your own App's bot, so no other account, such as `github-actions[bot]`, can forge it.
- **Reviewer tools**: Reviewers that run on the Claude CLI (`claude_code_oauth_token`) or the Codex CLI (`openai_oauth_token`) can read the PR beyond the diff. Manki fetches the head commit with 500 commits of history into a fresh folder that holds no credential. A Claude reviewer gets Read, Grep and Glob limited to that folder (`--restricted`), and a Codex reviewer gets `read_file`, `grep` and `glob` from Manki's own tool server. Both also get three tools of Manki's own: the git history of a file or lines, ast-grep structural search, and `repo_info`, which tells whether a GitHub repository given as `owner/name` exists and is public, archived or a fork, and names its default branch. `repo_info` makes unauthenticated reads of public repository metadata from the GitHub API, so no token reaches the CLI. It returns no contents, a private repository reads as "not publicly visible: private, or doesn't exist", and its answer reaches the model fenced as untrusted data. Each repository is asked once per run. A rate limit answers that it cannot tell, and the repository is asked again after five minutes. The reviewer has no shell, no other web access and no other tool, and Manki's tools refuse any path outside the folder, also through a symlink. A reviewer reads a [related repository](how-reviews-work.md#related-repositories) only through Manki's own tools, confined to that repository's checkout the same way. Symlinks in the PR are checked out as plain files that hold their target. Each reviewer gets a budget of tool calls by risk: 8 for the quick check of a trivial PR, 30 for a single finder and 40 when two finders read the PR or it touches a security, supply chain or data contract path. Three calls before the end, Manki tells the reviewer to wrap up, and after the last one it refuses every further call, so the reviewer answers with what it checked. It marks a finding it could not finish checking as not checked yet, and reports what it was still looking into as open leads: the judge settles a lead graded `blocker`, and with tools also one graded `warning`, and the progress comment lists the others, and the ones it could not settle, under "Not finished checking". A 15-minute limit per reviewer is only a safety net. The Codex CLI runs in its read-only sandbox with approvals off and every built-in tool that reads files or reaches the network or an account turned off, so Manki's tool server is all it has. Reviewers on an Anthropic or OpenAI API key, or on Gemini, review the diff without tools. The Gemini CLI gets a policy that denies every tool, so it cannot search or fetch the web either. A judge on the Claude or Codex CLI gets the same tools. With `judge.tool_steps` above 0, it reads the PR with them while it grades, up to that many calls. In every case it tries to refute each blocker and each open lead it keeps, the verdict reader's blockers included, and each finding it lowered for want of proof or would grade higher if a premise it doubts holds, with 15 calls each. The refuter reads PR content, so its answer never clears a blocker on its own. A disproved blocker keeps its grade and is posted with the refuter's reason. With a second refuter on `models.refuter_pair`, a blocker both refuters disprove stays a blocker as well, posted with both reasons, in every case but one: no finder graded the finding a blocker, the judge alone raised it to one, and two refuters on different models both disprove it. It then goes back to the highest grade a finder gave it. A security finding, a tool alert, an open lead the judge graded blocker and a finding that restates an earlier blocker or an open thread that blocks never go back (see [Severity tiers](how-reviews-work.md#severity-tiers)). A disproof drops only a finding graded below blocker, such as an open lead or a finding capped at warning for want of proof, and only when it cites a line of the finding's own file or of the PR's diff. Its reason is shown in the progress comment. A confirmed finding is posted with the lines that prove it, and one the refuter cannot settle keeps its grade, except an open lead below blocker, which is listed as not finished instead of posted. A security finding changes only when confirmed. The outcome is stored with the finding, so a later round reuses it while the files it rests on are unchanged. A finding whose higher grade the judge left to the tools is checked afresh each round, since the code or caller it rests on can sit in any file. The planner and dedup stages get no tools.
- **Memory access control**: Only people with write access to the repository can use `/manki remember`, `/manki forget`, and `/manki dismiss`. A global learning (`/manki remember global:`) is never stored by a run: global learnings reach every repo that shares the memory, so the owner of the memory repository edits `_global/` by hand. Commands from anyone else are ignored so memory cannot be poisoned by drive-by PRs. In the central memory repository, a run cannot write another repo's folder or `_global/`, so a suppression added in one repo never hides findings in another. That repository holds only public repos' memory, only the token service writes it, and Manki redacts its own secret values from everything it writes there. A private repo uses only a memory repo of its own, and on every run Manki checks with the API that this repo is private and has the same owner. Otherwise memory is skipped, and the review body says why.
- **Judge trust model**: The judge agent grades every finding and can lower any of them, from `blocker` down to `ignore`. This is intentional: a single precise judge produces fewer false positives than trusting individual reviewers.
- **OIDC authentication**: When using the GitHub App identity, token service requests are authenticated via GitHub Actions OIDC tokens. The request is cryptographically proven to come from a legitimate workflow run, so no shared secret is exchanged between your workflow and the token service.
- **Manki's own repository**: Manki reviews its own PRs with the build of the PR head (`.github/workflows/manki.yml`). Only a head in the same repository is built, and a fork's head gets the default branch. The build and the review run that head's code with every secret of the job and `id-token: write`, so this is safe only while everyone who can push a branch to the repository is trusted. Your own workflow runs the released action and never builds a PR.
