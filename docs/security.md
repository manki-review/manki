# Security model

Manki handles untrusted PR content and cross-repo tokens. The security model rests on these guarantees:

- **Prompt injection** — PR diffs are untrusted content passed into LLM prompts. All findings are sanitized before posting to GitHub so that embedded HTML, scripts, and `@mention` strings cannot be used to inject content or trigger notifications. The finders and the verdict reader get the PR title and description, linked issues, file contents and the diff in fenced blocks that no text inside can close, each labelled as untrusted data, and are told never to follow instructions in them. The judge gets the same content labelled as untrusted.
- **Token handling** — All secrets are masked in workflow logs via `core.setSecret()`. The App's review token covers only the reviewed repo and only reads its code. Memory writes use a separate token: `memory_repo_token`, or an App token that can write only the memory repo (`<owner>/review-memory` with the manki-review App). Your own App's private key needs more care, see [Your own GitHub App](getting-started.md#your-own-github-app). The provider CLIs get only the variables they need to run (`PATH`, `HOME`, temp folders, locale, `XDG_*`, the proxy settings including `ALL_PROXY` and `NODE_USE_ENV_PROXY`, and the CA settings), their own configuration and their own credential. The Claude CLI gets `ANTHROPIC_*`, `CLAUDE_CODE_*`, `DISABLE_*`, `VERTEX_REGION_*`, `CLAUDE_CONFIG_DIR`, `API_TIMEOUT_MS`, `MAX_THINKING_TOKENS`, `MCP_TIMEOUT`, `MCP_TOOL_TIMEOUT`, `CLOUD_ML_REGION`, and the AWS region, profile, config file, role and web identity variables. The Codex CLI gets `OPENAI_*` and `CODEX_*`. The Gemini CLI gets `GEMINI_*`, `GOOGLE_*` and `VERTEX_*`. A variable named like a secret (`*_TOKEN`, `*_KEY`, `*_SECRET`, `*_PASSWORD`, `*_CREDENTIALS` and similar) never reaches a CLI, so no other variable of the Manki step does either, whatever its name, and neither do the action inputs and the OIDC endpoint. The one exception is the credentials of a Claude setup that is on: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and `AWS_BEARER_TOKEN_BEDROCK` with `CLAUDE_CODE_USE_BEDROCK`, `GOOGLE_APPLICATION_CREDENTIALS` with `CLAUDE_CODE_USE_VERTEX`, and `ANTHROPIC_AUTH_TOKEN` with `ANTHROPIC_BASE_URL`. They go to the Claude CLI only, and Manki redacts their values from everything it posts. Manki reads its own state only from comments and reviews by `manki-review[bot]`, or by your own App's bot, so no other account, such as `github-actions[bot]`, can forge it.
- **Reviewer tools** — Reviewers that run on the Claude CLI (`claude_code_oauth_token`) or the Codex CLI (`openai_oauth_token`) can read the PR beyond the diff. Manki fetches the head commit with 500 commits of history into a fresh folder that holds no credential. A Claude reviewer gets Read, Grep and Glob limited to that folder (`--restricted`), and a Codex reviewer gets `read_file`, `grep` and `glob` from Manki's own tool server. Both also get two tools of Manki's own: the git history of a file or lines, and ast-grep structural search. The reviewer has no shell, no web access and no other tool, and Manki's tools refuse any path outside the folder, also through a symlink. A reviewer reads a [related repository](how-reviews-work.md#related-repositories) only through Manki's own tools, confined to that repository's checkout the same way. Symlinks in the PR are checked out as plain files that hold their target. Each reviewer gets a budget of tool calls by risk: 8 for the quick check of a trivial PR, 15 for a single reviewer and 30 when two reviewers read the PR or it touches a security, supply chain or data contract path. Three calls before the end, Manki tells the reviewer to wrap up, and after the last one it refuses every further call, so the reviewer answers with what it checked. It marks a finding it could not finish checking as not checked yet, and reports what it was still looking into as open leads: the judge settles a lead that could block, and the progress comment lists the others under "Not finished checking". A 10-minute limit per reviewer is only a safety net. Reviewers on an Anthropic or OpenAI API key, or on Gemini, review the diff without tools. A judge on the Claude or Codex CLI gets the same tools for one purpose: it tries to refute each blocker and each open lead that could block, with 15 calls each. A disproved one is dropped and its reason shown in the progress comment, a confirmed one is posted with the lines that prove it, and one it cannot settle is posted as a warning at most. A security finding is never dropped or lowered this way. The outcome is stored with the finding, so a later round reuses it while the files it rests on are unchanged. The planner and dedup stages get no tools.
- **Memory access control** — Only people with write access to the repository can use `/manki remember`, `/manki forget`, and `/manki dismiss`. Commands from anyone else are ignored so memory cannot be poisoned by drive-by PRs.
- **Judge trust model** — The judge agent has final say on severity and can downgrade `required` to `ignore`. This is intentional: a single precise judge produces fewer false positives than trusting individual reviewers.
- **OIDC authentication** — When using the GitHub App identity, token service requests are authenticated via GitHub Actions OIDC tokens. The request is cryptographically proven to come from a legitimate workflow run, so no shared secret is exchanged between your workflow and the token service.
