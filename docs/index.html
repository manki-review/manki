🚫 Blocker · Security · Quick fix

Methods declared on one line share a member id, so a crafted file makes the new group filter cubic in its method count

What goes wrong: A member's id is ${m.file}:${m.decl.start}, so every method on one line, such as a one-line TypeScript class class A { m0() { return 1 } m1() { return 1 } ... }, a Go line of ;-separated methods or a one-line Rust impl, gets the same id. With a sibling file declaring each m_i on its own line, asked.get('a.ts:1') grows with every kept group.

How to fix it, why, and 9 places read · double-checked

How to fix it
Key members by their declaration node, which is unique per method, instead of by start line. That makes the code comment's claim true: a member sits in at most one group per key it has, so at most 9 groups. Add a size case with many methods on one line.

    return [{ members, order, ids: members.map(m => `${m.file}:${m.decl.key}`), touchedCount: touchedMembers.length, lines }];

Why it matters
For each of those groups, ids.every(id => asked.get(id)?.includes(group)) scans that same list again, so the filter runs about N³/6 steps. 10,000 methods means about 10^11 steps of synchronous work with no timeout, and this PR removes the per-file cap of 50 keys that bounded N. The same collision drops real groups: when the partner methods also share one line, each later group's ids equal the first group's, so only one of the N distinct comparisons is asked. That breaks the PR's own rule of dropping a group only when one asked group holds all its members.

What to test

The review model wrote these steps. Check what a step runs before you follow it.

Setup: Use a repository checkout where the PR head is available, so listUsesOutsideDiff runs with ast-grep.

  1. Change 60 dunder methods on a Python class Many(Base) and add Other(Base) with only the last one. Expect a sibling implementation question for the last method with Many and Other.
  2. Change many methods on a Go type that has a sibling type beside it. Expect exactly 20 implementation questions, returned within a few seconds.
  3. Give three Python classes __eq__ where each pair shares one base. Expect three separate __eq__ questions, with the group whose two members both changed listed first.
  4. Change two sibling groups that tie on changed members and changed lines. Expect the group with more members listed first.
  5. Put several methods of a TypeScript class on one line and change them. Expect each method to get its own question.
  6. Make three sibling methods whose bodies are each about 900 KB. Expect the group to be asked even when two bodies match, since the third falls past the 2 MB budget.

One comment tracks every round: who read the change, on which model, and what the judge kept. Its checkboxes pause reviews or ask for another one.

How a round runs.

Five stages, each with one job. The defaults work out of the box, and every stage is yours to tune.

1

Planner

A fast pass looks at what kind of change this is and sizes the review. It never counts lines.

2

Finders

The readers of your change, and you decide who they are. By default one finder reads it, or two on different models when a miss would reach a user.

Your modelseach reader gets its own model and effort, from any provider
Your checksadd what matters in your project to their checklist
Your groupssend risky paths to a stronger set of readers
3

Dedup

Drops findings that repeat ones already resolved in earlier rounds.

4

Judge

Checks each finding against the code, merges duplicates and grades them. Only a blocker blocks.

Refuteron the Claude or Codex CLI, it tries to disprove every blocker
5

Verdict reader

Runs only when nothing blocks. It reads the whole diff cold and looks for a reason not to merge.

On your pull request

One thread per real problem, and a review that approves or asks for changes.

trivial

Could a defect hide here at all?

If not, a single quick check reads it. Docs, renames and generated files.

subtle

Does judging it need reasoning about behaviour?

If so, the finders work at high effort.

paired

Could a defect reach a user if every reader missed it?

If so, a second finder joins on another model.

Security-sensitive paths, CI and dependency files, and data contracts always get at least two finders, whatever the planner answers.

One file, your rules.

Pick a model for each stage and set up your own groups of readers for the changes that matter most. Manki reads .manki.yml from the base branch, so a pull request cannot weaken its own review.

Questions.

What does it cost?

You pay your own provider for the tokens a review uses, or run it on your subscription. There is no per-seat fee. Every review ends with the tokens it used.

Where does my code go?

Only to the model provider you configured, from your own runner. Manki has no server that stores your code.

Can a pull request switch off its own review?

No. Manki reads its config from the base branch. A change to the config applies after it merges.

Is it open source?

Yes, under AGPL-3.0. You can read every prompt and every line.

Can the author dismiss a blocker?

Not alone. A blocker or a security finding stays open until someone else with write access resolves it.
