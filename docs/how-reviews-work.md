# How reviews work

What Manki does on each round, how it picks its readers, how it grades findings, and what it reads besides the diff.

## Review pipeline

Manki reviews run in these stages:

1. **Planner** (pre-review): A fast Haiku pass answers three questions about the nature of the change, never its line count, plus the judge effort and PR type. A repository can fix the judge effort with `judge.effort` instead. `trivial`: could a defect hide here at all? A trivial change (docs, a rename or move, a repeated mechanical edit, dead code, fixtures) is read by a single **quick check**. The planner sees only the list of changed files, never the PR title, description or diff text, and Manki believes a `trivial` answer only when every changed file is docs, snapshots or generated, deleted, or renamed without edits. A change to tests alone is not trivial: one finder reads it. `subtle`: does judging it need reasoning about behavior? That sets the finders' effort to high, otherwise medium. `paired`: could a defect reach a user if every reader missed it? By default that adds a second finder. A missing or unclear answer or a timeout takes the side that adds review: by default two finders at high effort. A diff that touches a security-sensitive path (auth, tokens, secrets, crypto, sessions, permissions and similar), CI or automation (`.github/workflows/**`, `.github/actions/**`, `action.yml`), a dependency or toolchain manifest (`package.json`, lockfiles, `Cargo.toml`, `go.mod`, `pyproject.toml`, `requirements*.txt`, `Gemfile`, `*.gemspec`, `rust-toolchain*`, `.nvmrc`, `Dockerfile*`), or a data contract (`migrations/**`, `*.sql`, `*.proto`, `schema.*`, `openapi*.yml`, `openapi*.yaml`, `openapi*.json`) is never trivial and always paired, whatever the planner says. Each round is triaged fresh. See [Review groups](#review-groups) for how the answers and paths pick the readers.
2. **Finders**: The readers of the PR's [review group](#review-groups) read the diff in parallel. Which group a PR gets and who is in it is yours to set. By default it is one finder on Sonnet, plus on paired rounds a second on Opus. Every finder runs the same checklist, so the two default finders differ only in their models, and a reader of a group of your own can add a `focus` line. It checks the change itself: correctness first, then security, including resource exhaustion from outside input such as an allocation sized by a length a caller passes. When the PR title, description or changed code says the change matches another implementation, a spec or a standard, it opens that code, in a `reference` related repository when one is configured, and reports each difference. When the code implements or mirrors a reference, such as a spec, another implementation or an API it talks to, it compares each contract in both directions: what the code produces against what the reference accepts and the other way round, along with limits, field order, field types and versions. Then it checks error paths and cases a pattern match, error handler, ignored result or fallback drops. Once it finds a defect, it names the other kinds of input that reach the same lines and the other places in the change that make the same mistake, and lists every case that fails the same way in that one finding, with a fix that covers each of them. It proposes the fix for the root cause of the problem, never another patch for its symptom: when its evidence shows where the problem starts, the fix goes there. It never advises repeating the PR's own handling on another path when one change at the root cause covers every path. The sibling comparisons, the related repository checks, the claim checks, the sweeps and the verdict reader write their fix advice by the same rule. For a change that fixes a problem, it asks whether the change fixes the root cause of the problem or is a hacky workaround for the symptom. The same gap on a second path, or the change handling the same condition in more than one place, points to a root cause elsewhere, so the finder finds the one decision that produces the condition and reads that code first. It reports a workaround only when it can cite the code that causes the problem and say what change there would replace the PR's fix, or name the input or path that still fails. When the PR's own text calls something an intended workaround, that is a claim it checks, never a reason to skip the question. Such a finding is graded by its damage like any other. It then checks tests that would still pass if the change were reverted or that set internal state. It looks for an existing helper the change could reuse and for breaks of the rules in the repository's `AGENTS.md`, `CLAUDE.md` or `CONTRIBUTING.md`, and reports such a finding only with the helper's `file:line` or the rule quoted. It also goes through the rules about the change as a whole, such as a test or a migration that a kind of change requires (see [Rules from instruction files](#rules-from-instruction-files)). Then it checks contract breaks, and when the change narrows what it accepts (a lower or new limit, stricter validation, a narrower type, a new required field or a stricter format) it finds every producer of that input, in the repository or a reference it mirrors, and checks that each still fits. It also searches outside the diff: every reader of a changed type, field, variant or function across the repository, sibling state that holds the same item or is computed from it (other collections, caches, indexes, derived totals or counts, serializers, change notifications), and counterparts that must check alike, such as encode and decode. Every round, each finder searches the whole PR: it reports every blocker, warning and security issue it finds, follows the callers of changed code and other routes to the same outcome, and for each defect checks the whole PR for the same kind, reporting one finding that lists every place. The default finders are both Claude models, so they need no extra credential. Another provider is used only when you name its model in a review group. A finder that fails is run once more, unless it reached a used-up limit or ran out of time, since a retry from the start would end the same way. If any finder still fails, the round ends incomplete and never approves. A reply that is not the list of findings fails the finder too, and so does one where no entry has a title or a description. The retry then tells the finder what was wrong with its reply. A finder that opens none of the code Manki listed for it outside the changed files is asked once more (see [Uses outside the diff](#uses-outside-the-diff)). Once every finder has answered, a [second read](#second-reads) can read the change again, told what the round found so far. Each finder also answers for every unit of the change, each changed function and each changed condition, in a line of its own, and is asked once more about a unit it gave no line (see [Units of the change](#units-of-the-change)).
3. **Sibling comparisons**: Alongside the finders, small targeted calls on the model of the group's first reader compare the changed code with the code beside it: whether a sibling field can hold the item a changed line looks up, and what checks one implementation of a function has that its siblings lack. Their findings go through dedup and the judge like any finder's. See [Sibling comparisons](#sibling-comparisons). Each counterpart that the search of the [related repositories](#related-repositories) finds gets such a call too. So does each piece of structure the change adds, such as a new file, type or function, whose call compares it with how the repository already does the same kind of thing. See [Patterns of the codebase](#patterns-of-the-codebase).
4. **Claim checks**: Also alongside the finders, each statement in the PR title, its description or an added comment that the change relies on, such as "the upload service already rejects files over 10 MB", gets one small call on the model of the group's first reader that looks for the code that proves or breaks it. That call never reads the PR description. Only a statement the code disproves gives a finding. See [Claims of the PR text](#claims-of-the-pr-text). Each fix the diff holds gets such a call too, which follows the problem to its cause and gives a finding only for a workaround that leaves the cause as it was. See [Fixes in the change](#fixes-in-the-change).
5. **Scope reader**: Also alongside the finders, one call on the judge's model reads the whole diff, the PR title and description and the linked issues, and answers two questions about the PR as a whole: is the change useful, and does it mix topics that belong in separate PRs. It runs only when the diff changed since the last round it ran on, and never on a trivial change. Its answer is listed in the review body, or with `review.scope_blocks` posted as warnings. See [The scope of a PR](#the-scope-of-a-pr).
6. **Dedup**: A two-tier dedup pass drops findings that repeat an earlier resolved finding before judge evaluation. A static matcher takes only a certain repeat: the same title in the same file, at most 5 lines from the earlier finding, matching a thread whose code moved on the line it was posted on. Shared title words or a nearby line alone never make a repeat, since a new defect can sit next to an earlier one. Then an LLM dedup pass (Haiku) compares each finding's title, line and description with the earlier resolved findings and with every other thread Manki answered, so a repeat in other words or on another line is caught too. A repeat of such an answered thread is never dropped there: in the thread's own file it goes to the judge with Manki's answer. When the call fails, every finding goes on. A thread Manki resolved counts as resolved here too when it was settled without a fix: Manki accepted an answer that accepted no fix, such as "Withdrawn." or "Agreed.", as the record in its own reply says. Only Manki's own comments say so, so a person's dismiss command does not. A thread where Manki accepted or confirmed a fix, or a judge ever found it fixed, does not count, and neither does any other thread Manki resolved, so a repeat there goes to the judge. A match counts in the finding's own file, or in another file when the finding cites a line that the earlier finding sits on or cited, as its round record keeps them. A finding tied to no file matches only in its own place. A match with a thread a person resolved, in that thread's own file, is dropped. Any other match is dropped only while no push since the thread was raised changed its file, a file its findings cited or a file the repeat cites: a match in another file, since it can be a fix that came back there, and a match with a thread Manki resolved, since its answer held only for the code it read. For a repeat of a thread Manki settled by its answer, in any file, the check is by line instead: each hunk since the round that raised the thread, in a file with a cited line, must start more than 10 lines after the last such line, before and after. Those hunks are the push's when it is the only change since that round, and otherwise GitHub's comparison of that round's commit with the head. A comparison that cannot be read, as after a force push, counts as a change. The cited lines are the thread's line, the lines its findings cited, the lines Manki's answer cited, and the repeat's own line and cited lines. This check applies only when Manki's answer checked every statement of the reply and each of them cites a line of the PR, and every round record of the thread still holds its findings' cited lines. An answer resting on a search or on the PR description gets the file check instead. A file cited without a line, such as the file of a finding on a whole file, counts as changed by any hunk in it, and so does a renamed file or a file GitHub lists without its lines. The judge may also link a finding to the finding of such a thread, when its cited code passes the same check, and does so only when the earlier finding already names every failure the new one names. A linked finding is then dropped as a repeat of the settled thread. A thread Manki settled by agreeing with an answer that names a tracking issue, such as "Bounding it in #12 is fine", needs no line check for that link while the issue still verifies in the round: it is open, a person with write access opened it, and its title or the start of its description names a name in a code span that the thread's finding or the evidence of its round entries cites. The file alone does not count, since an issue about another defect of the same file names it too. A plain lowercase name, such as `dialed`, counts here when the issue writes it in a code span too, as in `Bans::dialed`. A failed lookup of a tracking issue, other than one GitHub does not find, is named in the round record and defers nothing. Manki reads such an issue by its number and never lists it as related work of the PR. Only an answer that agreed defers a thread, so an issue a withdrawal names in passing defers nothing. A linked repeat of such a thread is then kept in the round record only, whatever the push changed, unless it is graded above the thread. Once the issue is closed or no longer names that code, a repeat is posted again. After such a push, or when the push is unknown, a repeat in the thread's own file goes to the judge with Manki's answer, as an answered repeat does in the static matcher, and a repeat in another file goes to the judge on its own and is posted at its own place. An earlier finding graded below the new one never drops it, so a resolved suggestion lets a later warning or blocker on the same spot through. The same holds for an author's agreement or a resolved thread in later steps, and for an open thread, which carries only a finding graded at or below its own grade. An agreement in those steps drops no repeat unless the same line check finds the lines its thread and the repeat cite unchanged. A thread a person resolved still drops it. So a warning or a blocker about the problem of a suggestion thread gets a thread of its own.
7. **Judge agent**: A single agent evaluates the deduplicated reviewer findings for accuracy, actionability, and severity. It filters out noise, merges any remaining overlap, and grades each surviving finding as a blocker, a warning or a note. After its grading, copies with the same title in one file at most 5 lines apart are merged as one finding, which keeps the highest grade of the copies and every copy's reviewers. The same title further apart stays two findings, since it can be the same mistake in two places. It reads each finding's code and the diff of every file with a finding, a line a finding cites as proof or in an evidence line, or an open thread, cut to 200,000 characters when those files are larger. With `review.sweep`, a finding it keeps can start a [sweep](#sweeping-for-a-defect-class) for other instances of its defect class, whose findings it then judges too. A round with nothing to judge skips the judge: no finding is left after dedup, no review thread is open, and no warning carried from the last round's review body is asked about. The round then says "No new problems found.", its record sets `judge.skipped` to `nothing_to_judge`, and the progress comment shows the judge as skipped. When the open threads or an earlier round record could not be read, the judge runs.
8. **Other finder's vote**: On a round where two or more finders ran, each blocker and warning only one of them reported asks a finder that did not report it for the harm it causes, on that finder's model. See [the other finder's vote](#the-other-finders-vote).
9. **Importance**: One call on the judge's model rates the warnings the round is about to post, each from 1 to 10. A warning whose trigger is rated below `review.min_warning_trigger` and that does little harm is not posted. See [the importance of a warning](#the-importance-of-a-warning).
10. **Verdict reader**: Runs only when no finding blocks. It reads the whole diff cold on the judge's model, without the PR description or earlier rounds' findings, and looks for a reason not to merge. A large diff is read in the same slices as the finders, one call each, and the PR is `READY` only when every slice is. Each call is told which slice it reads, so code missing from its slice is no defect, and gets the same map of the other slices as a finder. The blockers of all slices are posted. A finding the judge kept that names the same problem as one of them is folded into that blocker, so one problem gets one thread. Without a model it counts as the same problem only when both have the same title in one file, at most 5 lines apart. Any other finding is checked when it sits near the blocker: their lines or narrow proof lines are at most 5 lines apart. It is also checked when the two share a cited line in any file, such as a finding at a caller whose proof cites the blocker's line in the callee. A cited line there is a finding's own line, or a proof or evidence line in a span of at most seven lines. A finding tied to no file, such as a scope warning, is never paired this way. The dedup model gets every such pair of the round in one call. It folds a pair only when it answers that both describe the same defect, with the same root cause and the same fix. An unsure answer, no dedup model or a failed call keeps two threads, so a new defect next to a blocker is never lost in it. A proof line counts only as a single line or a span whose first and last line are at most 5 apart. When the folded finding's title says something the blocker's does not, the blocker's description ends with "Also reported as:" and that title, followed by its file and line when it sits in another file. From the second round it also gets the files changed since the last reviewed round, as the finders do. `READY` approves with "What this does" and "What to test" sections. `ADDRESS_FIRST` requests changes and posts its blockers as inline comments, each with what the reader checked and the lines that prove it. When the judge has repository tools, it first tries to refute each of these blockers as it does its own, and the outcome closes the collapsed section under the blocker, after its fix and checks. Output that cannot be parsed ends the round as incomplete, never as an approval.
11. **Review posted**: Surviving findings are posted as inline PR comments or listed in the review body, under a summary and the verdict. From the second round on, a note on a test file is dropped, unless it is a security finding or a tool alert. A test file is any file under a `test/`, `tests/`, `__tests__/`, `testdata/` or `test_utils/` folder, data and documents included, so `src/test/` of Java and Kotlin counts. Every other mark counts only in the languages whose test tools use it: `spec/` and `a_spec.rb` or `a_spec.ts` for Ruby, JavaScript and TypeScript, `a.test.ts` and `a.spec.js` for JavaScript and TypeScript, `a_test` for Go, Python, Ruby, Rust, JavaScript and TypeScript, `a_tests.rs` and `tests.rs` for Rust, `test_a.py`, `conftest.py` and `tests.py` for Python, a name or a folder above the file that ends in `Test` or `Tests` for Swift, Java, Kotlin, Scala, Groovy and C#, such as Swift's `Tests/` or C#'s `App.Tests/`, and a name that ends in `Spec` for Scala and Groovy. So an `api/spec/openapi.yaml`, an `openapi_spec.yaml` or a `PodSpec.kt` is no test file. Manki tells test files apart by the same rule when it lists the uses outside the diff.

No finder or verdict reader prompt cuts the diff. They read it in slices of about 1,500 changed lines and at most 200,000 characters, so a normal PR is read whole in one call, and each call is told which slice it reads. A file with more changed lines stays whole in a slice of its own, and one over 200,000 characters is split between its hunks, or inside a hunk between lines. An added line over 20,000 characters cannot be shown in full, so a round whose reviewed diff holds one ends incomplete before any model runs, and names the first 10 such lines. Split the line, or exclude its file in `exclude_paths` on the base branch. Lines in excluded files do not count. A longer removed or unchanged line is shortened, since cutting it hides no new code, so deleting a minified file still gets a review. Each slice costs one call per reader, so the size of the reviewable diff is also capped in characters, next to `auto_review_max_lines` and `max_diff_lines`. A PR over 2,000,000 characters gets no automatic review, only the too-big notice with the review box in its settings block, and one over 4,000,000 is never reviewed, even when forced. These two limits are fixed. GitHub refuses the diff of a large PR, such as one with more than 300 files, or one that takes too long to generate. Manki then builds the diff from the PR's list of changed files and applies the same limits to it. GitHub lists at most 3,000 files, so a PR that changes more gets the too-big notice and is never reviewed.

Code missing from the slice a call reads, such as a caller or a test, is no defect there. Each call also gets a map of the other slices, so a slice that calls a function another slice changes is checked against that change. The map lists each changed file only the other slices hold, under the first slice that holds it, with how the file changed and its added and removed lines. It names up to 6 declarations per file, in this order: those the change removes, those whose declaration changed (the signature, type, doc or attributes), those whose body changed, and those it adds. Manki compares each declaration with its namesake before the change, a method by its type and name: one only the base holds is removed, one only the head holds is added, one whose part before its body differs has a changed declaration, and any other changed one has a changed body. Several namesakes in one file, such as a getter and its setter, count as one declaration. A new value of a constant, a type alias, a class attribute or a config key is a changed body. So a declaration next to removed code is named only when it changed itself. Both versions of a file are parsed with the parser that lists the [uses outside the diff](#uses-outside-the-diff). In a parsed file, a declaration inside a function is never named. A file in a language without a grammar, or past the parse limit, gets the declarations its added and removed lines name by keyword, whatever their indentation, except an indented constant, which is a local variable and is never named, whether removed, changed or added. So a removed method of a class and a removed config key nested in a section are named. Such a file cannot tell other declarations inside a function from the rest, so among its declarations with the same kind of change the least indented come first. A round without a checkout of the PR head gets no declarations. Test files, documents, generated, vendored and mock files, and paths in `exclude_paths`, name none. The map shows at most 50 files and says how many more there are. It says where something changed, not how, so a finder reads the code an entry points to before a finding relies on it. The map costs no model call.

When a provider's safety filter refuses a stage, Manki sends that stage once more on `models.fallback`. Without that setting, or for a stage already on that model, the stage goes to the first model of the `full` review group that is another model than its own, which is Sonnet by default and Opus for a stage on Sonnet. When `full` has no other model, the stage is not sent again. The round context records the stage, the fallback model and the refusal reason under `models.fallbacks`. A second refusal fails the stage, which ends the round incomplete for a finder, the judge or the verdict reader, and other errors are never retried on the fallback model.

A call made with repository tools never goes to a fallback model that has none, after a refusal or a limit. A model has these tools through the Claude or Codex CLI, and has none with an Anthropic or OpenAI API key or on Gemini. Besides the PR's head, every stage with these tools can read a file as it was before the PR: `read_file` with `ref` set to `base` reads it at the merge base the PR's diff starts from. A file `exclude_paths` names is not read there, and a path `closed_paths` closes is refused there as at the head. See [security](security.md) for how the base is fetched. A fallback model without them would answer as if it had read the code, so the call fails with its own error, as it does without a fallback model. This holds for the finders, the sibling comparisons, the related repository checks, the claim checks, the pattern checks, the fix checks, the sweeps and the refuter. The judge instead grades without tools for the whole round when its fallback model has none, so it keeps that fallback.

A stage whose model stays limited moves to the same fallback model. That covers a used-up subscription limit, quota or rate limit, a model at capacity and an overloaded provider, once the provider client's own waits and resumes are used up. It also covers a model whose endpoint could not be reached at all: a Codex run on an [OpenAI-compatible endpoint](getting-started.md#openai-compatible-endpoint) that reported nothing after its turn started but that it was waiting for the network, until it was ended after 2 minutes, so no request reached the model. On a ChatGPT login the Codex CLI retries over WebSocket first, which proves nothing, so a failed connection there keeps its own error. A run that got any answer, that failed in another way or that ran out of time keeps its own error. Only Codex prints output that proves no request reached the model, so a failed connection on any other client does not move a stage. The failed call is sent to the fallback model once, with the time it left of its limit, and the stage's later calls go there once the fallback model answered. For a finder, the judge, the refuter or the verdict reader, the review then says so in its "About this review" fold and in the Review metadata of the progress comment, such as "`gpt-5.5` reached its limit, so `claude-sonnet-5-5` read in its place", or "`gpt-5.5` could not be reached" when its endpoint could not be reached. The line says "judged" for the judge and the verdict reader, and "checked" for the refuter. `models.fallbacks` records the stage with `limit: true` and the limit as the reason, such as `OpenAI endpoint unreachable`, and adds `unreachable: true` when the endpoint could not be reached. A finder never moves to a model that already reads for the round, as another finder's model or as the model another finder moved to, because two reads by one model are weaker than the group. A finder holds its fallback model from the moment it is sent there, so two finders that reach a limit at once never both get it. When that fallback model fails, the model is free again for a finder that reaches a limit later. A limit is never retried on the model that reported it. When the stage has no fallback model, the finder may not move, the call needs tools the fallback model lacks, or the fallback model fails too, the stage fails with the limit of its own model, and the log names the error of a fallback model that failed. It fails too when it sits behind the same used-up limit, such as two Claude models on one subscription. For a finder, the judge or the verdict reader the round then ends incomplete and names the limit, with its reset time when the provider gives one. To see it coming, the Review metadata section of the progress comment lists how much of each usage window the Claude and ChatGPT subscriptions have used, as the Claude and Codex CLIs report it after their calls, with the reset times. A call that fails, such as on the used-up limit itself, keeps its readings too. When a window has just passed the 70% or 80% mark, at most 2 points past it, the review body shows a red box under the verdict. From 90% the box shows on every review. It names each such window and the highest of the 70, 80 and 90% marks it passed. The readings in Review metadata show on every review either way. API keys and Gemini report no such windows, so they show none.

Each call of a finder and the verdict reader has 15 minutes. The judge has 15 minutes for all the calls of one attempt: the first call, one more when the reply cannot be read, and one more when the reply leaves out a finding or an open thread. A judge on a model through the Codex CLI can take several minutes. A judge with repository tools that fails, by running out of time or otherwise, grades once more without them. That second attempt gets what the first left of its 15 minutes, and at least 5 minutes, so the judge's own calls take at most 15 minutes without tools and 20 minutes with them. A call that a safety filter refused, or that reached a limit of its model, gets only the time it left of its time limit on the fallback model. The refuter's checks come after the judge's calls and are not part of that time: each of their calls has 10 minutes. The installation of a provider CLI on a runner that has none is not part of it either. With `review.sweep`, the judge's run on the findings of a sweep has the same limits again. When the judge ends on a call that runs out of time, the round ends incomplete and its summary says "The judge ran out of time".

A review in the action has 25 minutes for its model calls, counted from the start of the action. No step of a GitHub Actions job can read the job's `timeout-minutes`, so this time is fixed below the 30 minutes of the [workflow template](getting-started.md#step-3-add-the-workflow) and leaves time to post the round. A workflow with a shorter `timeout-minutes` gets the same 25 minutes. Every model call gets at most the time the round has left. The calls of the finders, their retries, their moves to the fallback model and the [second reads](#second-reads) leave the last 8 minutes to the dedup, the judge and the stages after it. A retry or a second read starts only with at least 5 minutes of the finders' time. After the finders, every model call checks the time left before it starts: each call of the judge, the refuters, the sweeps and the verdict reader needs at least 2 minutes of the round, and each dedup call at least 30 seconds, which is more than these calls usually take. A fallback model gets what the failed call left of that time too. Otherwise the round ends incomplete in time to post, and its summary says why. Once one call does not start, the round starts no other call and stops the calls still running beside it. Their stage treats each such call as a failed call without a warning and keeps every result it already has: a check that did not run confirms nothing, and a dedup that did not run drops nothing. The round then ends after that stage, and its record keeps everything the round produced up to there. That is what the judge graded, the checks that answered, the sweeps that answered and the places they found, and the verdict reader's blockers as raw findings, unconfirmed. The stopped calls count in the usage as failed calls, with whatever use their provider reported. A call that did not start shows only under `notStarted`: it counts as no failed call or retry, and leaves no sweep or check in the record. A check that does not start confirms no finding, and a round that does not run its verdict reader approves nothing. The record lists each retry, move to a fallback model and call the round did not start under `notStarted`, with the reason, and the line of the finder in the progress comment says it too. A local review has no such limit.

An incomplete round posts a comment, fails the `Manki` check and keeps an earlier request for changes. It dismisses Manki's approval of an older commit, since no model approved the code pushed since. An approval of the same commit stays. Once no Manki approval stands and every dismissal worked, Manki tells the token service that no approval stands. A review command then reviews the commit again, also when an earlier review of it was complete. The comment carries the round's record, with what ran and what failed. A later round does not count it as an earlier round: it does not use up the round cap, and the next round compares against the last round that completed.

The token service reviews such a commit once more on its own, a few minutes later, since its head has no finished review (see [what the service does](getting-started.md#what-the-service-does)). The incomplete round of a push says so: "Manki starts one more review of this commit on its own within a few minutes. If that one does not finish either, retry with /manki review." It says so only where the retry is sure to follow: a round started by a pull request opened or pushed to, on a branch of the same repository, that is not a draft, not opened by a bot, not started by a box and not that retry itself. A pull request reopened or marked ready gets no promise, since its head can have had its retry already. Any other incomplete round names only the command. The service can still retry after such a round, and the retry then says what it is. When limits stopped the round, its record holds in `meta.retryAfter` the latest time Manki can read at which one of them lifts, and the review carries the same time in a hidden `<!-- manki-retry-after: ... -->` line below the record. The service starts no retry before that time, and the round says "after" that time, in UTC. Manki reads the time from a usage window the provider reports as used up, from a wait such as "in 1m30s", or from an ISO 8601 time with its zone. Other wording, such as "resets 3pm (America/New_York)", is quoted in the summary, but leaves the day or the zone unsure, so Manki reads no time from it. The round promises a retry after a limit only when it read a reset time for every limit that stopped it, and that time is at most 23 hours away, since the service looks only at pull requests updated in the last day. Otherwise each limit names the command for after it lifts. The service still retries such a round, after the latest time it recorded or within minutes when it recorded none, and that retry can meet the same limit.

The retry says "Started automatically, since no review of this commit had finished." at the top of its progress comment and below the first line of its review, and its record sets `meta.trigger.catchUp`. The service names its delivery `catch-up-` and the first 12 characters of the commit, which tells Manki the run is that retry. A run on a commit whose last run failed or ended incomplete keeps that run's progress comment and moves the settings block to its own. Once its review starts, it marks the earlier comment "Review superseded by a later review", above the report of which reader failed and why. A run that reviews nothing, such as one that finds the pull request too big or reads no file of it, leaves that report as it is.

A review of a commit whose last round ended incomplete starts from that round's record and runs only what did not finish. A finder whose read finished is not run again, and its findings from the record go on to dedup and the judge as they were. So does each sibling comparison, related repository check, claim check and fix check that answered. The list of fixes is asked again, so a fix check is kept only when the list gives the same fix with the same problem. When every finder is kept, so are the [second reads](#second-reads) of the attempt, since each would be sent the same again. That holds only for reads that ended because a read added nothing or because of the cap. Reads cut short by time or a failure run again. A finder or check that failed, or that moved to a fallback model, runs again. When only the judge, a check after it or the verdict reader failed, no finder runs, and dedup, the judge and the stages after it run on the recorded findings. This holds for the token service's retry and for a review command alike. Review again and Deeper review keep nothing, since they ask for a new read.

Manki keeps a result only when it is certain the retry would read the same thing. The record must be the newest round record on the PR, written by Manki and never edited, of a round that ended incomplete on the same commit and diff, under the same Manki release, with the same review group, models and efforts, and with every finding in full. Each finder and check records `inputDigest`, a SHA-256 of everything it was sent: its prompt, the diff, the instruction files, the PR text, the CI results, the uses outside the diff, the units it answers for, and its model, effort and tool steps. A result is kept only when the retry would send exactly the same. A finder also records `findingsReturned`, the number of findings it gave, and when that differs from the findings the record holds for any finder, nothing is kept. With related repositories, once a part could be kept, the retry fetches each one a call of the attempt read, and each must be at the commit the attempt read. The finders that run anyway start without waiting for that. A finder whose second ask failed did not finish its read, records no `inputDigest`, and runs again. A repository no call of the attempt read cannot change a kept result, so its commit does not matter. Anything else gives a full review. When every finder is kept, the checks asked again still get the time a finder could have taken before their minute of grace starts.

The review says what it kept in one line below its first line, such as "Claude Opus 5.5 read this commit in the last attempt, and its findings were kept." The progress comment shows such a finder as kept from the last attempt. The record names the attempt in `meta.reusedFrom`, with the id of its review and the time it ended, and marks each kept finder, comparison, claim check and fix check `reused`, and `secondReads` too when it kept them. Its usage and cost count only the calls the retry made.

## Review groups

You decide who reviews what. Each round sorts the PR into a **review class**, and the class picks a **review group**: the readers that run as finders. The `review` block configures all three. A group is a list of one or more readers, each with its own model from any supported provider, its effort and an optional `focus` line. The groups are the only place that says which models read a PR. A class matches PRs by path, by the planner's answers or both. The routing names the group for each class. Without a `review` block the built-in classes and groups below apply, which give a PR the quick check, one finder or two.

The class with the highest rank among those that match wins.

| Class | Rank | Matches | Built-in group |
|-------|------|---------|----------------|
| `security` | 100 | a security-sensitive path (`@security_paths`) | `full` |
| `supply_chain` | 90 | CI, automation, a dependency or toolchain manifest, a file that fetches or builds code such as `.gitmodules`, `.gitattributes`, `.npmrc`, `build.rs`, `setup.py`, a `Makefile` or a `.husky` hook, or a `.manki.yml` or `manki.yml` anywhere (`@ci_dependency_paths`) | `full` |
| `data_contract` | 80 | migrations, `*.sql`, `*.proto`, `schema.*`, OpenAPI files (`@data_contract_paths`) | `full` |
| `behavior` | 50 | the planner answered `paired: true` | `full` |
| `internal` | 30 | the planner answered `paired: false` | `solo` |
| `docs` | 20 | the planner answered `trivial: true` and every file is prose (Markdown, reStructuredText, AsciiDoc or a license), a snapshot or generated, deleted, or renamed without edits. Agent instructions such as `AGENTS.md`, `CLAUDE.md` or files under `.claude/`, `.cursor/` or `.github/instructions/` never count as prose here | `trivial` |

The built-in groups are `trivial` (the quick check on `claude-sonnet-5-5` at medium effort), `solo` (one finder on `claude-sonnet-5-5`) and `full` (a finder on `claude-sonnet-5-5` and one on `claude-opus-5-5`). The finders' effort is `auto`: high when the planner answers `subtle: true`, otherwise medium. The sibling comparisons, related repository checks, claim checks, pattern checks, fix checks and sweeps of a round run on the model of the first reader of the group that reads the PR.

The progress comment names the class and group in its review header, such as `Review (security · full)`. It names each reader by its model, the effort it ran at and the start of its `focus` when one is set, such as `Claude Sonnet 5.5 · high` or `Claude Opus 5.5 · high · consensus rules`. The quick check shows as `Quick check · Claude Sonnet 5.5`. A second reader with the same name gets ` #2`. The same names appear in failure lines, logs and the `Manki context` block.

While a review runs, Manki edits the progress comment every 20 seconds, so each time it shows is the time of the last edit. A running finder on the Claude or Codex CLI shows the tool calls it started and its time since its call started, such as `⏳ Claude Opus 5.5 · high: 9 tool steps · 2m 3s so far`. A finder without repository tools shows its time alone, and a finder that is retried shows 🔁. The sibling comparisons, related repository checks, claim checks, pattern checks and fix checks share one line that counts their calls, such as `⏳ Comparisons and claim checks: 2 of 5 done, 1 finding`, and the [second reads](#second-reads) get a line of their own, such as `⏳ Second reads: 0 of 1 done`. Under the judge, the comment shows how long it has been grading, then how many findings it kept, dropped and merged into another, then the refuter's checks done with their outcomes so far, then the origin checks, then the sweeps, which search for more of the findings the judge kept, such as `sweeps: 1 of 3 done`, and the verdict reader while it reads. Once the refuter or the origin checks ended, their line gives the result instead, such as `refuter: 2 checked · 2 confirmed` or `origin checks: 3 checked · 1 older than this PR`. While the judge grades, its line names what changed the count it grades, such as `grading 4 findings (1 tool alert added)`. No stage waits for an edit, and an edit that fails only logs a warning.

The finished comment keeps each finder's line and the lines of the side checks and the second reads, so the review's count is the sum of those lines. Under the judge it keeps the line of every step that ran, with its result. The `graded` line counts the judge's own decisions: how many findings it kept, dropped and merged into another one. A finding the judge kept that a later step took out still counts as kept. The line below it gives the grades the finders filed the dropped findings at, such as `dropped, as the finders filed them: 2 blockers · 3 warnings`. These lines name every step between the review's count and the graded count, each only when its count is not zero:

- `before the judge` names what the round added and dropped before grading. It adds tool alerts and leads carried over from the last round, as possible problems. It drops leads listed as not finished checking before the judge saw them, and repeats of earlier resolved findings.
- The sweeps' line adds the places the sweeps found, and the line below it drops those the round had judged already and those that repeat earlier resolved findings.

So the review's count, plus what was added and less what was dropped, equals what the judge kept, dropped and merged.

The **Posted** section follows, with the count and the grades of the findings the review posted. What the judge kept, plus the findings added after it, equals the posted count plus the lines below it, each shown only when its count is not zero:

- `added after the judge` counts the findings no judge call graded, such as the verdict reader's blockers.
- `not posted` names why each finding stayed out of the review, with a count per reason, such as `1 older than this PR · 2 no proof`. Manki's record of this review keeps these findings.
- `not finished checking` counts the leads the judge kept that its checks left unsettled, as possible problems.
- `left out as repeats of other findings` counts the findings the judge kept that a later step folded into another one, such as a verdict reader's blocker.
- `left out` counts the suggestions on test files left out from round 2 on.

`security`, `supply_chain` and `data_contract` are **floor classes**. Path rules decide them, so nothing in the PR's text can change them. A PR in a floor class always gets at least two finders on two distinct models, none at `low` effort. The floor is checked after routing: if the routed group misses it, the PR moves up to the floor class's own group, then to the `full` group. So a class of your own that outranks `security` cannot pull a PR that also touches auth into a weaker group.

The `review` block changes the groups and the routing:

```yaml
review:
  groups:
    trivial: [claude-sonnet-5-5]                  # the quick check of a trivial change
    solo: [claude-sonnet-5-5]                     # a low-risk change, one finder
    full: [claude-sonnet-5-5, claude-opus-5-5]    # everything else
    deep:                                         # a group of your own
      - { model: claude-opus-5-5, effort: high }
      - { model: gpt-5.5, effort: high }
  routing:
    security: deep
    data_contract: deep
```

That minimal example sends security and data contract PRs to two strong readers on two providers and reviews the rest as the built-ins do. A fuller one:

```yaml
review:
  groups:
    trivial: [claude-sonnet-5-5]
    solo: [claude-sonnet-5-5]
    full: [claude-sonnet-5-5, gpt-6.1-terra]
    deep:
      - { model: claude-opus-5-5, effort: high, focus: "authz, injection, secret handling" }
      - { model: gemini-3-pro, effort: high }
      - { model: claude-sonnet-5-5, effort: medium, focus: "error paths and rollback" }
  classes:
    security:                      # adds paths to the built-in rule, never narrows it
      match: { paths_any: ["src/billing/**"] }
    hot_path:
      rank: 85
      match: { paths_any: ["src/consensus/**", "src/net/**"] }
  routing:
    security: deep
    hot_path: deep
    internal: solo
```

- **`groups`**: each group is a list of its reviewers. An entry is a model id or `provider/model`, or a map with `model` (required), `effort` (`low`, `medium`, `high`, `xhigh`, `max` or `auto`, the default) and an optional `focus` line added to that finder's prompt. A config that sets `groups` must define all three of `trivial`, `solo` and `full`, so the file shows everyone who reviews, and it may add groups under any other name. One that leaves a built-in name out does not load. The readers of the group named `trivial` run the quick check, and the readers of every other group are finders. A quick check entry takes `model` and `effort` only, and its effort is `medium` when unset, so `trivial: [claude-sonnet-5-5]` is the built-in quick check. A `focus` there gets the unknown key warning. `full` must hold at least two finders on two distinct models, whatever routes to it, since a floor and a Deeper review move a PR up to it. A config whose `full` holds fewer does not load. One model written with and without its provider, such as `gpt-5.5` and `openai/gpt-5.5`, counts as one model.
- **`classes`**: a new class needs a `rank` no other class has, and a `match` with `paths_any` (globs, or the `@security_paths`, `@ci_dependency_paths` and `@data_contract_paths` aliases), `triage` (`trivial`, `subtle` or `paired` set to true or false), or both. Every condition must hold. On `security`, `supply_chain` and `data_contract`, `match.paths_any` adds paths to the built-in rule. The other built-in classes cannot be changed.
- **`routing`**: the group per class. A built-in class you leave out keeps its built-in group, and a class of your own with no route goes to `full`. A config that routes a floor class to a group below the floor does not load, and the warning gives the reason. Once such a config is on the base branch, Manki reviews with the default settings and does not approve.
- **`critical_paths`**: globs, or the path aliases above, that mark critical areas, where any wrong result is severe even in a rare internal edge case. They need no class or rank, and can name paths a built-in class already matches. The judge sees which findings sit in a critical area, with the first glob that matches, and grades a wrong result there as severe damage, which blocks when the other blocker tests hold.
- **`outside_input`**: what counts as outside input in your repository, in a sentence or two. The judge treats a failure that this input can trigger as reachable, never as a rare internal case. The finders get this rule and the list of critical paths too, so they grade by the same table as the judge.
- **`examples`**: worked examples from your repository, one string each, under `blocker` for findings that block and `not_blocker` for findings that do not. Set either side or both. The judge reads them next to its built-in examples on the same two sides.

The last three only change how findings are graded: `critical_paths` and `outside_input` by the finders and the judge, `examples` by the judge alone. A repository with consensus code might set them like this:

```yaml
review:
  critical_paths: ["dash/src/consensus/**", "dash/src/blockdata/**"]
  outside_input: >-
    Anything a network peer sends: P2P messages, blocks, transactions, headers
    and the length prefixes inside them.
  examples:
    blocker:
      - "Indexing `buf[len]` with a length read from a peer message panics on a short message."
      - "Changing the field order in a `consensus_encode` implementation changes the bytes on the wire, even when every test passes."
      - "An inverted weight comparison picks the wrong quorum member on every block."
    not_blocker:
      - "A debug log of a decoded message that leaves out the peer address: `note`."
```

Each review's `Manki context` block records a `routing` object: the class, its rank and source, every matched class, the group and why it was picked, any floor and escalation, where the `review` block came from, a `configDigest` of the classes, groups and routes, and each reader's model, provider and effort. Each finder's entry in `reviewers.agentMetrics` counts the kept findings only it raised (`keptOnly`) and those it raised with another finder (`keptShared`).

Manki reads the `review` block, like every other setting, from the PR's base branch only, so a PR cannot weaken its own review. A PR that changes the block is reviewed with the base branch's, and the change applies after merge. When the PR's own block does not load, for example because it misses a floor, Manki logs a warning and still reviews with the base branch's block. If the PR itself changes the file, Manki also holds its approval, so it never approves a broken block. When the base branch's config does not load because its block is invalid or misses a floor, Manki uses the built-ins and the default settings with a warning, never the PR's copy, and does not approve. It keeps the file's `closed_paths`, and the PR that fixes it still gets reviewed. A file whose YAML does not parse and never names `closed_paths` gets the same treatment. When the file cannot be read on a second try, or its YAML does not parse while it names `closed_paths`, Manki cannot tell which paths `closed_paths` closes, so the round fails before it reads any code, see [Security model](security.md).

## Severity tiers

Each finding gets one of three severity levels, or is dropped:

| Severity | Meaning | Effect |
|----------|---------|--------|
| `blocker` | Must fix before merge | Blocks approval (REQUEST_CHANGES), posted as a review thread |
| `warning` | Should fix, or give a reason Manki accepts | Posted as a review thread, or listed in the review body. Requests no changes, but its thread holds the approval until the warning is fixed or its hold is lifted |
| `note` | An optional improvement, never a defect | Posted as a suggestion: a review thread that never blocks when its line is in the PR's diff, or else listed in the review body. PR can still be approved |
| `ignore` | False positive or irrelevant | Not posted. The progress comment keeps the judge's reason |

The judge's grade comes from its cell. It states two grades of its own: the grade its reasoning concludes, which can only hold a blocker cell back, and the grade described below for a finding it doubts. For each finding it states a cell of its severity table: the row is what goes wrong (severe damage, wrong behaviour, degraded but correct behaviour, an improvement, or style), and the column is whether normal use or outside input reaches it, or only a rare internal edge case. Manki works out the grade from the cell, so the judge has no field in which to lower the grade of a finding it does not doubt for a reason of its own. The exceptions are `rareTrigger`, for a trigger that is not realistic, and a verdict below a blocker cell, which hold the blocker until a check confirms it, as described below. A reply that leaves a finding out, or gives it an entry that names no row of the table, is not complete. Manki keeps the entries the reply does have and asks the judge once more for the missing ones only, together with any open thread the reply did not evaluate. If a finding still has no entry after that, the judge fails, so the round ends incomplete instead of posting a grade the judge did not give. A thread that is still not evaluated stays open.

A finding is a blocker only when it passes five tests: the PR causes it (lines it adds, changes or removes), the failure can be named ("when X happens, Y goes wrong"), the damage is serious, the code proves it with cited lines, and the author would fix it (it is not a declared placeholder, a stub that does nothing yet and that no path reaches, or a tracked TODO, which make it a note at most unless it is a security defect). Serious damage is wrong behaviour in normal use or from outside input, lost or corrupted data, a crash, hang or resource exhaustion from outside input, a security defect, memory unsafety or undefined behaviour, or a broken public contract with no migration. The judge states one of these only when it names the damage the code itself causes. A broken public contract is one that existing callers already rely on and that the PR changes, so a doc that promises more than new code does is graded by what the code does, and the promise alone is a note. A wrong figure in a heading, a label, a status line or a log line beside content that is right is a warning, while a figure that is itself the result, such as an invoice total, can block. Wrong behaviour in a rare internal edge case is a warning. The rare column is a claim, and on the wrong behaviour row Manki checks it: it adds the premise that normal use or outside input can produce the state to every such finding, and the refuter searches for a caller, stored data or concurrent use of a public API that produces it. Whatever the refuter answers, the finding stays where the judge put it: the answer is recorded and never raises the grade, so wrong behaviour blocks only when the judge itself states the normal column. Degraded but correct behaviour is a warning, or a note when rare, and there the column is taken as stated, since it blocks nothing either way. A warning needs a consequence someone would notice in realistic use, such as a wrong result or a slowdown users feel. A point nobody would notice is a note, such as an extra pass over a small input. The judge grades a finding a note on this ground only when its description names no consequence anyone would notice and the code it sees confirms the small scale, never on the finding's word alone. It keeps the warning when the code does not show the scale or contradicts the finding. A warning on the degraded row also needs a realistic trigger: a sequence of events normal use produces, as in "when a user opens the page". A trigger that needs a timing window much shorter than the operations around it, such as a few instructions between two lines while each job takes seconds, or an event nothing in normal use produces, is not realistic. Neither is one that needs odds no real use meets, such as two random names colliding, two failures in a row whose only effect is that a hold, a lock or a pending approval stays in place longer, or a public function called in a way no caller in the repository calls it, such as a second `start()` on an object every caller starts once, when no outside input reaches that call. The judge names the trigger of every finding it keeps in `trigger`, and leaves it empty when it finds no realistic one or is unsure whether anyone would notice. Such a warning is kept in the round record only, under `findings.unposted` with `unpostedReason: no_trigger`, and is never posted, not even as a suggestion. The judge keeps its row rather than lowering it to a note. A finding on the severe or wrong behaviour row is posted however rare its trigger, until a check disproves that trigger, since lost data, a security hole, a broken contract, a crash or a wrong result that persists matters even when it is rare. So do a security finding and a tool alert. Without a realistic trigger such a finding is a warning: the judge marks it `rareTrigger`, and Manki adds the premise that its trigger happens in realistic use as a doubt about the cell, since a check that confirms the defect does not show that its trigger happens. The blocker cell is then held at a warning like any doubted one, and the refuter gives the blocker back only when it confirms that premise with cited lines, such as a caller that runs the sequence or outside input that reaches it, together with every other doubt and, as for any doubted blocker cell that not every finder filed as a blocker, the consequence the judge names. A trigger it leaves open keeps the warning posted. One it disproves, while no check confirms it, keeps the warning out of the review with `no_trigger`, also when the check confirmed the defect itself. A later judge that names that premise again holds the blocker cell the same way, also without `rareTrigger`. The premise stays in the round record with the finding. A security finding and a tool alert keep their blocker. A warning that would be a blocker if true, such as one the judge graded a blocker or one whose cell would block if the judge's doubts hold, stays posted without a trigger until a check disproves the trigger, as below. The grade a finder filed does not count. The round record keeps the trigger of each finding under `trigger`. So a finder, a sibling comparison, a claim check, a fix check or a sweep that reports a cost, such as time, memory or size, states the realistic scale the code shows and what that costs in practice, files it as a note when the code shows nobody would notice, and says so when the code does not show the scale. It also names the realistic trigger of the cost, or says that it found none. Missing tests, style, naming, docs, commit messages, performance without a crash and checks on trusted internal values never block. A test that cannot fail when the code it names breaks is a warning, and a doc that says the code does something it does not is a note. For a library, outside input is anything a caller of its public API can pass, such as readers and byte streams, and resource exhaustion or denial of service from outside input is a security defect. Behaviour that is intended but surprising becomes a note that asks about it, unless it is a removed guard, resource exhaustion or a security defect. A gap the author admits is no such choice: one the PR description, a comment or a TODO calls deferred, out of scope, left open or not handled yet keeps the grade its damage earns, and only a declared placeholder or a TODO with a tracking issue lowers it. A defect in lines the PR adds is the PR's own, even when the bad state those lines mishandle existed before, so "not worse than before" is no reason for a lower cell. The defect a PR fixes in one path and leaves in a sibling path is the PR's own too: a PR that adds an auth check to `POST /items` and leaves `PUT /items/:id` open has an incomplete fix, which is never pre-existing. This covers a sibling path in a file the PR changes. The same defect in a file the PR does not change is code the PR did not touch, so the judge drops it. The judge and the verdict reader mark a finding that claims the code fails to compile, type-check or pass its tests. Such a claim blocks only when a CI annotation on the commit reports the error, unless it is a security defect. Otherwise it is posted as a warning that asks to check that it builds, since CI fails the build or the test itself. Code the judge cannot see never drops a blocker or a warning: the judge sees the diff of each file a finding sits on or cites in a proving line or an evidence line, the uses outside the diff and the code each finding cites outside it, a finding that cites one of those is graded on its merits, and the judge grades a finding that rests on code beyond that as a doubt, so a blocker it cannot follow becomes a warning. A note that rests on code the judge cannot see is the exception: the judge drops it, since a missed note costs less than a false one. A doubt that the failure is reached, such as no caller in the code shown, is graded the same way, and a path through a library's public API counts as reached without a caller in the repository. So does a function, method or handler the PR adds: it is there to be called, so a missing caller is no doubt. A value the code shown proves the code's own logic keeps valid is evidence, not a doubt, so the rules for rare internal edge cases and trusted internal values still apply to it. For every finding the judge states the row its consequence would earn if every premise it doubts holds, such as unseen code, reachability or whether the PR causes it, and lists each doubted premise as a fact the code can confirm or disprove. A premise its reasoning settles from cited lines is no doubt and is not listed. A premise that lowers or caps the grade, such as callers probably validating a value, counts as a doubt too unless the code proves it. Each premise decides either whether the defect exists at all or only which cell it earns. Manki grades a blocker cell with an open doubt as a warning until the refuter confirms every doubt, except on a tool alert or a security finding. The judge names the class of each security finding, and two classes are held down like any other finding: resource exhaustion, such as a slow loop or a large allocation, and a check gap, an unusual form of input that a parser, sanitizer, filter or check misses, when what gets past does no damage of another class. Input that gets past a filter and then reaches a shell, a path, a query or a prompt is an injection. Their blocker rests on the cost or the edge case being reached, so only a confirmation of every doubt gives it, and the judge's own `warning` answer never keeps them lower. Like any security finding, such a warning is posted without further proof, its thread is guarded, and no disproof lowers or drops it. A finding in any other class, such as an injection, keeps its blocker with a doubt open. Next to the doubts of such a finding the judge also states the grade the finding earns once every doubt holds, `blocker` or `warning`. This is where the judge says how serious the damage is. With `warning`, the judge names the blocker test that still fails, and the finding stays a warning when the refuter confirms every doubt. Example: a status line counts one retry too many while every result is right. A doubt the judge listed, a rare state and "not worse than before" are no reason for `warning`. With `blocker`, or no answer, the judge also lists the consequence that puts the finding on its row as a premise of its own: what goes wrong once the defect happens and where it lands, worded so the blocker needs it to be true. It never holds a finding down on its own: listed with no other doubt, it is dropped and the cell blocks at once, as with no doubt. A confirmation of every doubt gives the cell's grade to a finding every finder that reported it filed as a blocker, and Manki drops the consequence premise from such a finding, so it is graded as if the judge had not named one. A doubt means the judge named the blocker cell for code it had not seen, and a confirmed defect alone does not show that the damage is serious. So any other finding gets the cell's blocker only when every check that answered confirms the defect itself and every premise, the consequence included. Such a finding is checked like a blocker, outside the eight checks of warnings. A check that leaves the consequence or the defect open, disproves the consequence, contradicts itself or runs out of steps leaves it a warning, posted with the status that check gives it, and a later round checks it again while the doubt stays open. The next judge sees each of its premises as confirmed only when every check confirmed the defect and every premise. When the judge names no consequence, the finding is a warning from the refuter's step on, whatever its check answers. It then takes one of the eight checks of warnings described below. It stays posted while no check has run on it, such as when the eight do not reach it. Once a check runs on it, it is posted only when a check confirms it, since it then needs proof like any other warning. A memory suppression, a thread the author resolved or an earlier agreement hides it like any warning. Example: a finder files a warning that a Python CSV export writes dates in the server's time zone. The judge states wrong behaviour, doubts that any export runs outside UTC, and names as the consequence that the exported file shows the wrong day for records near midnight. The refuter finds a scheduled export for an office in another zone and the line that writes the date, and the finding is a blocker. Had the refuter left the consequence open, the finding would be posted as a warning confirmed with tools, which holds the approval like any other warning. When the finders split, one filing a blocker and another a warning for the same defect, the finding needs the consequence like one no finder filed as a blocker. So when the judge doubts such a finding in a blocker cell, it becomes a blocker only once every check confirms the defect and the consequence the judge named, and without a named consequence it stays a warning. With no doubt the cell blocks at once. The judge also states in `grade` the grade its reasoning concludes. When that is lower than a blocker cell gives, the cell alone does not make the finding a blocker: Manki holds it at a warning as if the judge had doubted its damage. Its consequence premise is the one the judge named, or else that the failure does the damage the row names and that normal operation, such as a retry, a rescan, a restart or a later sync, does not undo it. Only a check that confirms the defect and that damage gives the blocker, so a round without tools, or a check that leaves the damage open or disproves it, keeps the warning. This only adds a hold: a finding another doubt already holds keeps its own path, so one with no named consequence stays a warning whatever the check says. A cell lower than the reasoning changes nothing, and a finding every finder filed as a blocker, a security finding and a tool alert keep the grade of their cell. Two kinds of finding rise whatever their finders filed: a security finding, and a finding that restates a blocker of an earlier round or an open thread that blocks. It restates one when the judge links it to that blocker or its thread, or when it has the thread's title at most 5 lines from it. Another finding in the same file is a defect of its own. Manki reads the judge's answer nowhere else: a blocker cell without a doubt blocks at once unless the judge marks its trigger not realistic, states a lower `grade`, only one of two or more finders reported it, or no finder filed it as a blocker, and a tool alert and a security finding outside those two classes keep the grade of their cell. A blocker the judge raised above every finder's grade rests on the judge's reading alone, so it is posted as a blocker only when the refuter's checks agree that the defect is confirmed, read as stored: a confirmation that rests on outside behavior no cited line states does not count. With no check, as in a round without tools, or with a check that leaves the defect open, the finding goes back to the highest grade a finder gave it. Example: a finder files a warning that a retry skips rows already sent, and the judge grades it a blocker. The refuter leaves open whether the rows are lost, so the finding is posted as a warning. As with a disproof, a security finding, a tool alert, an open lead and a finding that restates an earlier blocker keep the judge's blocker, and a finding that breaks a confirmed [required rule](#rules-from-instruction-files) goes no lower than the grade `review.rules` gives. A doubt about the cell alone counts only on the wrong behaviour row, where the column decides whether the finding blocks, and on a security finding of those two classes, where whether outside input reaches it decides whether it is a security defect at all. On every other row Manki drops it, so only a doubt whether the defect exists holds a severe finding down. A doubt alone never drops a finding that would earn a warning or a blocker. A finding is a warning only when the PR causes it, the failure can be named and cited lines show it. A warning the judge cannot prove from the code shown or its own tools names its doubt, and Manki posts it only once it is proven, as described below. The finders, the judge, the refuter and the verdict reader treat everything they are told about the code as a claim to check: the PR description, code comments, linked issues, author replies, another model's finding or reasoning and an earlier round's verdict. A claim the code confirms is evidence. One they cannot check is noted but never raises or lowers a grade on its own. The exceptions are an author's statement that behaviour the code shows working is intended, a declared placeholder or a TODO with a tracking issue, and a PR description that says a change breaks no consumer. A statement of the author that a finding does no harm, such as that a value is checked elsewhere, a path cannot be reached or other code guarantees it, is no exception: the judge lowers or drops the finding only with the line that shows it, and otherwise lists the premise the statement denies as a doubt. Review memory is the maintainers' recorded decision, not a claim to check, and so are the rules in the repository's instruction files, which the judge sees as the finders do. A finding that says the change breaks one of those rules is checked against the rule's text, and a convention such as naming or import placement is graded a note. The judge grades a finding on its central claim: a wrong side detail, such as an off line number or a misnamed helper, is corrected in its reasoning and never drops the finding on its own. A later round keeps a finding's cell unless the code or the evidence changed, but only a cell with no doubt behind it anchors. For a finding from a record that stored only a grade, the judge states a cell that gives that grade. It does the same for a finding an earlier round kept at a warning in a blocker cell, by the judge's own answer or because not every finder had filed a blocker: the later judge is shown its grade without that cell, so a settled doubt never turns it into the blocker the earlier round did not give. A grade an earlier round kept below its conditional grade is regraded from the code, and when the judge keeps it without naming a doubt while no check settled the earlier one, Manki sends the earlier doubts to the refuter. A check that confirmed the defect while it disproved a premise the defect rests on settled none of them.

With `judge.tool_steps` above 0, a judge with repository tools also reads the code a finding rests on while it grades, up to that many calls, so code it read counts as code shown and only a doubt its calls left open goes on to the refuter. It is off by default, since it makes the judge call longer. When the judge has repository tools, it also tries to refute each blocker, each open lead graded `blocker` or `warning`, each blocker posted as a warning for want of proving lines or of a CI result, each finding that would earn a higher grade if a premise the judge doubts holds, such as code it could not see or a path it doubts is reached, each finding the judge placed in the rare column of the wrong behaviour row, each blocker a finder filed that the judge drops for a reason about code outside the diff, and up to eight warnings a round that nothing proves yet: a warning the judge keeps while doubting the defect exists, and a warning that cites no proving lines. A finding kept below `warning` with such a doubt is not checked. These checks run before Manki hides a finding that repeats one the author agreed with or resolved: a finding the judge links to it, or one with its title at most 5 lines from it, so that step sees each finding's settled grade and never hides one a check raised to a blocker. A finding that step hides is checked only when a confirmation can raise it, so it takes none of the eight checks. The refuter names the general rule the finding relies on, such as a language or library behaviour, and searches the unchanged code for code that relies on the same rule. One such counterexample that already builds or runs disproves the finding. For a reachability doubt the refuter searches for a path from an entry point. A public function, method or field is one when the repository is a library or its `review.outside_input`, which the refuter is given, names that API. In an application an exported function needs a caller. Either way the triggering value has to be one that callers, tests, documentation or outside input actually supply, not merely one the type accepts. For a finding with such a doubt the refuter also sees the PR's change to the files the finding cites. It confirms a doubt that the PR causes the defect only when a changed line does, and never disproves a finding only because the change shown does not cause it. The refuter answers each premise the judge listed on its own, and besides them whether the defect itself exists. It confirms the defect only when the failure happens in normal use and gives a wrong result someone can observe, and it cites lines for both: the trigger, such as a caller, a test, stored data, documented use or a path from outside input, and the result, such as a wrong value returned, stored or sent, a crash, lost data, a check that passes when it should fail or, for correct but slow or costly code, a cost that grows with what normal use supplies, such as a query repeated for each item. A confirmation without a line for each counts as unsettled. The refuter also answers unsettled when its own reasoning finds the effect negligible, such as a state a later pass heals, a short delay, a drift of a few percent or a small cost that stays the same whatever the input. A rare trigger is no such effect: one that normal use can still produce counts. Neither is needed for the scope reader's doubt, which is no failure, or for a finding that `review.rules` set to `warn` or `block` grades by a rule the judge confirmed it breaks, unless its grade, or the grade a confirmation would give it, is above the rule's. An answer about a premise never needs them, since it only says whether a stated fact holds. A confirmation without its lines still contradicts a disproved premise about the defect, so that check settles nothing, and it never stops a disproved premise of a dropped blocker from bringing the finding back. The judge lists as a doubt only a fact that reading code can settle, about the code, the PR's base, a caller or a config. It never lists how a person, a model, a peer or the network will behave at run time, and whether a realistic trigger happens is for the trigger it names. On a finding that no confirmation raises, such as a warning the judge doubts, the message tells the refuter so, and the refuter answers a premise that still states such behaviour on its code part, such as the input the code passes or the check the PR removes. So a defect the code confirms counts as confirmed, and the confirmation changes no grade. On any other finding a confirmation can raise the grade, so such a premise stays unsettled unless the code alone settles it. Reading code also cannot show how a program outside the code the refuter reads behaves when it runs that code or reads its files: an external tool or command line program, a package manager, a runtime or platform, or a remote service. The rules of the language itself are not such behaviour. A confirmation of the defect or of a premise that rests on such behaviour names it, with the lines that state it, such as the program's documentation or source in the checkout, a related repository or a dependency source, or the instruction files. Without such a line the confirmation counts as unsettled: it raises no grade, settles no doubt and never shows the finding as confirmed with tools, and premises the code confirmed do not raise a finding whose defect rests on such behaviour. It still stands against a disproof, so it never lets a second refuter's disproof lower, drop or hide the finding, and a warning it backs is not hidden for want of proof. The next round's judge sees such a premise as unsettled, also when the other refuter disproved it. The round record keeps the behaviour as `outside` on the check or on the premise, with `stated` saying whether a cited line states it, and the stating lines join the check's proof. The premises decide the grade: a finding with such a doubt gets the higher grade its cell gives only when every premise is confirmed. A blocker cell gives its blocker then to a finding every finder that reported it filed as a blocker, a security finding or one that restates an earlier blocker. When two or more finders ran and only one of them reported the finding, it does not count as filed by every finder, since the other finder read the same diff and did not report it. Another check that reported the same finding, such as a sibling comparison, a pattern check, a claim check, a fix check or a related repo check, counts as a second reporter. A second read and a sweep start from findings already reported, so a second read counts as the finder whose call it repeated, and a sweep as the reporters of the finding it started from. A finding only a second read or a sweep reported then counts as reported by one finder alone. A read was shown every finder's findings, so beside a finder's report of the same finding it adds no second reporter, whichever finder's call it repeated. A read or a sweep whose finder is not known, such as in a replay of stored findings or on a lead carried over from an earlier round, counts as no reporter. Being reported by one finder alone counts as a doubt of its own: when the judge has repository tools, a blocker cell no other doubt holds is held at a warning too, with the consequence premise the judge named or, without one, the damage premise described above for a lower `grade`. Without tools no check could settle it, so such a blocker cell blocks as before. A check that disproves such a blocker never drops it: it is posted as a guarded warning, like any blocker a check disproves. The round record then shows the judge's step to `warning` with the reason "only one of the finders reported it". Any other finding gets the blocker only when the check also confirms the defect and the consequence the judge named, as described above. A round with one finder is unchanged. No finding gets it when the judge stated `warning` as the grade it earns then. A finding in the rare column of the wrong behaviour row is the exception. The refuter is asked whether normal use or outside input can produce the state the failure needs, and whatever it answers, the finding keeps its grade and its column: only the judge places a finding in the normal column. The answer about the defect decides whether the finding counts as confirmed. A disproved premise that the defect rests on drops a finding below blocker, and a disproved premise that only the grade rests on keeps the judge's grade. A check that disproves a premise the defect rests on while it confirms the defect itself contradicts itself, so it settles nothing: the finding keeps the grade it had before the check. An answer that the defect does not exist counts as a disproof in the same way, whatever the premises of that check add up to. So no finding gets a higher grade while a refuter says its defect does not exist, also when every premise is confirmed, and a finding below blocker is dropped. A drop can rest on code outside the diff too, such as other code that checks every input before it reaches the changed lines. The judge then states the premise its drop rests on, in general form, and the cell the finding earns if that premise is false. On a finding a finder filed as a blocker, also as a copy the judge or the merge of same-titled copies folded into another, the refuter checks that premise in the same call as any doubt, outside the eight checks of warnings. The check stays with whichever copy is kept. The finding comes back only when a check disproves the premise with the lines of a path it does not hold on, and no check confirms the premise or says the defect does not exist. It is then graded by that cell like any finding the judge doubted, so a blocker the finders split on also needs the consequence the judge names before it blocks. A premise the checks confirm or cannot settle leaves the finding dropped. A drop whose reason the diff itself shows is never checked, and neither is a finding no finder filed as a blocker or one whose cell would give a note or sit in the rare column of the wrong behaviour row. The round record keeps the premise on the dropped finding as a doubt with `decides: drop`, beside the check and its answer. A round without repository tools checks no drop, so its record keeps no such premise, cell or grade. No later round reuses such a check, since it answered whether the reason to drop holds and not whether the finding is wrong, so a later round that keeps the finding checks it afresh. A confirmation makes an unproven blocker a blocker again, but a claimed build failure stays a warning, since reading code is not compiling it. The verdict reader's blockers get the same build claim check, and when every one of them was such a claim, the change stays ready. For an open lead the refuter is told to start with what the finder left to check, so its tool steps go to the open point first, and to treat what the finder says it checked as a claim. A lead it confirms is posted at its grade, one it disproves is dropped, and one below `blocker` it cannot settle is listed in the review body under "Not finished checking". With `review.rules` set to `warn` or `block`, a disproved lead that breaks a [rule the judge confirmed](#rules-from-instruction-files) is posted as a finding, since the check finished it and no disproof drops a confirmed rule break. A lead still unsettled carries over to the next round's judge as an earlier lead, matched by file and title, instead of coming up as new, and the review body lists it once with the round it first came up in. When no check of the new round settled it, its entry gives the reason of the check from the round it comes from, as in "No check in this round settled it. In round 2: ...", cut to two sentences of its own. A lead a finder raises again keeps that reason too, and so does a lead that again no check reaches, through every round it carries over. That reason is shown only, and no check, judge or grade reads it. It carries over while its file is in the PR and known to be unchanged since the last round, for at most three rounds. A security lead the tools do not confirm stays posted. Each round records how each lead ended under `leads`, with the refuters' answers. A disproof never drops a blocker. When every refuter that ran disproves it, a blocker from the judge or from the verdict reader is posted as a warning with the refuters' reasons, which says "Manki found a reason this may not happen, so this does not block. Please check it yourself." Text in the PR could steer the refuter, so its thread is guarded as a security warning's is. It holds the approval until a review confirms a fix, or until someone other than the PR author with write access resolves it, answers it in agreement or dismisses it. The PR author's own answer never clears it, and the author may clear it only with the role `author_clear_role` sets. A blocker stays a blocker when a refuter that ran is unsure or confirms it, and so does an open lead, a security finding and a finding that restates a blocker of an earlier round or an open thread that blocks. A tool alert, such as one from actionlint, zizmor or shellcheck, stays a blocker too unless a second refuter runs and both refuters, on two different models, disprove it with cited lines, for example a repository config that turns the rule off. It is then posted as a guarded warning like any disproved blocker, never at a lower grade and never dropped. A tool alert keeps blocking either way when its source reports only security problems (dependency review, the dependency scanner, the secret scanner, hidden characters and lockfile changes), or when its tool or rule id names one, such as an injection rule. A disproof still drops a finding graded below blocker, such as an open lead or a finding capped at warning for want of proof, when it cites a line of the finding's own file or of the diff. With `review.rules` set to `warn` or `block`, the one exception is a finding that breaks a [rule the judge confirmed](#rules-from-instruction-files), which no disproof drops. See [security](security.md) for the tools.

The refuter runs on the judge's model (`models.judge`). With `models.second_refuter` set, a second refuter on that model checks the same findings at the same time, with the same prompt and tool budget. Models of one family can share a blind spot, so pick one from another provider. Unset, there is no second refuter and no extra call. An unsettled answer, or a call that fails, counts as no vote, and the other answer decides as it would alone. The exception is a finding that needs its consequence confirmed to become a blocker: an answer that leaves the defect or any premise open keeps it a warning. When one refuter disproves a finding and the other backs it, the finding keeps the judge's grade. Where it is posted, it shows both reasons and is marked not confirmed. A refuter backs a finding when it does not disprove it and confirms the defect or at least one of the premises the judge doubted. A refuter that disproves a premise only the grade rests on stops a higher grade in the same way. A disproof goes further in one case: no finder graded the finding a blocker and the judge alone raised it to one. It then goes back to the highest grade a finder gave it, which can be a note, with no guard, the same place a check that settles nothing leaves such a raise. It is posted with each refuter's reason, and every rule for that grade applies to it. Every other blocker that both refuters disprove becomes a warning, as with one refuter. With `review.rules` set to `warn` or `block`, a finding that breaks a confirmed rule of the instruction files goes no lower than the grade the setting gives, so with `block` it stays a blocker. A second refuter that fails leaves the decision to the first. The round record keeps the model with each answer and the judge's cell as `judgeCell`. The next round's judge sees the finding at its finders' grade with no cell, so it has no blocker cell to restate. For a finding below blocker it works as one refuter does: one confirmation with no disproof raises it, and one disproof with no confirmation drops it. A security finding still changes only when confirmed. The round record stores the second answer as `pairRefutation` beside `refutation`, and the model as `models.refuterPair` on rounds where it checked a finding or an earlier answer of it was reused. Its calls are recorded under the `refute_pair` agent. The second refuter needs repository tools, so the Claude or Codex CLI, and runs only when the judge's refuter does. Otherwise the run logs a warning. A later round reuses a refuter's answer for the same finding while the files it rests on are unchanged, and makes no new call for it. An unsettled answer whose call ended on its step budget is not reused: the refuter was told to finish or took its last step, so it may only have run out of steps, and the finding is checked again.

Only `blocker` findings block, in every round. A `warning` requests no changes, but a warning on the PR's own code holds the approval until it is fixed or its hold is lifted, as described below. The one finding that blocks without serious damage is a confirmed [rule finding](#rules-from-instruction-files) in a repository that sets `review.rules: block`. A blocker from the verdict reader blocks too, unless every refuter that checked it disproves it. A security finding blocks only as a blocker. Manki grades it in the normal column of the row the judge states, since an attacker chooses the input, and no doubt holds it down. So a security defect with severe damage or wrong behaviour is a blocker, while one that only degrades behaviour, or one that cites no proving lines, is a `warning`, which requests no changes.

A warning is posted only when it is proven. It is proven when it cites the lines that show the failure and the judge does not doubt that the defect exists, or when a refuter confirms it. With repository tools, the refuter checks each warning the judge doubts and each one that cites no proving lines, up to eight a round. When two finders ran and fewer than two of them reported a warning on the degraded row, Manki adds the premise that its trigger happens in realistic use, so the refuter checks the trigger as well as the defect. The refuter confirms that premise only when a path normal use takes produces the trigger, and disproves it when the trigger needs a timing window much shorter than the operations around it or one of the other events above. For a call no caller makes, it searches for the callers with its tools and cites them. Concurrent use of a public API confirms the trigger only when a caller or the API's documentation shows that use. Such a warning is posted only once a check confirms both, and it shows as proven from the cited lines no more. A check that disproves the trigger keeps it out of the review. When that check confirms the defect itself, the warning is recorded with `no_trigger`. When it does not, the disproved premise drops the warning, as it drops any warning whose defect premise a check disproves. One that leaves the trigger open, or that the eight checks do not reach, keeps it there as an unproven warning. Manki also adds the premise to a warning on the degraded row that the judge graded a blocker at some point and named no trigger for, about the sequence of events its description names, however many finders ran. A check that disproves that trigger keeps the warning out of the review the same way. Any other answer leaves it posted, since it would be a blocker if true. That covers a warning one finder reported alone and one that only a sweep, a sibling comparison, a claim check, a fix check or a second read found. A warning both finders reported, and any warning in a round with one finder, keeps the rules below. The findings of a `review.sweep` share those eight. A warning is confirmed when the refuter answers that the defect exists, not when it confirms a premise. That answer confirms nothing while a premise the judge says decides whether the defect exists comes back unsettled or disproved. A warning the check confirms is posted, and one it disproves is dropped. A warning the check cannot settle, or that the eight checks did not reach, is not posted. Without repository tools no check runs, so the cited lines decide: a warning that cites them is posted, and one that cites none is not. The cited lines also decide whenever no check could run on a warning for another reason, such as a refuter call that failed or a file the refuter cannot read, like one the PR deletes. Such a warning takes none of the eight checks. Neither does a warning a later step keeps out of the review whatever a check says: one the author already agreed to or resolved in its thread, and one a memory suppression matches. A warning in the rare column of the wrong behaviour row gets no check in those cases either, although its check is outside the eight, since no answer raises it. The same holds for a finding the judge keeps at a warning in a blocker cell: no answer raises it, so those steps hide it like any other warning. A tool alert takes none either. A warning that restates a finding an earlier round still shows is checked after the other warnings whose posting a check decides, and not left out, since that match is settled only after the checks. A security finding is posted whatever a check says, so a check of one the judge doubts only settles the status it shows. With `review.rules` set to `warn` or `block`, a finding that breaks a [rule the judge confirmed](#rules-from-instruction-files) is posted without proof too, and no check of one the judge doubts drops it. Both come last among the eight, after every check that decides whether the review shows a warning. A round can judge findings in more than one call, since the judge grades the findings of a `review.sweep` in a call of their own. Each call checks only its own unproven warnings on changed code that restate no earlier finding. Every other check of the eight runs once, after the round's last judge call, so those never take a check from a warning a later call brings. The round record keeps each warning left out under `findings.unposted`, with `unpostedReason` set to `unsettled_check`, `not_checked` or `no_proof`, `no_trigger` for a warning without a realistic trigger. The review body names each warning it leaves out because nothing proves it, with the reason, in its "Checked and left out" section. A warning left out with `no_trigger` is not named there. The progress comment keeps the judge's reasoning for each one under "Judge decisions". An incomplete round has no such log, so its review has no such section, and the round record still keeps the warnings. This rule never leaves out a finding that would be a blocker if true: one whose cell would block if the judge's doubts hold, one the judge placed in the rare column of the wrong behaviour row, or one the judge graded a blocker, such as a blocker posted as a warning for want of proving lines or of a CI result. The grade a finder filed does not count, so a finder's blocker that the judge graded a warning needs proof like any other warning. A blocker cell where the judge stated `warning` for the case that its doubts hold keeps its warning only until a check runs on it: once a check runs without confirming it, the rule applies to it like any other warning. It is posted as a warning that says Manki could not confirm it. The one exception, on any row, is a missing realistic trigger: once a check disproves the trigger and no check confirms it, such a warning is recorded with `no_trigger`. The rule also never leaves out a security finding, a tool alert, or a finding that restates one an earlier round still shows, so no open thread and no "Still open" entry changes because of it. A link the judge names to an earlier finding the review no longer shows keeps nothing. A later round that finds the same warning again checks it again.

Each blocker and warning a round posts says how it was checked: proven from the cited lines, confirmed with tools, or not confirmed. A thread names it in the title of its collapsed section, and a finding listed in the review body in a line "How this was checked" inside its fold. Code works this out from the finding, and the judge returns no confidence. A finding is not confirmed unless one of two things holds. It is confirmed with tools when a refuter answered that the defect itself exists, and no premise the judge says decides whether the defect exists came back unsettled or disproved in that check. On a finding that no confirmation raises, a premise about run time behaviour comes back on its code part, as described above, so that behaviour alone does not leave a defect the code confirms not confirmed. On any other finding the refuter answers such a premise `outside_code`: it depends on something no code in reach can show, such as how a model, a person, a peer or the network behaves, or code outside the checkout, the PR's base, a related repository and a dependency source. Such an answer does not stop the status confirmed with tools when the check confirmed the defect. For everything else it counts as unsettled: it never raises a grade, settles a doubt or lifts a hold, so the finding is graded exactly as with an unsettled answer. A check an earlier round stored keeps what each of its premises decided, so a later judge who names other doubts does not turn its open premise into a confirmation. The refuter gives that answer for every finding it checks, apart from its answers to the premises the judge doubts, so a confirmed premise, such as that normal use reaches the code, never gives this status. It is proven from the cited lines when no refuter checked it, it cites proving lines, the finder finished checking it, so it is no open lead and no finding the finder ran out of tool steps on, and the judge names no doubt whether the defect exists. Neither holds for a finding a refuter disproved, whether in a premise the defect rests on or in its answer about the defect. A check that confirms the defect itself while it disproves such a premise contradicts itself. It disproves nothing, and it confirms nothing either. So a finding a refuter checked is confirmed with tools or not confirmed, whatever lines the check added, and a finding that fits neither description is not confirmed without a rule of its own. Such a finding says under its title what stayed open. After a check confirmed the defect, the line names the first premise about code that check left open: "Manki confirmed the code path but could not check:" and the premise. When the check left no such premise open but its confirmation rests on outside behaviour no cited line states, the line names that behaviour in its place. A finding that cites no proving line and that no refuter checked says "Manki could not confirm this, since no line in the code was cited for it." Any other says "Manki could not confirm this, so please check it." That includes a warning the judge doubts and the cited lines keep because no check could run on it: on a round without tools, after a refuter call that failed, or in a file the refuter cannot read. It also includes two findings a check cannot confirm, whatever the refuter answered: a claimed build, type or test failure that no CI result reports, since reading code is not compiling it, and a finding still posted as a warning for want of proof. A tool alert has no status, since the tool is its source. The round record keeps the status as `checkStatus` on each finding entry, and an `outside_code` answer as `outsideCode` on its premise. Under "Checked in the code" the same section lists what was read: the reviewer's checks with a preview of the code, the proving lines, and the lines a refuter's confirmation added. A confirmation that rests on a [related repository](#related-repositories) lists each of its lines there as `owner/name:path:line`, linked to that line at the commit the round fetched. Only the location is shown, never the line's text. A check that did not confirm names the lines it read in its own sentence, related lines included.

Every round reviews the whole diff as thoroughly as the first. From the second round, the finders and the verdict reader also get the files the author changed since the last reviewed round, listed ahead of everything else, and check that new code first. A rebase onto the base branch changes no file, and when the change since the last round is unknown, the list is left out. The finders, but not the verdict reader, also get the diff since the last reviewed commit, the one the judge reads, after that list. A fix can add a defect of its own, so they check what the changed lines break, such as a guard that moved or a new path for input. That diff is cut at the judge's limit of 20,000 characters, with the files of open blocker and warning threads, the files their findings cited and the files of earlier warnings first, and the message says when it was cut. On a large diff read in slices, each slice gets only the part of that diff for its own files. The finders still get the full PR diff, the file contents or code windows, and their tools. The finders also get each earlier blocker a judge confirmed fixed, and each open blocker whose file changed since the last round. A fix often closes only the route the blocker named, so they check the other routes to the same outcome.

A finding the PR did not cause is tagged `pre-existing`. Manki finds such a finding in two ways. The first is by location. A finding about code the PR did not touch counts only when all of these hold: the reviewer marks it pre-existing with a reason the defect exists without this PR's change, its line is not one the PR adds, the judge keeps that mark, it sits outside every hunk of the PR's diff, none of the lines it cites as proof is in the diff, and the PR neither deletes its file nor leaves the file out through `exclude_paths`. So an unchanged caller that breaks because the PR changed a function keeps blocking. The second is the origin check. With repository tools, every blocker and warning the judge kept gets one small call, beside the refuter at the round's end, that asks whether the PR caused the failure, whether or not anyone called it older. A note takes none, and neither does a tool alert or a finding the location already settles. A round checks at most 8, blockers first. A blocker from the verdict reader takes a check only while the round has one left. The call sees the finding, the PR's change to the files it cites up to 8,000 characters, and the list of the other files the PR changes, every one that fits in 50,000 characters, which is about 1,000 typical paths. When a larger PR cuts that list, the check still runs, but its answer stays `unsure`, since a change the list leaves out looks the same at the base. A reviewer's claim that the finding is older is passed on as a claim to check. It reads files at the PR's base, the merge base with the branch the PR targets, with `read_file` and `ref` set to `base`, and answers in a fixed form: `introduced` when the base does not fail that way or the PR makes the path newly reachable, `worsened` when the PR makes an older failure worse, `pre_existing` when the base fails the same way for the same input through the same path, or `unsure`. A failure that comes from what the PR added to a line, such as a new argument, is the PR's own, and so is a crash, wrong result or security hole that a new caller of old code reaches. A cost finding, about time, memory, calls or work, is different. When the PR's new path runs existing work no more often and on no larger input than a path at the base already runs it for the same input, the cost is `pre_existing`, and the answer cites that path at the base. A cost that outside input can now trigger through the new caller, and could not trigger at the base, is a security hole such as resource exhaustion, and stays `introduced`. A cost the PR makes grow faster, such as a new loop around the work, a larger or unbounded input or a repeat that grows with the input, is `introduced`. Running the work again for an input the base already runs it for, such as a second delivery of the same data, is `pre_existing` even though the total work grows. A cost is `worsened` only when the PR makes each run of the work more expensive. A `pre_existing` answer cites the failing lines on both sides, and Manki reads each one: the head lines must include a line of the finding's file, and every base line must be there at the base commit. On a flagged line the PR left unchanged, the base lines must also include that line at its place in the base, with the same text. On a line the PR added or changed, they must include a line of the finding's own file at the base, so a finding in a file the PR added is never pre-existing. Anything less makes the answer `unsure`. What the answers can do depends on the finding. A warning or a note on a line the PR left unchanged that would never block, is no security finding and is not the warning of a disproved blocker leaves the review on one `pre_existing` answer, unless another answer says `introduced` or `worsened`. Everything else needs two `pre_existing` answers from two different known models, the first on the judge's model and the second on `models.second_refuter`: a finding on a line the PR added or changed, which has no place at the base to compare, a blocker, a warning the judge graded a blocker at any step, a warning a confirmation would make a blocker, a warning whose cell gives a blocker, the warning of a disproved blocker, and a security finding. Manki asks the second model only for such a finding. Without a second model, a passing answer leaves a blocker a blocker, security or not. Its thread and its entry in the review body only say "**Possibly older than this PR.** One check found the same problem on `main` at" the first line it cited, "If that is right, a maintainer can dismiss the finding.", with the PR's own base branch in place of `main`. The fold lists the other lines it cited. An `unsure` answer, a failed call, a round without repository tools or without the base, and a finding over the round's 8 origin checks all leave the finding the PR's own. The round record keeps every answer, with its lines and model. The answers never change whether the defect exists or the grade the finding earns as the PR's own, and the judge's own call that a finding is pre-existing never lowers its grade. Reviewers report pre-existing defects too, so they are not lost. Manki posts a pre-existing finding only when it is a security finding. Every other pre-existing finding is kept in the round record only, with its reason, whatever its grade, and the review body does not mention it, so a defect the PR did not cause never holds it up. A tool alert is never pre-existing, since it carries no reviewer's mark and takes no origin check. The exception is an incomplete fix. A `pre_existing` answer may also name, in `fixed_elsewhere_in_pr`, a line where this PR fixes the same failure on another path, such as the same check added to a sibling function. Manki accepts that line only when the head holds it, the PR added or changed it, and it is not the flagged line. A finding the origin check made pre-existing whose answer names such a line is posted as a note, since the author of the fix wants to know it is incomplete. It must pass the proof and trigger checks a warning gets, and a finding from the verdict reader never becomes such a note. It says "**The same problem remains here.** This PR fixes it at" the linked line "but not on this path." It never blocks or holds the approval, and the round record keeps the line in the answer. A posted one shows "Pre-existing" in its header and is listed under "Pre-existing" in the review body. When the origin checks made it pre-existing, the finding says "**Already broken before this PR.** Two checks found the same problem on `main` at" the first line they read, linked at the base commit, ", so it doesn't block this PR.", again with the PR's own base branch. The other lines they read are in the fold of its thread, or in a line of their own in a reply. In the review body such a finding is short: its title and location, that line, what goes wrong and how to fix it. The lines it was checked against and the refuters' answers stay in the round record and in its thread, if it has one. A security finding on code the PR did not touch keeps its grade and blocks wherever it sits, whatever the origin checks found. Every other posted one never blocks or holds the approval: a security blocker on lines the PR changed that two models find the same before the PR is posted as a pre-existing warning and keeps its security tag, and the round record keeps its original grade. A blocker from the verdict reader is never pre-existing by location, since no judge checks its mark, and the origin check applies to it like any other.

From the second round, each finding is tagged as new, previously missed or still open: new when it sits within a few lines of code the PR changed since the last reviewed round, previously missed when an earlier round already reviewed that code. A finding is also new when a line it cites sits within a few lines of such a change: a proving line, a line at the start of an evidence check, or a line a refuter's answer cites. A push that changes code the finding relies on, such as a function it calls, can make an untouched line wrong, so no earlier round missed it. A finding the judge or the dedup model ties to an earlier Manki thread is never previously missed, since that round raised it. Manki compares the PR's own change at both rounds by line text, so a rebase or shifted line numbers do not make reviewed code new. A blocker blocks wherever it sits. A warning on reviewed code is posted like one on new code, in a thread of its own that holds the approval. Its thread says in one sentence that an earlier round reviewed those lines and missed it, and that it still holds the approval, since it is in the PR's own code. The reason is left out when an origin check found the problem before the PR. For a security warning it says a fix or a maintainer's resolve. On a repository that requires resolved conversations, the thread has to be resolved before the merge like any other. A security finding below a warning on reviewed code stays listed under "Missed by an earlier review". A note on reviewed code is not posted at all, unless it is a note on an incomplete fix, whose fix can be newer than that review. The round record keeps it under `findings.unposted` with the reason `reviewed_code`. Manki leaves one out only where it compared the lines with the earlier round. A round that could not read the PR's change at the last reviewed commit, or the diff since that commit, leaves out none of them, and neither is a note in a file outside the PR's diff. A finding that restates an earlier finding still open gets no thread of its own either. The judge links each finding to the earlier one that names the same defect, from every earlier blocker and every other earlier finding still open, in a thread or in a review body. A finding it does not link is matched by the rules that fold a finding into a verdict reader blocker, and the dedup model checks a pair those rules leave apart that sits nearby or shares a cited line in any file. An open thread is matched by its own finding and by every finding an earlier round took into it. A restatement of an open thread is not posted, and a blocker among them, the verdict reader's included, is listed under a link to that thread. This holds only for a restatement graded at or below the highest grade the thread had, so a blocker thread a partial fix lowered still takes its blocker back. A thread whose round records could not all be read may have been raised, so it takes any restatement. One graded above it gets a thread of its own, so a warning or a blocker never sits under a lower label. The check uses the final grade, so a finding the judge raises after an earlier step linked it leaves that thread again. A security finding is never carried by a thread that is not a security thread, since only a thread's first comment guards it. The warning of a blocker a check disproved is carried only by such a thread or by the thread of another disproved blocker. It joins the security thread that says the same, or is posted on its own, and keeps no link to another thread, so that thread stays among the open ones in the verdict. When the judge calls a finding another instance of the same mistake, such as another field the same check misses, Manki replies with it in that thread, unless the thread took it already or the finding is graded above the thread. These replies go out before the review, and a finding whose reply fails is posted on its own instead. When the review then does not post at all, Manki deletes the replies again. A thread the judge finds addressed this round takes nothing. When the review threads cannot be read, no finding is matched to an earlier one that round, since every finding of a thread would look like one listed in a review body. A restatement of a finding an earlier round listed in its review body is listed under "Still open from round N", whatever code it sits on, unless it is pre-existing, which stays under "Pre-existing", or a warning, which gets a thread of its own and holds the approval again. That thread says under the title "An earlier round already listed this in its review body", and it carries the warning while it is open: a later round that names either the body entry or the thread's own finding goes into that thread, so the defect gets no second thread. One graded above the listed finding is posted as a new finding instead. A note among them is not listed again, and the round record keeps it with the reason `listed_earlier`. Neither rule leaves out a security finding, a tool alert, or a finding that goes into an earlier thread, and a "Review again" run leaves out nothing. Each finding's `origin` in the round record says which it is, and `raisedIn` the round that first listed it. Manki also does not object to a change it asked for: a smaller finding on code that applies a fix an earlier round suggested is dropped, unless the judge finds the new code worse. A security finding or a tool alert there is never dropped. A finding that repeats a problem Manki already answered in a thread, with Fixed, Withdrawn, Agreed, Kept or Unverified, never gets a new thread, unless it is graded above that thread. It is dropped when it has the thread's title at most 5 lines from it and its file did not change since the last round, unless Manki settled the thread by an answer that cited lines, whose repeat goes to the judge and the line check. A repeat in other words reaches that thread only when the dedup model or the judge calls it the same defect. Otherwise the judge keeps it only when the code there got worse, and Manki then replies in that thread and reopens it if it was closed. Warnings and blockers Manki agreed to leave for later work are listed in every later review body under a "follow-ups agreed for later" heading, one line each: the location and title, a link to the thread, and the issue filed for it with `Create an issue for this`, when there is one. An agreed suggestion is not listed again.

A warning that an earlier round listed only in its review body has no thread to keep it visible, so Manki carries it forward. When a round lists a warning in the body, its record keeps a hash of the line the warning points at together with the line before and the line after it, as the file reads at that commit and without the whitespace around each line, and how many places of the file read the same (`citedLine`). Each later round reads the file at its own head. The review lists the warning again in one line under "Earlier warnings, not fixed", with the round that listed it first, and an approval counts it in its first line. When exactly one place of the file still reads the same, the line shown is the one that place is on at the round's head, which the carried entry records as `currentLine`, and a finding of the round is compared with that line. When several places of the file read the same, or none does, the list shows the file without a line. It never blocks and never holds an approval. Line numbers and the history between the two commits play no part in this line check, so a rebase, code moved within the file and an edit elsewhere in the file keep the line found, and a line the PR never changed or a file outside its diff is treated the same way. An edit to the cited line or to the line right before or after it ends nothing by itself, since an unrelated edit to a direct neighbour changes the hash as much as a fix does. The judge decides whether the warning still holds, as below. A warning whose file is gone leaves the list as `file_gone`, since later diffs no longer show that file to the judge. When the file cannot be read, the warning stays listed. A file that exists but is not read, such as a symlink or a file over the size limit while `closed_paths` closes any path, counts as unread and never as gone. A warning without a line, or on a line its file does not have, has no place to compare and is not carried, and a file that was renamed or moved reads as gone. A warning on a file the listing round could not read is recorded as `unread` instead of with a `citedLine`. It is carried without a line check, so only the judge finding it fixed or a finding of a round that names it ends it. When the PR's own change differs from the last round, the judge also gets each carried warning in the call that evaluates the open threads, with its title, file, line and a short description, next to the diff since that round. A warning the judge finds fixed leaves the list, also when the fix sits away from the cited line. Any other answer keeps it listed, and so does a missing answer or a failed judge call. A carried warning also leaves the list when a finding the judge graded this round names the same problem: the judge or the dedup model links the two, or the finding has the warning's title at most 5 lines from it, which then stands in its place whatever became of that finding. The reason is taken after the last step that leaves a finding out, so a note that names the warning and goes over `review.notes` ends it as `hidden_note`. A warning that names it and is left out because nothing proves it does not end it, so the carried warning stays listed. Neither does a pre-existing warning the review leaves out. Notes are never carried. The round record keeps the carried warnings under `findings.carried`, apart from the round's own findings, and the ones that left the list under `findings.carriedEnded`, each with its reason: `file_gone`, `restated`, `hidden_note`, `judge_dropped`, `left_out` or `fixed`.

The review body leads with the verdict, which counts the findings this round posted. A warning posted as a thread counts as a warning, as in "1 blocker, plus 1 warning in threads". So does an earlier warning thread that a finding of the round restates, as in "1 warning still open from an earlier review", and a warning the body lists, as in "1 warning listed below". Each earlier thread counts once, as a blocker when it still blocks or carries a blocker of the round. It is listed once under "Still open from earlier reviews", with what the round names it as below its link. A finding posted as a thread is only counted there, since its thread sits right below the review. The judge's summary follows under "What blocks:" when changes are requested. The review of an approval leaves the judge's summary out. When an approval is withheld because an earlier round record could not be read, the summary follows under "Summary:". The judge writes it before later steps can take a finding out of the round, such as a disproof or a note the review leaves out. So when the judge kept a finding and the round lists none of the findings it kept, the summary is left out. Later steps can also make a blocker the summary never saw, so the summary is left out as well when a finding blocks that the judge did not grade a blocker in the call that wrote it: the judge named a doubt on it, the cell the judge stated gives a lower grade than the column Manki graded it in, the judge stated no cell for it, or the sweep found it. A blocker that was lowered for citing no proving lines and that the refuter then confirmed still counts as the judge's, since the cell the judge stated gives a blocker. So does one that was held only because one finder alone reported it. A later step can also lower a blocker the judge graded, and the summary may still call it one. So the summary is left out too when such a finding no longer blocks: it was posted as a warning for citing no proving lines or for claiming a build failure no CI result reports, it sits in code the PR left alone, two refuters disproved it, only one finder reported it and no check confirmed its damage, or a later step dropped it. A round that requests changes then says what blocks with the first two sentences of the top blocker's description, as it does when the verdict reader found the blockers. The `Manki` check and the command line output show the same sentence as the review. On an approval they show the judge's summary, which the review leaves out. A round that approves without the judge's summary has no sentence, so the check shows only its title and the command line output only its heading. When only earlier threads block, the review lists them under "Still open from earlier reviews", and the check and the command line output show that list. On an approval, "What this does" follows in at most two sentences. A review held for warnings leaves it and "What to test" out, also behind a draft or a conflict. Its round record keeps both under `readyReport`, and the approval that follows once no warning thread holds any more shows them, "What this does" under its first line and "What to test" collapsed at the end. When repository settings refuse that approval, the notice that says so shows both parts below its line, so the person who approves by hand still sees them. A review held for files no model read or for a config file keeps both, with or without warnings, and so does one held for warnings with `auto_approve: false`. No approval check follows those, so the person who approves needs both. An approval held only for another reason keeps both in the review too. An approval held for files no model read says so in the verdict. So does an approval held for warnings: the verdict line counts the warnings to address, and asks to fix each one, reply in its thread with a reason Manki accepts, or tick `Create an issue for this` to track it for later. When the warnings are all that holds and `auto_approve` is on, it adds that Manki approves once every warning is handled. For a security warning, or a warning a check lowered from a blocker, it asks for a fix or a maintainer's resolve instead, since neither a reply nor the box clears one. A warning that has no thread, such as one GitHub refused as a thread, can only be fixed, and the verdict line says how many of them hold until a later round no longer finds them. Under the verdict line, the review lists each warning thread of an earlier review that still holds, under "Still open from earlier reviews", with its file, line and a link to its thread. So a round that finds nothing new still names what holds it. A warning this review posts shows in its own thread or section and is not listed there again. The box is left out of the line then. With `auto_approve: false` the line asks instead to tick the review box once every warning is handled, since only a review round approves then. When the PR is also a draft or conflicts with its base, the verdict line still comes first and ends with one sentence, such as "The PR also conflicts with `main`, so rebase it." The long steps and the box for a draft show only when no warning holds. With files no model read, the verdict line also says a person must approve. A config file that did not load is named below the verdict line then, and also when the round requests changes. When no warning holds, a config file, a draft or a conflict gets an "Approval held" line above the verdict line. When the round cannot read the warning threads, or cannot read every round record while a Manki thread is open or a security thread is resolved, it holds the approval as well and says so. Then `/manki check` decides, or with `auto_approve: false` a round started with Review again. The findings listed in the body come next, grouped by where they sit, each group headed by its counts per severity: "Found this round" ("Findings" on a first round), "Still open from round N", "Missed by an earlier review" and "Pre-existing". Files no model read get their own group, "Not read by any model". Each finding is a collapsed fold with its whole description, most severe first. A note is an optional improvement, never a defect, and the review calls it a suggestion. The judge orders the notes by how much the author gains from acting on each, and a note it did not rank follows the ranked ones, as does a note from the sweep's own judge call. When two or more finders ran, a note only one of them reported follows the notes that more than one finder or check reported, within each group below. A review posts at most `review.notes` suggestions, 3 by default, and `0` posts none. Every note in the `style` row of the severity table, about wording, formatting, naming or taste, comes after every other note, whatever the judge's order. So a style note is posted only when fewer other notes than places exist. For a note about tests, the judge names the line the PR changes whose removal or reversal no existing test would catch (`revertGap`), and only such a gap ranks high in its order. A note that only says how a test is built, such as a test that sets private state, calls code directly instead of through the public API, or is a unit test where an integration test could run, names no such line. It comes after every other note except the style notes, also when the repository's instructions state that test convention. A note that says no test catches such a revert, when the judge finds an existing test that already fails on it, is not posted. It takes none of the places, and the round record keeps it under `findings.unposted` with `unpostedReason: caught_by_test`. A note on an incomplete fix, a pre-existing failure this PR fixes on another path, comes before every other note. A suggestion whose line is in the PR's diff gets an inline thread that opens with **Suggestion, not blocking**, and a short code fix there gets GitHub's commit button. Such a thread never blocks and never holds an approval, in the round or in the approval check after a thread changes. A later round does not post it again. A warning or a blocker about the same problem still gets a thread of its own, also when the judge names it as that thread's finding. A later round resolves the thread with a "Fixed in" reply once a push fixes it, and otherwise leaves it open without a new comment. A reply there gets Manki's usual answer. The body lists every other suggestion after the other findings in one collapsed section, a fold per suggestion with its code fix as a code block. Those are one without a line in the diff, a pre-existing one, and one on code an earlier round reviewed or that restates a finding an earlier review body listed. A round usually leaves the last two out, as described above, so the body lists them only when it keeps them, such as on a "Review again" run. A line under them says how many more suggestions are not listed, and the round record keeps those under `findings.unposted`, with `unpostedReason: note_cap`. A suggestion that an open thread from an earlier round already carries is not posted again and takes none of the places. A security finding is never a note, so it keeps its thread. A tool alert below a warning is listed with the suggestions in the body, gets no thread, takes none of the places and is never left out. "What to test" follows, collapsed, and a rule sets each section apart. A collapsed "Checked and left out" comes last when the round has anything for it, and its summary line gives the count. Inside, it lists up to four kinds, each under a heading with its own count: each finding a check of the code disproved, with the start of the check's reason, each warning not listed because nothing proves it, with the reason, each warning not listed because its [trigger is rare](#the-importance-of-a-warning), with its score and the cut-off, and each lead not finished checking, as a possible problem, with the start of the reason the check could not settle it, or that no check in this round settled it, and the round it first came up in when that was an earlier round. Every entry links to its line, and each kind shows at most ten. The progress comment keeps the facts about the run, and under "Judge decisions" in its "Review metadata" section the judge's full reasoning for each finding. An incomplete round has no such section. A collapsed "About this review" closes the body with the reviewed commit, the round, the lines read, the review time, the models that found and judged the findings, and the tokens the round used with its cost estimated at public API prices. The cost is marked "partly priced" when some calls had no known price, and left out when none had one. On a subscription account it still shows how heavy the round was. When the round recorded its runner, the fold also shows whether it was GitHub-hosted or self-hosted, the time from the start of the workflow run until Manki started, and the most memory the run held against the memory it may use, such as "Runner: self-hosted · started after 11m 3s · peak memory 1.5 GiB of 2.0 GiB". That time covers the wait for a runner and the job's steps before Manki, such as a checkout or a build. Every finding opens with one line: its severity, then the category and the effort the judge set, such as **Blocker** · Concurrency · Moderate. A warning on the PR's own code that its thread can clear opens with a plain **Warning**, since the review's first line says how to clear it. A security warning, or a warning a check lowered from a blocker, says **Warning, needs a fix** instead, since a reply does not clear it, and so does a warning the body lists because it has no thread. Any other finding that does not block says so, as in **Suggestion, not blocking**, or **Warning, not blocking** for a pre-existing warning. The categories are correctness, security, reliability, data integrity, concurrency, performance, compatibility, testing, maintainability, documentation and style. The effort is a quick fix, moderate or a larger change. An inline finding then shows its title and up to three sentences of what goes wrong, about 700 characters at most. A short code fix GitHub can commit shows right below as a suggestion, in a thread on the finding's own line. Everything else sits in one collapsed section, in this order: how to fix it, why it matters (the rest of the description), how it was checked (what was read or searched, with code previews of the lines that prove it), and last, for a finding a refuter checked, the outcome of that check. A finding in the review body lists the same parts inside its own fold. It never shows raw tool output. Every warning gets a thread, as described below. Up to five security findings below a warning on changed lines get inline threads, and the rest are listed in the body. Suggestions do not count toward the five. Each review's round record stores `output.bodyLength` and `output.commentLengths`, the length of the body and of each comment as Manki composed them, before GitHub accepted or refused any comment.

The PR author cannot dismiss a blocker, a security finding of any severity, or a blocker that every refuter disproved and Manki posted as a warning. Their own reply, also one that gets Manki to answer Fixed, Withdrawn or Agreed, or resolving the thread leaves it blocking, and auto-approve waits for it. When the author resolves the thread, Manki reopens it right away, without waiting for a push, and replies to say why. When the author also replied in the thread, the reason is part of Manki's answer to that reply. An answer that confirms the fix does not ask for a maintainer or a fix. It opens with a bold line instead of Fixed, "**Fix seen, the thread stays open until a review or a maintainer confirms it.**", or on a thread that stays resolved "**Fix seen, the finding is not cleared until a review or a maintainer confirms it.**". The model's text follows, and then that a review confirms the fix only after a push changes the thread's file or a file its finding cited, naming those files. Everything that reads the thread takes that answer as Fixed. On a thread tied to no file, which no review clears, the answer is Unverified and opens with "**Not settled yet.**", and both it and the reopen reply name only someone other than the PR author with write access. A Withdrawn or Agreed on such a thread opens the same way, with "Finding withdrawn" or "Deferral accepted" in place of "Fix seen", and says that the thread stays open until a maintainer closes it, or on a thread that stays resolved that the finding is not cleared until a maintainer clears it. Manki reopens a thread only once. When the author resolves it again, it stays closed and keeps blocking. It is cleared when someone else with write access resolves the thread, replies and gets Manki to answer Fixed, Withdrawn or Agreed, or comments `/manki dismiss` in it, or when the judge marks the thread addressed. A reply in agreement or a dismissal also clears a thread the author had resolved: Manki reopens it and resolves it itself. Manki's own resolve of such a thread counts only when something backs it: the latest round that checked the thread marked it addressed, or Manki's own reply in the thread records that it cleared the thread for someone other than the PR author with write access, as when it withdraws the finding on a maintainer's reply or accepts a maintainer's dismissal. Review rounds and the approval check read the same rule. Manki writes that record only for someone who has write access at that time. Whoever resolves the thread, or the person Manki's record names, counts only when GitHub's permission lookup confirms a person with write access, so a resolve by a bot, an app or a workflow token clears nothing. The round record backs only Manki's own resolve. When the judge confirms a fix in a thread someone else resolved, Manki reopens the thread and resolves it itself, so GitHub names Manki as the resolver. When the PR author later reopens such a thread and resolves it, it blocks again until a round confirms the fix once more. A thread backed this way stays cleared on later pushes, and a blocker found there again pauses automatic review for a person. A thread Manki resolved with nothing to back it keeps blocking: the next review lists it under "Still open from earlier reviews" and checks it again, and the approval check names it with the reason. A later reply in the thread, by the PR author or anyone else, changes nothing, since only Manki's record counts and no person's comment does. When Manki reopens the thread, or finds the problem there again, its records from before no longer count. A later round never drops a new blocker as a repeat of a thread that was not cleared this way. A later round leaves a security finding, or a warning a check lowered from a blocker, out as already settled only when its earlier thread was a blocker or such a thread that was cleared this way. A thread the author could resolve alone hides a repeat of an ordinary finding, never one of those. These rules also cover threads resolved before an upgrade to 7.5. So on a PR that was open at the upgrade, a blocker or security thread that was not cleared this way blocks again.

A PR author with a high enough repository role may clear such a finding on their own PR, so a repo with a single maintainer is not stuck. They resolve the thread in the GitHub UI, or comment `/manki dismiss` in the thread. `author_clear_role` sets the lowest role that may: `admin`, `maintain` or `write`. The default is `maintain`, so a maintainer and an admin may, and a contributor who can only push may not. A repository owned by a user account has no `maintain` role, so with the default only its owner may. With `write`, everyone who can push may clear the blockers on their own PRs, so a blocker no longer holds their PR and only tells them what Manki found. The setting is read from the base branch only, so a PR that changes it cannot lower the role for itself. It changes nothing for anyone else: someone other than the author still needs write access. Manki reads the author's role and everyone's write access through the GitHub API, because comments show an org owner, and an org member with read access, as a plain member. Only a role GitHub confirms counts. An author with a custom role, a role the API does not return or a lookup that fails may not clear. While the base branch's config cannot be read or loaded, only an author with the `admin` role may clear, since that role may under every value of the setting, and Manki approves nothing: a review round holds its approval, a resolved thread starts no approval check, and `/manki check` answers that the approval is held. Every such override is recorded: Manki replies once in the thread with "Finding dismissed by `@<login>`, the PR author, who has the `<role>` role on this repository.", the round context lists it with the role under `recap.securityOverrides`, and an approval that relies on it names it and the role in the review body. When Manki answers Fixed, Agreed or Withdrawn on a blocking or security thread that the replier may not clear, the answer says that the thread stays open and who can close it. A Withdrawn there saves no [learning](memory.md#how-memory-works), since the finding is not settled. On a thread the author resolved again, the answer says that the finding keeps blocking, and so does the answer to the author's `/manki dismiss` there.

Every blocker gets a thread, so a later round can evaluate it as fixed and a person can resolve it. So does every warning except a pre-existing one, so it can be answered there. GitHub only allows comments on changed lines, so a blocker or a warning in a file outside the diff, or one tied to no file, gets its thread on the first changed line of the first changed file. That thread says in its first lines where the finding is, and the review body names the finding and the file its thread is on. A scope reader warning judges the whole PR, so neither its thread nor the review body says that. A push never clears a thread that is tied to no file. Only a person does. A blocker or a warning on a line of a changed file that takes no comment gets its thread on the first changed line of that file. The thread opens with a link to the finding's line at the reviewed commit, or says the finding concerns the whole file when it names no line. Every such thread is a comment of the review itself, so the PR shows one review. A finding in a changed file with no changed line, such as a deleted file or one only renamed, gets a file-level thread on that file, posted right after the review. A finding that an open thread already carries stays in that thread. A finding that restates an open thread graded below it, or a security finding that restates a thread without the security guard, gets a thread of its own instead. Once that thread is posted, Manki replies in the earlier thread with a link to it, such as "Raised to a blocker, continued in this thread", and resolves the earlier thread, so the PR shows the problem once. That reply lifts the earlier thread's hold on the approval, since the new thread holds instead. A later round counts the earlier thread neither as fixed nor as settled, so it drops no restatement of the problem, and the closed thread carries no later finding, which gets a thread of its own. An earlier thread that only a fix or a person clears, such as a blocker or a security thread, stays open. So does an earlier warning thread when the new thread holds less, as a security suggestion does, or when the round also put a finding into the earlier thread, such as another instance of the same problem. When GitHub refuses the review's line comments, Manki posts the review without them, and each blocker and warning among them gets a file-level thread on its file instead. When GitHub refuses that thread too, the blocker is listed in the review body, and the next round posts it as a thread again without asking a model about it. A finding of that round that restates the blocker at a lower grade lifts nothing: the blocker is listed again and stands for it, and the record keeps the finding without posting it. A blocker that a later round restated as a blocker with its own thread is not posted again: that thread carries it, and it blocks until that thread is cleared. A security blocker rides only on a security thread. When the restatement got no thread either, only the first of the two is posted again. A warning GitHub refuses that way is listed in the review body under "Warnings that could not be posted as threads". It still holds the approval, and with no thread, it clears only when a later round no longer finds it. The body says so under the list.

A round ends in one of three verdicts. With a blocker open, Manki requests changes. With no blocker but a warning open, it posts a comment review that holds the approval, and the `Manki` check is neutral with the title "Approval held: warnings wait for a fix or an accepted answer". The title stays the same when the PR is also a draft or conflicts with its base, and the summary ends with the review's sentence for that. When a config file that did not load or a changed file no model read holds as well, the title names that hold and the summary says that warnings also hold. Those two also come before a draft or a conflict, which the review still names. With only suggestions, or nothing, it approves. A warning thread counts from any round, a warning on lines an earlier round already reviewed included, and a later round's warning takes back an approval Manki gave before, also one of the same commit, as when Review again runs on an approved commit. A blocking thread that is open again after Manki approved, because a person or Manki reopened it, takes the approval back too: the approval check that runs on the reopen, or after a reply that reopens it, dismisses Manki's approval, a round's or an auto-approval, also while `auto_approve` is off. Once it dismissed one, it also tells the token service that no approval stands, and fails the `Manki` check on the head with the title "Changes requested", so a required check no longer passes. A dismissed approval no longer covers the head, so resolving the threads afterwards approves nothing: the next review round decides. A dismissal GitHub refuses leaves that approval and the token service's record of it as they are, also when another dismissal worked. The check still fails, also when no dismissal worked. With no approval left to dismiss, as after a person dismissed it by hand, the check fails when the newest `Manki` check on the head passed, so an open blocker never sits beside a passing check. A check that fails to write is tried once more. While a round record cannot be read, every thread counts as blocking, so this check then dismisses nothing. A pre-existing finding never holds the approval. A warning thread stops holding only when one of four things is certain. Manki answered a reply in the thread, by the PR author or by someone with write access, with Fixed, Withdrawn or Agreed. A later round found the warning fixed and resolved the thread. Someone with write access ticked its `Create an issue for this` box and Manki filed the issue. Or someone with a role that `author_clear_role` allows resolved the thread by hand, the PR author included. Nothing else lifts the hold. A reply that Manki answers with Kept or Unverified leaves it in place, and so does a reply Manki has not answered yet or could not answer. So does an accepting answer to anyone else, such as someone whose permission Manki could not read. So does a resolve by hand from anyone below that role, the PR author included, and so does `/manki dismiss`, which resolves the thread and leaves the hold. Someone with the role then reopens the thread and resolves it by hand to lift it. Manki's Kept or Unverified answer on such a thread says what lifts the hold. So does an accepting answer to someone it resolves no thread for, and so does its reply to a dismissal. Manki reads its own answer and the filed issue only from hidden markers below the marker of its own comment, so text a person writes or quotes in the thread lifts nothing. An answer whose record cannot be read, or that was written while Manki could not read the thread, lifts nothing either. An accepted answer or a filed issue counts only when it came after the thread became a warning: after the review that posted it as one, or that lowered a blocker thread to one, was posted. When a later round puts a warning into the thread again, by naming its warning again or by finding its answered problem worse, an accepted answer, a filed issue or a fix from before that round no longer counts, also in that round's own verdict. Only one that follows that round lifts the hold again. A resolve by someone with the role counts whenever GitHub shows it, since a round puts a finding only into a thread it read as open or as resolved by Manki. When the time a round was posted cannot be told, no answer counts as made after it. A tick of the issue box that a version before 7.5.2 handled left no marker, so its thread holds until one of the other ways clears it. A security warning clears only the way a blocker does: by a fix, or by a resolve from someone with write access other than the PR author, or from a PR author with a role that `author_clear_role` allows. A thread whose grade cannot be read, because a round record cannot be read, counts as blocking. When the last warning thread clears, the approval check below approves without a new round. With `auto_approve: false` no approval check runs, so tick Review again in the settings block, and that round approves. A push that leaves the PR's change as it was, such as a clean rebase, gets the earlier approval again without a round, unless a warning thread holds it or a blocking thread was reopened since. This holds for an approval by a round and for one the approval check gave once every thread was resolved. Then the push gets a full round. On a draft or a PR that conflicts with its base, such a push gets no round and the approval stays held. When warning threads hold it too, the check names the warnings first and ends with the sentence on the draft or the conflict. After such a push GitHub can list a review under the new head, although Manki reviewed an earlier commit. So Manki takes the commit a review covers only from the review's own text: the commit the "About this review" footer links, or the head that an approval posted without a round names in a hidden marker or in its approval record. The commit GitHub lists for a review never counts. A review that names no full commit covers no commit, such as an approval that a version before 7.5.1 posted again after such a push, or a review from before 7.1. A push after it gets a full round, and resolving threads approves nothing until that round.

Before auto-approve approves, it reads the record of the review that covers the head. Resolving threads lifts that review's block only when a thread on the PR carries every blocker the record names. The record alone never proves a thread. A blocker the round posted as a thread counts only while a thread that the round posted for it is on the PR, so a thread that is not posted yet, that GitHub refused or that someone deleted holds the approval. A thread posted later carries its blocker from then on, and resolving it runs the check again. The record marks each warning that holds the approval with `holds`, and such a warning counts the same way: while no thread the round posted for it, or the earlier thread it went into, is on the PR, it holds the approval. A blocker GitHub refused as a thread is listed only in the review body, so no thread stands for it, and the same goes for a warning that holds the approval with no thread. In those cases, and when the record cannot be read or does not say what the review blocked on, Manki does not approve and the next review round decides. A review that a version before 7.5 posted names no thread for its blockers, so resolving its threads approves nothing until a new round. To start one, tick the review box in the settings block, or push a commit. If the push starts no review, as while automatic review is off or paused, comment `/manki review`. An approval that Manki posts again after a push that changed nothing has no record and blocks on nothing, since it only restates the approval of the same change. A request for changes on the head that a person dismissed on GitHub still covers the head while it is Manki's newest verdict there, so its record still decides what blocks, and once its threads are resolved Manki approves as usual. Only a person's dismissal counts this way: a dismissed approval, and a review that Manki, a push or another app dismissed, covers nothing. When a person dismisses Manki's newest approval of the head, no earlier review of the head covers it either, so resolving threads approves nothing until a new round. The same holds when Manki cannot tell who dismissed its newest review of the head, as when the timeline cannot be read. `/manki check` runs the same check and replies with every reason it found, in this order: the threads that block and that someone allowed to has to resolve them, the blocker or warning no thread carries, or a head no review covers, then the warning threads that still hold, each with the reason when it is resolved, with one sentence for a draft or a conflict beside them, then an approval held for a person, and, when no warning thread holds, a draft or a conflict with the base. A `/manki review` on a head that already has a complete review runs the check too, instead of a new round. Marking a draft ready runs the check too, on the review that covers the head, so a draft whose review found nothing to block is approved without another round. So does a run that ends because its head already has a review that held its approval, when a `Manki` check waits for that run, as after a duplicate event. The waiting check then shows the hold as it stands now, or the approval once nothing holds it. When the check holds the approval after the covering review held it for another reason, its notice first says which of that review's holds cleared, as in "Every warning that held the approval is handled. **Approval is still held:** this PR conflicts with `main`." It names only a hold the check tested and found cleared. The check tests warnings, then a draft, then a conflict, so a notice for a draft says nothing about a conflict. With the same hold as the review, or none before, the notice reads as it did.

Every finding ends with a `Create an issue for this` box: at the end of its thread, and in the review body right under each finding listed there, the Pre-existing section included. When someone with write access ticks it, Manki files the finding as an issue, with the finding as posted, a permalink to its line at the reviewed commit and a link back to where it was posted, and replaces only that box line with "Issue #N created by `@login`". The issue also mentions the person who ticked the box in a "Requested by" sentence, so GitHub notifies them of the new issue. In a thread, it also replies with the link and resolves a thread the PR author may clear. A hidden marker on that reply is what lifts a warning's hold. The thread of a blocker, or of a security finding of any severity, stays open, since only someone other than the PR author clears it. After a tick that files the issue in such a thread, the approval check runs, as it does after a resolve by hand, so a warning cleared this way lets Manki approve. That holds for a thread that was already resolved too. A tick in the review body resolves nothing, so it lifts no hold. When an open issue Manki filed for the same finding exists, the tick links it instead of filing another, and leaves that issue as it is. When no issue is filed, because GitHub refuses it or Manki cannot find the box's finding in the review, Manki says so in the thread or in a PR comment and clears the box. A tick by someone without write access does nothing.

A message that names a next step carries the box for it, so the step is one tick instead of a command. The box sits below the text that names the step, and the text keeps naming the command too. **Review again** appears where a message asks for a new round: the answer to a `/manki review` on a head that already has a review, a review that ends incomplete with a retry, the Needs a human list, an approval hold while `auto_approve` is off, an answer about a head Manki has not reviewed, and the answers that say the next round decides. It works like the review box in the settings block: it reviews the head commit, and a tick while a review is queued or running joins that review. A tick edits the review it sits in, and Manki reuses no part of an edited review, since anyone who can edit it could change its record. So in a review that ended incomplete, the box reads the whole change again. **Check approval** appears where an approval hold says to comment `/manki check`, and runs that check. **Forget this learning** appears below the answer that saved a learning, and removes it as `/manki forget <id>` does. **Dismiss this finding** appears in the thread of a suggestion that is not about security, and dismisses it as a `/manki dismiss` reply in that thread does. Manki replies in the thread that `@login` dismissed it, and later rounds count the thread as settled. When a later round raised the thread to a warning, the reply settles nothing, since a dismissal never lifts a warning's hold. A blocker, a warning and a security finding get no such box, since a dismissal clears none of them. A tick acts only for someone allowed to run the same command, and Manki then replaces the box line with "<step> requested by `@login`". When the step does nothing or fails, as for a dismiss of a thread that is already resolved or a learning that is already gone, Manki puts the box back unticked. Check summaries hold no box, since GitHub shows them as plain text.

On a merged or closed pull request Manki still answers a person and changes nothing about the review. A thread that is resolved or reopened there, or a review that is submitted or dismissed, starts no approval check, so Manki reopens no thread, approves nothing and dismisses no review. A reply in one of its threads gets its answer, and the thread stays as it is: Manki neither resolves nor reopens it, and a Withdrawn saves no learning. An answer that would have settled the thread says that the thread stays as it is. `/manki dismiss` resolves no thread and stores no suppression, and says so. `/manki check` approves nothing, and with `auto_approve` on it says that the PR is merged or closed. `/manki review` runs no review, and Manki answers once that the PR is merged or closed and nothing was reviewed. The answer carries a Review anyway box, and a tick by someone with write access runs the review once. `explain`, `help`, `remember`, `forget` and free-form questions work as on an open PR, since none of them changes the review, and a tick of a `Create an issue for this` box still files the issue and resolves its thread. Manki reads whether the PR is open from GitHub when its run starts, and the approval check reads it again right before it decides.

Each round checks the open Manki threads against the push. When the PR changes the file of an open blocker or warning thread, that file is read in full before the other changed files compete for the 400 KB of files read in full. A thread's file outside the PR's change keeps its place among the rest. A file over 200 KB is never read whole. When the 400 KB cannot hold every file, source files come before test files and smaller files before larger ones, so one large test file never pushes out the source it tests. These whole files go to the verdict reader and to a finder without repository tools. A finder with repository tools gets code windows instead: the 20 lines on each side of each hunk of a modified or renamed file, numbered and read from the PR head. An added file is already whole in the diff. When the windows pass 150,000 characters, the files the diff changes the largest share of come first. A finder with tools reads more of a file with them when a window ends before what it needs. The finders and the verdict reader are told which changed files were left out and why, so a finder with tools can read one when the change needs it. The diff since the last round is capped at 20,000 characters and cut from its start, with lockfiles at its end. Before a longer one is cut, the files of open blocker and warning threads move to its front, then the files their findings cited and the files of carried warnings. A file the push renamed counts under its old and its new path, so a thread posted on the old path moves to the front, gets the note that its fix may not be shown, and counts as a thread whose file the push changed. The judge is told which file the cut runs through and which files fall past it, naming at most 200, and each thread whose files are cut, left out or could not be read says that its fix may not be shown, as does each carried warning whose file is cut or left out. A file that is not at the head, such as one the PR deleted or renamed away in any round, does not count as a failed read. A read that fails for another reason, such as the size limits or an API error, does. For a thread whose line is gone, the judge sees the code it named on the commit it was posted on, and where that code sits now, found by several of its lines lining up again. When the code left its file and exactly one other changed file holds it unchanged, the judge sees it there, with the file named. In every other case the judge is told that it is not found, and sees the head's code near the same line. An unchanged file never reads as proof that the problem remains. When Manki itself answered in the thread, such as "Fixed." with the lines it cites, the judge must confirm that evidence or say which part is wrong before it keeps the thread open. On a blocker or security thread the judge also sees the latest reply there, when the PR author or someone with write access wrote it. Anyone can comment on a PR, so a reply by anyone else is not shown. The reply is a claim to check, never evidence: the verdict says why it does or does not settle the finding, and no reply makes a thread count as fixed. A fix on such a thread counts only when the push changed the thread's file or a file its finding cited in its "Checked in the code" links, such as a blocker on one file whose fix belongs in a caller the finding cited. Manki reads those files from the hidden data of its own first comment in the thread. A thread whose first comment names none, such as one posted before this was recorded, counts only its own file. The judge is told which threads stay open for that reason, so its summary does not call them fixed. When the judge finds such a blocker thread fixed by a change to another file the push changed, such as a caller of the flagged code, it names that file. The refuter then checks whether the thread's failure still happens at the head. When both refuters, on different models, find that it cannot happen and each cites a line the push added to that file, Manki replies in the thread with "Fix seen in" that file. The thread still stays open and keeps blocking: a fix outside the files the finding cited never resolves a blocker by itself, since text the PR author wrote there could steer both refuters. Someone other than the PR author with write access can resolve the thread, and so can the PR author with a role that `author_clear_role` allows. Or a push that changes the thread's file or a file its finding cited lets the next review confirm the fix the usual way. The check needs `models.second_refuter`, and without it the judge is not asked for the file. A thread the round names again, or one a fix check found only worked around, is not checked. One refuter, an unsure or failed check, a disproof that rests on other lines, a security thread and a thread tied to no file get no such reply. The push counts only for what it changed in the PR's own change, so a rebase onto the base branch changes no file. When it confirms a fix in a file the push changed, it resolves the thread with a short "Fixed in" reply and the thread stops blocking. The reply names a commit only when it is certain which one fixed the thread: the only commit since the last reviewed one that changed the thread's file, editing it in place. In every other case, such as two commits changing the file, a commit that renamed, added or deleted it, a rebase, a merge from another branch or more than 20 new commits, the reply says "Fixed by the commits up to" the head, which is always true. A thread counts as fixed only when every failure it names is gone. A push that only works around the reported case, such as a guard where the wrong result shows up while the code that causes it stays as it was, is a partial fix: the judge keeps the thread open and names the code that causes the problem or the input or path that still fails. When it can name neither, it decides as for any other fix. A [fix check](#fixes-in-the-change) whose finding stands and that finds the push hides the symptom at the thread's lines keeps the thread open the same way. When the push fixes only part, the thread stays open and gets a "Partly fixed" reply that says what still goes wrong, and it keeps the grade that remaining damage earns: its own grade when the damage is the same, never a higher one, and one below the grade it carries only when the push changed the thread's file or a file its finding cited. The judge states the severity table cell of what remains, and Manki works out that grade from the cell. Nothing checks a rare claim on a thread, so on the wrong behaviour row what remains is graded in the normal column and a partly fixed blocker keeps blocking. A partial fix never lowers a security thread, or the thread of a warning a check lowered from a blocker. A partly fixed blocker thread blocks only while what remains is a blocker, in later rounds too. It gets back the highest grade it had, with an "Open again" reply, when a later round names its blocker again, repeats its problem as a blocker, or finds it not fixed after a push to its file or a file its finding cited. The round record keeps each thread's grade under `judge.threadEvaluations`, and Manki reads it from the latest record that set one, so the grade holds exactly while the review that decided it stands. The record keeps the cell the judge stated as `cell` when that cell gives the thread's grade. When the thread keeps another grade, the record keeps the cell as `judgeCell`, and the next round's judge sees only the grade. A reply that fails to post loses only the note. A blocker a later round carries on the thread, by naming it, folding into it or repeating its answered problem, raises it to blocker the same way, and outranks a lower grade in the same round. No reply that Manki posts decides whether a thread blocks. When a round record cannot be read, a grade it held is unknown: the approval check counts every Manki thread as blocking, the review round requests changes while a Manki thread stays open, and the PR author cannot clear a Manki thread by resolving it, though an author with a role that `author_clear_role` allows still can. The review leads with an "Approval withheld" line that links each review whose record it could not read, in place of the usual count of blockers, and shows the judge's summary under "Summary". The check summary does the same, so a person sees why, and no open thread is called a blocker it may not be. The hold lasts until a maintainer has resolved the open threads. A round that requests changes for another reason does not name the unread record. A thread the round resolves, or one someone with write access agreed away, does not count as open for this hold. The judge also checks that each finding's fix removes every failure the finding names, and a fix that removes only part says what it leaves. A thread gets one Manki fix confirmation per head commit: when Manki already answered a reply there with "Fixed." on that commit, the round resolves the thread without its own line, and a reply answered after the round's line gets no second "Fixed.". A blocker that a round names again while its thread is still open stays in that thread instead of getting a new one.

**A blocker restated after its own fix.** When a blocker of the round restates an open blocker thread after the push applied the fix that thread's finding suggested under "How to fix it", the restatement is posted as a warning in that thread and stops blocking. The thread gets a "Partly fixed" reply with what the restatement says remains, and its entry in `judge.threadEvaluations` records `ownFix`. Manki lowers it only when it is certain: the thread records a fix, the push changed the thread's file or a file its finding cited, and a refuter with repository tools confirms that the push applies that fix by citing a line the push added in one of those files. With `models.second_refuter` set, both refuters must confirm it on different models. Without one, the judge's refuter alone may, since the result is still a warning that holds the approval. A blocker of the verdict reader on that thread is lowered the same way. Only a restatement of the thread's own finding is lowered: a variant of the same mistake in another place, or a restatement of another finding recorded under the thread, keeps its grade. A later round keeps the warning without a new check while its push changes none of those files, and checks again after a push that does. A security finding, a tool alert, a security thread and the thread of a blocker a check disproved are never lowered this way, and anything less certain keeps the blocker.

When a blocker comes back after a fix was claimed for it, the review keeps requesting changes, lists the blocker under "Needs a human", and pauses automatic review. A blocker of the verdict reader names an earlier blocker only when it has that blocker's title at most 5 lines from it, or when the dedup model calls a nearby pair the same defect. Another defect next to a fixed blocker pauses nothing. Its first line also counts the round's other findings, as in "1 blocker came back after a fix, plus 3 new blockers and 1 warning in threads". A fix is claimed when Manki confirmed it in an earlier round, when the thread counts as resolved or is gone, as after someone with write access other than the PR author resolved it, or when such a person agreed the thread away. No other reply in the thread claims a fix, whoever wrote it and whatever it says. Neither does the PR author resolving a blocker thread, which keeps blocking. A waived finding never counts. A thread is waived when Manki's own comments record that it was settled without a fix: Manki's answer accepted no fix, Manki recorded a dismissal it accepted and resolved the thread on, or Manki recorded that the PR author cleared it with a role that `author_clear_role` allows. Whenever Manki resolves a thread on a dismiss it accepted, by a comment or the Dismiss box, it records the dismissal in the thread once, in the same note it posts for the PR author's clearing, and that note is its only reply. On a blocker or security thread that is a dismiss by someone with write access other than the PR author. If the note cannot be posted, the thread stays open. No person's comment counts, whoever wrote it, so a dismiss command alone waives nothing and cancels no waiver. Manki reads that only from a thread whose comments it read in full, and never when an answer of Manki's accepted or confirmed a fix or a judge found it fixed. Only Manki's latest settling comment since it last reopened the thread counts, and the resolve must still be the one that waiver made. So a thread waived once and then reopened, fixed and resolved again by someone else is no waiver. A mention of another pull request waives nothing either. Pausing automatic review needs a sure claim of a fix in this PR, so a waived blocker found again after a push to its file pauses nothing. When the judge names it as the same finding in the thread's own file, the round drops it as dedup drops a repeat of a waived thread, on a thread Manki resolved only while that code is unchanged since. Anywhere else, the finding is posted as a new blocker. So a blocker named again while its thread still counts as open just stays open, as after a rebase or after the author answered that the change is intended and resolved the thread: the round requests changes, and automatic review goes on. A claimed fix also counts only when a fix was tried: a push since the blocker was last raised changed its file or a file its finding cited. Manki proves those files unchanged only from the PR's own change since the last round and an empty one in the record of every round in between, so a round whose record it cannot read counts as a change. So any other resolved thread without a push to that code is a decision, not a fix, and its blocker found again pauses nothing. Dedup drops such a finding before the judge only when the dedup model calls it the same defect as the thread, and only when it sits in the thread's file or cites a line that the thread's finding sits on or cited. In another file, and on a thread Manki resolved itself, the code must also be unchanged since, as the dedup step says. Any other such finding is posted as a new blocker: the round requests changes, and automatic review goes on. The last automatic round, round `max_auto_rounds` (default 10) counted from Manki's last approval, approves when nothing blocks, or stops the same way when a blocker is still open. Its first line then counts the blockers still open, and the round's other findings the same way. Rounds after an approval, such as on rebases, start the count again. An approval held because the PR conflicts with its base counts as an approval here, and so does auto-approve after the last blocking thread is resolved. An approval that warnings held does not count, also when another hold comes first, so warnings that keep coming back still reach the cap. That approval also ends a pause from a blocker that came back. Only rounds that reviewed a new change count, so another round on a change Manki already reviewed, such as Review again on the same commit, does not. While automatic review is paused, its notice lists the blocking threads still open, with links. A pause by the round cap also asks the author to step back and reconsider the approach, since rounds that keep finding problems usually mean the design needs another look. A push starts no review, but replies in threads, auto-approve after the last blocking thread is resolved and the Review again and Deeper review boxes in the settings block still work. `/manki review` reviews the head commit unless Manki's newest review of it is complete, so during a pause it starts a round only after a push or after a round that did not finish. A command that starts no round for that reason gets a reply. It says that the commit already has a review, that the command starts a round after a push, and that the Review again box reviews the same commit again. During a pause the reply also gives the reason for the pause and lists the blocking threads still open, with links. Below that list it says that the PR author may not clear a blocking thread without a role that `author_clear_role` allows. The reply leaves all of that out while `auto_review` is off or the Pause box is ticked, and whenever Manki cannot read the pause for certain, such as with a round record it cannot read. Each such command gets its own reply. A review started by a box or the command also turns automatic review back on for the next 3 automatic rounds, or for the rounds the cap still allows after the restarted round if that is more. After a restart, the notice counts the rounds since the last approval and how many came after the last review started by hand. When they pass without an approval, automatic review pauses again with the same notice, and the next review started by hand turns it back on again.

Choose different models for the finders and the judge, such as a faster model for the finders and a more precise one for the judge: `review.groups` names the finders' models and `models.judge` the judge's.

The judge treats two finders reporting the same defect as strong evidence that it is real, and one finder's silence as no evidence against the other's finding. Agreement never raises a finding's severity.

To give the second finder its own model, name it in the `full` review group.

## Replies in a review thread

A reply in one of Manki's threads gets one answer that starts with Fixed, Withdrawn, Agreed, Kept or Unverified. The [README](../README.md#talk-to-manki) says what each means and who gets a thread resolved by it. On a warning thread, only Fixed, Withdrawn or Agreed lifts the hold on the approval, as [Severity tiers](#severity-tiers) describes.

When that word alone would not tell what happens to the thread, the answer opens with a bold line Manki writes on the thread's state instead, and the model's text follows below it. Everything that reads the thread takes such an answer as the outcome it stands for:

- An Unverified answer opens with who or what settles the thread, followed by why the answer settles nothing, as described below.
- A Fixed, Withdrawn or Agreed that leaves the thread as it is opens with "Fix seen", "Finding withdrawn" or "Deferral accepted" and the reason: a blocker or security thread that stays open, a merged or closed pull request, or a reply by someone who is neither the PR author nor a collaborator, as in "**Deferral accepted, but only the PR author or someone with write access settles a thread by a reply.**".
- An answer that leaves a warning holding the approval says what lifts the hold right after that line. A Kept there opens with "**Kept.**" and the same sentence.

A reply is read on the newest commit of the PR's branch. GitHub can show a push on the PR minutes after the branch has it, so Manki waits up to 3 minutes for the two to match. It checks them again before it posts, and reads the reply once more when the head moved. When the PR still does not show the push, Manki says that it did not check the reply, and the thread stays as it is.

A reply can wait in the queue behind a running review and get its answer after that review. The model then sees what that review found in the thread. A review that finds a thread only partly fixed says nothing there while the answer to a reply is certain to follow: the token service names the reply as queued and no newer review with it, the reply was written before the review's record, its writer has write access, and it is no command. A push or a failure in between can still drop that note from the answer. The answer then says what the review still found open, unless it resolves the thread. That note follows the answer's bold first line, before the model's text, and an answer without such a line opens with its outcome word in bold, such as "**Kept.**". The round record keeps the grade either way. When the queue cannot be read, the review replies itself. It may also have replied in the thread for another reason, such as Partly fixed, Open again, Fix seen in or Found again. On a blocker or security thread a Fixed answer points to that review's verdict instead. When any other answer resolves the thread on the same head commit, its bold first line, "**Fixed.**", "**Withdrawn.**" or "**Agreed.**", goes on to say that it reads the reply and replaces the verdict of that review. An answer that leaves the thread open, such as one to someone Manki resolves no thread for, says nothing of the kind.

That review may also have confirmed the fix already. When the model then answers Fixed but cites no line that counts, the answer is "The review of `abc1234`, which finished after this reply, confirmed this fix." instead of Unverified, with the list of checked statements below it. When the model says that the reply needs no answer, since it only says that the finding is fixed and how, and no check found anything against a statement of it, Manki adds a thumbs-up reaction and posts nothing. Either way it settles nothing, changes no thread and lifts no hold, and later rounds do not read it as an answer. Manki does either only when all of this is certain: the PR is open, every review record was read and no newer review ended incomplete, the newest review is on the head commit, finished after the reply and found this thread fixed, Manki resolved the thread and confirmed the fix on the head commit, the thread holds nothing, no earlier answer of Manki stands in the thread, and the reply was never edited and has no question mark. Otherwise, and for every other outcome of the model, the answer is the usual one.

Later rounds read a reply only through that answer, never through its words. A reply counts as agreement only when Manki answered the latest reply by a person in the thread with Fixed, Withdrawn or Agreed and settled the thread with it, in an answer whose record names that very reply, or recorded a dismissal after it, and Manki has not reopened the thread since. Such an agreement takes a blocker off the open list and hides a later repeat of the finding. From someone who may clear the thread, it also counts as a claimed fix. A reply Manki has not answered yet, a question such as "Has this been addressed?", "I haven't fixed this yet", a plain "done" and a reply Manki answered with Kept or Unverified agree to nothing, so the thread stays open.

Before it answers, Manki checks what the reply says about code and about the PR description. It lists up to 5 statements below its answer, each in the developer's own words, with what Manki checked. The list is in a closed fold, whose summary says how many were checked, such as "3 statements checked, evidence cited against 1, 2 not checked". A statement that Manki cited something against also shows above the fold. Each line says only what was checked, never that the statement is right:

- **Line cited for it exists at** or **Line cited against it exists at** a place, such as `src/retry.ts:48`, or `owner/name:path:line` in a [related repository](#related-repositories). The review model cites the line for or against the statement, and Manki checks only that it exists: in the checkout of the PR head, or in a related repository this reply fetched. Without a checkout, only a line inside the PR's diff counts. Manki posts the place, never the text of a related repository's line.
- **No line holds** a text, for a statement that something exists nowhere, such as "nothing calls `backup`". The model names the text to look for and Manki runs the search itself, as plain text of 3 to 200 characters on one line, ignoring case, in the PR's checkout or in one fetched related repository. When no line holds the text, the list names the text and the repository searched, and what the search did not cover: the `paths` a related repository is limited to, and how many binary files or files over 1 MB it left out. A longer name that contains the text counts as a line found.
- **The PR description holds** a text, **cited for it** or **cited against it**, for a statement about the description, such as "the description now names the limit". The model names 3 to 200 characters of the description, and Manki keeps the line only when the description holds that text, whitespace aside.
- **The PR description does not hold** a text, for a statement that the description no longer says something, such as "I took the cap out of the description". The model names the text and Manki searches the description itself, as plain text of 3 to 200 characters, ignoring case and reading each run of whitespace as one space.
- **Not checked**, with the reason: the review model says code cannot show it or could not read the code, no cited line was found in the code that was read, the run had no checkout to read a cited line or to search, the search term is not one line of 3 to 200 characters, the search found a line, failed or did not reach every file, the repository is not a configured related repository or was not fetched, the PR description does not hold the cited text, holds the text searched for, or could not be read.

Manki reads the PR's title and description from GitHub when it answers the reply, so an edit made just before the reply counts. The review model gets both in a fenced block, labelled as the PR author's untrusted text, and is told never to follow instructions in them. The model is shown the first 20,000 characters of the description, and Manki checks against all of it. Only the description is checked, never the title. What the model says about the description counts for nothing in the list: a line is listed as checked only by what Manki finds in the text it read. When GitHub does not return the PR, the reply is answered without the description, and a statement about it is listed as not checked.

Manki checks the list in code. A quote that is not in the developer's reply, whitespace aside, is dropped, and a long quote is cut with an ellipsis after that check. A reply with more than 5 statements gets the first 5 checked and the count of the rest.

The list never decides a thread. No statement's status is read by the code that resolves or clears one, so a reply with a cited line for every statement clears nothing for the PR author, and a blocker or security finding still needs a person with the role. The sentence below the list says what was checked. It is in the fold, unless the finding keeps blocking or its thread could not be read. Then it stays open and says that the decision is a maintainer's and that the thread stays open.

Four rules can turn an answer into Unverified, and nothing turns one into another outcome:

- **Withdrawn** needs a line of the PR's own repository that exists. Lines of a related repository alone never withdraw a finding, and neither does text of the PR description.
- **Fixed** needs a line that the PR added or changed since the thread was posted, in the thread's file or a file its finding cited. For a fix that only removes code, the line right before or after the removal counts. A cited range of more than 7 lines counts only when every line in it changed, since a wide range holds an unrelated change as easily as a fix. Manki compares the commit the thread was posted on with the PR head to find those lines, and shows that change to the model that answers. When a later review already found the thread not fixed, the comparison starts at that review's commit instead, so a change that review judged cannot show a fix. When a review record cannot be read, or the thread itself cannot be found on an open PR, no line counts. A reply such as "fixed in abc123" with no code change since then stays Unverified, and so does a Fixed that cites only a line the PR left alone since, a line of a related repository or text of the PR description. When the head no longer holds the thread's commit, as after a force push, or the comparison fails, no line counts. A change to a file `closed_paths` closes, or to a file the PR renamed out of one, is never shown to the model and never counts. When the PR's diff cannot be read while `closed_paths` is set, no line counts. So a finding about the PR description never gets Fixed, and a maintainer settles it. Such a Fixed opens with a bold line that says what happens next, instead of Unverified, then why no line counted, and the model's text follows. On an open thread tied to a file that `closed_paths` does not close, the line is "**Not settled yet: the next review after a push checks the fix.**", or "**Not settled yet: the next review checks the fix.**" when an open PR was rebased or force pushed since the finding was posted. On any other open blocker or security thread it says "**Not settled yet.**". On any other thread that is open, and on a resolved thread that still blocks or holds the approval, it says that a maintainer should decide. On a resolved thread that holds nothing it says "Not settled by this reply.". Why no line counted names the files in which a reply counts a fix, or says that the branch was rebased or force pushed since the finding was posted, that the change could not be read, or that the finding is tied to no file. On such a thread that is no blocker or security finding, and not rebased, it adds that the next review after a push checks the whole push. On an open blocker or security thread a note below says who closes the thread. Everything that reads the thread takes that answer as Unverified.
- **Fixed** on a blocker or security thread tied to no file that stays open. No review can confirm a fix there, so the answer says so, and that someone other than the PR author with write access has to close the thread.
- An answer that is not in the form Manki asks the model for.

Any other Unverified answer opens with a bold line too, followed by the reason when a check turned the answer into Unverified, and the model's text follows. On an open thread the line is "**Not settled yet: a maintainer should decide and resolve this thread.**". On a resolved thread that holds nothing it is "**Not settled by this reply.**", and when the thread still holds something or could not be read, as on a merged or closed PR, it is "**Not settled yet: a maintainer should decide.**".

### A fix in another pull request

A reply can say that another pull request of the same repository fixes a blocker or a security finding. Manki checks that claim and reports what it found in its answer. On any other finding it checks nothing and says so, since nothing reads the result there. The check never clears a thread: it resolves nothing and lifts no hold, whoever wrote the reply and whatever the check finds. The fix is not in this PR's own code, and the next round reviews that code, so the thread keeps blocking or holding exactly as before. Once the other pull request is merged, update this branch with the default branch. The next round then sees the fix in this PR's code and resolves the thread the usual way.

Only a fix merged into the repository's default branch counts, since the author of an open pull request can put any code there, and so can anyone who may push to the base branch of a stacked PR. Manki answers "**Confirmed: #N fixes this in `main`, not in this PR, so this thread stays as it is.**", with the sentence that #N, merged into `main`, replaced the cited line, only when all of this holds:

- The reply names the pull request as `#N` or by its URL. The review model only says which one the reply names, and a number the reply does not hold counts for nothing.
- This PR's base is the default branch, as the repository's settings name it. On a stacked PR the check never runs.
- It is another pull request of this repository, merged into the default branch.
- GitHub's merge of this PR into its base holds both this PR's head and that pull request's merge, and this PR's head does not hold that merge yet. A pull request merged before this PR branched is already in its code, so it cannot be what fixes it.
- It changes the finding's file or a file the finding cited, by GitHub's list of its files, under the name the file has on the base when this PR renamed it. A finding tied to no file or to no line never counts.
- GitHub's merge of this PR replaces the finding's line, compared with this PR's head, and keeps its file. That merge holds every change on the base since this PR branched, so the named pull request's own diff, as GitHub lists its files, must replace that same line at the place it has on the base. Manki works out that place from this PR's own diff. A thread on another file than its finding's, or one GitHub marks outdated, names the line on the commit it was posted on, so Manki maps it to this PR's head through what this PR changed since. When this PR has changed that line or renamed its file since then, or its head no longer holds that commit, the line at the head is not certain and nothing is confirmed. The lines that replace it in GitHub's merge of this PR must be exactly the lines the named pull request's diff puts there. Nothing else counts: a change on a nearby line, such as a guard added above the finding's line, a fix that only removes the line and puts nothing in its place, or a fix that another pull request made or changed again, confirms nothing. All of this is checked in code.
- A second model call with the same tools, 15 steps and 5 minutes reads a checkout of GitHub's merge of this PR. The message to the model holds the finding, the lines of that checkout that replaced the finding's line, and what the named pull request changes in the finding's files, numbered as in that pull request. It leaves out the pull request's title and description. The model's tools can still read the commit history of the checkout, and a commit subject there often repeats a title. It answers Fixed only with lines that exist in that checkout, and every line it cites must be one of the lines the named pull request put in place of the finding's line.

Anything less answers Unverified with the reason. When the reason can pass later, the answer says that Manki could not check the fix yet and when to reply again: once the pull request is merged, while it is open, or in a few minutes, when GitHub has not updated its merge of this PR yet, a lookup or the checkout failed, or the second model call failed or ran out of time. A new reply starts the check again. Any other reason says that a maintainer should decide, unless the thread is resolved and holds nothing. Such reasons include a number that is no pull request of the repository, a stacked PR, a pull request into another branch, a pull request closed without a merge, a check that finds the defect still there, a merge that deletes the finding's file, and a change GitHub does not show in full: a patch too large to show, a pull request with more files than GitHub lists, or a comparison past the 300 files GitHub lists. A reply run without repository tools confirms none and reads nothing from GitHub for it. Nor does one in a repository that sets `closed_paths`, so the check is off there: Manki reads no other pull request's merge and a maintainer decides, see [Security model](security.md). On a merged or closed PR nothing is checked, and the answer says that the PR is no longer open. The text of the reply only names the pull request to check. Who wrote it changes nothing about the check, and only an account with write access starts a reply run at all.

Manki's answer carries a hidden marker with the pull request and whether Manki confirmed the fix. When the PR author with a role that `author_clear_role` allows dismisses a blocker or security finding, the note that records the dismissal names that pull request and says whether Manki confirmed the fix. An approval lists such a finding with a confirmed fix under a heading of its own, with the pull request, apart from the other findings the PR author dismissed. Manki reads the marker only from its own latest answer that holds one, below the marker of its own reply, so text a person writes confirms nothing. Without such an answer, as when an account without write access made the claim and so started no check, the note names the other pull request that the latest reply naming one names, as `#N` or by this repository's PR URL, and says that Manki did not check whether it fixes the finding. Such a reply may only mention it, so the note never calls it the fix. Such a finding is listed with the other dismissed findings. A thread whose comments Manki could not all read names no claim, and its finding is listed with the other dismissed findings too. The claim changes only the note and the list: the dismissal stays the role's right.

A reply is one model call with 15 tool steps and 5 minutes, and a second one only to check a fix in another pull request. A reply without repository tools, or whose checkout failed, checks lines against the diff and searches no code. It still checks the PR description, which needs no checkout. The reply record stores each statement's status, its lines and the reason it was not checked, without the developer's words and without the search text. For a statement checked against the PR description it stores only whether the description held the text or lacked it, never the text. It also stores `modelAnswer`: the outcome the model gave before the checks, the lines of its proof that exist, and its first 10 proof entries as it wrote them, each with secrets removed and cut to 200 characters. Those entries are the model's text, so one can repeat words of the developer. Nothing decides on `modelAnswer`.

## Rules from instruction files

Manki reads the repository's instruction files from the PR's base branch only, so a PR cannot relax a rule for itself: the nearest `AGENTS.md` and `CLAUDE.md` above each changed file, the root `AGENTS.md`, `CLAUDE.md` and `.claude/CLAUDE.md`, the contributing guide, and the `.md` files these link to. Like GitHub, Manki reads one contributing guide: the first `CONTRIBUTING.md` it finds in `.github/`, the root and `docs/`, in that order. A PR that edits one of them is reviewed against the base branch's text, and the edit applies after merge.

The files are printed in that order, up to 30,000 characters in total. The file that crosses the limit is cut and the files after it are left out, so the review does not see their rules. The run then logs a warning that names the cut file. The round record lists the files the round read under `instructions.files` and the cut one under `instructions.cut`.

The finders use these files in two ways. They check each added line against the rules. They also go through the rules about the change as a whole: what a change must include, such as a test, a migration or a documentation update, and how it must be scoped. Example: a Django project's `CONTRIBUTING.md` says every model change needs a migration, and a PR adds a model field without one. For the change as a whole, only a rule stated as a requirement counts ("must", "needs", "never", "always"). Advice ("prefer", "try to", "consider") is not reported there. An `AGENTS.md` or `CLAUDE.md` in a subdirectory covers only changes under that directory.

A finding about a rule for the change as a whole names the instruction file and quotes the rule. Manki looks the quote up in the files it loaded, ignoring case, line wraps and Markdown emphasis, and marks the finding as a rule finding only when the named file holds it. A rule a finder read anywhere else, such as in the PR's own edit of an instruction file, gives no mark. A rule that holds a Markdown link or image matches when the finder quotes it as plain text. Manki keeps the text of a link in the quote and never its target, which is not compared with the file. The round record keeps the mark as `rule` on the finding, with the `file` and the `quote`, also on a finding the judge dropped.

The mark alone changes no grade. The judge first answers two questions about each marked finding, each in its own field of its reply: whether the quote states a requirement, and whether this PR breaks it. Advice, an example, a description of how the project works and a fragment that states no rule on its own are no requirement. When the rule requires a companion for something the PR newly defines, such as a documentation entry for a new flag, the list of changed files settles it: a file the PR leaves unchanged cannot cover what did not exist before. For a round with a rule finding, the list also names the changed files no model reads: the ones `exclude_paths` leaves out, and the ones with no text to read, such as a binary or a file that was only renamed. Past 200 such files the judge gets a count of the rest and treats each as one that could hold the companion. A break that rests on code the judge cannot see is not shown. That is a changed file it cannot read that could hold the companion, such as an excluded `docs/api.md`, or a file outside the diff that may already list a name the PR only uses. The judge then names, in a third field, the one fact that would make the rule broken. Manki works the answers into `rule.verdict` on the finding: `no_requirement`, `not_broken`, or `confirmed` when both answers are yes, the judge keeps the finding, and the finder or the judge cites a line that proves the break. The verdict is `unproven` when the judge names such a fact, kept as `rule.unseen`, or when both answers are yes but one of the other conditions is missing. A doubt the judge names about the damage, such as whether a rollback fails at run time, decides the grade the damage gives and not the verdict. Only a `confirmed` rule finding counts in the grade, and only with `review.rules` set to `warn` or `block`. Any other is graded by its damage alone, like a finding without a mark.

With `review.rules` set to `warn` or `block`, an `unproven` rule can still be confirmed in the same round, when the review has repository tools. The fact the judge could not see becomes a doubt of the finding, and the refuter checks it, for example whether `.env.example` lists a variable. Only its answer about that fact settles the rule. When the refuter confirms the fact, the rule is `confirmed` and the finding gets the grade `review.rules` sets, recorded as a `rule` step, whatever it answers about a doubt the judge has about the damage. When it disproves the fact with a line of the finding's own file or of the diff, the finding is dropped, also when the refuter confirms the defect, since that answer is about the damage. A disproof that cites only another file settles nothing, like any disproof, so PR text cannot point the refuter at a file that drops a finding. When the refuter cannot settle the fact, or two refuters disagree about it, the rule stays `unproven` and the finding never blocks. After that check the note keeps the fact under `rule.unseen` only, without the doubt and the grade the rule would have given. So no later step of the round, such as a memory suppression, and no later round takes them for a grade the damage earned. The next round's judge answers the rule again from its own questions. No other confirmed doubt stands in for the fact the judge named. The refuter's own answer that the defect does not exist confirms no rule either, since that answer can be about the rule. The fact is added as a doubt only to a finding graded a note, so a finding graded by its own damage is never dropped over a rule. The other way round, with either of these settings, no refuter disproof drops a finding whose rule the judge confirmed. The refuter checks whether a failure can happen, not whether a rule is followed, and the same rule break with no damage to check is posted unchecked. Such a finding stays at its grade and is recorded without the cell and the conditional grade that stated the damage, so a later round does not raise it from them. In the posted finding the check says that the finding stays because the rule break is confirmed, and that the check disagrees about the damage or the defect. The cost: when the judge wrongly confirms a rule, the warning is posted with the refuter's contrary reason next to it. With `auto` none of this applies. The fact the judge could not see becomes no doubt and gets no check, so the rule stays `unproven`. A confirmed rule finding that its damage makes a warning needs proof like any other warning, and a check that disproves that damage drops it.

[`review.rules`](configuration.md#reference) sets the grade of a confirmed rule finding. With `auto`, the default, the rule sets no grade: the finding is graded by the damage it can do, like any other finding. A broken style rule, such as one that asks for imports at the top of a module, is a note, and a rule break that can crash or corrupt data still earns a warning or a blocker on its own. The posted finding still names the rule. With `warn` it is at least a warning. With `block` it is a blocker, so the PR is not approved until the rule is followed. Example: a Flask project's `CONTRIBUTING.md` says every new endpoint must be listed in `docs/api.md`, and a PR adds a route without changing that file. The setting only raises a grade, so a finding whose damage already gives a higher one keeps it, and the step is recorded as `rule` in `gradePath`. A rule finding blocks only when all of this is certain: `review.rules: block` is set on the base branch, the named base-branch file holds the quote, and the judge confirmed both points or a refuter confirmed the fact the judge could not see. Like every blocker it also needs a search behind a claim that something is missing. Without one it is a warning that the refuter checks, since its check is the search the finding left out. A confirmation makes it a blocker. A disproof or a check that settles nothing leaves the warning. With `warn` no such check runs, and the warning is posted on the judge's rule verdict alone. With any setting, a confirmed rule finding that its own damage made a blocker is held at a warning in the same way, for want of a search or of a CI result for a claimed build failure, and only a confirmation gives the blocker back. The posted finding shows the rule with its checks: a line that names the instruction file and quotes the rule, and on a blocker the rule raised, that it blocks because the repository sets `review.rules: block`. With `warn` or `block`, a confirmed rule finding is proven by the rule's text and the cited change, so a warning of this kind is posted without a check that proves it. One the judge doubts is still checked, last among the eight checks for warnings, and that check only settles the status the warning shows. The refuter checks a blocker the rule raised like any other blocker and adds the proof it finds. Its disproof does not lower that blocker, since the refuter checks whether a failure can happen, not whether a rule is followed. So a rule blocker rests on the judge's two answers and the cited line, also when no refuter runs or its check settles nothing.

Manki proposes splitting a PR only when an instruction file requires focused changes, such as one concern per PR, and only when a finder with repository tools shows that a part is independent: the rest of the PR does not use the part, and the part does not use the rest. The finding quotes the rule, names the parts and lists what was searched. Without such a rule, or when the finder has no repository tools, no finder proposes a split or reports a change only for being unrelated to the PR's purpose. The scope reader asks whether a PR should be split on every round, as a judgment that never blocks. See [The scope of a PR](#the-scope-of-a-pr).

## Skipping PRs

`skip_labels`, `skip_authors` and `skip_branches` name PRs that get no automatic review, such as dependency bumps from a bot. Manki reads them from `.manki.yml` on the base branch only, so a PR that edits them cannot skip itself. A PR that matches any rule gets no review, no comment and no approval. Its `Manki` check completes as skipped. A `/manki review` comment still reviews it.

A skipped check passes a required status check, so a branch protection rule that requires `Manki` lets a skipped PR merge without a review. GitHub counts a neutral check as passed too, and the `Manki` check is neutral when Manki holds its approval, so also require an approving review (see [Branch protection](getting-started.md#branch-protection)). Use rules that only trusted actors can meet. GitHub sets the author, so `skip_authors` for bot accounts is the safest. It skips an event only when its sender is a listed author too, so a person who pushes to a bot's PR still gets a review. A label or branch rule matches only PRs whose head branch is in the repo itself, never a fork's. A fork's author can name a branch freely and keep pushing after a label is added, for example by a path-based labeler. Anyone with write access can still pick a matching branch name or add a skip label.

A PR that conflicts with its base gets no review at all, also on a `/manki review` comment. The token service posts one note, "This PR conflicts with `<base>`. Rebase it, and Manki reviews it then.", and completes the `Manki` check as "Rebase needed". The next skip edits that note instead of adding another, and Manki deletes it once a review posts after the rebase. A conflict that appears while a review runs still turns its approval into "Approval held".

## Reading CI results

Manki reads what your CI already reported on the PR head commit and gives the reviewers the results that sit on lines of the diff: check-run annotations (linters, type checkers, test reporters), open code scanning alerts, and vulnerable packages from the dependency review. The tool text reaches the reviewers fenced and marked as untrusted, and only for the lines they review. When a Manki note sits on the same file and line as a tool result, Manki drops it because the author already sees the tool's result. Warnings, blockers and security findings are always kept, because they can be a different problem on the same line. The drops are listed in the `Manki context` block.

Some tool results also go to the judge as candidate findings, next to the reviewers' findings:

- A vulnerable package, or a result whose tool or rule id names a security class (such as `security`, `injection`, `xss`, `format-string` or `secret`), always does.
- A style or formatting result never does, because the linter already shows it. Manki recognises these by rule id, such as `prettier/prettier`, `@stylistic/*`, `indent` or `max-len`. A result without a rule id is judged by its tool name, such as `rustfmt`.
- Any other code scanning alert does, and a check annotation only at the `failure` level.

The judge keeps a real defect at the grade it earns and refutes a false positive with a reason. A refuted result is never posted. A kept one is posted with the tool in its label, such as `⚠️ **Warning** (CodeQL)`.

Before the judge runs, Manki also checks each reviewer finding against the code, without running it: the file is in the diff, the line is in the file, and whether each symbol the finding names in backticks occurs in the file or the diff. Only a file outside the diff or a line past the end of the file contradicts a finding. A missing symbol is only noted, since it can live elsewhere. A claimed type or compile error is confirmed by a failing annotation near the line from a type checker or compiler, such as `tsc`, `mypy` or `rustc`. A lint error there does not confirm it. The judge sees the result as confirmed, contradicted or unchecked. Only the judge can drop a contradicted finding, and a tool that says nothing never lowers or drops a finding. Each finding in the `Manki context` block records `toolEvidence` as `confirmed`, `contradicted` or `none`.

Manki reads these results with the workflow token (`github_token`), so grant the permissions in the workflow, even when the Manki app posts the review:

| Permission | Source |
|------------|--------|
| `checks: read` | Check-run annotations |
| `security-events: read` | Code scanning alerts (needs code scanning, and GitHub Advanced Security on private repositories) |
| `contents: read` | Dependency review (needs the dependency graph, and GitHub Advanced Security on private repositories) |

A source Manki cannot read is skipped with one info line in the log. Turn a source off with `static_analysis` in `.manki.yml` (see [Configuration](configuration.md)). Manki reads that block from the base branch, so a PR cannot turn off the tool that would flag it.

Manki only sees checks that finished before it runs. Manki runs in its own workflow, so `needs:` cannot order it after your CI. List the check runs to wait for in `static_analysis.wait_for_checks` instead. Manki polls them on the PR head every 15 seconds and reads the results once each has finished. After 300 seconds it stops waiting, reads what is there, and records the checks still running in the `Manki context` block. The last poll starts at that limit and may take up to 11 seconds more. If it does not answer in that time, the wait still ends as timed out: the record holds the checks the last answered poll saw running, or every listed check when no poll was answered. A poll that fails or meets a GitHub rate limit ends the wait early with a warning, and Manki reads what is there. A name is the check run's name as the PR's checks list shows it, usually the job name.

```yaml
static_analysis:
  wait_for_checks: [lint, CodeQL]
```

## Running Manki's analyzers

Manki can run analyzers itself. `actionlint`, `zizmor` and `shellcheck` are on by default, but each runs only when a file it checks changes, and only when CI does not run the same tool already. Manki's Rust rules for `ast_grep` are on by default in a Cargo repository (see below). The others are off by default, for a repository without CI checks. Turn them on or off in `.manki.yml` on the base branch:

```yaml
static_analysis:
  analyzers:
    ast_grep: true
    secrets: true
    dependencies: true
    semgrep:
      rules: [.semgrep/manki.yml]
    shellcheck: false
```

`analyzers: all` turns on every analyzer that needs no rules from you, including ones later releases add. Semgrep only runs when you list rule files.

| Analyzer | Tool | What it checks |
|----------|------|----------------|
| `ast_grep` | [ast-grep](https://ast-grep.github.io) 0.51.1 | Manki's own rules in [`rules/ast-grep`](../rules/ast-grep) (MIT licensed): code and shell injection, HTML sinks, disabled TLS checks and unsafe deserialization, plus error-prone patterns such as an async `forEach` callback, a comparison with `NaN` or a mutable default argument. Runs on the changed JavaScript, TypeScript and Python files. The Rust rules also run on a changed Rust file that has a `Cargo.toml` in its directory or one above it on the base branch, even without `ast_grep: true`: a narrowing `as` cast of a length, count or index, `unwrap` or `expect` on decoded input, `with_capacity` sized by a decoded length, a new `unsafe` block, and `==` on secret bytes. They report hints on added lines only, skip tests, benchmarks, examples and build scripts, and stop with `ast_grep: false`. |
| `secrets` | [gitleaks](https://github.com/gitleaks/gitleaks) 8.30.1 | Secrets on the lines the PR adds in any changed file, with gitleaks' default rules through Manki's [`rules/gitleaks.toml`](../rules/gitleaks.toml). `gitleaks:allow` comments are ignored. |
| `dependencies` | [OSV-Scanner](https://github.com/google/osv-scanner) 2.7.0 | Known vulnerabilities in the packages of the changed lockfiles, such as `package-lock.json`, `pnpm-lock.yaml`, `go.mod` or `requirements.txt`, with Manki's [`rules/osv-scanner.toml`](../rules/osv-scanner.toml). A result sits on the line that adds the package. |
| `semgrep` | [Opengrep](https://github.com/opengrep/opengrep) 1.33.1 | Your Semgrep rules on the changed files. List rule files in the repository, read from the base branch. Manki ships no Semgrep rules and never fetches registry rules such as `p/default`. `nosemgrep` comments are ignored. |
| `actionlint` | [actionlint](https://github.com/rhysd/actionlint) 1.7.12 | Mistakes in the changed workflow files under `.github/workflows`, such as invalid syntax, expression type errors or untrusted input in a `run` script. Uses `.github/actionlint.yaml` from the base branch when there is one, so self-hosted runner labels are known. Its shellcheck and pyflakes checks stay off. |
| `zizmor` | [zizmor](https://github.com/zizmorcore/zizmor) 1.32.0 | Security problems in the changed workflow files, such as template injection, dangerous triggers or excessive permissions. Runs offline, without the repository's zizmor config, and ignores `zizmor: ignore` comments. |
| `shellcheck` | [ShellCheck](https://github.com/koalaman/shellcheck) 0.11.0 | Bugs in the changed shell scripts: `.sh` and `.bash` files, and files without an extension, that start with a `sh`, `bash`, `dash` or `ksh` shebang. A `.sh` or `.bash` file without a shebang counts too. Reports down to `info`, without the repository's `.shellcheckrc`. |

The analyzers never run code from the PR. Manki reads the changed files through the API at the head commit and gives the tools the files, never a checkout. It never uses rules or config from the PR: each tool gets Manki's config or the rule files from the base branch, and the files a tool would read as its own config or ignore list, such as `.gitleaksignore` or `.semgrepignore`, are left out of what it scans. The tools run without the action's environment, so they never see a token.

Manki downloads each tool at the pinned version, checks it against its pinned digest (SHA-512 for the ast-grep packages from npm, SHA-256 for the release binaries), and caches it for the run. The ast-grep native module and its Go, Python and Rust grammars load in process. ncc can only bundle the native module for the platform that builds `dist/`, so they load at run time. Builds are pinned for Linux and macOS (x64 and arm64) and Windows (x64). A download that fails or delivers no data for 20 seconds is tried again, three times at most. If it still fails, the platform has no pinned build or a tool fails, that analyzer is skipped with a warning and the review goes on.

A self-hosted runner also keeps each download for later runs, in the `manki-pinned` folder of its tool cache (`RUNNER_TOOL_CACHE`). A later run checks the kept file against the pinned digest and unpacks it again, so it downloads nothing. This holds for the Claude CLI too, which Manki downloads the same way. [Security](security.md) says what is checked.

`exclude_paths` keeps files away from the reviewers, and `ast_grep` and `semgrep` follow it. A file `closed_paths` closes is left out like an excluded one, and no analyzer checks it either, see [Security model](security.md). `dependencies` checks every lockfile the PR changes, including the ones the default `exclude_paths` names, such as `yarn.lock` or `Cargo.lock`, within 10 MB per lockfile and 40 MB in all. `secrets` checks every changed file, since a PR can add its own `exclude_paths`, and for the same reason `actionlint`, `zizmor` and `shellcheck` check every changed workflow or shell script. A result on an excluded file has no inline thread. A blocker or a warning there gets its thread on the first file the reviewers read, unless the warning is pre-existing, and every other result is listed in the review body. A PR whose every changed file is excluded, closed or has no code to read is never approved. No code to read means a binary, a rename, a mode change, an empty file, a file whose diff GitHub does not show because it is too large, a Git LFS pointer, whose lines only name the content by hash, or a submodule bump, whose line only names a commit. Manki posts a comment that lists each skipped file and why, with what the analyzers found on them, and the `Manki` check waits for a person. When the PR also changes files the models read, a clean round still holds its approval: Manki posts its review as a comment that lists the skipped files, the `Manki` check reports the approval held, and a person approves. Auto-approve after the last blocking thread is resolved never gives that approval either. A deleted binary leaves nothing unread, so in a PR that also changes files the models read it holds no approval. A PR that only deletes binaries is still not reviewed: Manki posts the comment that lists them, and the `Manki` check waits for a person. A deleted Git LFS pointer or submodule is not skipped, since the models read its removed lines like those of any other deleted file.

Manki reads a changed `Cargo.lock`, `package-lock.json` (or `npm-shrinkwrap.json`) from npm 7 on, `yarn.lock` from Yarn 1 or later, or `pnpm-lock.yaml` into a package list, whatever `exclude_paths` says: each package the PR adds, with its source and fields, each package it removes, and each package it updates, with its old and new version and the changes to its source, checksum and other fields. The legacy `dependencies` map of a version 2 `package-lock.json`, which only npm 6 installs from, must name the same artifacts as its `packages` map, and the list then leaves it out. The finders, the judge and the verdict reader read that list, and the judge reads it in place of the lockfile's hunks. A local review and the benchmark read lockfiles the same way. The planner and the review groups count the lockfile as changed, so a lockfile change gets two finders on the supply chain floor. Such a lockfile holds no approval, and a PR that only bumps a lockfile can be approved. Manki adds a `lockfile-change` alert, which the judge triages like any tool result, for a package whose source moved to another registry or repository, an added one from a registry the lockfile did not use before (in a new lockfile, from another registry than most of its packages), one that comes from a git repository or a path, one whose checksum changed without a version change, one that moved to a lower version, and one whose tarball URL names another package or version. Manki reads the lockfile at the PR head and undoes the diff to get the version before it. A lockfile it cannot read or parse, one whose diff does not match the file, one in another format such as `poetry.lock`, or one past 100,000 characters of package lists in all, stays unread and holds the approval as before.

Analyzer results follow the path of the CI results above, limited to lines of the diff. `actionlint`, `zizmor` and `shellcheck` keep only results on the lines the PR adds or changes, so a problem the PR did not touch is never raised.

Manki also looks for hidden characters on the lines the PR adds in any changed file, whatever `static_analysis` or `exclude_paths` says: control characters other than tab and newline, format characters such as zero-width spaces and bidi controls, the line and paragraph separators U+2028 and U+2029, the invisible Hangul filler letters, and variation selectors other than U+FE0F, the one that follows most emoji. A file that adds any gets one `hidden-characters` alert from Manki at the first such line. A bidi embedding, override or isolate, which can make code display differently than it runs, makes the alert an error. Any other hidden character makes it a warning. A suggested fix that holds a hidden character is never offered as a `suggestion` block, and no text a model wrote can open a `suggestion` block. Manki rebuilds every code block in that text with its own fence, which nothing inside can close, keeps a plain language name at most, and escapes any other run of three backticks or tildes.

Manki skips `actionlint`, `zizmor` or `shellcheck` when CI already runs it: when a workflow on the base branch names the tool outside a comment line, or a check run on the base branch's head commit has the tool's name in its name. The PR can change neither, so a job it adds cannot turn a tool off. The `Manki context` block records the skip. Since no CI shows them to the author, every result goes to the judge as a candidate finding, and a reviewer finding on the same line is never dropped for it. A result the judge keeps is posted with the tool in its label, such as `⚠️ **Warning** (shellcheck)`. A clean run posts nothing. The `Manki context` block records each analyzer that had a file to check under `staticAnalysis.analyzers`, with how many results it found or why it was skipped.

## Uses outside the diff

When the PR head is checked out for the repository tools, Manki lists where the code the PR changes is used elsewhere, before any finder runs. It takes the changed types, struct fields, enum variants, functions, constants and config keys from the hunks: through ast-grep for Rust, TypeScript, JavaScript, Python and Go, and from keyword declarations (`func`, `class`, `struct` and similar) and config keys with an underscore in other files. When a type's body changes, its other fields and variants are searched too, after the changed symbols. The search takes at most 80 changed symbols, 20 fields the changed lines read and 8 fields they look an item up in, and lists at most 6 types. When it does not search every changed symbol, because there are more than 80 or because a name is too common, too short or too long to search for, the section says how many of how many it searched. The types list shows at most 3 types per read field, the likeliest first, and none for a field that more than 6 types declare. A list that was cut says how many of the types found it shows, how many of the read fields it looked up, and for how many read fields it lists no type, so it never reads as complete. The log names each limit on size (80 symbols, 20 read fields, 8 looked-up fields, 6 types) that a change went past. Manki searches the head commit for each name as a whole word, outside the changed lines and `exclude_paths`. Code comes first, then comments, then documents. Within each, a package that depends on the changed one comes first, then other files of the same package, then the same file, and last a package that does not depend on it, which can only hold a namesake. A package whose manifest is not read, because it is larger than 1 MB or resolves outside the checkout, counts as one that may depend on it, and the log says why it was not read. One round reads and searches at most 64 MB of manifest text, and a package past that counts the same way. Each symbol shows at most 4 uses and the list at most 60, and the section says how many it left out. Among a symbol's code uses in packages that can reach it, production code comes first, then lines that only call `.name()`, then test files. Within each, one file shows at most 3 while another file still has one to show. A name as common as `new`, `len` or `from`, shorter than 4 characters or longer than 160, is not searched at all. The names are searched together in one pattern of at most 15 KB, which fits the command line of every platform Manki runs on. A name that no longer fits it is not searched, and the section names it as not searched. A name with more than 80 uses is named but not listed, except a field or variant that existed before the PR and whose own lines the diff changes, such as its type, even on a line after its name, or its doc: its readers are what the change can break, so they are listed however many there are, up to 12, and its uses outside test files take their place before other symbols' uses fill the 60 lines, up to 30 shared in turn by all redefined fields, so changed functions and types keep room however many fields a PR redefines. Among each file's first 3 uses, and again among the rest, its uses in files that also name its type come first, and uses in files that never name it come last, since they likely read a field of the same name on another type. Within those, a read of the field as `.name` comes before other code that names it, such as a struct literal. The note on the uses left out says how many of them are in files that name the type. A new field has no readers yet, so its matches are namesakes and the cutoff applies. A line that only declares a field of the same name on another type, or reads it as `self.name`, `this.name` or through a Go receiver in a method of such a type, is likely a field of the same name on another type, so it ranks after every other use of the symbol. It is never left out, since the guess can be wrong, and it counts in the uses not shown when the list is full. A function inside that method that binds the name again reads another value, so its reads rank as usual: a TypeScript `function`, object literal method or class, or a nested Python function or Go func literal with a parameter of that name. A method whose body binds the name again in a statement, such as Go `for _, v := range` or a `select` case, or a Python assignment to `self`, ranks all its reads as usual. A field of the same name that the diff also changes on another type is no namesake. A type that may derive from the changed type counts as that type: a subclass, an interface that extends it or a TypeScript type alias that names it, directly or through other types the same file declares, and a type with a base declared in another file or named through a module, such as `other.Base`. A read Manki cannot place on a type, such as `x.name` on a local, ranks as usual. The list also shows the types whose fields the changed lines read or change, each with all its fields, so the finders see state kept next to the field the PR touches.

The finders, the judge and the refuter all get the list, in two copies that differ in which uses they show and in what order. The order above is the one the judge and the refuter get, so a finding that cites a line of their copy rests on code the judge can see. A line that only the finders' copy lists reaches the judge only when its model has repository tools: Manki then shows the cited code under the finding. A judge without repository tools grades such a finding as one that rests on code it cannot see.

The finders get a copy made for a reader who opens files. The same limits apply, but each symbol shows the best use of each file before a second use of any file, test files included, so its uses point at as many files as the limits allow. Uses in generated code, test doubles and vendored code come after those of every other file. Manki tells such a file by its path, such as a `gen/`, `mocks/` or `vendor/` directory or a name like `schema.generated.ts`, `store_mock.go` or `app.min.js`, and by the header a generator writes in a comment line within the first 2 KB of the file, such as `// Code generated by protoc-gen-go. DO NOT EDIT.` or `@generated`. It reads the start of at most 2000 files of a checkout for that header, and past them only the path counts. A namesake still comes after every other line of the symbol. Among the lines of the other files, and again among those of generated code, test doubles and vendored code, a line that likely is no use of the symbol comes after every line that is: a mention in a comment or a document, a line in a package that does not depend on the changed one, and for a field a line that only calls `.name()` or a file that never names its type. So a use in generated code, a test double or vendored code comes after a mention in a comment or a document of another file. Every finder gets this copy, the quick check of a trivial PR included. For a finder with repository tools, the copy also says to open the file of each use in a file the PR does not change before it answers, up to 5 files. That finder reads the same where its tools are described, in place of the general advice to follow every path the change affects, which its instructions already give. Two readers get the copy without that sentence: a finder without repository tools, which can open none, and the quick check, whose 8 tool steps are too few.

The round record keeps the finders' copy as `usesOutsideDiff`: the location of each use shown, each type with its fields, and the names left out, with those that were not searched as `unsearched`, without the quoted code, so a missed defect can be traced to what the finders were shown. Building it takes seconds and calls no model. Without a checkout, or when the search fails, the review runs without it and the log says why. A failed search also leaves its reason in the round record as `usesOutsideDiff.failed`, such as a search that took longer than 30 seconds or found more than 64 MB of matching lines, so it can be told from a change with nothing to list.

A finder that opens nothing outside the diff is asked once more: its answer came without opening any file that this list or the "In the Reference Repos" section of a [related repository](#related-repositories) names outside the PR's changed files. A changed file never counts, since the finder already has it in its message, so a PR whose listed uses all sit in its changed files names nothing and no finder is asked again. A file counts as opened however the call spelled its path, such as `./src/a.ts`. The second ask is the same call with a note that names up to 8 of those files, the uses before the reference lines, and asks the finder to open them and answer again with its full list of findings. The second answer replaces the first, unless the same ask also names units of the change without a line (see [Units of the change](#units-of-the-change)): then it asks only for the findings it adds, and the first findings stay. A finder that reads a large diff in slices counts the files of all its slices together. When none of them opened a listed file, it is asked about them once, in the call on the slice that holds the most of the changed names those files use, by the file that declares a name or a changed line that names it. Its note names the files that use the names of that slice first. When no slice holds any of them, it is not asked again. That call asks only for the findings it adds, and the findings of the slices stay next to them. A finding it repeats reaches the judge as one more copy from the same finder, which the judge folds like any duplicate. When the second ask fails or its reply cannot be used, the first answer stays and the round does not end incomplete because of it. A finder is asked again at most once a round, and about the files only when Manki knows which files it read, which the Claude and Codex CLIs report. The trivial verifier is never asked again. A finder without repository tools is never asked again about the files, and neither is a sliced finder when a slice's call does not report what it read. The round record sets `askedAgain` on the finder's entry in `reviewers.agentMetrics`, and its `warnings` keep why a second ask failed.

## Units of the change

From the same parse as the uses outside the diff, Manki splits the change into units before any finder runs, and each finder answers for every unit in a line of its own. A unit is a function the change touches, as the uses outside the diff name them, or a run of changed lines that adds, changes or removes a condition. A condition is a line whose code opens a branch, loop, guard or assertion: `if`, `elif`, `elsif`, `elseif`, `else if`, `while`, `until`, `unless`, `guard`, `assert` or a workflow's `if:` key, or joins checks with `&&` or `||` between two operands. Python's and Ruby's `and` and `or` are not counted, since the words also appear in prose and strings. A reference type such as `&&str` or a closure such as `|| {` joins no checks. A `for`, `switch`, `case`, `when` or `match` line is no condition unit, so such a loop or branch is answered for through the unit of its function. Changed condition lines next to each other are one unit, which shows at most 6 of them. A changed condition shows the lines it replaced, and a condition the change only removes is a unit at the line where it was. A file the PR deletes adds a unit for each stretch of condition lines it removes, at its lines in the base. Test files, test functions, documents, generated code, test doubles, vendored code and `exclude_paths` add no unit, and neither does a comment. Generated code is told as for the uses outside the diff. The changed files that can add a unit or a piece of structure are read for a generator's header within a budget of 2000 files of their own, so a large change never uses up the reads that rank the uses. A round lists at most 100 units, in diff order. Code picks the units, so a finder cannot choose which parts of the change it skips, and a skipped one shows in the round record.

The finder's message lists the units right before the diff. Next to its findings, in the same JSON array, the finder gives one line per unit: `{"unit": "U1", "checked": "...", "defect": "..."}`. For a function it says which paths through the changed lines it followed. For a condition it names the input or state that passes it but should not, and what happens when a command or call the condition relies on fails, returns nothing or returns an error. `defect` is the title of its finding there, or `none`. A unit line is never posted, only findings are, and the message says that a line without a defect is a full answer. A line counts only when it says what was checked. An element with a string `unit` and no `title` is a unit line, whatever else it holds. An element with a `title` is a finding, so a malformed finding fails the reply as it would without units.

One call answers for at most 20 units. When a change has no more, every finder answers for all of them. Past 20, the units are dealt out between the finders in turns, so each unit goes to one finder, and the units past 20 per finder are left out. Every finder still reads the whole diff and can report a defect anywhere in it, and the units add no call of their own: a finder answers in the calls it makes anyway, and only a finder that leaves a unit without a line is asked once more. A finder that reads a large diff in slices answers for a unit in the call on the first slice whose hunks hold one of the unit's lines, since a large file can be split between slices, with the same cap per call. A condition of a deleted file, or one the change only removes, is placed by its lines in the base. The quick check of a trivial change answers for none.

A finder whose answer gives a unit no line is asked once more. That is the same second ask as the one for unopened files under [Uses outside the diff](#uses-outside-the-diff), so a finder is still asked again at most once a round. The second ask is the same message with a note that names the units without a line, and it asks for a line for each of them and only the findings the finder adds. The first answer's findings stay. A sliced finder is asked in one call on each slice that holds a unit without a line, and on the slice the unopened files pick, and each note names only the units of its slice. A unit that still has no line is recorded as not covered. When the second ask fails, the first answer stays.

The round record lists the units under `units.listed`, each with its `id`, its `kind` (`function` or `condition`), its location as `at`, a function's `name`, `deleted` on a condition of a deleted file, and `cut` on a unit no finder was asked about. `units.overLimit` counts the units past 100. Each finder's entry in `reviewers.agentMetrics` holds its line for each unit it was asked about under `units`, with what it `checked` and the `defect` it named, each cut to 200 characters. A unit without `checked` was not covered. A finder kept from the last attempt keeps its lines. `askedAgain` is set when the finder was asked once more for either reason. The benchmark report prints how many units each finder left uncovered. A record too large even compressed leaves out `units` and each finder's `units` along with the other per-finding diagnostics, and `meta.omitted` names them.

## Sibling comparisons

Two kinds of defect hide next to the change rather than in it, and a finder that sees the clue can still miss the comparison. So Manki asks the comparison itself, from the same parse that builds the uses outside the diff, in one small call per question:

- **Sibling fields**: when a changed line looks an item up in a collection field, such as `queue.pending.get(id)` in Rust or TypeScript, `id in self.pending` or `self.pending[id]` in Python, or `q.pending[id]` or `delete(q.pending, id)` in Go, each other collection field of the same type that shares the item's type gets the question "The change looks up `id` in `pending`. Can `id` be held in `cancelled` instead? If so, does the change handle it?", with the type's definition and the changed hunks. A field of the same type comes first, then one with the same key type, then one sharing any element type. A fixed-size array such as `[u8; 32]` or `[32]byte` is a value, not a collection, so it gets no question. A Python field is one assigned in the class body or on `self` in `__init__`. Without a type annotation, its type is the kind of its first value, such as `dict` for `{}`, so it is compared only with a field of the same kind.
- **Sibling implementations**: when the change touches a function that sibling types also declare, such as the same trait method in two `impl` blocks, a method of the same name on two classes, or one on two Go types, in the changed files or the other files of their directories, up to 4 of them go side by side with "List every check, guard, version test, bound, error or event one has and another lacks." Functions that read the same are not asked about. A round compares at most 2 MB of function text, and functions past that count as different. Methods every type has, such as Python's `__init__` and other dunder methods, TypeScript's `constructor` or `toString`, Go's `String` or `Error` and a Rust `new`, are compared only between classes that share a base class or interface, together with the base class's own one, and implementations of standard Rust traits such as `Display`, `Debug`, `Clone`, `Default`, `From` or `PartialEq` are not compared, since unrelated types each have their own. Groups where the change touches more of the functions come first, then trait methods, then more changed lines, then more functions. A group whose functions all sit in one group already asked, such as two subclasses that share two bases, is not asked again.

Each call runs on the model of the group's first reader at the finders' effort, at the same time as the finders, and with repository tools when the finders have them, at most 12 steps. A round asks at most 6 questions of each kind, and cuts the lowest ranked first. The findings go through dedup and the judge like any finder's, named after their question, such as `Sibling field: pending vs cancelled`. Each call follows the finders' rules for a claim that something is missing, which needs the search that came back empty, and for a defect in code the PR did not change, which is marked pre-existing. A question whose call fails goes unanswered, and the round still completes, since the finders read the whole change. Once the finders are done, the round waits at most one more minute for the comparisons, then stops the calls still running. The round record lists each question under `comparisons`, with where it points, whether it was answered, failed, cut by the cap or timed out, and how many findings it gave, and `usage.llmCalls` records each call under the `compare` stage.

## Patterns of the codebase

A review of a feature or a refactoring asks a question a bug hunt does not: does the new code fit how this repository already does the same kind of thing? Manki asks it only about the structure a change adds, and keeps only a difference the code shows, never what a model would prefer.

**What counts as added structure.** From the same parse that builds the uses outside the diff, Manki lists each file the PR adds, and each type, function, error kind and config key declared on an added line of a file that already existed. An error kind is a type, or an enum variant of a type, whose name ends in `Error`, `Exception`, `Err`, `Failure` or `Fault`. A function also counts when a constant's value starts as one, such as `export const load = async () => {`, but not `const ids = items.map(i => i.id)`. A name declared on a line the diff removes, in any file, is left out, since that piece was moved or renamed, not added. The removed lines are read the same way as the added ones: with the grammar on the base version of the file, so a method declared without a keyword counts too, and by keyword in a language without a grammar. Up to 40 base versions are parsed, with a budget of their own, so they never take a parse from the uses outside the diff. Only files that can add pieces spend it, and a file past it is never read: the removed lines of the rest are read by keyword. Those include the files `exclude_paths` leaves out, so a piece moved out of a generated file is not new either. A piece renamed to a new name is listed as new, since only its name tells a moved piece apart. In a language Manki has no grammar for, a declaration runs over the added lines below it that are indented deeper, and a closing line at its own indent, such as `}` or `end`. A type there whose body the PR does not add is left out, since its header alone shows no structure. Test code, docs, generated, vendored and mock files, and paths in `exclude_paths`, add nothing. A piece inside a larger one, such as a method of a new class or anything declared in a new file, is part of it. The PR type does not matter: a fix that adds a module gets the check, and a feature that only edits lines gets none. The pieces are listed largest first, by the lines the PR adds to each, at most 20.

**The check.** Each piece gets one call on the model of the group's first reader at the finders' effort, at the same time as the finders, with read-only repository tools and at most 12 steps. The call sees the piece's added lines and the paths of the repository's instruction files. It searches the repository for at least two existing places that do the same kind of thing, says what they have in common (where the code lives and which layer calls which, how errors are returned, how state is held, and how the piece is wired up, named and tested), and compares the new code with that. It answers `follows`, `differs_with_reason` when the code states why it differs, `differs`, or `no_comparable` when it found fewer than two such places. One existing example is not a pattern.

**What makes a finding.** Only a `differs` answer reports findings, and Manki keeps one only when both hold:

- Its `proof` cites at least two existing places, lines that exist in the head commit and that the PR does not add in any file it changes, the files `exclude_paths` leaves out included, or it quotes a rule that one of the repository's instruction files holds (see [Rules from instruction files](#rules-from-instruction-files)).
- It sits on a line the PR adds.

Places are compared by their path from the repository root, so `./src/a.ts:2` and `src/a.ts:2` are one place, and places in one file whose lines overlap count once. A kept finding's `proof` holds only those existing places and its own line.

So a change that moves the existing places over to a new pattern on purpose gives no finding, since those places are then lines the PR adds. A finding says what the difference costs in practice, such as a caller that now has two ways to do one thing, a check the shared path has and the new one lacks, or a layer that now reaches into another, and that cost ends its description. A finding that names no cost reaches the judge as a note. That is only its finder's grade: the judge sets the final grade from the severity table, like any finding's. The findings go through dedup and the judge like any finder's, named `Pattern check:` and the piece's name, such as `Pattern check: RefundHandler`, or its file name for a new file. Nothing about these calls changes how a finding is graded.

A round checks at most 4 pieces, the largest first. A call without repository tools could not search the repository, so it is not made, and the quick check of a trivial change makes none. Once the finders are done, these calls get the same grace of one minute as the comparisons. The round record lists each piece under `comparisons` with the kind `pattern`: the reviewer name, the piece's first line, whether it was answered, failed, cut by the cap, timed out or skipped, the `answer`, the existing places the call read (`places`), how many findings it gave and how many it dropped (`dropped`). `usage.llmCalls` records each call under the `pattern_check` stage.

## Claims of the PR text

A PR often says why it is safe: "the upload service already rejects files over 10 MB", "every caller passes a sorted list", "no behaviour change for existing configs". A reader that has taken in a well argued description tends to review the diff through it, and the code that would test the statement is never opened. So Manki checks such statements itself, each in a call that never reads the description, so only code can argue for the statement.

**Listing the claims.** While the planner runs, one call to the `dedup` model reads the PR title and description, cut to 20,000 characters, and the comments on added lines, at most 200 lines of 300 characters. It lists the statements the change relies on: that something is safe, cannot happen, is already checked elsewhere, is always done by callers, behaves as before, or is guaranteed by other code. What the change does, why it was written and how it was tested are no claims. The call takes at most 45 seconds and shows in `usage` as the `claims` stage. A PR without a title, description or added comment gets no such call.

Manki keeps a statement only when the PR text holds it word for word, whatever its case, markup and line breaks, so the model cannot add a statement of its own. A quote is cut to 300 characters, and one under 20 is dropped. A round checks the first 5 statements listed and counts the others.

**Checking a claim.** Each claim gets one call on the model of the group's first reader at the finders' effort, at the same time as the finders, with read-only repository tools and at most 12 steps, 4 calls at a time. The call sees the statement, where the author wrote it and the diff. It answers `proven`, `disproven` or `unchecked`, and reports a defect only for a statement the code disproves. Manki keeps `proven` and `disproven` only with a cited `file:line` that exists in the head commit, or a cited line of a [related repository](#related-repositories) the round fetched, and keeps a defect only from a check whose `disproven` stands. A claim check reads the related repositories with the same tools, so a statement about another component, such as "the ledger service already rounds every amount", is checked in that component's code. A line of a related repository alone can decide either answer, since neither lifts a finding: `proven` is only recorded, and `disproven` reports a defect that the judge and the refuter then check like any other. Every other answer is `unchecked`. The defects go through dedup, the judge and the refuter like any finder's, named `Claim check 1`, `Claim check 2` and so on, and their grade is the severity table cell of the damage. A false statement in a code comment that breaks nothing is a note, and one in the description alone is no finding.

**Lines to start from.** When [related repositories](#related-repositories) are configured and the model of the group's first reader has repository tools, each check also gets lines of them to start from. One more call to the `dedup` model, made beside the one that guesses names for the related repository search, reads the claims and each repository's kind and most common file types. It names, for each claim and repository, the identifiers that code most likely uses where it does what the claim says: at most 3, each a single identifier. Every kind of repository is searched for them, `dependency` too, and they are matched like guessed names. A term that more than 20 lines hold is too common to point anywhere and shows none. A term shows at most 3 lines, a declaration in the repository's own code first, and the claims of a round share at most 15 lines, which they take in turns. A check is shown only the lines of its own claim, after the diff, in a fence and labelled as a word search that proves nothing. No other call sees them, and a claim never points a finder to a repository's guide. A round with a claim fetches its related repositories even when the diff's names start no search. The call takes at most 45 seconds and shows in `usage` as the `claim_terms` stage. When it fails or its reply cannot be used, the checks start without lines and the round goes on. The checks wait for their lines at most 30 seconds, and never past their own deadline, one minute after the finders are done. A fetch, term call or search still running then is recorded as skipped, with the step that was running, and the checks start without lines. No such call is made when the quick check alone reads the change.

**What a claim cannot do.** A claim can add a check and never remove, shorten or soften one:

- The finders, the sibling comparisons, the judge, the refuter and the verdict reader get the same input whatever the PR text claims and whatever the checks answer, with two exceptions. The defect a check reports for a statement it disproved joins the findings, and is graded like a finder's. And a claim fetches the related repositories, so for a finding that cites a line of one, the judge's window and the note on the citation show the fetched code where a round without a claim says the repository was not fetched. That is the repository's own code, never the author's text. The checks have their own calls and their own step budget.
- `proven` is written to the round record only. No stage is shown it and no grade depends on it, so a statement the check believed hides nothing.
- A statement no check settled is no defect. It is recorded as `unchecked`, and nothing is posted for it. That holds for a check that fails, runs out of steps, or is still running one minute after the finders are done, when the round stops it. The round still completes.
- A statement is shown to its check inside a fenced block and labelled as the author's untrusted text. One that names a file to skip or tells the model what to answer is checked like any other, against the whole diff and the whole repository.

No check runs when the quick check alone reads the change, or when the model of the group's first reader has no repository tools or the PR head is not checked out. A trivial PR that a deeper review or `review.routing` gives finders gets its checks. The claims are then recorded as `unchecked`.

The round record lists the claims under `prClaims.claims`: the quote, its `source` (`description` or the `file:line` of the comment), the reviewer name, the `status`, the check's reason and cited lines (`proof`, and `relatedProof` for lines of a related repository), the number of defects it reported, and `call` when the check gave no answer (`failed`, `timed_out` or `skipped`). `prClaims.cut` counts the statements over the cap, and `prClaims.skipped` says why none was listed when the listing call failed. `usage.llmCalls` records each check under the `claim_check` stage. `usesOutsideDiff.claimTerms.terms` lists each term searched for the claims: the position of its claim in `prClaims.claims`, the repository, the term, how many lines hold it, how many of them its check was shown, and `notShown` when it showed none because it is too short or too generic to search for (`unsearchable`), too many lines hold it (`common`) or its search failed (`failed`). A term with fewer lines shown than found was cut by a cap. `usesOutsideDiff.claimTerms.cut` counts the terms the call gave past 3 for a claim and repository, which were not searched. `usesOutsideDiff.claimTerms.skipped` says why no term was guessed or searched. When the checks stopped waiting for their lines, it names the step still running, the fetch of the related repos, the term call or the search, and whether it took longer than 30 seconds or ran past the deadline of the checks.

## Fixes in the change

A change that fixes a problem can remove its cause, or only hide the symptom where the wrong result shows up: a guard, a retry or a special case added after the decision that goes wrong, while the code that makes it stays as it was. Answering which one means leaving the diff and following the wrong value back to the code that produces it, which competes with everything else in a finder's call. So Manki finds the fixes of a change and checks each in a call of its own. A finder still asks the same question, and the judge merges the two findings when both report one workaround.

**Listing the fixes.** Once the planner has picked the readers, one call to the `dedup` model reads the diff and lists each part of it that corrects a behaviour: the changed lines, and the wrong behaviour they correct in one sentence. It reads the diff alone, never the PR title or description, so a fix inside a feature or a refactor that nobody calls a fix is listed too, and the text of the PR cannot add or remove one. Manki reads the first 40 entries of the reply. It reads each range's path from the repository root, also when it starts with `./` or `/`, cuts the range to the lines the diff adds or removes in it (a removal after the last line counts at that line, and a file the change deletes holds no fix), and keeps a fix only when such a line is left, and cuts its sentence to 300 characters. It reads the first 5 ranges of each fix and keeps every run of changed lines in them, up to 200 changed lines for the fix, and it keeps at most 10 fixes. Each call takes at most 90 seconds. A reply that cannot be used is asked for once more, so the listing can take up to 3 minutes, and it stops with the other side checks one minute after the finders are done. Its calls show in `usage` as the `fixes` stage.

**Checking a fix.** A round checks at most 4 fixes, those with the most changed lines first. Each gets one call on the model of the group's first reader at the finders' effort, at the same time as the finders, with read-only repository tools and at most 12 steps. The call sees the lines of the fix, its problem and the diff. It answers in a fixed form: where the problem comes from, whether the fix acts there or where the wrong result shows up, which input or path still fails, the lines it cites, and a status of `root_cause`, `workaround` or `unchecked`. A retry, a wait, a guard or a default is no workaround by itself: it is the right fix when the cause is outside the code's control, such as a network or another system. A comment that calls the fix an intended workaround is checked like any other fix.

Manki keeps `root_cause` only when the call says the fix acts at the cause, and `workaround` only when it says the fix acts at the symptom and cites a line that is neither a line of the fix nor right next to one, such as the signature above an added guard. A cited path is read from the repository root however the call spelled it, such as `./src/a.ts`, so the fix's own lines never count as outside it. Each also needs a cited `file:line` that exists in the head commit, or a cited line of a [related repository](#related-repositories) the round fetched. Every other answer is `unchecked`. Only a `workaround` that stands reports its finding, at most one per fix, and the finding cites the lines the status stood on. When the call gives a finding with neither a title nor a description, Manki writes one from the check's own answer: on the first line of the fix, titled with the fix's problem alone so two such findings in one file stay apart, with where the problem comes from and what still fails, as a warning when something still fails and a note otherwise. Its fix advice names the change at the cause. The findings go through dedup, the judge and the refuter like any finder's, named `Fix check 1`, `Fix check 2` and so on. A check's status and record set no grade of a finding. The severity of its finding is the finder grade, which the judge reads and grades like any finder's.

**A push that hides the symptom.** From the second round, a fix whose check stands as `workaround` and whose lines the push changed keeps a thread open even when the judge finds the thread fixed. It does so only for a thread whose line sits within 5 lines of a line of the fix, or of a line the check cited as the cause or the path that still fails, and only while the check's finding stands: kept by the judge as a warning or a blocker, and not disproved by the refuter. The thread gets a "Partly fixed" reply with the fix's problem, where it comes from, what still fails and the lines the check cited, and it keeps the grade it carries. When the diff since the last round is unknown, every `workaround` counts as changed by the push. A fix that is `root_cause` or `unchecked`, or that the push did not change, leaves the judge's call as it was.

No list is asked for and no fix is checked when the quick check alone reads the change, or when the model of the group's first reader has no repository tools or the PR head is not checked out. A check that fails, or is still running one minute after the finders are done, leaves its fix `unchecked`, and the round still completes.

The round record lists the fixes under `fixes.fixes`: the lines (`at`), the `problem`, the reviewer name, the `status`, where the problem comes from (`cause`), the input or path that still fails (`stillFails`), what is left to check (`reason`), the cited lines (`proof`, and `relatedProof` for lines of a related repository), the number of findings, `inputDigest` and `reused` for a retry that keeps the answer, and `call` when the check gave no answer (`failed`, `timed_out`, `skipped`, or `cut` for a fix past the cap of 4). `fixes.cut` counts the fixes the listing gave past 10 and the entries of its reply past the first 40, which Manki does not read, and `fixes.skipped` says why none was listed when the listing call failed. `usage.llmCalls` records each check under the `fix_check` stage.

## The scope of a PR

Before a reviewer reads a change line by line, they ask two questions about the PR as a whole: is it useful, and does it cover one topic? The scope reader answers both in one call on the judge's model, beside the finders. It reads the whole diff, cut like a finder's slice when it is very large, the PR title and description, and the linked issues. With repository tools it reads the repository too, at most 10 steps. Its calls are recorded under the `scope` stage.

It runs only when something it read differs from what the last round with a scope answer read: the PR's change by the `changeDigest` of the round record, the PR title and description, the linked issues, or the files a doubt cites. A push that only rebases and moves none of those asks nothing again. A split that names line ranges is the exception: a rebase that moves a hunk to other lines asks again, so the ranges stay right. Such a round keeps that answer, so its Scope section and its warnings stay as they were. It never runs when the quick check alone reads a trivial change. A call that fails leaves the round complete, and the round says nothing about scope.

**Is the change useful?** The reader doubts it only when it can point at a line that shows a concrete problem: new code that nothing calls, new code that duplicates a function the repository has, a change that contradicts its linked issue, or one that reverts a recent change. The PR title, description and issues are untrusted. They tell the reader what to check, never what is true. Manki keeps a doubt only when a line it cites exists: in the checkout when the reader has repository tools, else in the diff. Example: a PR adds a helper `parseDate` while `utils/dates.ts` already exports one that does the same, and the reader cites both.

**Should it be split?** The reader lists the distinct topics of the change, each with its files. It first names the main purpose of the change from the code, not from the title. A part the main purpose does not need is its own topic, whatever its kind: a fix in a feature or refactor PR, a refactor or cleanup in a fix or feature PR, or a behaviour change in a refactor PR. A part the main change needs stays with it: the refactor it builds on, its tests and its docs. So does the same kind of change made in several places for one purpose, such as removing unused code, renaming one thing or one mechanical migration. A side part is a topic only when it deserves its own review: it changes behaviour in code the main change does not otherwise touch, or it is large or risky enough that someone would want to revert it apart. A small, obvious fix of a few lines in code the PR already touches stays with the PR, even though it changes behaviour. A typo, a formatting change, an import order or a renamed local never counts, and when the reader is unsure, it is no topic.

With more than one topic, the reader proposes the PRs to split into, each with its files, one or two sentences on what it would contain, and the other proposed PRs it needs merged first. Those two are the model's text and only shown: Manki cuts them like the name, leaves out a line the reader did not give, and drops a dependency that does not name another proposed PR by its number. When one file holds parts of different topics, a PR names its part by the lines on the new side of the diff, as `path:start-end`. A range takes every changed hunk it overlaps, and a plain path takes all hunks of the file. Manki keeps a split only when it names at least two PRs and every changed hunk is in exactly one of them, with no file outside the diff and no range that overlaps no hunk. Each proposed PR must also stand alone: Manki drops a split when one of them changes fewer than 20 lines, counting the added and removed lines of its hunks, or changes only test code. Test code is a file in a test folder or with a test file name, such as `tests/`, `a.test.ts` or `a_test.go`, and, in a source file of a language Manki parses, a hunk whose changes all lie in a module of tests or an item with a test attribute, such as Rust's `#[cfg(test)] mod tests`. In another language only the path counts. The round record keeps the reason under `dropped`. A round that carries the last answer without asking again checks its split again the same way. Example: a PR fixes a timeout in the HTTP client and also renames a CLI flag, and the reader proposes one PR for each. When the flag rename sits in `src/cli.ts` next to a line of the timeout fix, one PR lists `src/cli.ts:10-14` and the other `src/cli.ts:80-86`. Two changes inside one hunk cannot be split apart.

By default the answer is advisory. A kept doubt or split is listed in the review body under **Scope**, and never holds the approval. The doubt shows its cited lines. The split shows each proposed PR under its number and name, with what it would contain, its files grouped by folder, and the PRs it needs first, such as "Needs PR 1 first." A PR shows at most 10 files in all, then how many more it has. In place of the reader's line ranges, a file names the changed functions, types, test functions and modules of tests that the PR's hunks there fall in, a function in a test file counting as a test, each once and linked to its line at the head commit, the code first and the tests after, at most 10 per file. Manki finds them in the same syntax tree parse as the [uses outside the diff](#uses-outside-the-diff), and takes the innermost one around each changed line. A file the PR takes whole, a hunk outside any of them and a file without a parsed syntax tree show the file name alone. Example: `` `src/network/`: `discovery.rs`, `manager.rs` (`Supervisor`, `spawn_pump`, tests `started_from_seeds`) ``. A PR that is useful and covers one topic shows no Scope section.

With [`review.scope_blocks: true`](configuration.md#reference), each kept part is posted as a warning instead, which holds the approval until its thread is resolved like any warning's. Both are threads tied to no file, and the doubt lists the lines it cites. The split thread says it is a suggestion about the PR as a whole, lists the proposed PRs as the review body does, and asks the author to split the PR or reply with why the parts belong together. The reader reads text the PR author wrote, so a doubt becomes a warning only once the refuter confirms it from the code, as it checks a finding the judge doubts. That check counts toward the round's limit on checks of warnings. A doubt the refuter disproves or cannot confirm, or one on a round without repository tools, is left out like an answer that fails the checks. Only a disproof leaves it out for good. Any other doubt is checked again on the next round, also when that round carries the answer of an unchanged diff. A later round reuses the confirmation without a call while the doubt, the PR's diff and the code the check read are unchanged. A split needs no refuter, since the code checks it against the diff. A [dismissal stored in memory](memory.md) hides either warning, as it hides any warning, unless the dismissal is for some files only. The author answers in the thread, for example "these belong together because the flag rename is what the timeout fix reads", and the reply is checked like any reply. A tick on the issue box files it as an issue. The warning is a judgment, not a proven defect, so it skips the judge's grading and is never a blocker. It shows no check status, since it cites no code that could be checked. The checks above and the refuter stand in for that grading, so an answer that fails them never becomes a warning. The reader words its answer anew each time, so its text never decides which thread a warning goes to. A PR has at most one doubt thread and one split thread, each known by its fixed title:

- While that thread is open, the round's warning of the same kind goes into it, whatever it says or cites, and never into a thread of its own. When the reader was asked again that round, Manki replies in the thread with its current wording.
- Once that thread is settled, by an answer such as "Withdrawn" or "Agreed" or by someone resolving it, it stays settled until the PR title or description changes. A push that changes the diff, or a reader that words its doubt differently, does not reopen it. After a change of the title or description, the round reopens the thread and replies there with its warning.
- A doubt the refuter disproves in a later round is left out of that round, but its open thread stays open until it is fixed, answered or resolved, like any warning's thread.

The rule path above is separate. When an instruction file requires focused changes, a finder still reports a split as a rule finding, graded like any rule finding.

The round record keeps the answer under `scope`: `doubt` with its `proof`, the `topics`, the `split` with each proposed PR's `contents` and `needs` when the reader gave them and its files as Manki shows them under `shown`, each with the changed items under `items`, the parts the checks or the refuter left out under `dropped` with why, `warned` when they were posted as warnings, and the digests that decide whether the next round asks again: `purpose` for the PR title and description, `issues` for the linked issues and `cited` for the files a doubt cites. A round that did not ask has `skipped` set to `trivial`, or to `unchanged` with the round it ran on in `since` and that round's answer. A failed call has `failed` with why.

## Second reads

A finder tends to stop after a few findings, and a later round then finds more on lines the first round already read. Each such round costs a push and a whole review. So after the finders, one finder's model reads the change once more in the same round, told what the round has found so far.

A round runs second reads on the PR's first review that completes, and on a later round after a push that changed more than half of the diff's changed lines. Only the push's lines in files the PR changes count, so a merge of the base branch does not. A later round whose change since the last round is unknown runs none. Neither does the quick check of a trivial change, nor a diff read in slices, where each read would cost a call per slice.

A second read is the finder's own call again: the same system prompt and message, so the provider can reuse its cached prompt, the same effort and tool steps, and the same repository tools and related repositories. A note at the end lists the location and title of each finding the finders and earlier reads raised, never the reasoning behind it, so the read does not follow it. The note says the list is not complete, and asks only for defects that no listed finding covers, to the same standard as the first answer. An empty answer is a full answer. The findings of the sibling comparisons, related repository checks and claim checks are not listed, since a claim check's finding starts from the PR text, which no finder reads.

The read runs on the finder whose reads so far found the fewest findings, so in a group of two it runs on the other model than the one that found the most. A tie goes to the first finder of the group. No second read runs in a round where any call reached a limit, on any model or account, since a read is an extra and would most likely fail again. A finder whose own call moved to a fallback model is passed over. A second read never moves to a fallback model.

A read that adds a blocker or a warning starts one more read, at most two a round. A finding counts as added only when it sits near no finding the read was shown, those of the finders and earlier reads, in its file and shares no cited line with one. A read that adds only notes or findings graded `ignore`, or restates a listed finding, ends the reads. So does a read that fails: the round stays complete, keeps what the finders and earlier reads found, and its record says the read failed.

The findings of a read are named `Second read 1` and `Second read 2`. They go through dedup and the judge like a finder's. The judge is told that such a copy of a finding never counts as a second finder agreeing, since the read was shown the finders' titles. A read's copy never changes the grade a finder gave the finding, up or down: when the judge or the merge of same-titled copies puts it together with a finder's copy, only the finder's grades count, and of copies graded alike the finder's is the one kept. A finding only second reads raised keeps the grade they gave it. Nothing else about a second read changes how a finding is graded. The progress comment counts the reads on a line of their own, as it counts the side checks. A push during the reads stops the round before dedup and the judge, as a push during the finders does.

The round record lists the reads under `secondReads`: each read's `reviewer` name, the `finder` whose call it repeated, its `status` (`answered` or `failed`), the `findings` it reported before dedup and the judge, how many of them it `added` by the rule above, and the `error` of a failed read. `stop` says why no further read ran: `nothing_new`, `cap` after two reads, `failed`, `no_time` when the finders had less than 5 minutes left, or `no_reader` when every finder's model reached a limit or was refused. Each read's calls are recorded in `usage.llmCalls` under the `reviewer` stage with its reviewer name as the agent, so their cost shows apart from the finders'. A first round with second reads costs one or two more finder calls and their time. A review that retries an incomplete round keeps the reads of that round when it keeps every finder and they ended on `nothing_new` or `cap`, and otherwise reads again.

## The other finder's vote

Two finders on different models read the same diff. When only one of them reports a blocker or a warning, the other one read past it, so Manki asks it once about that finding. This runs on a round where two or more finders ran, after the judge and the refuter. A finding counts as reported by one finder alone when no other finder and no other check, such as a sibling comparison, a pattern check, a claim check, a fix check or a related repo check, reported it too. A second read and a sweep count as the finder they repeat, as [Severity tiers](#severity-tiers) describes, so neither is a second reporter beside it, and a finding only they reported goes to a finder other than that one.

The call goes to the model of the first finder that did not report the finding, without tools. It shows the finding's title and description as a claim to test, never its grade, with the code of the lines it cites at the PR's head and the PR's change to those files. The model answers three things: the harm the finding causes to a user or an operator of the code, in one sentence, the realistic situation in normal use where it happens, and the line where the harm happens with its code quoted, or `none` when it cannot name a harm with a realistic situation. Manki reads that line at the head. The answer declines the finding when it names `none`, or a line whose file at the head holds the quoted code neither on that line nor within 3 lines of it. An answer that names a file Manki cannot read at the head, one missing or too large, gives no vote. Any other answer backs the finding.

A declined blocker is posted as a warning, and its `gradePath` step `other_finder` gives the reason "the other finder would not block on it". Its fold says why it does not block and, in its thread, what clears it. Like a blocker a check disproved, that warning is guarded: only a fix, or someone other than the PR author with write access, clears its thread. Text in the code that steers the vote can then at most turn a blocker into a warning the author cannot clear. The blocker's severity cell is kept as `judgeCell`, as for a disproof, so a later round does not restore the blocker from it. A declined warning is posted as a note, with the reason "the other finder named no harm in realistic use", so it stays visible. No step that leaves notes out removes such a note: the `review.notes` limit lists it first and never counts it, and neither reviewed code nor a test file in a later round, nor a CI tool on the same line, hides it. A vote lowers a finding at most one step below the grade of its severity cell, so a blocker cell the judge already held at a warning stays a warning. A backed finding keeps its grade. A call that fails or answers twice in a form Manki cannot read changes nothing. A vote starts only while the round has time left for its whole call, 2 minutes, plus the 2 minutes a judge call starts with, so the dedup and verdict reader calls after it keep theirs. A vote without that time is skipped and listed under `notStarted`, and the round goes on without it. A security finding, a finding a [required rule](#rules-from-instruction-files) grades, also one whose rule the refuter confirms only after the vote was asked, a finding that restates an earlier thread and a round with one finder get no vote. Nor does a blocker the refuter already disproved, since that disproof already lowered it one step. A blocker or warning a check confirmed still gets a vote, since a check confirms that the code path is real, not that the finding matters. A declined one only goes one step lower: a blocker to a guarded warning, a warning to a note that stays in the review. The round record keeps each answer under the finding's `otherFinderVote`: the `finder` whose model answered, the `harm`, the `situation`, the `line` and `quote` when it named one, and whether it `declined`. Its calls are counted under the `vote` stage.

## The importance of a warning

Many warnings are true but about an edge case that hardly anyone reaches. So after the judge, the refuter, the vote and the steps that leave warnings out, and before the outcome, one call on the judge's model rates every warning about to be posted that may be left out. Without such a warning there is no call. The call shows each finding's title and description with the code of the lines it cites at the PR's head, and the PR's change to those files, in an order that says nothing about the findings. It shows no severity, no reporter and no check, and the model has no tools. The code and the change are fenced and marked as the PR author's untrusted content, the call takes each finding as true, since other calls check that, and a comment, a name, a string or a test that calls a problem handled, rare, accepted or intended counts for nothing. Each finding gets four scores from 1 to 10: how easily it is triggered, how clearly this PR introduces it, how much it matters when it happens, and the whole finding. The first and the third decide. The other two are kept in the round record.

A warning whose trigger score is below [`review.min_warning_trigger`](configuration.md#reference), 4 by default, and whose third score is below 7, is not posted. The second condition keeps a rare but very harmful warning, such as lost data or a crash. The setting takes a whole number from 1 to 10, a higher number filters more, and 1 turns the filter off and skips the call. Like every setting it is read from the base branch, so a PR cannot set its own cut-off. A warning that is not posted gets no thread and no entry as a suggestion, and it does not hold the approval. The review body names it in the collapsed "Checked and left out" section, such as "Trigger 3 of 10, below the cut-off of 4.", and the "Judge decisions" of the progress comment add the model's reason. Every other warning is posted as before, without its scores.

These are never rated and never left out by the score:

- a blocker
- a security finding
- the warning of a blocker that a check disproved or the other finder's vote declined
- a tool alert
- a finding a [required rule](#rules-from-instruction-files) grades
- a finding the judge graded a blocker, or that a confirmation of its doubts makes one
- a pre-existing finding
- a [scope](#the-scope-of-a-pr) warning
- an open lead
- a finding that an open thread, an answered thread or an earlier review body carries, so no thread loses its finding, and one that restates an earlier blocker

The call reads text the PR author wrote: the cited code, the change, and the finding's own words, which can quote both. The fences and the prompt work against it, but they prove nothing. A comment planted to lower a score could keep a warning that is no security finding out of sight, not only take away its hold. It stays listed in "Checked and left out" and in the round record.

The scores never change by themselves. A warning that restates one an earlier round rated keeps that round's scores, whether or not its code changed since. One that round left out stays out, and one it posted stays posted. A posted one is recognized by the judge's link to it, or by the same title in the same file, at most 5 lines apart. One left out is recognized by title and place only, since the judge is not shown it. A problem a push made worse still counts when the judge grades it a blocker or a confirmed doubt would. A finding with another title and no link is new, so it gets a rating of its own. The stored scores are compared with the cut-off of the current round, so a lower `review.min_warning_trigger` posts a warning an earlier round left out, and a higher one takes back no warning an earlier round posted. A round record too large to post can lose the findings left out, and a round that cannot read the earlier threads matches nothing, so such a warning is rated again or posted.

A call that fails, an answer Manki cannot read and a finding the answer leaves out give no scores, and the warning is posted. An unusable answer is asked for once more, and the usable scores of the first answer count when the second call fails. The call starts only while the round has time left for its whole call, 2 minutes, plus the 2 minutes a judge call starts with, and it never makes a review incomplete. Without a checkout, with `review.min_warning_trigger: 1`, or when the earlier threads could not be read in a later round, nothing is rated.

The round record keeps the four scores and the reason for the trigger score under the finding's `importance`. A warning left out is under `findings.unposted` with the `unpostedReason` `rare_trigger`, and its `importance` also holds the `cutOff`. The calls are counted under the `rating` stage.

## Sweeping for a defect class

A finder that reports one instance of a mistake often stops there, although the same kind of mistake can sit elsewhere in the PR. The first place found is not always the one that matters: a mistake noted in a test helper can be a blocker where production code makes it. With `review.sweep`, read from the base branch, a finding the judge keeps starts one more call. The value names the lowest grade that starts one:

- **`off`** (the default): no finding does.
- **`blockers`**: each blocker.
- **`warnings`**: each blocker, and each warning that its cited lines or a tool check prove.
- **`notes`**: those, and each note outside the `style` row of the severity table, so not one about wording, formatting, naming or docs.

A finding a check disproved starts none. Below blocker, neither does a tool alert, since the tool reports every place itself, nor a finding on code the PR did not change. A round runs at most three sweeps, whatever the value and however many findings it kept. The security findings go first, then the blockers, the warnings and the notes. Within a grade, those a check confirmed with tools come before those the cited lines prove, and the notes keep the judge's order. The rest are recorded as `cut`. So `notes` reaches a note only in a round with fewer than three findings above it.

The call states the finding's defect class in general terms, such as "a cache key leaves out a field the cached value depends on", never the instance, and lists every other place in the diff that makes the same mistake, each with its own proof. When it judges the class too specific to recur, such as a typo or a wrong constant, it reports nothing. Each place is graded on its own, by the judge and by what goes wrong there. It does not take the grade of the finding that started the sweep, so a note can lead to a blocker and a blocker to a note. Once found, it also stands on its own: when a later step drops or hides the finding that started the sweep, such as a memory suppression, the `review.notes` limit or a check at the round's end, the places that sweep found stay.

Each call runs on the model of the group's first reader at the finders' effort, with repository tools when the finders have them, at most 15 steps, and its calls are recorded under the `sweep` stage. The dedup and judge calls on what the sweeps reported are recorded with the agent `sweep`, and a refuter's call for a finding a sweep raised with `sweep: true`, so their cost can be counted as the sweep's. A call shared with the round's other findings, such as the verdict reader's, is not. A place on or next to a line the starting finding cites, or exactly on a line another finding the judge kept this round cites, as its own line, proof or evidence, in any file, is dropped and logged, and so is one the judge already judged this round. So is one the dedup model calls the same defect as a judged finding it sits near in one file, or shares a cited line with in any file. A cited line there is a finding's own line, or a proof or evidence line in a span of at most seven lines, so a place that reports a judged finding again from another file is caught too. An evidence line counts there by the `path:line` it starts with, read like a proof line, so one that cites a related repository as `owner/name:path:line` names no line of the PR. The rest go through dedup against earlier rounds and through one more judge call, which sees no open threads, like any finding. When that judge call fails, the round ends incomplete and posts no findings, so a blocker the sweep found is never lost behind an approval. They are named `Sweep 1`, `Sweep 2` and so on, never after the starting finding's text, and one that restates an earlier open thread folds into it. Their tool checks come out of the round's eight, so the setting never raises that number. The round record lists each sweep under `sweeps`: its reviewer name, the location and grade of the finding that started it (`source` and `severity`), its status (`answered`, `too_specific`, `failed` or `cut`), the class it stated and how many places it found.

A round with sweeps costs at most three sweep calls, which run at the same time, one call of the dedup model for places near a judged finding or sharing a cited line with one, the usual dedup against earlier rounds, and one more judge call. With `blockers` only a round that keeps a blocker pays that. With `notes` most rounds that keep any finding do. The setting is off by default until a benchmark run decides whether the extra calls pay for themselves. `bench/variants/sweep.yml`, `sweep-warnings.yml` and `sweep-notes.yml` turn on one value each.

## Related repositories

`related_repos` lists public repositories on github.com that the review may read as context. Each entry has:

- **`repo`**: the repository as `owner/name`.
- **`kind`**: `reference` for a repository this one implements or ports, such as a protocol's reference implementation or its specifications. `consumer` for a repository that depends on this one, where a change to a public API or a wire or data format can break it. `dependency` for a repository this one depends on, such as a library it calls, where a change can rely on something the library does not guarantee.
- **`ref`** (optional): the branch, tag or full commit hash to read. The default is the repository's default branch. A `dependency` without a `ref` is read at the commit that the lockfiles of the PR head lock for it: a `Cargo.lock`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock` or `pnpm-lock.yaml` that git tracks, outside `node_modules` and `target`, and never a symlink. A `Cargo.lock` in the folder of a workspace member does not count when the workspace root holds a `Cargo.lock` of its own, since Cargo builds every member against the root's. A member is a folder that the root `Cargo.toml` lists under `[workspace] members` and does not name under `exclude`. When the root manifest does not parse, or lists more than 1000 `members` and `exclude` entries, the member's lockfile counts. Only the full commit of a git source on github.com counts, after `#` or Yarn's `#commit=`, or in a `codeload.github.com` tarball URL, so a PR that bumps the dependency is reviewed against the new commit. A round reads at most 50 lockfiles, 10 MB of one and 40 MB in all, as for the `dependencies` analyzer. The cap counts the lockfiles of workspace members too, and the `Cargo.toml` files read to find them count toward the 40 MB. When no lockfile locks the repo at a commit, or two lock it at different commits, it is read at its default branch. So is every such dependency when one lockfile does not parse or is past a limit, since it may lock another commit. The round record says why (`unlocked`), or names the lockfile that set the commit (`lockfile`). Set `ref` for a dependency the lockfiles do not lock this way, such as one from a registry. Write a branch or tag whose name looks like a short commit hash, such as `20240115`, as `refs/heads/20240115` or `refs/tags/20240115`.
- **`paths`** (optional): up to 20 paths or globs inside the repository, such as `src/` or `packages/rs-*`. Only these are fetched, along with a root `AGENTS.md` and `CLAUDE.md`. The default is the whole repository. Set it for a large dependency, so its code does not crowd out the PR's own.

```yaml
related_repos:
  - { repo: dashpay/dash, kind: reference, paths: [src/] }
  - { repo: dashpay/dips, kind: reference }
  - { repo: dashpay/platform, kind: consumer, paths: ["packages/rs-*"] }
  - { repo: tokio-rs/tokio, kind: dependency, ref: tokio-1.38.0, paths: [tokio/src/] }
```

Every stage with [repository tools](security.md) reads these repositories through the same tools, by naming one in a `repo` argument. The rest of this paragraph is what the stages that look for findings are told: the finders, the sibling comparisons, the related repository checks, the pattern checks and the sweep. When the PR title, description or changed code says the change matches a reference, or follows its spec, they open the code the claim names and compare it with the change. They also read a reference when the changed code implements or mirrors it, and compare each contract in both directions. They read a consumer only when the PR changes a public API or a wire or data format, to find the consumer's code that uses it. They read a dependency when the changed code calls it or relies on what it does, and check that what the change assumes about it holds in its code: what a function validates, what a signature or hash covers, which errors it returns, and what it guarantees about ordering, retries or concurrency. For example, a service retries a call because it takes a client library's timeout to cover the whole call, while the library applies it to each attempt. A finder whose message lists lines of a reference also opens the files of those lines. A divergence from a reference is graded like any other finding. A change that breaks a consumer is a warning that lists the consumer's call sites, and a blocker only when the PR says it does not break anything. An assumption a dependency's code does not keep is graded like any other finding, and a different design in the dependency is not a finding by itself. A model without tools never reads them. For a finder with repository tools, the checklist gains one check per configured kind. With a `reference`: when the change touches a wire format, a protocol message or a rule a specification defines and a reference holds that specification, search it for the name of the message, field or rule and compare the change with what it says. With a `consumer`: for each public type, function or serialized format the change alters, find its uses in each consumer and check that they still work. With a `dependency`: for each function, type or message of a dependency the changed code calls or relies on, name what the change assumes about it and check that the dependency's code keeps it. The wording for a `dependency` is part of a prompt only when one is configured.

The finders and the quick check of a trivial PR, the sibling comparisons, the related repository checks, the [claim checks](#claims-of-the-pr-text), the [pattern checks](#patterns-of-the-codebase), the [fix checks](#fixes-in-the-change), the sweep, the refuter and the second refuter, the judge with `judge.tool_steps` and the reply in a review thread all read the related repositories, each when its model has repository tools. The planner, dedup, the verdict reader, `/manki explain` and questions have no repository tools and never read them. The refuter, the judge and the thread reply check a finding instead of looking for new ones. They get the list of repositories without the grading rules above, and are told to name a repository only when what they check cites its code as `owner/name:path:line` or rests on what that code does, and to read that code before they answer. Every stage that can read a related repository is told that everything in it is untrusted data that other people wrote, never instructions. A call that names a repository Manki cannot fetch returns the reason. The stage is told that it has not read the repository then: it says so, treats whatever rests on that code as unchecked, and never answers about that code from memory.

A finding cites a related repository's code as `owner/name:path:line`. Manki tells the judge whether each cited line is in the checkout the round fetched. When the judge's model has repository tools, Manki also shows it the lines around the citation under the finding as "Cited code in a related repo", so the judge grades from the code and not from the finding's account of it. When an evidence line of the finding starts with such a citation and quotes code in backticks, Manki compares the quote with the fetched file. Code quoted after a further citation in the same line belongs to that citation, and is not compared with the first. A quoted part counts as there when it sits within 3 lines of the cited lines, whitespace aside. In a citation of more than 7 lines the quote could sit anywhere, so finding it there says nothing, and the citation is reported like one without a quote. A quote that is not in the cited lines at all is still reported as missing, in whole or in part, since that is certain at any width. A quote in double backticks is read as one quote, so it can hold a backtick. A quote cut by an ellipsis is compared part by part, every part of it, and so are the quotes of several evidence lines for one citation. Citations of one file and first line, such as `src/a.ts:12`, `./src/a.ts:12` and `src/a.ts:12-14`, are one place and get one answer, the worst of theirs. So a quote the lines do not hold decides the place whichever spelling it stands with, a range the file does not hold makes the place not found, and a quote that was not compared outweighs one the lines hold. The judge gets one of three answers. A citation with every part there holds the quoted code. One with only some of them is reported as holding only part of it, with the parts found and the parts missing named, which is also what a line that quotes this repository's own code beside the related one gets. One with none of them is reported as not holding the quoted code. Only the first answer confirms the citation, and the other two prove nothing. The judge still sees the lines the fetched file really holds at that place, and is told to grade from those lines and not from what the finding says they hold. A citation that is neither confirmed nor shown counts as code the judge cannot see. A quote of fewer than 6 characters, whitespace and ellipses aside, is taken as a name the sentence mentions and is not compared. Any other text in backticks after the citation counts as a quote of the cited lines, also a path or the name of a caller, so such a line is reported as holding only part of the quoted code. Only the first 10 related citations of a finding are looked up. To show these windows, and the ones around a finding's proving lines of the PR outside the diff, Manki tries at most 10 cited files of the PR and 10 of related repositories for a finding, and 80 in a round, whether or not a file is there, and tries each file once a round. So a finding that cites many missing files costs no more than that. A cited file over 1 MiB is not read: the judge is told its citation is unchecked, and a refuter's answer cannot use a line of it as proof. Git allows `:` in a file name, so a PR can hold a file at the very path a citation spells, such as a file named `acme/reports:src/import.ts`. Such a file changes nothing about the citation: it is looked up in the related checkout like any other, and its note to the judge only remarks that the PR also has a file at that path. A file the PR adds can therefore never take away what a related repository's code shows.

A refuter's answer lists the lines that decide it. A line of a file over 1 MiB is not read and proves nothing, in the PR's repository or in a related one. Neither does a line its file does not hold: line 0, a range that runs backwards, or a line past the last one. A line of a related repository counts there only when it is in a checkout the round fetched, at most 10 for the answer and 10 for each premise, and the round record keeps them as `relatedProof` on the refutation and on each premise. Only the first 10 related lines a list cites are looked up. Manki writes each kept location itself, from the repository's configured name and the file's own path in the checkout. The finding shows it wherever it shows its checks: in a review thread, in the review body and in the output of `manki review`. There it is a link to the line at the commit the round fetched, or the location alone when the round recorded no commit. A blocker that a round lists again from an earlier record, because no thread carries it, shows its related lines as locations without a link, since they were read at the commit that earlier round fetched. It is listed under "Checked in the code" on the condition that makes a check's lines of the PR proof of the finding: the check confirmed the defect, or its confirmation raised the grade. The round record then keeps it as `relatedProof` in the finding's `evidence`, at most 10 lines for a finding however many checks add to it. A finding that is folded into another, as a duplicate or into a blocker of the verdict reader, brings its related lines along, under the same limit of 10. Of a check with premises the lines of its own answer are kept before the lines of its premises. A check that did not, such as one that confirmed only a premise, names the line in its own sentence. A line of a repository that is not configured or was not fetched, or that the fetched file does not hold, is neither proof nor shown. An entry of the list that reads as a line of a related repository is never read as a line of the PR as well, and a file of the PR at the path it spells does not make it one. A related line that counts can confirm a finding or a premise. It never disproves one alone: a disproof still needs a line of the finding's own file or of the diff, since a disproof can lift a finding and a related repository is code the PR's reviewers do not control. A check that rests on a related line is never reused in a later round, because the repository can change while the PR's files do not, so the next round checks the finding again. An answer from a round before that check is not reused in its place either: only the latest stored answer for a finding counts.

A reply in a review thread reads `related_repos` from the base branch like a review. It fetches nothing up front. A repository is fetched the first time the reply names it, within a minute, and the reply as a whole has 15 tool steps and 5 minutes. [Replies in a review thread](#replies-in-a-review-thread) says how a line of a related repository counts for a statement of the reply. The reply record lists each configured repository as `relatedRepos`, like a round record. A reply that keeps a finding has to cite a line the finding did not cite. A line of a related repository counts there as a location of its own, and is never taken for the line of the PR's file at the same path.

Manki reads `related_repos` from the PR's base branch only, so a PR cannot make Manki fetch another repository. A PR that changes it is reviewed with the base branch's list. Every related repository is fetched before the finders run, on a round whose finders have repository tools and whose diff names something to search for. On any other round where a model has repository tools, a repository is fetched the first time a stage names it. So a round whose finders have no tools still fetches a repository that its refuter or its judge names. Each is fetched once per round however many stages read it. When a stage is stopped in the middle of its fetch, the next stage that names the repository fetches it again, into a folder of its own that no cache keeps, since the git process of the stopped stage can still be writing the first one. The fetch is a shallow, path-limited clone of one commit (`git` with `--depth 1`, `--filter=blob:none` and a sparse checkout of `paths` and the two root guide files), run without any credentials, so a private repository cannot be read. A repository that is private, missing, or not fetched within a minute gives a warning, and the review goes on without it. So does one whose fetch was stopped with its stage when no later stage asked for it, and its reason in the round record says that. The round record lists each configured repository as `relatedRepos`: fetched, failed with the reason, unused when the round never fetched it, or skipped when no model of the round had repository tools, with how long its fetch took, how many tool calls read it (`reads`) and how many of those each stage made (`readsByStage`, with the refuters as `refute` and `refute_pair`). Each call with tools in `usage.llmCalls` counts its own reads as `relatedReads`.

Before the finders run, Manki searches each fetched related repository for the names the diff changes or reads and the names its added comments mention, such as `MAX_BODY_LENGTH` in a comment that says the change follows that limit. The search ignores case and underscores, so `retry_delay` also finds `retryDelay` and `URLInfo` finds `URLINFO`, except that an `ALL_CAPS` constant keeps its case. Names of test functions, words that do not read as code and names longer than 160 characters are left out, and so are the root `AGENTS.md` and `CLAUDE.md` of the repository. The names are searched together in one pattern of at most 15 KB, and a name that no longer fits it is not searched. The section names it as not searched, apart from the names nothing matched. When the search of one repository fails and another of the same kind is searched, the section names the repository that was not searched, and a name the others do not hold is listed as not searched there, never as a name nothing matched. A dependency is searched for a different list, which Manki collects only when a `dependency` repository is configured: the names the added comments mention, then the functions the changed lines call and the fields they read, most used first, such as `verify_chunk` in `store.verify_chunk(data)`. Calls and reads in test files and in Rust test code are left out. So is a called or read name that the change also declares, since a library does not hold it. The list for a dependency holds at most 80 names. One call to the `dedup` model first guesses what each fetched repository calls those names, from the names, the file types the change touches and each repository's most common file types: a Go server may call a Python client's `fetch_profile` `GetUserProfile`. The search then looks for the guessed names as well as the original ones, at most 2 guesses a name. No names are guessed for a dependency, since the names a change calls are the dependency's own. A line only a guessed name finds is listed under the original name, marked "also searched as", after the lines the original name finds, and the section says that such a name is a guess to check. A guess that reads as code is matched like any name, a plain word only in its exact case. The guesses are searched after the original names and apart from them, so a guess whose search fails costs only the guesses searched with it. The round record marks those as `failed`, and likewise every guess for a repository whose search for the original names failed, and a guess that found no line and no longer fit the pattern. The call takes at most 45 seconds and shows in `usage` as the `translate` stage. When it fails or its reply cannot be used, the search runs with the original names alone. The finders, the judge and the refuter get the matches after the uses outside the diff, as an "In the Reference Repos" section, an "In the Consumer Repos" section and an "In the Dependency Repos" section, each only when a repository of that kind is fetched. Each lists for each name at most 4 lines, 40 lines in all, and the names nothing matched. The reference section asks to compare the change with the reference. For a name that starts with a capital letter, such as a constant or a type, it puts a line that declares the name first. The consumer section asks to check that each line still works with the change. The dependency section asks to check that what the change assumes about a line holds in that code, and orders its lines like the reference section. All three then list the repository's other code, comments and documents, then its tests, then vendored code. As with the uses outside the diff, the finders get a copy of their own: it shows a line of each file before a second line of any file and puts generated code, test doubles and vendored code after every other file. A file's first line comes before any file's second line whatever the two lines are, so a line of a document in a second file comes before the second code line of the first file. For a finder with repository tools other than the quick check, its reference section also says to open the file of each line before it answers, up to 5 files. The round record keeps the locations of the finders' copy under `usesOutsideDiff.reference`, the names nothing matched under `usesOutsideDiff.referenceMissing`, the names the 40-line cap left out under `usesOutsideDiff.referenceCapped`, and the names that were not searched in every repository under `usesOutsideDiff.referenceUnsearched`, with `consumer`, `consumerMissing`, `consumerCapped` and `consumerUnsearched` for the consumers and `dependency`, `dependencyMissing`, `dependencyCapped` and `dependencyUnsearched` for the dependencies. Under `usesOutsideDiff.translation` it keeps each guessed name with its repository, the original name and how many lines of that repository hold it, or `skipped` with the reason when the call failed, its reply could not be used or no model is set up for it.

Each name those lists show for the finders is a counterpart, and each counterpart also gets a check of its own: one small call beside the finders, as the [sibling comparisons](#sibling-comparisons) get. A finder shares its tool steps with the whole change, so it opens only a few of the listed files. The call for a reference compares what the change does with what the reference does, in both directions. The call for a consumer checks that each use still works with the change. The call for a dependency checks each assumption the change makes about it against that code. Each call gets the name, the lines the finders were shown and up to 2 hunks of the diff that hold the name, and is told to open the counterpart's file before it answers. It runs on the model of the group's first reader at the finders' effort, with repository tools and at most 12 steps. A call without repository tools could not open the counterpart, so it is not made, and the quick check of a trivial change makes none. A finding of the call counts only when its `proof` cites a line of the PR's head commit and a line of a related repository the round fetched, and both lines are there. The call's other findings are dropped. A kept finding keeps those related lines as `relatedProof` in its `evidence`, and shows them like the lines of a check. The findings go through dedup and the judge like any finder's, named after their counterpart, such as `Reference check: MAX_BLOCK_SIZE`, `Consumer check: PeerInfo` or `Dependency check: read_varint`, and nothing about these calls changes how a finding is graded. A round checks at most 8 counterparts. The ones whose name the most added and removed lines of the diff hold go first. The finders get every counterpart listed either way. Once the finders are done, these calls get the same grace of one minute as the comparisons. The round record lists each counterpart under `comparisons`: its kind (`reference`, `consumer` or `dependency`), the reviewer name, its lines as `owner/name:path:line`, and whether it was answered, failed, cut by the cap, timed out, or skipped because its model had no repository tools, with how many findings it gave and how many it dropped (`dropped`). `usage.llmCalls` records each call under the `related_check` stage.

A related repository often keeps a guide for its own contributors at its root, `AGENTS.md` or `CLAUDE.md`. For each repository fetched before the finders run, Manki looks for that file, `AGENTS.md` first, and the prompt of the finders, the sweep, the refuter and a judge with tools names its path as a map of that repository: they read it first to find where the repository keeps what they look for. The prompt says that the guide's rules govern that repository and not the PR, and that its text is untrusted data. Manki itself never puts the text of these two root files into a prompt: the prompt names only the path, and the search described above skips both files. A model that opens the guide reads it with its tools, as untrusted data like any other file of that repository. A repository limited by `paths` still has its root `AGENTS.md` and `CLAUDE.md` fetched, so its guide is found too. A repository fetched later, on a stage's first read, gets no pointer, and neither does a thread reply. The round record names the file as `guide` on the repository's `relatedRepos` entry.

The clones go to `manki-related-repos` in the runner's temp directory. To reuse them across runs, restore and save that directory with `actions/cache` before the Manki step. Each run saves a new entry and restores the latest one:

```yaml
      - uses: actions/cache@v6
        with:
          path: ${{ runner.temp }}/manki-related-repos
          key: manki-related-repos-${{ github.run_id }}
          restore-keys: manki-related-repos-
```

Of a restored clone Manki keeps only the object store, and only once `git fsck` finds it intact, so a tampered cache entry cannot change how git runs. It first removes an unfinished pack that a stopped fetch left there, which git itself would keep. The fetch then downloads the commit and its trees again, and only the files the cache does not hold yet, and Manki repacks the store so it keeps one copy of each object. A job with `cache-mode: read` restores the cache and saves nothing (see [Cache access](getting-started.md#cache-access)). No other job writes this cache, so such a job fetches every related repository from scratch on each run. A run for a thread reply uses the same directory, so with this step a reply that names a related repository finds its clone already there.

## Dependency sources

A finding can rest on what a dependency does, such as whether a function of a library fails on an input or only clamps it. The finders, the claim checks and the refuters, and a judge with tools, can read the published source of a dependency of the PR to settle that. The quick check of a trivial PR, the sweeps, the sibling comparisons, the related repository checks, the pattern checks and the fix checks cannot. It needs no setting. Manki reads crates from crates.io and packages from npm.

A call names the package as `crates.io/<name>` or `npm/<name>`, and Manki picks the version from the PR's own files, in one of two ways. Only the files git tracks count, as for a [`dependency` repository](#related-repositories), and for Cargo nothing under `target`, where only Cargo builds.

1. A committed lockfile locks it: `Cargo.lock`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock` or `pnpm-lock.yaml`, in any folder. A `Cargo.lock` of a workspace member does not count when the workspace root holds one, as for [related repositories](#related-repositories). Manki reads exactly the version the lockfile locks. When a manifest states a requirement for the package that the version read does not meet, such as a PR that bumps `time = "0.4"` beside a `Cargo.lock` still at 0.3.47, an install would not use the locked version, so the package is refused. So is a requirement Manki cannot parse. When the lockfiles lock several versions of the name, as a `Cargo.lock` often does, the package is refused unless the call names one of them, such as `crates.io/syn@2.0.87`.
2. No committed lockfile locks it, and it is a direct dependency: a `Cargo.toml` or `package.json` names it, and all of them that do state the same requirement. Manki reads the newest published version that requirement allows that is not yanked, and not a prerelease unless the requirement names one. For npm it is the version npm marks as `latest` when that one matches, and never a deprecated one when another version matches. Manki reads a requirement only in the forms it is sure of: npm's ranges, and for Cargo an operator `^`, `~`, `=`, `>`, `>=`, `<` or `<=` or none, which means `^`, and a bare `*`, `1.*` or `1.2.*`, joined by commas. A requirement is looked up under the name its manifest spells, so `crates.io/serde-json` finds the `serde_json` a `Cargo.toml` names.

Manki reads a package only when it is certain which code the PR runs, and otherwise refuses it with the reason. It refuses a package when:

- the manifests state several distinct requirements for it and no lockfile locks it, or the requirement is in a form Manki does not read, such as Cargo's `=1.2.*` or `1.*.*`. A package that no lockfile locks and no manifest names is not a dependency, and is not read either.
- any lockfile locks it with a patch applied, such as a Yarn `patch:` or a pnpm patch, or from a git repository, a path, a `portal:`, `link:`, `file:` or `exec:` source, or from another package's archive under an alias. One such entry refuses the name, even next to a plain entry from the registry.
- a manifest takes it from somewhere other than the registry: an npm requirement that names no version, such as an `npm:` alias, a path, a git repository or a dist-tag, or a Cargo entry with `path`, `git`, `registry` or `registry-index`, or with a field Manki does not know.
- any manifest overrides or patches it: npm `overrides`, Yarn `resolutions`, Bun `patchedDependencies`, `pnpm.overrides` or `pnpm.patchedDependencies`, the `overrides` or `patchedDependencies` of `pnpm-workspace.yaml`, or a Cargo `[patch]` or `[replace]` in any `Cargo.toml` or `.cargo/config.toml`, also one that names the crate through `package`. So does an npm package of the same name in the checkout, which a workspace install can link in its place.
- any manifest has an install script, such as `postinstall` or `prepare`, whatever command it runs, since such a script can change any installed package.
- a setting takes packages from another registry or changes the lockfile: a registry other than the public one in an `.npmrc`, `.yarnrc.yml` or `pnpm-workspace.yaml`, any `registry` line in a Yarn 1 `.yarnrc`, `package-lock`, `shrinkwrap`, `lockfile` or pnpm's `shared-workspace-lockfile` set to anything but `true`, `lockfile-dir`, `--no-lockfile`, `yarn-path`, `lockfileFilename`, `yarnPath`, `cacheFolder` or any Yarn `plugins`, a pnpm hook, a patch-package file under `patches/` that names it, or a `.cargo/config.toml` that sets `replace-with`, `paths`, `include`, `registry.index` or a `crates-io` entry of `[registries]`.
- the version would come from a requirement, and a setting makes a fresh install pick another one than the newest it allows: `before`, `tag`, `resolution-mode`, `min-release-age` or `minimum-release-age` in an `.npmrc`, `minimumReleaseAge` or `resolutionMode` in `pnpm-workspace.yaml`, `npmMinimalAgeGate` in a `.yarnrc.yml`, or a Cargo `rust-version` together with edition 2024, `resolver = "3"` or `incompatible-rust-versions`. Manki still reads the newest version under such a resolver when Cargo has no reason to take an older one. Every package in the checkout must state a `rust-version` Manki can read, its own or its workspace's, and the crates.io index must state for that version no Rust version, or one no higher than each of theirs.
- for npm, the checkout holds a committed install anywhere: any tracked path under `node_modules` or `.yarn/cache`, since the project can run that copy in place of the registry's archive.
- for npm, the checkout holds an install file Manki does not read anywhere: `bun.lock`, `bun.lockb`, `bunfig.toml`, `deno.lock`, `deno.json`, `deno.jsonc`, the old pnpm `shrinkwrap.yaml`, Rush's `rush.json`, vlt's `vlt-lock.json` or `vlt.json`, or pnpm's `package.json5` or `package.yaml`.
- a lockfile, manifest or setting is too large to read or does not parse. Cargo files are read with a standard TOML parser.
- the checkout holds a git submodule, whose files Manki does not list, or a symlink that an install could follow to a file Manki does not see: a link under the name of a lockfile, manifest or setting, or one to a folder, to a path outside the checkout or to nothing. A checkout without symlinks, as Manki's own is, holds such a link as a plain file with the target's path, and git still tells it apart.
- `closed_paths` removed a lockfile, manifest, setting or git submodule from the checkout, or anything under `node_modules` or `.yarn/cache`, since an install reads it while Manki no longer sees it. Manki also refuses when it cannot read which files were removed. A closed path that removes only other files changes nothing.
- git cannot list the checkout, or it holds more lockfiles, manifests and settings than Manki lists, or more lockfiles of the registry than Manki reads, since one Manki does not read may lock the package. The reason names the cap.
- the runner's file system does not tell apart names that differ only in case or Unicode form, as on macOS and Windows, since two files of a package could land on one path. Manki checks this once per round, and dependency reading is then off for the round.

A refused package is recorded as `refused` with the reason, and the check stays unsettled. A version the PR does not use is not read, nor a requirement no published version meets, and the record says `failed` with the reason. The first read of a package downloads its archive, checks it against its checksum and unpacks it. Every later read in the round uses that copy, and a round fetches at most 10 packages. A fetch gets its own time: when resolving the version left the call too little for it, the call says to name the package again, and the next call fetches it with the resolution the round kept. A fetch or a read of the registry that runs out of time, or meets an error that may pass, such as an HTTP 503 or a dropped connection, is tried again by a later call, and the round record keeps only the last outcome. Each answer starts with a line that names the package, its version and where that version came from, such as "the version `Cargo.lock` locks" or "the version a fresh install picks for the requirement `0.3` in `Cargo.toml`". [Security](security.md) lists what Manki contacts, what it refuses, and the cap on each archive, registry answer and read of the checkout.

A check cites a dependency's line as `<registry>/<name>@<version>:path:line`, such as `crates.io/time@0.3.47:src/date.rs:120`. Such a line counts as proof the way a line of a related repository does, under the same rules: only for a package the round read, only for a line its file holds, and as `relatedProof` in the record. It can confirm a finding but never disprove one alone, and a check that rests on one is checked again in the next round. A finding shows these lines under "In a dependency's published source", as locations without a link. Which features of a dependency the build turns on is not in its source, so a statement that rests on that stays unchecked. Neither are the files a build script or an install script writes, such as those under `OUT_DIR` or a compiled addon, so a statement that rests on them stays unchecked too. Two things Manki cannot see either: settings outside the checkout, such as the runner's own `~/.npmrc` or Cargo home, and the other requirements of the dependency graph that can hold an install to a lower version than the newest a manifest allows. A package that cannot be read leaves the check as it would be without it, unsettled, and the call says why.

The round record lists each package a tool call read or tried to read as `dependencySources`: the package with its version, its `registry` and `name`, where the version came from (`source` is `lockfile` or `requirement`, `file` the lockfile or manifest, and `requirement` the requirement it was resolved from), and `status`. That is `fetched`, `failed` with the `reason`, `refused` with the `reason` when Manki is not certain which code the PR runs for it, such as an overridden or patched package or one another registry may serve, or `mismatch` when the archive did not match its checksum and nothing of it was read. It also holds how long the fetch took, how many tool calls read the package (`reads`) and how many of those each stage made (`readsByStage`). Each call in `usage.llmCalls` counts its reads under `relatedReads`, keyed by the package and version.

## Related open PRs and issues

Manki looks for other open work on the same change while the review runs. It lists up to 5 open PRs, drafts included, that change a file this PR changes, from the 50 most recently updated, most shared files first. It also searches the repository's open issues for up to 6 words: names the PR's added lines declare, such as a new function, and the longer words of its title. GitHub refuses a query of more than 256 characters, so a word that no longer fits is left out. The search takes up to 5 issues and leaves out the ones the PR body links. One call to the `dedup` model then reads this PR's title, description and changed files next to each candidate's title, the start of its description and, for a PR, its changed files. It answers whether each one is a duplicate PR, an overlapping PR or issue, an issue this PR fixes without linking it, or unrelated.

The review body lists under "Related work" only what the author can act on, each with a link and what to do. A duplicate PR reads "#456 seems to make the same change. Close one of the two if so." An issue this PR fixes reads "This PR may fix #123. Add `Closes #123` to the description if it does." Duplicates come first. An overlapping or unrelated candidate is not listed, and with nothing to act on the section is left out. The model's one line of reasoning stays out of the review, since the candidates' text could steer it, and only the round record keeps it. The note never blocks, never opens a thread and never changes the verdict: whether a duplicate PR should close is the author's call. The other PRs' and issues' text reaches the model only as untrusted data in fenced blocks, cut to 400 characters each, and their titles are sanitized before they are posted. A list that fails is skipped with a warning. Neither request is retried or held for a rate limit, and the whole lookup gives up after 15 seconds, so the review waits at most that long. A list still running then is cancelled and recorded as timed out. A local review has no GitHub to ask and skips the step. The round record keeps each candidate under `relatedWork.candidates`, with its number, how many files it shares, the classification and the reason, and names any list or call that was skipped. The model call shows in `usage` as the `related` stage.

Manki also links the open issues and PRs that already track a finding. Once every finding is graded, one more call to the `dedup` model reads the posted findings next to the candidates and names, for each finding, the one that describes the same defect in the same code, if any. Only a candidate opened by a person with write access counts, so nobody else can attach an issue to a finding. A match also needs the candidate's title or the start of its description to name the file the finding sits on or a name the finding cites in a code span, so an issue that only shares a word with the finding is never linked. A finding with a match shows "Tracked in #N" in its thread or in its entry in the review body, the "Pre-existing" section included. The link is only shown. It never changes a grade, a thread or whether the approval waits, so a blocker this PR introduces still blocks when an open issue describes it. Only the check of the code before the PR makes a blocker pre-existing. A failed call links nothing. The call shows in `usage` as the `related` stage too.

## Round records

Each review summary on the PR embeds a `Manki context` block. The block is a hidden HTML comment holding the round's diagnostics as JSON: models and effort, timings, token use, the planner's choices, every finding the finders reported (`reviewers.rawFindings`), dedup drops, and the judge's decisions with its reasoning, including the findings it dropped (`judge.dropped`). The visible review comes first: the record gets the room the review body leaves, at most 50,000 of the 60,000 characters Manki allows a review. When it would not fit there, Manki stores it gzip compressed and base64 encoded in the same comment instead of cutting it. Only a record too large even compressed loses its per-file and per-finding diagnostics, and `meta.omitted` then names each field left out. While it fits, such a record still keeps every finding the finders reported with only its title, location, severity and reviewers, and the uses outside the diff with only names and locations, so a missed defect can still be traced. `meta.compacted` then names those two fields. A record that still does not fit leaves out more, in a fixed order, and stops once it fits: first the LLM calls (`usage.llmCalls`), the judge's reasoning on each finding and the findings it did not post, then the parts no later round reads, such as `relatedWork`, `sweeps`, `staticAnalysis` and `runner`, then the parts only a retry that reuses an earlier attempt reads, such as `comparisons` and `prClaims`, and last each finding's stored checks, proposed fix and evidence, so a later round checks such a finding again, and the `fixed_elsewhere_in_pr` line of each origin answer. What remains is the minimal record later rounds need: the meta, the verdict, each finding with its fingerprint, grade and thread, the description a finding without a thread is listed again with, and the judge's thread evaluations. It holds a few hundred findings, and only a round whose minimal record is still over 50,000 characters fails without a review. When the review body does not fit beside the minimal record, Manki leaves out whole findings from the end of the least important section until it does: the pre-existing findings first, then the suggestions, then the other sections. A last line says how many findings were left out and that Manki's record of this review keeps them. The round record keeps them with `posted: record`, as findings that are in the record only. The run log names what was left out and holds the full record, gzip compressed and base64 encoded in lines of 1,000 characters, in the group "Full round record". To read it, run `gh run view <run id> --log | sed -n '/Full round record/,/##\[endgroup\]/p' | sed '1d;$d;s/^.*Z //' | tr -d '\n' | base64 -d | gunzip`. `usage.llmCalls` lists every LLM call of the round: the stage and finder, model and effort, input, output, cache read, cache write and reasoning tokens, the part of the cache writes kept for an hour when the provider reports it (`cacheWrite1hTokens`), duration, attempt, whether a fallback model answered, and an estimated cost in USD at public API prices, with a 1-hour cache write at twice the input price. A model that charges more for a long prompt charges it per request, so a call pays that price only when its largest request passes the limit. A call records the input of its largest request in `largestRequestInputTokens` when its client knows it: an API call is one request, the Claude CLI reports each request's input, and Codex writes it to its session file. When the client saw only some of a call's requests, it records the largest one it saw in `largestSeenRequestInputTokens`, and a seen request past the limit gives the long-prompt price. When no seen request passes the limit and the sum does, the call gets the standard price and records `costAssumesShortRequests`, since the estimate then assumes no request passed the limit. A Codex CLI call records the counts Codex reports when its turn completes, which on a resumed session cover the earlier runs of the call too. A call whose model has no known price, or whose provider reports no token counts (the Gemini CLI path), counts as unpriced, and subscription use is not billed per token, so the cost is an estimate of the same calls on the API. `usage` also holds the totals for the round, per stage (`perStage`) and per model (`perModel`), and in `limits` the newest reading of each subscription usage window the Claude and Codex CLIs reported: the account, the window, the share used and the reset time. Its `durationMs` is the time spent in model calls, and `wallClockMs` the wall-clock time of the whole run, the same time the finished progress comment shows in its headline, such as "Review complete in 4m 12s". Each call also records `promptDigest`, the first 12 hex digits of the SHA-256 of its system prompt with every number in it replaced, so calls before and after a prompt change compare and the counts a prompt quotes, such as the open threads, do not split one version (an edit that changes only a number in a prompt keeps its digest, so `meta.mankiVersion` tells such versions apart), and the judge's digest hashes its prompt with every round-dependent section on, so it changes only with the template or the repository's rules, and for a call with tools its `stepBudget`, and on a call through the Claude or Codex CLI `wrapUpNoted`, set when the model used enough steps to be told to wrap up. A call with tools through the Claude or Codex CLI also records `toolSteps`, each tool it called in order and an empty list when it called none, and `filesRead`, each file it read once, relative to the repository root, with `owner/name:` in front of a file in a related repo and the package as the call names it, such as `crates.io/time:`, in front of a file of a dependency, so a missed defect can be told apart from a file no finder opened. A step names its tool as the Claude CLI does, so a tool of Manki's tool server is `mcp__manki__read_file` on both CLIs and the Claude CLI's own file reader is `Read`. A step records how long it took (`durationMs`) when the CLI reported its start, the file it read in the spelling of `filesRead` (`file`), and the characters of text its result gave the model (`resultChars`), so the record shows which files each finder opened in which order, which it opened more than once, and how much text each read added to its prompt. A call that failed keeps its `filesRead` but no `toolSteps`. `meta.promptVersions` lists the distinct digests per stage. Each finder, sibling comparison, related repository check and claim check whose read finished records `inputDigest`, and a retry that kept its result marks it `reused` and names the attempt in `meta.reusedFrom` (see [Review pipeline](#review-pipeline)). The record also keeps why a round paused (`meta.needsHuman`, its cause and blockers), how each static analysis source ended (`staticAnalysis.sources` for checks, code scanning and dependency review, with the reason one gave nothing, such as an HTTP 403, next to `staticAnalysis.analyzers`, where `skippedFiles` names each lockfile the `dependencies` scan left out and why, such as a symlink, a file over the budget or a failed fetch), the learnings and suppressions memory loaded and each finding a suppression hid with the suppression's id (`memory.loaded`, `memory.suppressed`), and each call the run made to the token service before it posted, with its status, and for a failed one the error and the service's request id (`tokenService`). `runner` describes the machine and what the run took from it before it posted: `environment` (`github-hosted` or `self-hosted`), `os`, `arch`, `cpus`, the machine's `memoryBytes`, and `memoryLimitBytes` when a container limits the memory below that. It never holds the runner's name, since the record is posted with the review and a self-hosted runner's name can be a host name. `queuedMs` is the time from the start of the workflow run until Manki started, so the wait for a runner and the job's steps before Manki. It is left out when the workflow token cannot read the run, which needs `actions: read`, and when GitHub does not answer within ten seconds. Manki reads the run while it reviews, so a review posted before the answer has no `queuedMs` either, and its footer no such time. The last line of the run log still shows it. `peakMemoryBytes` is the most resident memory Manki and its child processes held at once, such as the model CLIs, git and the analyzers. Manki samples it every two seconds on Linux and macOS, and other systems leave it out. `peakCliProcesses` is the most model CLI processes that ran at the same time. The run log ends with the same figures, also for a run that posts no review. Each reply Manki posts in a thread or to a command carries the same usage in a hidden `<!-- manki-reply-record: ... -->` comment. A review state check that approves, holds or withholds the approval puts a hidden `<!-- manki-approval-record: ... -->` on what it posts: the approval review, or the held or withheld notice while that stands. It records the decision, the reason, the head commit and how many of Manki's threads are resolved. A check that skips posts nothing, and its decision shows only in the run log and in the token service's `coordinator_finished` log line. A reply record also keeps the token service calls of its run, and for a thread reply that opens with `Fixed`, `Agreed` or `Withdrawn` what it decided for the thread (`decision`): it resolves the thread, the thread stays open for a maintainer, a resolved thread stays resolved and keeps blocking, Manki could not resolve it, the replier may not resolve it, the thread was already resolved, is not found or could not be looked up, a later round already judged the fix, or the PR is merged or closed and the thread stays as it is.

Each finding, kept or dropped, records `gradePath`: every change of its severity after the reviewer graded it, in order, with what changed it and, where the stage said, why. The steps are `judge`, `rule` (a confirmed [rule finding](#rules-from-instruction-files) raised to the grade `review.rules` sets), `unproven` (a blocker without proving lines posted as a warning), `build_claim` (a blocker that claims a build, type or test failure no CI result reports, posted as a warning), `refutation`, `in_pr_suppression`, `own_proposal`, `ratchet`, `resolved_thread`, `pre_existing`, `own_fix` (a blocker restating a thread whose own suggested fix the push applies, posted as a warning), `unconfirmed_raise` (a blocker the judge raised above every finder's grade that no check confirmed, posted at the highest grade a finder gave it) and `other_finder` (a blocker or warning the [other finder's vote](#the-other-finders-vote) declined, posted one step lower). A finding the judge graded records `cell`: the row and column the grade was worked out from, with `judgeColumn` when Manki graded it in another column than the judge stated, because it is a security finding. An earlier record can hold `judgeColumn` on a finding a check moved out of the rare column. A blocker that two disproofs or an unconfirmed raise put back at its finders' grade records `judgeCell` in place of `cell`, and `reviewerSeverity` is the highest grade a finder gave the finding or a duplicate merged into it. `lowestReviewerSeverity` is the lowest such grade, recorded only when the finders split on it. A finding the judge doubted records `gradeIfConfirmed`, the grade its cell gives once every doubt holds, and its `doubts`, and its refutation records the answer to each premise under `premises`, each with what that premise decided when the check ran (`decides`). A finding the judge dropped for a reason about code outside the diff, when the refuter checks that drop, records the cell the judge stated for when the premise is false, the grade of that cell as `gradeIfConfirmed`, and the premise among its `doubts` with `decides: drop`. A disproof of that premise backs the finding, and a confirmation counts against it. A check stored without that is read against the doubts the finding has now, and a premise none of them names counts as one that decides whether the defect exists. A refutation that ended unsettled records `stepsUsedUp`: `yes` when its call ended on its step budget, so it took enough tool steps to be told to finish (12 of its 15) or took them all, which also holds for a call that was done anyway, `no` when it took fewer, and `unknown` when the client did not report the steps of the call. An open lead's entry in `leads` holds the same refutation, so the record shows how often a lead was left unsettled by a check that may have run out of steps. A `gradeIfConfirmed` of `warning` beside a `cell` that gives a blocker marks a finding no confirmation raises: the judge stated `warning` for that case, or not every finder filed a blocker or only one of two or more finders reported it, the finding is no security finding, it restates no earlier blocker and the judge named no consequence. The doubt that states the consequence records `consequence: true`. `judgeIfConfirmed` is the judge's own answer for that case, `blocker` or `warning`, and is missing when the judge stated none. For a finding in the rare column of the wrong behaviour row, `gradeIfConfirmed` is the grade of the normal column, which no check gives it. The answer to its premise tells a rare claim the code bears out (`disproved`) from one the check contradicts (`confirmed`) and one nobody could settle (`unsettled`), and a doubt with no refutation was never checked. A finding the reviewer marked pre-existing and the judge kept records `preExisting`: the reviewer's reason and how the claim was checked, `pre_existing` when it held, or the condition that failed (`no_location`, `excluded_file`, `deleted_file` or `touches_diff`). A finding memory hid is listed in `memory.suppressed`. Each entry of `findings.entries` records `posted`, where the round put the finding: `thread` for a thread of its own, `body` for the review body, or `earlier_thread` when a thread from an earlier round carries it. A warning that holds the approval, with a thread or without one, also records `holds`. An entry of `findings.unposted` records `record`. `findings.originsWithoutPrior` is set on a later round that tagged its findings without the PR's change at the last reviewed round, which is a "Review again" run or a failed fetch of that change. `findings.carried` holds the warnings the round carried from an earlier round's review body, each with `raisedIn` and `citedLine`, and `findings.carriedEnded` the ones it stopped carrying, each with its reason. They do not count in `findings.count`. An entry that restates a finding an earlier review body listed records `sameAs`, the key of the entry that listed it first. A round that read the diff in slices records the number of files in each slice and the verdict reader's answer on each (`slicing`). `diff.changedSinceLastRound` is the number of changed files the push since the last round touched, `judge.fixClaimedThreads` the threads where someone claimed a fix, and `approval` on a round that approved whether the approval was held, and why, with `warningsHeld` when warnings held it too. To pull the round and reply records of a PR or a whole repo into one JSON Lines file, run `npm run review-history -- <owner/repo> [<pr number>] > history.jsonl` in a manki checkout. A round record that does not decode gets a line of `kind` `undecoded` with its `repo` and `pr` in its place, so a reader knows the rounds of that PR are not all there. Add `--calls` to get one line per LLM call instead, ready to sum per agent, stage, model, PR or repo. The script decodes compressed records and reads the token from `GITHUB_TOKEN` or `gh auth token`.

To see whether a change to the review helps, run `npm run review-stats -- --repo <owner/repo> [--last <n>] [--fix-rate <fix-rate.jsonl>]` in a manki checkout before and after it. It reads the round records, approval records and thread replies of the last `n` merged PRs (40 by default), only reading from GitHub, and prints a markdown report:

- rounds per PR (mean, median and max), the share that passed after one round, the share that needed 5 or more, and the rounds that ended incomplete. A round numbers itself from the earlier records it could read, so a round after a failed read can call itself round 1 again. A PR whose round records do not all decode, or are not rounds 1, 2, 3 in posting order, is left out of every figure that reads a round number: the share that passed after one round, the findings first raised in a later round, the follow-up rounds and the rounds a carried warning waited. The report says how many PRs it left out;
- the approved rounds, and how many PRs ran more rounds after their first approval, with the number of such rounds;
- findings per round and per approved round by severity, and of the findings a later round raised for the first time, the share on code an earlier round reviewed. A finding the round put under an earlier Manki thread counts in none of these, such as another instance of a finding that went into its thread as a reply. A record from before the `posted` field does not say where a finding went. For those the script leaves out a finding that names an earlier thread, or that matches one by file, title and line. It cannot tell whether that thread was still open at that round, so it also leaves out a blocker posted again after its old thread was resolved. A finding first raised in a later round counts only when that round ran on Manki 7.5.0 or later, read the change the round before reviewed, and read the diff since that round. A round without the earlier round's change, which is a "Review again" run or a failed fetch of the change at the last reviewed commit, tags every finding `new` and says so in `findings.originsWithoutPrior`. A round without the diff since the last round can tag a line a push deleted or restored as reviewed, and records `judge.interRoundDiffState` as `unknown` or not at all. A note on reviewed code is not posted, so it counts in none of these either, and shows under `reviewed_code` in the table of findings recorded without posting;
- the blockers and warnings found in round 1 against those a later round first raised on code an earlier round had already reviewed. It gives the share found in round 1 per grade, in total and per PR. A finding round 1 posted counts even when its thread was resolved later. A later finding on code a push changed since the round before is not late, and a pre-existing finding counts in neither. The record does not say which earlier round read the lines, so a later finding on code a push after round 1 added counts as late too. A PR counts only when its records prove all this: every record decodes, its first record in posting order is of round 1, each later record is of the round after the one before, and each later round that posted a blocker or warning ran on Manki 7.5.0 or later, read the change the round before reviewed, and read the diff since that round. Without that diff a round can tag a line a push deleted or restored as reviewed. The same condition holds for the findings first raised in a later round on code an earlier round reviewed. A round numbers itself from the earlier records it could read, so a round after a failed read can call itself round 1 again. The report names the PRs it leaves out, how many have no round 1 record and how many of their round records cannot say;
- with `--fix-rate`, which takes the repository's `metrics/fix-rate.jsonl` from its memory repo, the fix rate by severity and by check status for the same PRs. A finding counts as fixed when the judge marked its thread addressed or a later commit touched its lines, whether or not that commit fixed it;
- how blocker threads ended: fixed, withdrawn by Manki, or other;
- per finder model, the raw findings, the kept findings only that model raised and those it raised with another finder, and the tool steps per call;
- per finder and round, by model, the tool steps, the files read, those of a related repo, the share of the other files the round's diff changes, the steps of the built-in `Read`, of Manki's `read_file` and of every other tool, and the characters of text per `Read` and per `read_file` step, which show how close the reads come to the limit of either tool. The finder's prompt already shows a changed file, unless the file did not fit the prompt's size budget. A call whose record lists no tool steps, such as an older record of a Codex call, counts in none of these. A call that failed keeps its files but not its steps, so it counts in none of these either. A second read is no finder and counts in none of these, and the table of second reads below counts it;
- the verdict reader's blockers, and the refutation outcomes per severity, counting the findings a disproof dropped, unposted ones and leads left unsettled, and an answer a later round reused only once;
- for the second refuter on `models.second_refuter`: what it cost, with the number of calls that had no known price, how often it agreed with the first refuter, how often the two split with one confirming and one disproving, and how often it changed the outcome the first refuter alone gave, with a count per pair of outcomes;
- for the [sweeps](#sweeping-for-a-defect-class) of `review.sweep`: the rounds that started one, how the sweeps ended, the places they reported, how many of those the rounds posted, recorded without posting or the judge dropped, what the sweep calls and the dedup, judge and refuter calls that ran only for what they reported cost, and with `--fix-rate` the fix rate of the findings a sweep raised beside that of every other finding;
- the cost per PR and per round, and the share of follow-up rounds whose inter-round diff was cut or unknown;
- how often each finder model was told to wrap up, the files changed since the last round, the fix claims, the memory loaded and the slices per round;
- per related repository, the rounds it was configured in and the rounds that read it, the reads per such round, and its fetch failures and skipped rounds;
- per week, account and subscription usage window, the highest share used any round read, and how many rounds read it at or past 70, 80 and 90%;
- a table per decision the records keep: prompt versions per stage, pause causes, static analysis sources with skip reasons, grade changes, pre-existing claims, rule findings per answer of the judge and grade, including the ones the judge dropped, memory suppressions, the findings recorded without posting per reason and severity, where a finding the judge dropped takes its severity from the last step of its `gradePath`, the warnings carried from an earlier review body, listed again by how many rounds ago they were first listed and ended per reason, the verdict reader per slice, the second reads per round with how many ran, the blockers and warnings they added and why they stopped, approvals, state check approvals, thread reply decisions and token service calls.

A scheduled workflow, `.github/workflows/review-stats.yml`, runs the report for manki and token-service every Monday and posts it as a comment on the open issue titled "Weekly review statistics", which it opens the first time. It takes the fix rates from the central memory repository. It uses only the workflow's own token, with read access and `issues: write`. Run it by hand from the Actions tab.
