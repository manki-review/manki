# How reviews work

What Manki does on each round, how it picks its readers, how it grades findings, and what it reads besides the diff.

## Review pipeline

Manki reviews run in these stages:

1. **Planner** (pre-review): A fast Haiku pass answers three questions about the nature of the change, never its line count, plus the judge effort and PR type. A repository can fix the judge effort with `judge.effort` instead. `trivial`: could a defect hide here at all? A trivial change (docs, a rename or move, a repeated mechanical edit, dead code, fixtures) is read by a single **quick check**. The planner sees only the list of changed files, never the PR title, description or diff text, and Manki believes a `trivial` answer only when every changed file is docs, snapshots or generated, deleted, or renamed without edits. A change to tests alone is not trivial: one finder reads it. `subtle`: does judging it need reasoning about behavior? That sets the finders' effort to high, otherwise medium. `paired`: could a defect reach a user if every reader missed it? By default that adds a second finder. A missing or unclear answer, a timeout or a disabled planner takes the side that adds review: by default two finders at high effort. A diff that touches a security-sensitive path (auth, tokens, secrets, crypto, sessions, permissions and similar), CI or automation (`.github/workflows/**`, `.github/actions/**`, `action.yml`), a dependency or toolchain manifest (`package.json`, lockfiles, `Cargo.toml`, `go.mod`, `pyproject.toml`, `requirements*.txt`, `Gemfile`, `*.gemspec`, `rust-toolchain*`, `.nvmrc`, `Dockerfile*`), or a data contract (`migrations/**`, `*.sql`, `*.proto`, `schema.*`, `openapi*.yml`, `openapi*.yaml`, `openapi*.json`) is never trivial and always paired, whatever the planner or `planner.paired` say. Each round is triaged fresh. See [Review groups](#review-groups) for how the answers and paths pick the readers.
2. **Finders**: The readers of the PR's [review group](#review-groups) read the diff in parallel. Which group a PR gets and who is in it is yours to set. By default it is one finder on `models.reviewer`, plus on paired rounds a second on `models.reviewer_pair`. Every finder runs the same checklist, so the default pair differs only in its models, and a reader of a group of your own can add a `focus` line. It checks the change itself: correctness first, then security, including resource exhaustion from outside input such as an allocation sized by a length a caller passes. When the PR title, description or changed code says the change matches another implementation, a spec or a standard, it opens that code, in a `reference` related repository when one is configured, and reports each difference. When the code implements or mirrors a reference, such as a spec, another implementation or an API it talks to, it compares each contract in both directions: what the code produces against what the reference accepts and the other way round, along with limits, field order, field types and versions. Then it checks error paths, cases a pattern match, error handler, ignored result or fallback drops, and tests that would still pass if the change were reverted or that set internal state. It looks for an existing helper the change could reuse and for breaks of the rules in the repository's `AGENTS.md`, `CLAUDE.md` or `CONTRIBUTING.md`, and reports such a finding only with the helper's `file:line` or the rule quoted. It also goes through the rules about the change as a whole, such as a test or a migration that a kind of change requires (see [Rules from instruction files](#rules-from-instruction-files)). Then it checks contract breaks, and when the change narrows what it accepts (a lower or new limit, stricter validation, a narrower type, a new required field or a stricter format) it finds every producer of that input, in the repository or a reference it mirrors, and checks that each still fits. It also searches outside the diff: every reader of a changed type, field, variant or function across the repository, sibling state that holds the same item or is computed from it (other collections, caches, indexes, derived totals or counts, serializers, change notifications), and counterparts that must check alike, such as encode and decode. Every finder gets any `reviewers:` entries. Every round, each finder searches the whole PR: it reports every blocker, warning and security issue it finds, follows the callers of changed code and other routes to the same outcome, and for each defect checks the whole PR for the same kind, reporting one finding that lists every place. Without `models.reviewer_pair` the second finder runs on the other Claude tier (Sonnet with Opus), which needs no extra credential. Another provider is used only when you set it. If any finder fails after its retry, the round ends incomplete and never approves.
3. **Sibling comparisons**: Alongside the finders, small targeted calls on `models.reviewer` compare the changed code with the code beside it: whether a sibling field can hold the item a changed line looks up, and what checks one implementation of a function has that its siblings lack. Their findings go through dedup and the judge like any finder's. See [Sibling comparisons](#sibling-comparisons).
4. **Dedup**: A two-tier dedup pass drops findings that repeat an earlier resolved finding before judge evaluation. A static matcher handles exact and near-exact titles on nearby lines, and matches a thread whose code moved on the line it was posted on. Then an LLM dedup pass (Haiku) compares each finding's title, line and description with the earlier resolved findings in its file, so a repeat in other words is caught too.
5. **Judge agent**: A single agent evaluates the deduplicated reviewer findings for accuracy, actionability, and severity. It filters out noise, merges any remaining overlap, and grades each surviving finding as a blocker, a warning or a note. It reads each finding's code and the diff of every file with a finding, a line a finding cites as proof, or an open thread, cut to 200,000 characters when those files are larger. With `review.sweep`, each blocker it keeps can start a [sweep](#sweeping-for-a-defect-class) for other instances of its defect class, whose findings it then judges too.
6. **Verdict reader**: Runs only when no finding blocks. It reads the whole diff cold on the judge's model, without the PR description or earlier rounds' findings, and looks for a reason not to merge. A large diff is read in the same slices as the finders, one call each, and the PR is `READY` only when every slice is. Each call is told which slice it reads and which changed files only the other slices hold, so code missing from its slice is no defect. The blockers of all slices are posted. A finding the judge kept that names the same problem as one of them is folded into that blocker, so one problem gets one thread. It counts as the same problem when both sit in one file at most 5 lines apart and cite at least one common line of that file as proof, within 5 lines of both, whatever their titles say. It also counts when one title contains the other, and they are at most 5 lines apart or one cites the other's line as proof. Titles that only share words must each cite the other's line. A finding these rules leave apart is still checked when it sits near the blocker: their lines or narrow proof lines are at most 5 lines apart. The dedup model gets every such pair of the round in one call. It folds a pair only when it answers that both describe the same defect, with the same root cause and the same fix. Without a dedup model, or when the call fails, the pair keeps two threads. A proof line counts only as a single line or a span whose first and last line are at most 5 apart. When the folded finding's title says something the blocker's does not, the blocker's description ends with "Also reported as:" and that title. From the second round it also gets the files changed since the last reviewed round, as the finders do. `READY` approves with "What this does" and "What to test" sections. `ADDRESS_FIRST` requests changes and posts its blockers as inline comments, each with what the reader checked and the lines that prove it. When the judge has repository tools, it first tries to refute each of these blockers as it does its own, and the outcome closes the collapsed section under the blocker, after its fix and checks. Output that cannot be parsed ends the round as incomplete, never as an approval.
7. **Review posted**: Surviving findings are posted as inline PR comments or listed in the review body, under a summary and the verdict.

No finder or verdict reader prompt cuts the diff. They read it in slices of about `slice_lines` changed lines and at most 200,000 characters, so a normal PR is read whole in one call, and each call is told which slice it reads. A file with more changed lines stays whole in a slice of its own, and one over 200,000 characters is split between its hunks, or inside a hunk between lines. An added line over 20,000 characters cannot be shown in full, so a round whose reviewed diff holds one ends incomplete before any model runs, and names the first 10 such lines. Split the line, or exclude its file in `exclude_paths` on the base branch. Lines in excluded files do not count. A longer removed or unchanged line is shortened, since cutting it hides no new code, so deleting a minified file still gets a review. Each slice costs one call per reader, so the size of the reviewable diff is also capped in characters, next to `auto_review_max_lines` and `max_diff_lines`. A PR over 2,000,000 characters gets no automatic review, only the too-big notice with Review again in its settings block, and one over 4,000,000 is never reviewed, even when forced. These two limits are fixed.
When a provider's safety filter refuses a stage, Manki sends that stage once more on `models.fallback`, which defaults to `models.reviewer`. A stage already on that model goes to its other Claude tier instead. The round context records the stage, the fallback model and the refusal reason under `models.fallbacks`. A second refusal fails the stage, which ends the round incomplete for a finder, the judge or the verdict reader, and other errors are never retried on the fallback model. A used-up subscription limit, quota or rate limit, or an overloaded provider, is neither retried nor sent to the fallback model. The round ends incomplete and names the limit, with its reset time when the provider gives one. To see it coming, the Review metadata section of the progress comment lists how much of each usage window the Claude and ChatGPT subscriptions have used, as the Claude and Codex CLIs report it after their calls, with the reset times. A call that fails, such as on the used-up limit itself, keeps its readings too. When a window has just passed the 70% or 80% mark, at most 2 points past it, the review body shows a red box under the verdict. From 90% the box shows on every review. It names each such window and the highest of the 70, 80 and 90% marks it passed. The readings in Review metadata show on every review either way. API keys and Gemini report no such windows, so they show none.

An incomplete round posts a comment, fails the `Manki` check and keeps an earlier request for changes. It dismisses Manki's approval of an older commit, since no model approved the code pushed since. An approval of the same commit stays. The comment carries the round's record, with what ran and what failed. A later round does not count it as an earlier round: it does not use up the round cap, and the next round compares against the last round that completed.

## Review groups

You decide who reviews what. Each round sorts the PR into a **review class**, and the class picks a **review group**: the readers that run as finders. The `review` block configures all three. A group lists one or more readers, each with its own model from any supported provider, its effort and an optional `focus` line. A class matches PRs by path, by the planner's answers or both. The routing names the group for each class. Without a `review` block the built-in classes and groups below apply, which give a PR the quick check, one finder or two.

The class with the highest rank among those that match wins.

| Class | Rank | Matches | Built-in group |
|-------|------|---------|----------------|
| `security` | 100 | a security-sensitive path (`@security_paths`) | `pair` |
| `supply_chain` | 90 | CI, automation, a dependency or toolchain manifest, a file that fetches or builds code such as `.gitmodules`, `.gitattributes`, `.npmrc`, `build.rs`, `setup.py`, a `Makefile` or a `.husky` hook, or a `.manki.yml` or `manki.yml` anywhere (`@ci_dependency_paths`) | `pair` |
| `data_contract` | 80 | migrations, `*.sql`, `*.proto`, `schema.*`, OpenAPI files (`@data_contract_paths`) | `pair` |
| `behavior` | 50 | the planner answered `paired: true` | `pair` |
| `internal` | 30 | the planner answered `paired: false` | `solo` |
| `docs` | 20 | the planner answered `trivial: true` and every file is prose (Markdown, reStructuredText, AsciiDoc or a license), a snapshot or generated, deleted, or renamed without edits. Agent instructions such as `AGENTS.md`, `CLAUDE.md` or files under `.claude/`, `.cursor/` or `.github/instructions/` never count as prose here | `trivial` |

The built-in groups are `trivial` (the quick check on `models.reviewer` at medium effort), `solo` (one finder on `models.reviewer`) and `pair` (a finder on `models.reviewer` and one on `models.reviewer_pair`). Their effort is `auto`: high when the planner answers `subtle: true`, otherwise medium.

The progress comment names the class and group in its review header, such as `Review (security · pair)`. It names each reader by its model, the effort it ran at and the start of its `focus` when one is set, such as `Claude Sonnet 5.5 · high` or `Claude Opus 5.5 · high · consensus rules`. The quick check shows as `Quick check · Claude Sonnet 5.5`. A second reader with the same name gets ` #2`. The same names appear in failure lines, logs and the `Manki context` block.

`security`, `supply_chain` and `data_contract` are **floor classes**. Path rules decide them, so nothing in the PR's text can change them. A PR in a floor class always gets at least two finders on two distinct models, none at `low` effort. The one exception is the built-in `pair` group when `models.reviewer` is not a Claude model and `models.reviewer_pair` is unset: both finders then run on that model. The floor is checked after routing: if the routed group misses it, the PR moves up to the floor class's own group, then to the built-in `pair` group. So a class of your own that outranks `security` cannot pull a PR that also touches auth into a weaker group.

The `review` block changes the groups and the routing:

```yaml
review:
  groups:
    deep:
      reviewers:
        - { model: claude-opus-5-5, effort: high }
        - { model: gpt-5.5, effort: high }
  routing:
    security: deep
    data_contract: deep
```

That minimal example sends security and data contract PRs to two strong readers on two providers and keeps the built-ins for the rest. A fuller one:

```yaml
review:
  default_group: pair
  groups:
    solo:
      reviewers: [{ model: "@reviewer", effort: auto }]
    pair:
      reviewers:
        - { model: "@reviewer", effort: auto }
        - { model: "@reviewer_pair", effort: auto }
    deep:
      reviewers:
        - { model: claude-opus-5-5, effort: high, focus: "authz, injection, secret handling" }
        - { model: gemini-3-pro, effort: high }
        - { model: claude-sonnet-5-5, effort: medium, focus: "error paths and rollback" }
  classes:
    security:                      # adds paths to the built-in rule, never narrows it
      match: { paths_any: ["src/billing/**"] }
    hot_path:
      rank: 85
      match: { paths_any: ["src/consensus/**", "src/net/**"] }
  routing:
    security: deep
    hot_path: deep
    internal: solo
```

- **`groups`**: each group lists its `reviewers`. A reviewer takes `model` (a model id, `provider/model`, or `@reviewer` and `@reviewer_pair`, which resolve through `models`; unset means `@reviewer`), `effort` (`low`, `medium`, `high`, `xhigh`, `max` or `auto`, the default), an optional `focus` line added to that finder's prompt, and `role` (`finder`, the default, or `verifier` for the quick check). A group with the name of a built-in replaces it.
- **`classes`**: a new class needs a `rank` no other class has, and a `match` with `paths_any` (globs, or the `@security_paths`, `@ci_dependency_paths` and `@data_contract_paths` aliases), `triage` (`trivial`, `subtle` or `paired` set to true or false), or both. Every condition must hold. On `security`, `supply_chain` and `data_contract`, `match.paths_any` adds paths to the built-in rule. The other built-in classes cannot be changed.
- **`routing`**: the group per class. Classes you leave out keep their built-in group. When you set `groups` but no `routing`, every class goes to `default_group`, and the floors still apply.
- **`default_group`**: the group for a class with no route (default `pair`).
- **`allow_weaker`**: floor classes allowed to route to a group below the floor, such as `allow_weaker: [security]`. Without it, a config that routes a floor class to a weaker group does not load, and the warning gives the reason. Once such a config is on the base branch, Manki reviews with the default settings and does not approve. Every round that runs below the floor logs a warning.
- **`critical_paths`**: globs, or the path aliases above, that mark critical areas, where any wrong result is severe even in a rare internal edge case. They need no class or rank, and can name paths a built-in class already matches. The judge sees which findings sit in a critical area, with the first glob that matches, and grades a wrong result there as severe damage, which blocks when the other blocker tests hold.
- **`outside_input`**: what counts as outside input in your repository, in a sentence or two. The judge treats a failure that this input can trigger as reachable, never as a rare internal case.
- **`examples`**: worked examples from your repository, one string each, under `blocker` for findings that block and `not_blocker` for findings that do not. Set either side or both. The judge reads them next to its built-in examples on the same two sides.

The last three only change how the judge grades findings. A repository with consensus code might set them like this:

```yaml
review:
  critical_paths: ["dash/src/consensus/**", "dash/src/blockdata/**"]
  outside_input: >-
    Anything a network peer sends: P2P messages, blocks, transactions, headers
    and the length prefixes inside them.
  examples:
    blocker:
      - "Indexing `buf[len]` with a length read from a peer message panics on a short message."
      - "Changing the field order in a `consensus_encode` implementation changes the bytes on the wire, even when every test passes."
      - "An inverted weight comparison picks the wrong quorum member on every block."
    not_blocker:
      - "A debug log of a decoded message that leaves out the peer address: `note`."
```

Each review's `Manki context` block records a `routing` object: the class, its rank and source, every matched class, the group and why it was picked, any floor and escalation, where the `review` block came from, a `configDigest` of the classes, groups and routes, and each reader's model, provider and effort. Each finder's entry in `reviewers.agentMetrics` counts the kept findings only it raised (`keptOnly`) and those it raised with another finder (`keptShared`).

Manki reads the `review` block, like every other setting, from the PR's base branch only, so a PR cannot weaken its own review. A PR that changes the block is reviewed with the base branch's, and the change applies after merge. When the PR's own block does not load, for example because it misses a floor, Manki logs a warning and still reviews with the base branch's block. If the PR itself changes the file, Manki also holds its approval, so it never approves a broken block. When the base branch's config cannot be read, or does not load because its block is invalid or misses a floor, Manki uses the built-ins and the default settings with a warning, never the PR's copy, and does not approve. The PR that fixes it still gets reviewed. The models behind `@reviewer` and `@reviewer_pair` come from the base branch's `models` block.

`planner.paired` still works and is deprecated in favour of `routing`: `always` turns `paired` on before the PR is classified, and `never` turns it off, which routes `behavior` changes to the `internal` class and its group.

## Severity tiers

Each finding gets one of three severity levels, or is dropped:

| Severity | Meaning | Effect |
|----------|---------|--------|
| `blocker` | Must fix before merge | Blocks approval (REQUEST_CHANGES), posted as a review thread |
| `warning` | Should fix, but not blocking | Listed in the review body, PR can still be approved |
| `note` | An optional improvement, never a defect | Listed in the review body, never as a thread, PR can still be approved |
| `ignore` | False positive or irrelevant | Dropped silently |

The judge returns no grade. For each finding it states a cell of its severity table: the row is what goes wrong (severe damage, wrong behaviour, degraded but correct behaviour, an improvement, or style), and the column is whether normal use or outside input reaches it, or only a rare internal edge case. Manki works out the grade from the cell, so the judge has no field in which to lower a grade for a reason of its own. A reply that leaves a finding out, or gives it an entry that names no row of the table, is not complete. Manki keeps the entries the reply does have and asks the judge once more for the missing ones only, together with any open thread the reply did not evaluate. If a finding still has no entry after that, the judge fails, so the round ends incomplete instead of posting a grade the judge did not give. A thread that is still not evaluated stays open.

A finding is a blocker only when it passes five tests: the PR causes it (lines it adds, changes or removes), the failure can be named ("when X happens, Y goes wrong"), the damage is serious, the code proves it with cited lines, and the author would fix it (it is not a declared placeholder, a stub that does nothing yet and that no path reaches, or a tracked TODO, which make it a note at most unless it is a security defect). Serious damage is wrong behaviour in normal use or from outside input, lost or corrupted data, a crash, hang or resource exhaustion from outside input, a security defect, memory unsafety or undefined behaviour, or a broken public contract with no migration. Wrong behaviour in a rare internal edge case is a warning. The rare column is a claim, and on the wrong behaviour row Manki checks it: it adds the premise that normal use or outside input can produce the state to every such finding, and the refuter searches for a caller, stored data or concurrent use of a public API that produces it. When the refuter confirms that premise and every doubt the judge named, the finding moves to the normal column and gets that cell's grade. One that says something is missing and cites no search that came back empty stays a warning even then, since a confirmed reach is no such search. No other confirmed doubt stands in for that premise. A claim the refuter disproves, cannot settle or never checks leaves the finding where the judge put it. Degraded but correct behaviour is a warning, or a note when rare, and there the column is taken as stated, since it blocks nothing either way. Missing tests, style, naming, docs, commit messages, performance without a crash and checks on trusted internal values never block. A test that cannot fail when the code it names breaks is a warning, and a doc that says the code does something it does not is a note. For a library, outside input is anything a caller of its public API can pass, such as readers and byte streams, and resource exhaustion or denial of service from outside input is a security defect. Behaviour that is intended but surprising becomes a note that asks about it, unless it is a removed guard, resource exhaustion or a security defect. A gap the author admits is no such choice: one the PR description, a comment or a TODO calls deferred, out of scope, left open or not handled yet keeps the grade its damage earns, and only a declared placeholder or a TODO with a tracking issue lowers it. A defect in lines the PR adds is the PR's own, even when the bad state those lines mishandle existed before, so "not worse than before" is no reason for a lower cell. The defect a PR fixes in one path and leaves in a sibling path is the PR's own too: a PR that adds an auth check to `POST /items` and leaves `PUT /items/:id` open has an incomplete fix, which is never pre-existing. The judge and the verdict reader mark a finding that claims the code fails to compile, type-check or pass its tests. Such a claim blocks only when a CI annotation on the commit reports the error, unless it is a security defect. Otherwise it is posted as a warning that asks to check that it builds, since CI fails the build or the test itself. Code the judge cannot see never drops a finding: the judge sees the uses outside the diff and the code each finding cites outside it, a finding that cites one of those is graded on its merits, and the judge grades a finding that rests on code beyond that as a doubt, so a blocker it cannot follow becomes a warning. A doubt that the failure is reached, such as no caller in the code shown, is graded the same way, and a path through a library's public API counts as reached without a caller in the repository. A value the code shown proves the code's own logic keeps valid is evidence, not a doubt, so the rules for rare internal edge cases and trusted internal values still apply to it. For every finding the judge states the row its consequence would earn if every premise it doubts holds, such as unseen code, reachability or whether the PR causes it, and lists each doubted premise as a fact the code can confirm or disprove. A premise its reasoning settles from cited lines is no doubt and is not listed. A premise that lowers or caps the grade, such as callers probably validating a value, counts as a doubt too unless the code proves it. Each premise decides either whether the defect exists at all or only which cell it earns. Manki grades a blocker cell with an open doubt as a warning until the refuter confirms every doubt, except on a security finding or a tool alert. A doubt about the cell alone counts only on the wrong behaviour row, where the column decides whether the finding blocks. On every other row Manki drops it, so only a doubt whether the defect exists holds a severe finding down. A doubt alone never drops a finding that would earn a warning or a blocker. The finders, the judge, the refuter and the verdict reader treat everything they are told about the code as a claim to check: the PR description, code comments, linked issues, author replies, another model's finding or reasoning and an earlier round's verdict. A claim the code confirms is evidence. One they cannot check is noted but never raises or lowers a grade on its own. The exceptions are an author's statement that behaviour the code shows working is intended, a declared placeholder or a TODO with a tracking issue, and a PR description that says a change breaks no consumer. Review memory is the maintainers' recorded decision, not a claim to check, and so are the rules in the repository's instruction files, which the judge sees as the finders do. A finding that says the change breaks one of those rules is checked against the rule's text, and a convention such as naming or import placement is graded a note. The judge grades a finding on its central claim: a wrong side detail, such as an off line number or a misnamed helper, is corrected in its reasoning and never drops the finding on its own. A later round keeps a finding's cell unless the code or the evidence changed, but only a cell with no doubt behind it anchors. For a finding from a record that stored only a grade, the judge states a cell that gives that grade. A grade an earlier round kept below its conditional grade is regraded from the code, and when the judge keeps it without naming a doubt while no check settled the earlier one, Manki sends the earlier doubts to the refuter.

With `judge.tool_steps` above 0, a judge with repository tools also reads the code a finding rests on while it grades, up to that many calls, so code it read counts as code shown and only a doubt its calls left open goes on to the refuter. It is off by default, since it makes the judge call longer. When the judge has repository tools, it also tries to refute each blocker, each open lead graded `blocker` or `warning`, each blocker posted as a warning for want of proving lines or of a CI result, each finding that would earn a higher grade if a premise the judge doubts holds, such as code it could not see, a path it doubts is reached or the rare column of the wrong behaviour row, and up to four findings a round that the judge keeps at `warning` or above while doubting the defect exists, the highest grades first. A finding kept below `warning` with such a doubt is not checked. These checks run before Manki hides a finding that repeats one the author agreed with or resolved, so that step sees each finding's settled grade and never hides one a check raised to a blocker. A finding that step hides is checked only when a confirmation can raise it, so it takes none of the four checks. The refuter names the general rule the finding relies on, such as a language or library behaviour, and searches the unchanged code for code that relies on the same rule. One such counterexample that already builds or runs disproves the finding. For a reachability doubt the refuter searches for a path from an entry point. A public function, method or field is one when the repository is a library or its `review.outside_input`, which the refuter is given, names that API. In an application an exported function needs a caller. For a finding with such a doubt the refuter also sees the PR's change to the files the finding cites. It confirms a doubt that the PR causes the defect only when a changed line does, and never disproves a finding only because the change shown does not cause it. The refuter answers each premise the judge listed on its own. A finding with such a doubt gets the higher grade its cell gives only when every premise is confirmed. A disproved premise that the defect rests on drops a finding below blocker, and a disproved premise that only the grade rests on keeps the judge's grade. A confirmation makes an unproven blocker a blocker again, but a claimed build failure stays a warning, since reading code is not compiling it. The verdict reader's blockers get the same build claim check, and when every one of them was such a claim, the change stays ready. A lead it confirms is posted at its grade, one it disproves is dropped, and one below `blocker` it cannot settle is listed under "Not finished checking". A lead still unsettled carries over to the next round's judge as an earlier lead, matched by file and title, instead of coming up as new, and the progress comment lists it once with the round it first came up in. It carries over while its file is in the PR and known to be unchanged since the last round, for at most three rounds. A security lead the tools do not confirm stays posted. Each round records how each lead ended under `leads`, with the refuters' answers. One refuter's answer never clears a blocker: a disproved blocker keeps its grade, whether it came in as a finding or an open lead, and is posted with the reason the refuter gave, so a maintainer can weigh it. Text in the PR could steer the refuter, so only a person can let such a blocker go, or two refuters in the one case described below. A disproof still drops a finding graded below blocker, such as an open lead or a finding capped at warning for want of proof, when it cites a line of the finding's own file or of the diff. See [security](security.md) for the tools.

The refuter runs on the judge's model (`models.judge`). With `models.refuter_pair` set, a second refuter on that model checks the same findings at the same time, with the same prompt and tool budget. Models of one family can share a blind spot, so pick one from another provider. Unset, there is no second refuter and no extra call. An unsettled answer, or a call that fails, counts as no vote, and the other answer decides as it would alone. When one refuter confirms a finding and the other disproves it, or disproves one of the premises the judge doubted, the finding keeps the judge's grade and is posted with both reasons. Two disproofs lower a blocker in one case only: no finder graded the finding a blocker, the judge alone raised it to one, and both refuters disprove it on two different models. It then goes back to the highest grade a finder gave it and is posted with both reasons, and every rule for that grade applies to it. Every other blocker that both refuters disprove stays a blocker and is posted with both reasons, since text in the PR could steer both alike: a blocker a finder filed, also as a duplicate the judge merged into another finding, a security finding, a tool alert, an open lead, a blocker the verdict reader adds, and a finding that restates a blocker of an earlier round or an open thread that blocks, or sits in the file of such a thread. The blocker also stays when the second refuter fails, is unsure or confirms, when `models.refuter_pair` is unset, and when both answers come from one model. The round record keeps the model with each answer and the judge's cell as `judgeCell`. The next round's judge sees the finding at its finders' grade with no cell, so it has no blocker cell to restate. For a finding below blocker it works as one refuter does: one confirmation with no disproof raises it, and one disproof with no confirmation drops it. A security finding still changes only when confirmed. The round record stores the second answer as `pairRefutation` beside `refutation`, and the model as `models.refuterPair` on rounds where it checked a finding or an earlier answer of it was reused. Its calls are recorded under the `refute_pair` agent. The second refuter needs repository tools, so the Claude or Codex CLI, and runs only when the judge's refuter does. Otherwise the run logs a warning.

Only `blocker` findings block, in every round. A `warning` is listed in the review body instead of becoming a thread, so the round can approve. A blocker from the verdict reader blocks too. A security finding blocks only as a blocker. Manki grades it in the normal column of the row the judge states, since an attacker chooses the input, and no doubt holds it down. So a security defect with severe damage or wrong behaviour is a blocker, while one that only degrades behaviour, or one that cites no proving lines, is a `warning`, which does not block.

Every round reviews the whole diff as thoroughly as the first. From the second round, the finders and the verdict reader also get the files the author changed since the last reviewed round, listed ahead of everything else, and check that new code first. A rebase onto the base branch changes no file, and when the change since the last round is unknown, the list is left out. The finders also get each earlier blocker a judge confirmed fixed, and each open blocker whose file changed since the last round. A fix often closes only the route the blocker named, so they check the other routes to the same outcome.

A finding about code the PR did not touch is tagged `pre-existing`. It counts as one only when all of these hold: the reviewer marks it pre-existing with a reason the defect exists without this PR's change, its line is not one the PR adds, the judge keeps that mark, it sits outside every hunk of the PR's diff, none of the lines it cites as proof is in the diff, and the PR neither deletes its file nor leaves the file out through `exclude_paths`. So an unchanged caller that breaks because the PR changed a function keeps blocking. Reviewers report such defects too, so they are not lost. Manki posts only the pre-existing findings worth an author's time: blockers, warnings the judge is highly confident in, and security findings. It keeps the others in the round record only. A posted one shows "Pre-existing" in its header and is listed under "Pre-existing" in the review body. It never blocks: a blocker there is posted as a warning, and the round record keeps its original grade. A security finding is the exception. It keeps its grade and blocks wherever it sits. A blocker from the verdict reader is never pre-existing, since no judge checks its mark.

From the second round, each finding is tagged as new, previously missed or still open: new when it sits within a few lines of code the PR changed since the last reviewed round, previously missed when an earlier round already reviewed that code. Manki compares the PR's own change at both rounds by line text, so a rebase or shifted line numbers do not make reviewed code new. A blocker blocks wherever it sits. A warning on reviewed code gets no thread and is listed under "Missed by an earlier review" in the review body. A note on reviewed code is not posted at all. The round record keeps it under `findings.unposted` with the reason `reviewed_code`. Manki leaves one out only where it compared the lines with the earlier round. A round that could not read the PR's change at the last reviewed commit, or the diff since that commit, leaves out none of them, and neither is a note in a file outside the PR's diff. A finding that restates an earlier finding still open gets no thread of its own either. The judge links each finding to the earlier one that names the same defect, from every earlier blocker and every other earlier finding still open, in a thread or in a review body. A finding it does not link is matched by the rules that fold a finding into a verdict reader blocker, and the dedup model checks a nearby pair those rules leave apart. An open thread is matched by its own finding and by every finding an earlier round took into it. A restatement of an open thread is not posted, and a blocker among them, the verdict reader's included, is listed under a link to that thread. When the restatement is graded above the thread, Manki replies there with it, and for a blocker the round record makes the thread block from then on. A security finding is never carried by a thread that is not a security thread, since only a thread's first comment guards it. It joins the security thread that says the same, or is posted on its own, and keeps no link to another thread, so that thread stays among the open ones in the verdict. A blocker that raises a thread which did not block before counts as a new blocker in the verdict line. When the judge calls a finding another instance of the same mistake, such as another field the same check misses, Manki replies with it in that thread, unless the thread took it already, and a blocker among them makes the thread block. These replies go out before the review, and a finding whose reply fails is posted on its own instead. When the review then does not post at all, Manki deletes the replies again. A thread the judge finds addressed this round takes nothing. When the review threads cannot be read, no finding is matched to an earlier one that round, since every finding of a thread would look like one listed in a review body. A restatement of a finding an earlier round listed in its review body is listed under "Still open from round N", whatever code it sits on, unless it is pre-existing, which stays under "Pre-existing". A note among them is not listed again, and the round record keeps it with the reason `listed_earlier`. Neither rule leaves out a security finding, a tool alert, or a finding that goes into an earlier thread, and a "Review again" run leaves out nothing. Each finding's `origin` in the round record says which it is, and `raisedIn` the round that first listed it. Manki also does not object to a change it asked for: a smaller finding on code that applies a fix an earlier round suggested is dropped, unless the judge finds the new code worse. A finding that repeats a problem Manki already answered in a thread, with Fixed, Withdrawn, Agreed, Kept or Unverified, never gets a new thread. It is dropped when its title matches the thread's and its file did not change since the last round. Otherwise the judge keeps it only when the code there got worse, and Manki then replies in that thread and reopens it if it was closed. When the finding is now a blocker, that thread blocks approval from then on, whatever its first comment's severity. Findings Manki agreed to leave for later work are listed in every later review body under a "follow-ups agreed for later" heading.

A warning that an earlier round listed only in its review body has no thread to keep it visible, so Manki carries it forward without a model call. When a round lists a warning in the body, its record keeps a hash of the line the warning points at together with the line before and the line after it, as the file reads at that commit and without the whitespace around each line, and how many places of the file read the same (`citedLine`). Each later round reads the file at its own head. While the file still has that many places reading the same, the review lists the warning again in one line under "Earlier warnings, code unchanged", with the round that listed it first, and an approval counts it in its first line. The line shown is the one that place is on at the round's head, which the carried entry records as `currentLine`, and a finding of the round is compared with that line. When several places of the file read the same, the list shows the file without a line. It never blocks and never holds an approval. The warning leaves the list when the file has fewer such places or is gone, and from then on the finders and the judge see the code as in any round. Line numbers and the history between the two commits play no part in whether it stays, so a rebase, code moved within the file and an edit elsewhere in the file change nothing, and a line the PR never changed or a file outside its diff is treated the same way. An edit to the line right before or after the cited one counts as a change, so a guard added above the line ends the warning, and so does an unrelated edit to a direct neighbour. When the file cannot be read, the warning stays listed. A warning without a line, or on a line the round could not read, has no place to compare and is not carried, and a file that was renamed or moved reads as gone. A carried warning also leaves the list when a finding the judge graded this round names the same problem, which then stands in its place whatever became of that finding. The reason is taken after the last step that leaves a finding out, so a note that names the warning and goes over `review.notes` ends it as `hidden_note`. Notes are never carried. The round record keeps the carried warnings under `findings.carried`, apart from the round's own findings, and the ones that left the list under `findings.carriedEnded`, each with its reason: `line_changed`, `restated`, `hidden_note`, `judge_dropped` or `left_out`.

The review body leads with the verdict, which counts the findings this round posted. A finding posted as a thread is only counted there, since its thread sits right below the review. The judge's summary follows under "What blocks:" when changes are requested, and under "Summary:" otherwise. On an approval, "What this does" follows in at most two sentences. An approval held for files no model read says so in the verdict. The findings listed in the body come next, grouped by where they sit, each group headed by its counts per severity: "Found this round" ("Findings" on a first round), "Still open from round N", "Missed by an earlier review" and "Pre-existing". Files no model read get their own group, "Not read by any model". Each finding is a collapsed fold with its whole description, most severe first. A note is an optional improvement, never a defect. A note never gets a thread or an inline comment. The body lists the notes after the other findings in one collapsed section, a fold per note with its code fix as a code block. The judge orders the notes by how much the author gains from acting on each, and a note it did not rank follows the ranked ones, as does a note from the sweep's own judge call. A review lists at most `review.notes` notes, 3 by default, and `0` lists none. A line under the notes says how many more notes are not listed, and the round record keeps those under `findings.unposted`, with `unpostedReason: note_cap`. A note that an open thread from an earlier round already carries is not listed again and takes none of the places. A security finding is never a note, so it keeps its thread. A tool alert below a warning is listed with the notes, takes none of the places and is never left out. "What to test" follows, collapsed, and a rule sets each section apart. A collapsed "About this review" closes the body with the reviewed commit, the round, the lines read, the review time, the models that found and judged the findings, and the tokens the round used with its cost estimated at public API prices. The cost is marked "partly priced" when some calls had no known price, and left out when none had one. On a subscription account it still shows how heavy the round was. Every finding opens with one line: its severity, then the category and the effort the judge set, such as **Warning** · Concurrency · Moderate. The categories are correctness, security, reliability, data integrity, concurrency, performance, compatibility, testing, maintainability, documentation and style. The effort is a quick fix, moderate or a larger change. An inline finding then shows its title and up to three sentences of what goes wrong, about 700 characters at most. A short code fix GitHub can commit shows right below as a suggestion. Everything else sits in one collapsed section, in this order: how to fix it, why it matters (the rest of the description), how it was checked (what was read or searched, with code previews of the lines that prove it), and last, for a blocker, the outcome of the judge's attempt to refute it. A finding in the review body lists the same parts inside its own fold. It never shows raw tool output. Up to five warnings and security findings below a warning on changed lines get inline threads, and the rest are listed in the body. Each review's round record stores `output.bodyLength` and `output.commentLengths`, the length of the body and of each comment as Manki composed them, before GitHub accepted or refused any comment.

The PR author cannot dismiss a blocker, or a security finding of any severity. Their own "agree" reply, a reply that gets Manki to answer Fixed or Agreed, or resolving the thread leaves it blocking, and auto-approve waits for it. When the author resolves the thread, the next round reopens it once and replies to say why. It is cleared when someone else with write access resolves the thread or replies in agreement, or when the judge marks the thread addressed. A later round never drops a new blocker as a repeat of a thread that was not cleared this way.

A PR author who is a repo admin may clear such a finding on their own PR, so a repo with a single maintainer is not stuck. They resolve the thread in the GitHub UI, or comment `@manki dismiss` in the thread. Manki checks admin and write permission through the GitHub API, because comments show an org owner, and an org member with read access, as a plain member. Every such override is recorded: Manki replies once in the thread with "Finding dismissed by @<login> (repo admin).", the round context lists it under `recap.securityOverrides`, and an approval that relies on it names it in the review body. When Manki answers Fixed, Agreed or Withdrawn on a blocking or security thread that the replier may not clear, the answer says that the thread stays open and who can close it.

Every finding ends with a `Create an issue for this` box: at the end of its thread, and in the review body right under each finding listed there, the Pre-existing section included. When someone with write access ticks it, Manki files the finding as an issue, with the finding as posted, a permalink to its line at the reviewed commit and a link back to where it was posted, and replaces only that box line with "Issue #N created by @login". In a thread, it also replies with the link and resolves a thread that does not block. A blocker's thread, a security one included, stays open, since only someone other than the PR author clears a blocker. When an open issue Manki filed for the same finding exists, the tick links it instead of filing another. A tick by someone without write access does nothing.

Each round checks the open Manki threads against the push. For a thread whose line is gone, the judge sees the code it named on the commit it was posted on, and where that code sits now, found by several of its lines lining up again. When the code left its file and exactly one other changed file holds it unchanged, the judge sees it there, with the file named. In every other case the judge is told that it is not found, and sees the head's code near the same line. An unchanged file never reads as proof that the problem remains. When Manki itself answered in the thread, such as "Fixed." with the lines it cites, the judge must confirm that evidence or say which part is wrong before it keeps the thread open. The push counts only for what it changed in the PR's own change, so a rebase onto the base branch changes no file. When it confirms a fix in a file the push changed, it resolves the thread with a short "Fixed in" reply and the thread stops blocking. The reply names a commit only when it is certain which one fixed the thread: the only commit since the last reviewed one that changed the thread's file, editing it in place. In every other case, such as two commits changing the file, a commit that renamed, added or deleted it, a rebase, a merge from another branch or more than 20 new commits, the reply says "Fixed by the commits up to" the head, which is always true. A thread counts as fixed only when every failure it names is gone. When the push fixes only part, the thread stays open and gets a "Partly fixed" reply that says what still goes wrong, and it keeps the grade that remaining damage earns: its own grade when the damage is the same, never a higher one, and one below the grade it carries only when the push changed the thread's file. The judge states the severity table cell of what remains, and Manki works out that grade from the cell. Nothing checks a rare claim on a thread, so on the wrong behaviour row what remains is graded in the normal column and a partly fixed blocker keeps blocking. A partial fix never lowers a security thread. A partly fixed blocker thread blocks only while what remains is a blocker, in later rounds too. It gets back the highest grade it had, with an "Open again" reply, when a later round names its blocker again, repeats its problem as a blocker, or finds it not fixed after a push to its file. The round record keeps each thread's grade under `judge.threadEvaluations`, and Manki reads it from the latest record that set one, so the grade holds exactly while the review that decided it stands. The record keeps the cell the judge stated as `cell` when that cell gives the thread's grade. When the thread keeps another grade, the record keeps the cell as `judgeCell`, and the next round's judge sees only the grade. A reply that fails to post loses only the note. A blocker a later round carries on the thread, by naming it, folding into it or repeating its answered problem, raises it to blocker the same way, and outranks a lower grade in the same round. No reply ever decides whether a thread blocks. When a round record cannot be read, a grade it held is unknown: the approval check counts every Manki thread as blocking, the review round requests changes while a Manki thread stays open, and the PR author cannot clear a Manki thread by resolving it, though a repo admin author still can. The review leads with an "Approval withheld" line that links each review whose record it could not read, in place of the usual count of blockers, and shows the judge's summary under "Summary". The check summary does the same, so a person sees why, and no open thread is called a blocker it may not be. The hold lasts until a maintainer has resolved the open threads. A round that requests changes for another reason does not name the unread record. A thread the round resolves, or one someone with write access agreed away, does not count as open for this hold. The judge also checks that each finding's fix removes every failure the finding names, and a fix that removes only part says what it leaves. A thread gets one Manki fix confirmation per head commit: when Manki already answered a reply there with "Fixed." on that commit, the round resolves the thread without its own line, and a reply answered after the round's line gets no second "Fixed.". A blocker that a round names again while its thread is still open stays in that thread instead of getting a new one.

When a blocker comes back after a fix was claimed for it (its thread was resolved, someone replied in it, or Manki confirmed the fix), the review keeps requesting changes, lists the blocker under "Needs a human", and pauses automatic review. A blocker named again after a rebase, with its thread still open and unanswered, just stays open. The last automatic round, round `convergence.max_auto_rounds` (default 10) counted from Manki's last approval, approves when nothing blocks, or stops the same way when a blocker is still open. Rounds after an approval, such as on rebases, start the count again. An approval held because the PR conflicts with its base counts as an approval here, and so does auto-approve after the last blocking thread is resolved. That approval also ends a pause from a blocker that came back. Only rounds that reviewed a new change count, so another round on a change Manki already reviewed, such as Review again on the same commit, does not. While automatic review is paused, its notice lists the blocking threads still open, with links. A pause by the round cap also asks the author to step back and reconsider the approach, since rounds that keep finding problems usually mean the design needs another look. A push starts no review, but replies in threads, auto-approve after the last blocking thread is resolved, the Review again and Deeper review boxes in the settings block and `@manki review` still work. A review started that way also turns automatic review back on for the next `convergence.rounds_after_restart` automatic rounds (default 3), or for the rounds the cap still allows after the restarted round if that is more. After a restart, the notice counts the rounds since the last approval and how many came after the last review started by hand. When they pass without an approval, automatic review pauses again with the same notice, and the next review started by hand turns it back on again.

Use the `models` config section to choose different models for the finders and the judge (e.g., a faster model for the finders and a more precise model for the judge).

The judge treats two finders reporting the same defect as strong evidence that it is real, and one finder's silence as no evidence against the other's finding. Agreement never raises a finding's severity.

To give the second finder its own model, set `models.reviewer_pair`, or name models in a review group.

## Rules from instruction files

Manki reads the repository's instruction files from the PR's base branch only, so a PR cannot relax a rule for itself: the root `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md` and `CONTRIBUTING.md`, the nearest `AGENTS.md` and `CLAUDE.md` above each changed file, and the `.md` files these link to. A PR that edits one of them is reviewed against the base branch's text, and the edit applies after merge.

The files are printed in that order, up to 30,000 characters in total. The file that crosses the limit is cut and the files after it are left out, so the review does not see their rules. The run then logs a warning that names the cut file. The round record lists the files the round read under `instructions.files` and the cut one under `instructions.cut`.

The finders use these files in two ways. They check each added line against the rules. They also go through the rules about the change as a whole: what a change must include, such as a test, a migration or a documentation update, and how it must be scoped. Example: a Django project's `CONTRIBUTING.md` says every model change needs a migration, and a PR adds a model field without one. For the change as a whole, only a rule stated as a requirement counts ("must", "needs", "never", "always"). Advice ("prefer", "try to", "consider") is not reported there. An `AGENTS.md` or `CLAUDE.md` in a subdirectory covers only changes under that directory.

A finding about a rule for the change as a whole names the instruction file and quotes the rule. Manki looks the quote up in the files it loaded, ignoring case, line wraps and Markdown emphasis, and marks the finding as a rule finding only when the named file holds it. A rule a finder read anywhere else, such as in the PR's own edit of an instruction file, gives no mark. The round record keeps the mark as `rule` on the finding, with the `file` and the `quote`, also on a finding the judge dropped. The mark changes no grade: a rule finding is graded like any other finding.

Manki proposes splitting a PR only when an instruction file requires focused changes, such as one concern per PR, and only when a finder with repository tools shows that a part is independent: the rest of the PR does not use the part, and the part does not use the rest. The finding quotes the rule, names the parts and lists what was searched. Without such a rule, or when the finder has no repository tools, Manki never proposes a split and never reports a change only for being unrelated to the PR's purpose.

## Skipping PRs

`skip_labels`, `skip_authors` and `skip_branches` name PRs that get no automatic review, such as dependency bumps from a bot. Manki reads them from `.manki.yml` on the base branch only, so a PR that edits them cannot skip itself. A PR that matches any rule gets no review, no comment and no approval. Its `Manki` check completes as skipped. A `@manki review` comment still reviews it.

A skipped check passes a required status check, so a branch protection rule that requires `Manki` lets a skipped PR merge without a review. Use rules that only trusted actors can meet. GitHub sets the author, so `skip_authors` for bot accounts is the safest. It skips an event only when its sender is a listed author too, so a person who pushes to a bot's PR still gets a review. A label or branch rule matches only PRs whose head branch is in the repo itself, never a fork's. A fork's author can name a branch freely and keep pushing after a label is added, for example by a path-based labeler. Anyone with write access can still pick a matching branch name or add a skip label.

A PR that conflicts with its base gets no review at all, also on a `@manki review` comment. The token service posts one note, "This PR conflicts with `<base>`. Rebase it, and Manki reviews it then.", and completes the `Manki` check as "Rebase needed". The next skip edits that note instead of adding another, and Manki deletes it once a review posts after the rebase. A conflict that appears while a review runs still turns its approval into "Approval held".

## Reading CI results

Manki reads what your CI already reported on the PR head commit and gives the reviewers the results that sit on lines of the diff: check-run annotations (linters, type checkers, test reporters), open code scanning alerts, and vulnerable packages from the dependency review. The tool text reaches the reviewers fenced and marked as untrusted, and only for the lines they review. When a Manki note sits on the same file and line as a tool result, Manki drops it because the author already sees the tool's result. Warnings, blockers and security findings are always kept, because they can be a different problem on the same line. The drops are listed in the `Manki context` block.

Some tool results also go to the judge as candidate findings, next to the reviewers' findings:

- A vulnerable package, or a result whose tool or rule id names a security class (such as `security`, `injection`, `xss`, `format-string` or `secret`), always does.
- A style or formatting result never does, because the linter already shows it. Manki recognises these by rule id, such as `prettier/prettier`, `@stylistic/*`, `indent` or `max-len`. A result without a rule id is judged by its tool name, such as `rustfmt`.
- Any other code scanning alert does, and a check annotation only at the `failure` level.

The judge keeps a real defect at the grade it earns and refutes a false positive with a reason. A refuted result is never posted. A kept one is posted with the tool in its label, such as `⚠️ **Warning, not blocking** (CodeQL)`.

Before the judge runs, Manki also checks each reviewer finding against the code, without running it: the file is in the diff, the line is in the file, and whether each symbol the finding names in backticks occurs in the file or the diff. Only a file outside the diff or a line past the end of the file contradicts a finding. A missing symbol is only noted, since it can live elsewhere. A claimed type or compile error is confirmed by a failing annotation near the line from a type checker or compiler, such as `tsc`, `mypy` or `rustc`. A lint error there does not confirm it. The judge sees the result as confirmed, contradicted or unchecked. Only the judge can drop a contradicted finding, and a tool that says nothing never lowers or drops a finding. Each finding in the `Manki context` block records `toolEvidence` as `confirmed`, `contradicted` or `none`.

Manki reads these results with the workflow token (`github_token`), so grant the permissions in the workflow, even when the Manki app posts the review:

| Permission | Source |
|------------|--------|
| `checks: read` | Check-run annotations |
| `security-events: read` | Code scanning alerts (needs code scanning, and GitHub Advanced Security on private repositories) |
| `contents: read` | Dependency review (needs the dependency graph, and GitHub Advanced Security on private repositories) |

A source Manki cannot read is skipped with one info line in the log. Turn a source off with `static_analysis` in `.manki.yml` (see [Configuration](configuration.md)). Manki reads that block from the base branch, so a PR cannot turn off the tool that would flag it.

Manki only sees checks that finished before it runs. Manki runs in its own workflow, so `needs:` cannot order it after your CI. List the check runs to wait for in `static_analysis.wait_for_checks` instead. Manki polls them on the PR head every 15 seconds and reads the results once each has finished. After `wait_timeout_seconds` (default 300) it stops waiting, reads what is there, and records the checks still running in the `Manki context` block. A name is the check run's name as the PR's checks list shows it, usually the job name.

```yaml
static_analysis:
  wait_for_checks: [lint, CodeQL]
  wait_timeout_seconds: 300
```

## Running Manki's analyzers

Manki can run analyzers itself. `actionlint`, `zizmor` and `shellcheck` are on by default, but each runs only when a file it checks changes, and only when CI does not run the same tool already. Manki's Rust rules for `ast_grep` are on by default in a Cargo repository (see below). The others are off by default, for a repository without CI checks. Turn them on or off in `.manki.yml` on the base branch:

```yaml
static_analysis:
  analyzers:
    ast_grep: true
    secrets: true
    dependencies: true
    semgrep:
      rules: [.semgrep/manki.yml]
    shellcheck: false
```

`analyzers: all` turns on every analyzer that needs no rules from you, including ones later releases add. Semgrep only runs when you list rule files.

| Analyzer | Tool | What it checks |
|----------|------|----------------|
| `ast_grep` | [ast-grep](https://ast-grep.github.io) 0.51.1 | Manki's own rules in [`rules/ast-grep`](../rules/ast-grep) (MIT licensed): code and shell injection, HTML sinks, disabled TLS checks and unsafe deserialization, plus error-prone patterns such as an async `forEach` callback, a comparison with `NaN` or a mutable default argument. Runs on the changed JavaScript, TypeScript and Python files. The Rust rules also run on a changed Rust file that has a `Cargo.toml` in its directory or one above it on the base branch, even without `ast_grep: true`: a narrowing `as` cast of a length, count or index, `unwrap` or `expect` on decoded input, `with_capacity` sized by a decoded length, a new `unsafe` block, and `==` on secret bytes. They report hints on added lines only, skip tests, benchmarks, examples and build scripts, and stop with `ast_grep: false`. |
| `secrets` | [gitleaks](https://github.com/gitleaks/gitleaks) 8.30.1 | Secrets on the lines the PR adds in any changed file, with gitleaks' default rules through Manki's [`rules/gitleaks.toml`](../rules/gitleaks.toml). `gitleaks:allow` comments are ignored. |
| `dependencies` | [OSV-Scanner](https://github.com/google/osv-scanner) 2.7.0 | Known vulnerabilities in the packages of the changed lockfiles, such as `package-lock.json`, `pnpm-lock.yaml`, `go.mod` or `requirements.txt`, with Manki's [`rules/osv-scanner.toml`](../rules/osv-scanner.toml). A result sits on the line that adds the package. |
| `semgrep` | [Opengrep](https://github.com/opengrep/opengrep) 1.33.1 | Your Semgrep rules on the changed files. List rule files in the repository, read from the base branch. Manki ships no Semgrep rules and never fetches registry rules such as `p/default`. `nosemgrep` comments are ignored. |
| `actionlint` | [actionlint](https://github.com/rhysd/actionlint) 1.7.12 | Mistakes in the changed workflow files under `.github/workflows`, such as invalid syntax, expression type errors or untrusted input in a `run` script. Uses `.github/actionlint.yaml` from the base branch when there is one, so self-hosted runner labels are known. Its shellcheck and pyflakes checks stay off. |
| `zizmor` | [zizmor](https://github.com/zizmorcore/zizmor) 1.32.0 | Security problems in the changed workflow files, such as template injection, dangerous triggers or excessive permissions. Runs offline, without the repository's zizmor config, and ignores `zizmor: ignore` comments. |
| `shellcheck` | [ShellCheck](https://github.com/koalaman/shellcheck) 0.11.0 | Bugs in the changed shell scripts: `.sh` and `.bash` files, and files without an extension, that start with a `sh`, `bash`, `dash` or `ksh` shebang. A `.sh` or `.bash` file without a shebang counts too. Reports down to `info`, without the repository's `.shellcheckrc`. |

The analyzers never run code from the PR. Manki reads the changed files through the API at the head commit and gives the tools the files, never a checkout. It never uses rules or config from the PR: each tool gets Manki's config or the rule files from the base branch, and the files a tool would read as its own config or ignore list, such as `.gitleaksignore` or `.semgrepignore`, are left out of what it scans. The tools run without the action's environment, so they never see a token.

Manki downloads each tool at the pinned version, checks it against its pinned digest (SHA-512 for the ast-grep packages from npm, SHA-256 for the release binaries), and caches it for the run. The ast-grep native module and its Go, Python and Rust grammars load in process. ncc can only bundle the native module for the platform that builds `dist/`, so they load at run time. Builds are pinned for Linux and macOS (x64 and arm64) and Windows (x64). If a download fails, the platform has no pinned build or a tool fails, that analyzer is skipped with a warning and the review goes on.

`exclude_paths` keeps files away from the reviewers, and `ast_grep` and `semgrep` follow it. `dependencies` checks every lockfile the PR changes, including the ones the default `exclude_paths` names, such as `yarn.lock` or `Cargo.lock`, within 10 MB per lockfile and 40 MB in all. `secrets` checks every changed file, since a PR can add its own `exclude_paths`, and for the same reason `actionlint`, `zizmor` and `shellcheck` check every changed workflow or shell script. A result on an excluded file has no inline thread, so it is listed in the review body. A PR whose every changed file is excluded or has no code to read is never approved. No code to read means a binary, a rename, a mode change, an empty file, a Git LFS pointer, whose lines only name the content by hash, or a submodule bump, whose line only names a commit. Manki posts a comment that lists each skipped file and why, with what the analyzers found on them, and the `Manki` check waits for a person. When the PR also changes files the models read, a clean round still holds its approval: Manki posts its review as a comment that lists the skipped files, the `Manki` check reports the approval held, and a person approves. Auto-approve after the last blocking thread is resolved never gives that approval either. A deleted binary, LFS file or submodule leaves nothing unread, so it holds no approval.

Manki reads a changed `Cargo.lock`, `package-lock.json` (or `npm-shrinkwrap.json`) from npm 7 on, `yarn.lock` from Yarn 1 or later, or `pnpm-lock.yaml` into a package list, whatever `exclude_paths` says: each package the PR adds, with its source and fields, each package it removes, and each package it updates, with its old and new version and the changes to its source, checksum and other fields. The legacy `dependencies` map of a version 2 `package-lock.json`, which only npm 6 installs from, must name the same artifacts as its `packages` map, and the list then leaves it out. The finders, the judge and the verdict reader read that list, and the judge reads it in place of the lockfile's hunks. A local review and the benchmark read lockfiles the same way. The planner and the review groups count the lockfile as changed, so a lockfile change gets two finders on the supply chain floor. Such a lockfile holds no approval, and a PR that only bumps a lockfile can be approved. Manki adds a `lockfile-change` alert, which the judge triages like any tool result, for a package whose source moved to another registry or repository, an added one from a registry the lockfile did not use before (in a new lockfile, from another registry than most of its packages), one that comes from a git repository or a path, one whose checksum changed without a version change, one that moved to a lower version, and one whose tarball URL names another package or version. Manki reads the lockfile at the PR head and undoes the diff to get the version before it. A lockfile it cannot read or parse, one whose diff does not match the file, one in another format such as `poetry.lock`, or one past 100,000 characters of package lists in all, stays unread and holds the approval as before.

Analyzer results follow the path of the CI results above, limited to lines of the diff. `actionlint`, `zizmor` and `shellcheck` keep only results on the lines the PR adds or changes, so a problem the PR did not touch is never raised.

Manki also looks for hidden characters on the lines the PR adds in any changed file, whatever `static_analysis` or `exclude_paths` says: control characters other than tab and newline, format characters such as zero-width spaces and bidi controls, the line and paragraph separators U+2028 and U+2029, the invisible Hangul filler letters, and variation selectors other than U+FE0F, the one that follows most emoji. A file that adds any gets one `hidden-characters` alert from Manki at the first such line. A bidi embedding, override or isolate, which can make code display differently than it runs, makes the alert an error. Any other hidden character makes it a warning. A suggested fix that holds a hidden character is never offered as a `suggestion` block, and no text a model wrote can open a `suggestion` block. Manki rebuilds every code block in that text with its own fence, which nothing inside can close, keeps a plain language name at most, and escapes any other run of three backticks or tildes.

Manki skips `actionlint`, `zizmor` or `shellcheck` when CI already runs it: when a workflow on the base branch names the tool outside a comment line, or a check run on the base branch's head commit has the tool's name in its name. The PR can change neither, so a job it adds cannot turn a tool off. The `Manki context` block records the skip. Since no CI shows them to the author, every result goes to the judge as a candidate finding, and a reviewer finding on the same line is never dropped for it. A result the judge keeps is posted with the tool in its label, such as `⚠️ **Warning, not blocking** (gitleaks)`. A clean run posts nothing. The `Manki context` block records each analyzer that had a file to check under `staticAnalysis.analyzers`, with how many results it found or why it was skipped.

## Uses outside the diff

When the PR head is checked out for the repository tools, Manki lists where the code the PR changes is used elsewhere, before any finder runs. It takes the changed types, struct fields, enum variants, functions, constants and config keys from the hunks: through ast-grep for Rust, TypeScript, JavaScript, Python and Go, and from keyword declarations (`func`, `class`, `struct` and similar) and config keys with an underscore in other files. When a type's body changes, its other fields and variants are searched too, after the changed symbols. Manki searches the head commit for each name as a whole word, outside the changed lines and `exclude_paths`. Code comes first, then comments, then documents. Within each, a package that depends on the changed one comes first, then other files of the same package, then the same file, and last a package that does not depend on it, which can only hold a namesake. Each symbol shows at most 4 uses and the list at most 60, and the section says how many it left out. Among a symbol's code uses in packages that can reach it, production code comes first, then lines that only call `.name()`, then test files. Within each, one file shows at most 3 while another file still has one to show. A name as common as `new`, `len` or `from`, or shorter than 4 characters, is not searched at all. A name with more than 80 uses is named but not listed, except a field or variant that existed before the PR and whose own lines the diff changes, such as its type, even on a line after its name, or its doc: its readers are what the change can break, so they are listed however many there are, up to 12, and its uses outside test files take their place before other symbols' uses fill the 60 lines, up to 30 shared in turn by all redefined fields, so changed functions and types keep room however many fields a PR redefines. Among each file's first 3 uses, and again among the rest, its uses in files that also name its type come first, and uses in files that never name it come last, since they likely read a field of the same name on another type. Within those, a read of the field as `.name` comes before other code that names it, such as a struct literal. The note on the uses left out says how many of them are in files that name the type. A new field has no readers yet, so its matches are namesakes and the cutoff applies. A line that only declares a field of the same name on another type, or reads it as `self.name`, `this.name` or through a Go receiver in a method of such a type, is likely a field of the same name on another type, so it ranks after every other use of the symbol. It is never left out, since the guess can be wrong, and it counts in the uses not shown when the list is full. A function inside that method that binds the name again reads another value, so its reads rank as usual: a TypeScript `function`, object literal method or class, or a nested Python function or Go func literal with a parameter of that name. A method whose body binds the name again in a statement, such as Go `for _, v := range` or a `select` case, or a Python assignment to `self`, ranks all its reads as usual. A field of the same name that the diff also changes on another type is no namesake. A type that may derive from the changed type counts as that type: a subclass, an interface that extends it or a TypeScript type alias that names it, directly or through other types the same file declares, and a type with a base declared in another file or named through a module, such as `other.Base`. A read Manki cannot place on a type, such as `x.name` on a local, ranks as usual. The list also shows each type whose fields the changed lines read or change, with all its fields, so the finders see state kept next to the field the PR touches.

The finders, the judge and the refuter all get the list, so a finding that cites one of its lines rests on code the judge can see. The round record keeps it as `usesOutsideDiff`: the location of each use shown, each type with its fields, and the names left out, without the quoted code, so a missed defect can be traced to what the finders were shown. Building it takes seconds and calls no model. Without a checkout, or when the search fails, the review runs without it and the log says why.

## Sibling comparisons

Two kinds of defect hide next to the change rather than in it, and a finder that sees the clue can still miss the comparison. So Manki asks the comparison itself, from the same parse that builds the uses outside the diff, in one small call per question:

- **Sibling fields**: when a changed line looks an item up in a collection field, such as `queue.pending.get(id)` in Rust or TypeScript, `id in self.pending` or `self.pending[id]` in Python, or `q.pending[id]` or `delete(q.pending, id)` in Go, each other collection field of the same type that shares the item's type gets the question "The change looks up `id` in `pending`. Can `id` be held in `cancelled` instead? If so, does the change handle it?", with the type's definition and the changed hunks. A field of the same type comes first, then one with the same key type, then one sharing any element type. A fixed-size array such as `[u8; 32]` or `[32]byte` is a value, not a collection, so it gets no question. A Python field is one assigned in the class body or on `self` in `__init__`. Without a type annotation, its type is the kind of its first value, such as `dict` for `{}`, so it is compared only with a field of the same kind.
- **Sibling implementations**: when the change touches a function that sibling types also declare, such as the same trait method in two `impl` blocks, a method of the same name on two classes, or one on two Go types, in the changed files or the other files of their directories, up to 4 of them go side by side with "List every check, guard, version test, bound, error or event one has and another lacks." Functions that read the same are not asked about. A round compares at most 2 MB of function text, and functions past that count as different. Methods every type has, such as Python's `__init__` and other dunder methods, TypeScript's `constructor` or `toString`, Go's `String` or `Error` and a Rust `new`, are compared only between classes that share a base class or interface, together with the base class's own one, and implementations of standard Rust traits such as `Display`, `Debug`, `Clone`, `Default`, `From` or `PartialEq` are not compared, since unrelated types each have their own. Groups where the change touches more of the functions come first, then trait methods, then more changed lines, then more functions. A group whose functions all sit in one group already asked, such as two subclasses that share two bases, is not asked again.

Each call runs on `models.reviewer` at the finders' effort, at the same time as the finders, and with repository tools when the finders have them, at most 12 steps. A round asks at most 6 questions of each kind, and cuts the lowest ranked first. The findings go through dedup and the judge like any finder's, named after their question, such as `Sibling field: pending vs cancelled`. Each call follows the finders' rules for a claim that something is missing, which needs the search that came back empty, and for a defect in code the PR did not change, which is marked pre-existing. A question whose call fails goes unanswered, and the round still completes, since the finders read the whole change. Once the finders are done, the round waits at most one more minute for the comparisons, then stops the calls still running. The round record lists each question under `comparisons`, with where it points, whether it was answered, failed, cut by the cap or timed out, and how many findings it gave, and `usage.llmCalls` records each call under the `compare` stage.

## Sweeping for a defect class

A finder that reports one instance of a mistake often stops there, although the same kind of mistake can sit elsewhere in the PR. With `review.sweep: true`, read from the base branch, each blocker the judge keeps starts one more call, at most three a round. The security blockers go first, then those the judge was surest of, and the rest are recorded as `cut`. The call states the blocker's defect class in general terms, such as "a cache key leaves out a field the cached value depends on", never the instance, and lists every other place in the diff that makes the same mistake, each with its own proof. When it judges the class too specific to recur, such as a typo or a wrong constant, it reports nothing.

Each call runs on `models.reviewer` at the finders' effort, with repository tools when the finders have them, at most 15 steps, and its calls are recorded under the `sweep` stage. A blocker the refuters disproved starts no sweep. A place on or next to a line the blocker cites, or exactly on a line another finding the judge kept this round cites, as its own line, proof or evidence, in any file, is dropped and logged, and so is one the judge already judged this round, or one the dedup model calls the same defect as a nearby judged finding. The rest go through dedup against earlier rounds and through one more judge call, which sees no open threads, like any finding. When that judge call fails, the round ends incomplete and posts no findings, so a blocker the sweep found is never lost behind an approval. They are named `Sweep 1`, `Sweep 2` and so on, never after the blocker's text, and one that restates an earlier open thread folds into it. The round record lists each sweep under `sweeps`: its reviewer name, the blocker's location, its status (`answered`, `too_specific`, `failed` or `cut`), the class it stated and how many places it found. The setting is off by default until a benchmark run decides whether the extra calls pay for themselves. `bench/variants/sweep.yml` turns it on.

## Related repositories

`related_repos` lists public repositories on github.com that the review may read as context. Each entry has:

- **`repo`**: the repository as `owner/name`.
- **`kind`**: `reference` for a repository this one implements or ports, such as a protocol's reference implementation or its specifications. `consumer` for a repository that depends on this one, where a change to a public API or a wire or data format can break it.
- **`ref`** (optional): the branch, tag or full commit hash to read. The default is the repository's default branch. Write a branch or tag whose name looks like a short commit hash, such as `20240115`, as `refs/heads/20240115` or `refs/tags/20240115`.
- **`paths`** (optional): up to 20 paths or globs inside the repository, such as `src/` or `packages/rs-*`. Only these are fetched, along with a root `AGENTS.md` and `CLAUDE.md`. The default is the whole repository.

```yaml
related_repos:
  - { repo: dashpay/dash, kind: reference, paths: [src/] }
  - { repo: dashpay/dips, kind: reference }
  - { repo: dashpay/platform, kind: consumer, paths: ["packages/rs-*"] }
```

Reviewers with [repository tools](security.md) read these repositories through the same tools, by naming one in a `repo` argument. When the PR title, description or changed code says the change matches a reference, or follows its spec, they open the code the claim names and compare it with the change. They also read a reference when the changed code implements or mirrors it, and compare each contract in both directions. They read a consumer only when the PR changes a public API or a wire or data format, to find the consumer's code that uses it. A divergence from a reference is graded like any other finding. A change that breaks a consumer is a warning that lists the consumer's call sites, and a blocker only when the PR says it does not break anything. Reviewers without tools never read them. For a finder with repository tools, the checklist gains one check per configured kind. With a `reference`: when the change touches a wire format, a protocol message or a rule a specification defines and a reference holds that specification, search it for the name of the message, field or rule and compare the change with what it says. With a `consumer`: for each public type, function or serialized format the change alters, find its uses in each consumer and check that they still work.

Manki reads `related_repos` from the PR's base branch only, so a PR cannot make Manki fetch another repository. A PR that changes it is reviewed with the base branch's list. Every related repository is fetched before the finders run, on a round whose finders have repository tools and whose diff names something to search for. On any other round with repository tools, a repository is fetched the first time a reviewer names it. Each is fetched once per round however many reviewers read it. The fetch is a shallow, path-limited clone of one commit (`git` with `--depth 1`, `--filter=blob:none` and a sparse checkout of `paths` and the two root guide files), run without any credentials, so a private repository cannot be read. A repository that is private, missing, or not fetched within a minute gives a warning, and the review goes on without it. The round record lists each configured repository as `relatedRepos`: fetched, failed with the reason, unused when the round never fetched it, or skipped when no reviewer had repository tools, with how long its fetch took and how many tool calls read it. Each finder call in `usage.llmCalls` counts its own reads as `relatedReads`.

Before the finders run, Manki searches each fetched related repository for the names the diff changes or reads and the names its added comments mention, such as `MAX_BODY_LENGTH` in a comment that says the change follows that limit. The search ignores case and underscores, so `retry_delay` also finds `retryDelay` and `URLInfo` finds `URLINFO`, except that an `ALL_CAPS` constant keeps its case. Names of test functions and words that do not read as code are left out, and so are the root `AGENTS.md` and `CLAUDE.md` of the repository. One call to the `dedup` model first guesses what each fetched repository calls those names, from the names, the file types the change touches and each repository's most common file types: a Go server may call a Python client's `fetch_profile` `GetUserProfile`. The search then looks for the guessed names as well as the original ones, at most 2 guesses a name. A line only a guessed name finds is listed under the original name, marked "also searched as", after the lines the original name finds, and the section says that such a name is a guess to check. A guess that reads as code is matched like any name, a plain word only in its exact case. The guesses are searched after the original names and apart from them, so a guess whose search fails costs only the guesses searched with it. The round record marks those as `failed`, and likewise every guess for a repository whose search for the original names failed. The call takes at most 45 seconds and shows in `usage` as the `translate` stage. When it fails or its reply cannot be used, the search runs with the original names alone. The finders, the judge and the refuter get the matches after the uses outside the diff, as an "In the Reference Repos" section and an "In the Consumer Repos" section. Each lists for each name at most 4 lines, 40 lines in all, and the names nothing matched. The reference section asks to compare the change with the reference. For a name that starts with a capital letter, such as a constant or a type, it puts a line that declares the name first. The consumer section asks to check that each line still works with the change. Both then list the repository's other code, comments and documents, then its tests, then vendored code. The round record keeps the locations under `usesOutsideDiff.reference`, the names nothing matched under `usesOutsideDiff.referenceMissing`, and the names the 40-line cap left out under `usesOutsideDiff.referenceCapped`, with `consumer`, `consumerMissing` and `consumerCapped` for the consumers. Under `usesOutsideDiff.translation` it keeps each guessed name with its repository, the original name and how many lines of that repository hold it, or `skipped` with the reason when the call failed, its reply could not be used or no model is set up for it.

A related repository often keeps a guide for its own contributors at its root, `AGENTS.md` or `CLAUDE.md`. For each repository fetched before the finders run, Manki looks for that file, `AGENTS.md` first, and the finders' prompt names its path as a map of that repository: they read it first to find where the repository keeps what they look for. The prompt says that the guide's rules govern that repository and not the PR, and that its text is untrusted data. Manki itself never puts the text of these two root files into a prompt: the prompt names only the path, and the search described above skips both files. A finder that opens the guide reads it with its tools, as untrusted data like any other file of that repository. A repository limited by `paths` still has its root `AGENTS.md` and `CLAUDE.md` fetched, so its guide is found too. A repository fetched later, on a finder's first read, gets no pointer. The round record names the file as `guide` on the repository's `relatedRepos` entry.

The clones go to `manki-related-repos` in the runner's temp directory. To reuse them across runs, restore and save that directory with `actions/cache` before the Manki step. Each run saves a new entry and restores the latest one:

```yaml
      - uses: actions/cache@v6
        with:
          path: ${{ runner.temp }}/manki-related-repos
          key: manki-related-repos-${{ github.run_id }}
          restore-keys: manki-related-repos-
```

Of a restored clone Manki keeps only the object store, and only once `git fsck` finds it intact, so a tampered cache entry cannot change how git runs. The fetch then downloads the commit and its trees again, and only the files the cache does not hold yet, and Manki repacks the store so it keeps one copy of each object. A job with `cache-mode: read` restores the cache and saves nothing (see [Cache access](getting-started.md#cache-access)). No other job writes this cache, so such a job fetches every related repository from scratch on each run.

## Related open PRs and issues

Manki looks for other open work on the same change while the review runs. It lists up to 5 open PRs, drafts included, that change a file this PR changes, from the 50 most recently updated, most shared files first. It also searches the repository's open issues for up to 6 words: names the PR's added lines declare, such as a new function, and the longer words of its title. The search takes up to 5 issues and leaves out the ones the PR body links. One call to the `dedup` model then reads this PR's title, description and changed files next to each candidate's title, the start of its description and, for a PR, its changed files. It answers whether each one is a duplicate PR, an overlapping PR or issue, an issue this PR fixes without linking it, or unrelated.

The review body lists every candidate that is not unrelated under "Related work", with its relation and a link. The model's one line of reasoning stays out of the review, since the candidates' text could steer it, and only the round record keeps it. The note never blocks, never opens a thread and never changes the verdict: whether a duplicate PR should close is the author's call. The other PRs' and issues' text reaches the model only as untrusted data in fenced blocks, cut to 400 characters each, and their titles are sanitized before they are posted. A list that fails is skipped with a warning. Neither request is retried or held for a rate limit, and the whole lookup gives up after 15 seconds, so the review waits at most that long. A list still running then is cancelled and recorded as timed out. A local review has no GitHub to ask and skips the step. The round record keeps each candidate under `relatedWork.candidates`, with its number, how many files it shares, the classification and the reason, and names any list or call that was skipped. The model call shows in `usage` as the `related` stage.

## Round records

Each review summary on the PR embeds a `Manki context` block. The block is a hidden HTML comment holding the round's diagnostics as JSON: models and effort, timings, token use, the planner's choices, every finding the finders reported (`reviewers.rawFindings`), dedup drops, and the judge's decisions with its reasoning, including the findings it dropped (`judge.dropped`). When it would not fit in the review body, Manki stores it gzip compressed and base64 encoded in the same comment instead of cutting it. Only a record too large even compressed loses its per-file and per-finding diagnostics, and `meta.omitted` then names each field left out. While it fits, such a record still keeps every finding the finders reported with only its title, location, severity and reviewers, and the uses outside the diff with only names and locations, so a missed defect can still be traced. `meta.compacted` then names those two fields. `usage.llmCalls` lists every LLM call of the round: the stage and finder, model and effort, input, output, cache read, cache write and reasoning tokens, duration, attempt, whether a fallback model answered, and an estimated cost in USD at public API prices. A call whose model has no known price, or whose provider reports no token counts (the Codex and Gemini CLI paths), counts as unpriced, and subscription use is not billed per token, so the cost is an estimate of the same calls on the API. `usage` also holds the totals for the round, per stage (`perStage`) and per model (`perModel`), and in `limits` the newest reading of each subscription usage window the Claude and Codex CLIs reported: the account, the window, the share used and the reset time. Its `durationMs` is the time spent in model calls, and `wallClockMs` the wall-clock time of the whole run, the same time the finished progress comment shows in its headline, such as "Review complete in 4m 12s". Each call also records `promptDigest`, the first 12 hex digits of the SHA-256 of its system prompt with every number in it replaced, so calls before and after a prompt change compare and the counts a prompt quotes, such as the open threads, do not split one version (an edit that changes only a number in a prompt keeps its digest, so `meta.mankiVersion` tells such versions apart), and the judge's digest hashes its prompt with every round-dependent section on, so it changes only with the template or the repository's rules, and for a call with tools its `stepBudget`, and on a Claude call `wrapUpNoted`, set when the model used enough steps to be told to wrap up. A Claude call with tools also records `toolSteps`, each tool it called in order, and `filesRead`, each file it read once, relative to the repository root, with `owner/name:` in front of a file in a related repo, so a missed defect can be told apart from a file no finder opened. `meta.promptVersions` lists the distinct digests per stage. The record also keeps why a round paused (`meta.needsHuman`, its cause and blockers), how each static analysis source ended (`staticAnalysis.sources` for checks, code scanning and dependency review, with the reason one gave nothing, such as an HTTP 403, next to `staticAnalysis.analyzers`), the learnings and suppressions memory loaded and each finding a suppression hid with the suppression's id (`memory.loaded`, `memory.suppressed`), and each call the run made to the token service before it posted, with its status, and for a failed one the error and the service's request id (`tokenService`). Each reply Manki posts in a thread or to a command carries the same usage in a hidden `<!-- manki-reply-record: ... -->` comment. A review state check that approves, holds or withholds the approval puts a hidden `<!-- manki-approval-record: ... -->` on what it posts: the approval review, or the held or withheld notice while that stands. It records the decision, the reason, the head commit and how many of Manki's threads are resolved. A check that skips posts nothing, and its decision shows only in the run log and in the token service's `coordinator_finished` log line. A reply record also keeps the token service calls of its run, and for a thread reply that opens with `Fixed`, `Agreed` or `Withdrawn` what it decided for the thread (`decision`): it resolves the thread, the thread stays open for a maintainer, the replier may not resolve it, the thread was already resolved, is not found or could not be looked up, or a later round already judged the fix.

Each finding, kept or dropped, records `gradePath`: every change of its severity after the reviewer graded it, in order, with what changed it and, where the stage said, why. The steps are `judge`, `unproven` (a blocker without proving lines posted as a warning), `build_claim` (a blocker that claims a build, type or test failure no CI result reports, posted as a warning), `refutation`, `in_pr_suppression`, `own_proposal`, `contradiction`, `ratchet`, `resolved_thread` and `pre_existing`. A finding the judge graded records `cell`: the row and column the grade was worked out from, with `judgeColumn` when Manki graded it in another column than the judge stated, because a check moved it or because it is a security finding. A blocker that two disproofs put back at its finders' grade records `judgeCell` in place of `cell`, and `reviewerSeverity` is the highest grade a finder gave the finding or a duplicate merged into it. A finding the judge doubted records `gradeIfConfirmed`, the grade its cell gives once every doubt holds, and its `doubts`, and its refutation records the answer to each premise under `premises`. That answer tells a rare claim the code bears out (`disproved`) from one nobody could settle (`unsettled`), and a doubt with no refutation was never checked. A finding the reviewer marked pre-existing and the judge kept records `preExisting`: the reviewer's reason and how the claim was checked, `pre_existing` when it held, or the condition that failed (`no_location`, `excluded_file`, `deleted_file` or `touches_diff`). A finding memory hid is listed in `memory.suppressed`. Each entry of `findings.entries` records `posted`, where the round put the finding: `thread` for a thread of its own, `body` for the review body, or `earlier_thread` when a thread from an earlier round carries it. An entry of `findings.unposted` records `record`. `findings.originsWithoutPrior` is set on a later round that tagged its findings without the PR's change at the last reviewed round, which is a "Review again" run or a failed fetch of that change. `findings.carried` holds the warnings the round carried from an earlier round's review body, each with `raisedIn` and `citedLine`, and `findings.carriedEnded` the ones it stopped carrying, each with its reason. They do not count in `findings.count`. An entry that restates a finding an earlier review body listed records `sameAs`, the key of the entry that listed it first. A round that read the diff in slices records the files in each slice and the verdict reader's answer on each (`slicing`). `diff.changedSinceLastRound` is the number of changed files the push since the last round touched, `judge.fixClaimedThreads` the threads where someone claimed a fix, and `approval` on a round that approved whether the approval was held, and why. To pull every record of a PR or a whole repo into one JSON Lines file, run `npm run review-history -- <owner/repo> [<pr number>] > history.jsonl` in a manki checkout. Add `--calls` to get one line per LLM call instead, ready to sum per agent, stage, model, PR or repo. The script decodes compressed records and reads the token from `GITHUB_TOKEN` or `gh auth token`.

To see whether a change to the review helps, run `npm run review-stats -- --repo <owner/repo> [--last <n>] [--fix-rate <fix-rate.jsonl>]` in a manki checkout before and after it. It reads the round records and thread replies of the last `n` merged PRs (40 by default), only reading from GitHub, and prints a markdown report:

- rounds per PR (mean, median and max), the share that passed after one round, the share that needed 5 or more, and the rounds that ended incomplete;
- the approved rounds, and how many PRs ran more rounds after their first approval, with the number of such rounds;
- findings per round and per approved round by severity, and of the findings a later round raised for the first time, the share on code an earlier round reviewed. A finding the round put under an earlier Manki thread counts in none of these, such as another instance of a finding that went into its thread as a reply. A record from before the `posted` field does not say where a finding went. For those the script leaves out a finding that names an earlier thread, or that matches one by file, title and line. It cannot tell whether that thread was still open at that round, so it also leaves out a blocker posted again after its old thread was resolved. A round that ran without the earlier round's change, which is a "Review again" run or a failed fetch of the change at the last reviewed commit, tags every finding `new`. A record that says so (`findings.originsWithoutPrior`) is left out of the reviewed-code share. An older record does not say so, and its findings on reviewed code are missing from the share, so the share reads too low. A suggestion or nitpick on reviewed code is not posted, so it counts in none of these either, and shows under `reviewed_code` in the table of findings recorded without posting;
- with `--fix-rate`, which takes the repository's `metrics/fix-rate.jsonl` from its memory repo, the fix rate by severity for the same PRs. A finding counts as fixed when the judge marked its thread addressed or a later commit touched its lines, whether or not that commit fixed it;
- how blocker threads ended: fixed, withdrawn by Manki, or other;
- per finder model, the raw findings, the kept findings only that model raised and those it raised with another finder, and the tool steps per call;
- the verdict reader's blockers, and the refutation outcomes per severity, counting the findings a disproof dropped, unposted ones and leads left unsettled, and an answer a later round reused only once;
- for the second refuter on `models.refuter_pair`: what it cost, with the number of calls that had no known price, how often it agreed with the first refuter, how often the two split with one confirming and one disproving, and how often it changed the outcome the first refuter alone gave, with a count per pair of outcomes;
- the cost per PR and per round, and the share of follow-up rounds whose inter-round diff was cut or unknown;
- how often each finder model was told to wrap up, the files changed since the last round, the fix claims, the memory loaded and the slices per round;
- per related repository, the rounds it was configured in and the rounds that read it, the reads per such round, and its fetch failures and skipped rounds;
- per week, account and subscription usage window, the highest share used any round read, and how many rounds read it at or past 70, 80 and 90%;
- a table per decision the records keep: prompt versions per stage, pause causes, static analysis sources with skip reasons, grade changes, pre-existing claims, memory suppressions, the findings recorded without posting per reason and severity, where a finding the judge dropped takes its severity from the last step of its `gradePath`, the warnings carried from an earlier review body, listed again by how many rounds ago they were first listed and ended per reason, the verdict reader per slice, approvals, thread reply decisions and token service calls.

A scheduled workflow, `.github/workflows/review-stats.yml`, runs the report for manki and token-service every Monday and posts it as a comment on the open issue titled "Weekly review statistics", which it opens the first time. It takes the fix rates from the central memory repository. It uses only the workflow's own token, with read access and `issues: write`. Run it by hand from the Actions tab.
