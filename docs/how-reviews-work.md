# How reviews work

What Manki does on each round, how it picks its readers, how it grades findings, and what it reads besides the diff.

## Review pipeline

Manki reviews run in these stages:

1. **Planner** (pre-review): A fast Haiku pass answers three questions about the nature of the change, never its line count, plus the judge effort and PR type. A repository can fix the judge effort with `judge.effort` instead. `trivial`: could a defect hide here at all? A trivial change (docs, a rename or move, a repeated mechanical edit, dead code, fixtures) is read by a single **quick check**. The planner sees only the list of changed files, never the PR title, description or diff text, and Manki believes a `trivial` answer only when every changed file is docs, snapshots or generated, deleted, or renamed without edits. A change to tests alone is not trivial: one finder reads it. `subtle`: does judging it need reasoning about behavior? That sets the finders' effort to high, otherwise medium. `paired`: could a defect reach a user if every reader missed it? By default that adds a second finder. A missing or unclear answer, a timeout or a disabled planner takes the side that adds review: by default two finders at high effort. A diff that touches a security-sensitive path (auth, tokens, secrets, crypto, sessions, permissions and similar), CI or automation (`.github/workflows/**`, `.github/actions/**`, `action.yml`), a dependency or toolchain manifest (`package.json`, lockfiles, `Cargo.toml`, `go.mod`, `pyproject.toml`, `requirements*.txt`, `Gemfile`, `*.gemspec`, `rust-toolchain*`, `.nvmrc`, `Dockerfile*`), or a data contract (`migrations/**`, `*.sql`, `*.proto`, `schema.*`, `openapi*.yml`, `openapi*.yaml`, `openapi*.json`) is never trivial and always paired, whatever the planner or `planner.paired` say. Each round is triaged fresh. See [Review groups](#review-groups) for how the answers and paths pick the readers.
2. **Finders**: The readers of the PR's [review group](#review-groups) read the diff in parallel. Which group a PR gets and who is in it is yours to set. By default it is one finder on `models.reviewer`, plus on paired rounds a second on `models.reviewer_pair`. Every finder runs the same checklist, so the default pair differs only in its models, and a reader of a group of your own can add a `focus` line. It checks the change itself: correctness first, then security, including resource exhaustion from outside input such as an allocation sized by a length a caller passes. When the PR title, description or changed code says the change matches another implementation, a spec or a standard, it opens that code, in a `reference` related repository when one is configured, and reports each difference. When the code implements or mirrors a reference, such as a spec, another implementation or an API it talks to, it compares each contract in both directions: what the code produces against what the reference accepts and the other way round, along with limits, field order, field types and versions. Then it checks error paths, cases a pattern match, error handler, ignored result or fallback drops, and tests that would still pass if the change were reverted or that set internal state. It looks for an existing helper the change could reuse and for breaks of the rules in the repository's `AGENTS.md`, `CLAUDE.md` or `CONTRIBUTING.md`, and reports such a finding only with the helper's `file:line` or the rule quoted. It also goes through the rules about the change as a whole, such as a test or a migration that a kind of change requires (see [Rules from instruction files](#rules-from-instruction-files)). Then it checks contract breaks, and when the change narrows what it accepts (a lower or new limit, stricter validation, a narrower type, a new required field or a stricter format) it finds every producer of that input, in the repository or a reference it mirrors, and checks that each still fits. It also searches outside the diff: every reader of a changed type, field, variant or function across the repository, sibling state that holds the same item or is computed from it (other collections, caches, indexes, derived totals or counts, serializers, change notifications), and counterparts that must check alike, such as encode and decode. Every finder gets any `reviewers:` entries. Every round, each finder searches the whole PR: it reports every blocker, warning and security issue it finds, follows the callers of changed code and other routes to the same outcome, and for each defect checks the whole PR for the same kind, reporting one finding that lists every place. Without `models.reviewer_pair` the second finder runs on the other Claude tier (Sonnet with Opus), which needs no extra credential. Another provider is used only when you set it. If any finder fails after its retry, the round ends incomplete and never approves. A reply that is not the list of findings fails the finder too, and so does one where no entry has a title or a description. The retry then tells the finder what was wrong with its reply.
3. **Sibling comparisons**: Alongside the finders, small targeted calls on `models.reviewer` compare the changed code with the code beside it: whether a sibling field can hold the item a changed line looks up, and what checks one implementation of a function has that its siblings lack. Their findings go through dedup and the judge like any finder's. See [Sibling comparisons](#sibling-comparisons).
4. **Claim checks**: Also alongside the finders, each statement in the PR title, its description or an added comment that the change relies on, such as "the upload service already rejects files over 10 MB", gets one small call on `models.reviewer` that looks for the code that proves or breaks it. That call never reads the PR description. Only a statement the code disproves gives a finding. See [Claims of the PR text](#claims-of-the-pr-text).
5. **Dedup**: A two-tier dedup pass drops findings that repeat an earlier resolved finding before judge evaluation. A static matcher handles exact and near-exact titles on nearby lines, and matches a thread whose code moved on the line it was posted on. Then an LLM dedup pass (Haiku) compares each finding's title, line and description with the earlier resolved findings in its file, so a repeat in other words is caught too.
6. **Judge agent**: A single agent evaluates the deduplicated reviewer findings for accuracy, actionability, and severity. It filters out noise, merges any remaining overlap, and grades each surviving finding as a blocker, a warning or a note. It reads each finding's code and the diff of every file with a finding, a line a finding cites as proof or in an evidence line, or an open thread, cut to 200,000 characters when those files are larger. With `review.sweep`, a finding it keeps can start a [sweep](#sweeping-for-a-defect-class) for other instances of its defect class, whose findings it then judges too.
7. **Verdict reader**: Runs only when no finding blocks. It reads the whole diff cold on the judge's model, without the PR description or earlier rounds' findings, and looks for a reason not to merge. A large diff is read in the same slices as the finders, one call each, and the PR is `READY` only when every slice is. Each call is told which slice it reads and which changed files only the other slices hold, so code missing from its slice is no defect. The blockers of all slices are posted. A finding the judge kept that names the same problem as one of them is folded into that blocker, so one problem gets one thread. It counts as the same problem when both sit in one file at most 5 lines apart and cite at least one common line of that file as proof, within 5 lines of both, whatever their titles say. It also counts when one title contains the other, and they are at most 5 lines apart or one cites the other's line as proof. Titles that only share words must each cite the other's line. A finding these rules leave apart is still checked when it sits near the blocker: their lines or narrow proof lines are at most 5 lines apart. The dedup model gets every such pair of the round in one call. It folds a pair only when it answers that both describe the same defect, with the same root cause and the same fix. Without a dedup model, or when the call fails, the pair keeps two threads. A proof line counts only as a single line or a span whose first and last line are at most 5 apart. When the folded finding's title says something the blocker's does not, the blocker's description ends with "Also reported as:" and that title. From the second round it also gets the files changed since the last reviewed round, as the finders do. `READY` approves with "What this does" and "What to test" sections. `ADDRESS_FIRST` requests changes and posts its blockers as inline comments, each with what the reader checked and the lines that prove it. When the judge has repository tools, it first tries to refute each of these blockers as it does its own, and the outcome closes the collapsed section under the blocker, after its fix and checks. Output that cannot be parsed ends the round as incomplete, never as an approval.
8. **Review posted**: Surviving findings are posted as inline PR comments or listed in the review body, under a summary and the verdict.

No finder or verdict reader prompt cuts the diff. They read it in slices of about `slice_lines` changed lines and at most 200,000 characters, so a normal PR is read whole in one call, and each call is told which slice it reads. A file with more changed lines stays whole in a slice of its own, and one over 200,000 characters is split between its hunks, or inside a hunk between lines. An added line over 20,000 characters cannot be shown in full, so a round whose reviewed diff holds one ends incomplete before any model runs, and names the first 10 such lines. Split the line, or exclude its file in `exclude_paths` on the base branch. Lines in excluded files do not count. A longer removed or unchanged line is shortened, since cutting it hides no new code, so deleting a minified file still gets a review. Each slice costs one call per reader, so the size of the reviewable diff is also capped in characters, next to `auto_review_max_lines` and `max_diff_lines`. A PR over 2,000,000 characters gets no automatic review, only the too-big notice with Review again in its settings block, and one over 4,000,000 is never reviewed, even when forced. These two limits are fixed.
When a provider's safety filter refuses a stage, Manki sends that stage once more on `models.fallback`, which defaults to `models.reviewer`. A stage already on that model goes to its other Claude tier instead. The round context records the stage, the fallback model and the refusal reason under `models.fallbacks`. A second refusal fails the stage, which ends the round incomplete for a finder, the judge or the verdict reader, and other errors are never retried on the fallback model. A used-up subscription limit, quota or rate limit, or an overloaded provider, is neither retried nor sent to the fallback model. The round ends incomplete and names the limit, with its reset time when the provider gives one. To see it coming, the Review metadata section of the progress comment lists how much of each usage window the Claude and ChatGPT subscriptions have used, as the Claude and Codex CLIs report it after their calls, with the reset times. A call that fails, such as on the used-up limit itself, keeps its readings too. When a window has just passed the 70% or 80% mark, at most 2 points past it, the review body shows a red box under the verdict. From 90% the box shows on every review. It names each such window and the highest of the 70, 80 and 90% marks it passed. The readings in Review metadata show on every review either way. API keys and Gemini report no such windows, so they show none.

An incomplete round posts a comment, fails the `Manki` check and keeps an earlier request for changes. It dismisses Manki's approval of an older commit, since no model approved the code pushed since. An approval of the same commit stays. A review command then reviews the commit again, also when an earlier review of it was complete. The comment carries the round's record, with what ran and what failed. A later round does not count it as an earlier round: it does not use up the round cap, and the next round compares against the last round that completed.

## Review groups

You decide who reviews what. Each round sorts the PR into a **review class**, and the class picks a **review group**: the readers that run as finders. The `review` block configures all three. A group lists one or more readers, each with its own model from any supported provider, its effort and an optional `focus` line. A class matches PRs by path, by the planner's answers or both. The routing names the group for each class. Without a `review` block the built-in classes and groups below apply, which give a PR the quick check, one finder or two.

The class with the highest rank among those that match wins.

| Class | Rank | Matches | Built-in group |
|-------|------|---------|----------------|
| `security` | 100 | a security-sensitive path (`@security_paths`) | `pair` |
| `supply_chain` | 90 | CI, automation, a dependency or toolchain manifest, a file that fetches or builds code such as `.gitmodules`, `.gitattributes`, `.npmrc`, `build.rs`, `setup.py`, a `Makefile` or a `.husky` hook, or a `.manki.yml` or `manki.yml` anywhere (`@ci_dependency_paths`) | `pair` |
| `data_contract` | 80 | migrations, `*.sql`, `*.proto`, `schema.*`, OpenAPI files (`@data_contract_paths`) | `pair` |
| `behavior` | 50 | the planner answered `paired: true` | `pair` |
| `internal` | 30 | the planner answered `paired: false` | `solo` |
| `docs` | 20 | the planner answered `trivial: true` and every file is prose (Markdown, reStructuredText, AsciiDoc or a license), a snapshot or generated, deleted, or renamed without edits. Agent instructions such as `AGENTS.md`, `CLAUDE.md` or files under `.claude/`, `.cursor/` or `.github/instructions/` never count as prose here | `trivial` |

The built-in groups are `trivial` (the quick check on `models.reviewer` at medium effort), `solo` (one finder on `models.reviewer`) and `pair` (a finder on `models.reviewer` and one on `models.reviewer_pair`). Their effort is `auto`: high when the planner answers `subtle: true`, otherwise medium.

The progress comment names the class and group in its review header, such as `Review (security · pair)`. It names each reader by its model, the effort it ran at and the start of its `focus` when one is set, such as `Claude Sonnet 5.5 · high` or `Claude Opus 5.5 · high · consensus rules`. The quick check shows as `Quick check · Claude Sonnet 5.5`. A second reader with the same name gets ` #2`. The same names appear in failure lines, logs and the `Manki context` block.

`security`, `supply_chain` and `data_contract` are **floor classes**. Path rules decide them, so nothing in the PR's text can change them. A PR in a floor class always gets at least two finders on two distinct models, none at `low` effort. The one exception is the built-in `pair` group when `models.reviewer` is not a Claude model and `models.reviewer_pair` is unset: both finders then run on that model. The floor is checked after routing: if the routed group misses it, the PR moves up to the floor class's own group, then to the built-in `pair` group. So a class of your own that outranks `security` cannot pull a PR that also touches auth into a weaker group.

The `review` block changes the groups and the routing:

```yaml
review:
  groups:
    deep:
      reviewers:
        - { model: claude-opus-5-5, effort: high }
        - { model: gpt-5.5, effort: high }
  routing:
    security: deep
    data_contract: deep
```

That minimal example sends security and data contract PRs to two strong readers on two providers and keeps the built-ins for the rest. A fuller one:

```yaml
review:
  default_group: pair
  groups:
    solo:
      reviewers: [{ model: "@reviewer", effort: auto }]
    pair:
      reviewers:
        - { model: "@reviewer", effort: auto }
        - { model: "@reviewer_pair", effort: auto }
    deep:
      reviewers:
        - { model: claude-opus-5-5, effort: high, focus: "authz, injection, secret handling" }
        - { model: gemini-3-pro, effort: high }
        - { model: claude-sonnet-5-5, effort: medium, focus: "error paths and rollback" }
  classes:
    security:                      # adds paths to the built-in rule, never narrows it
      match: { paths_any: ["src/billing/**"] }
    hot_path:
      rank: 85
      match: { paths_any: ["src/consensus/**", "src/net/**"] }
  routing:
    security: deep
    hot_path: deep
    internal: solo
```

- **`groups`**: each group lists its `reviewers`. A reviewer takes `model` (a model id, `provider/model`, or `@reviewer` and `@reviewer_pair`, which resolve through `models`; unset means `@reviewer`), `effort` (`low`, `medium`, `high`, `xhigh`, `max` or `auto`, the default), an optional `focus` line added to that finder's prompt, and `role` (`finder`, the default, or `verifier` for the quick check). A group with the name of a built-in replaces it.
- **`classes`**: a new class needs a `rank` no other class has, and a `match` with `paths_any` (globs, or the `@security_paths`, `@ci_dependency_paths` and `@data_contract_paths` aliases), `triage` (`trivial`, `subtle` or `paired` set to true or false), or both. Every condition must hold. On `security`, `supply_chain` and `data_contract`, `match.paths_any` adds paths to the built-in rule. The other built-in classes cannot be changed.
- **`routing`**: the group per class. Classes you leave out keep their built-in group. When you set `groups` but no `routing`, every class goes to `default_group`, and the floors still apply.
- **`default_group`**: the group for a class with no route (default `pair`).
- **`allow_weaker`**: floor classes allowed to route to a group below the floor, such as `allow_weaker: [security]`. Without it, a config that routes a floor class to a weaker group does not load, and the warning gives the reason. Once such a config is on the base branch, Manki reviews with the default settings and does not approve. Every round that runs below the floor logs a warning.
- **`critical_paths`**: globs, or the path aliases above, that mark critical areas, where any wrong result is severe even in a rare internal edge case. They need no class or rank, and can name paths a built-in class already matches. The judge sees which findings sit in a critical area, with the first glob that matches, and grades a wrong result there as severe damage, which blocks when the other blocker tests hold.
- **`outside_input`**: what counts as outside input in your repository, in a sentence or two. The judge treats a failure that this input can trigger as reachable, never as a rare internal case. The finders get this rule and the list of critical paths too, so they grade by the same table as the judge.
- **`examples`**: worked examples from your repository, one string each, under `blocker` for findings that block and `not_blocker` for findings that do not. Set either side or both. The judge reads them next to its built-in examples on the same two sides.

The last three only change how findings are graded: `critical_paths` and `outside_input` by the finders and the judge, `examples` by the judge alone. A repository with consensus code might set them like this:

```yaml
review:
  critical_paths: ["dash/src/consensus/**", "dash/src/blockdata/**"]
  outside_input: >-
    Anything a network peer sends: P2P messages, blocks, transactions, headers
    and the length prefixes inside them.
  examples:
    blocker:
      - "Indexing `buf[len]` with a length read from a peer message panics on a short message."
      - "Changing the field order in a `consensus_encode` implementation changes the bytes on the wire, even when every test passes."
      - "An inverted weight comparison picks the wrong quorum member on every block."
    not_blocker:
      - "A debug log of a decoded message that leaves out the peer address: `note`."
```

Each review's `Manki context` block records a `routing` object: the class, its rank and source, every matched class, the group and why it was picked, any floor and escalation, where the `review` block came from, a `configDigest` of the classes, groups and routes, and each reader's model, provider and effort. Each finder's entry in `reviewers.agentMetrics` counts the kept findings only it raised (`keptOnly`) and those it raised with another finder (`keptShared`).

Manki reads the `review` block, like every other setting, from the PR's base branch only, so a PR cannot weaken its own review. A PR that changes the block is reviewed with the base branch's, and the change applies after merge. When the PR's own block does not load, for example because it misses a floor, Manki logs a warning and still reviews with the base branch's block. If the PR itself changes the file, Manki also holds its approval, so it never approves a broken block. When the base branch's config cannot be read, or does not load because its block is invalid or misses a floor, Manki uses the built-ins and the default settings with a warning, never the PR's copy, and does not approve. The PR that fixes it still gets reviewed. The models behind `@reviewer` and `@reviewer_pair` come from the base branch's `models` block.

`planner.paired` still works and is deprecated in favour of `routing`: `always` turns `paired` on before the PR is classified, and `never` turns it off, which routes `behavior` changes to the `internal` class and its group.

## Severity tiers

Each finding gets one of three severity levels, or is dropped:

| Severity | Meaning | Effect |
|----------|---------|--------|
| `blocker` | Must fix before merge | Blocks approval (REQUEST_CHANGES), posted as a review thread |
| `warning` | Should fix, but not blocking | Posted as a review thread that does not block, or listed in the review body. PR can still be approved |
| `note` | An optional improvement, never a defect | Listed in the review body, never as a thread, PR can still be approved |
| `ignore` | False positive or irrelevant | Not posted. The progress comment keeps the judge's reason |

The judge returns no grade, with the one exception described below for a finding it doubts. For each finding it states a cell of its severity table: the row is what goes wrong (severe damage, wrong behaviour, degraded but correct behaviour, an improvement, or style), and the column is whether normal use or outside input reaches it, or only a rare internal edge case. Manki works out the grade from the cell, so the judge has no field in which to lower the grade of a finding it does not doubt for a reason of its own. A reply that leaves a finding out, or gives it an entry that names no row of the table, is not complete. Manki keeps the entries the reply does have and asks the judge once more for the missing ones only, together with any open thread the reply did not evaluate. If a finding still has no entry after that, the judge fails, so the round ends incomplete instead of posting a grade the judge did not give. A thread that is still not evaluated stays open.

A finding is a blocker only when it passes five tests: the PR causes it (lines it adds, changes or removes), the failure can be named ("when X happens, Y goes wrong"), the damage is serious, the code proves it with cited lines, and the author would fix it (it is not a declared placeholder, a stub that does nothing yet and that no path reaches, or a tracked TODO, which make it a note at most unless it is a security defect). Serious damage is wrong behaviour in normal use or from outside input, lost or corrupted data, a crash, hang or resource exhaustion from outside input, a security defect, memory unsafety or undefined behaviour, or a broken public contract with no migration. Wrong behaviour in a rare internal edge case is a warning. The rare column is a claim, and on the wrong behaviour row Manki checks it: it adds the premise that normal use or outside input can produce the state to every such finding, and the refuter searches for a caller, stored data or concurrent use of a public API that produces it. Whatever the refuter answers, the finding stays where the judge put it: the answer is recorded and never raises the grade, so wrong behaviour blocks only when the judge itself states the normal column. Degraded but correct behaviour is a warning, or a note when rare, and there the column is taken as stated, since it blocks nothing either way. Missing tests, style, naming, docs, commit messages, performance without a crash and checks on trusted internal values never block. A test that cannot fail when the code it names breaks is a warning, and a doc that says the code does something it does not is a note. For a library, outside input is anything a caller of its public API can pass, such as readers and byte streams, and resource exhaustion or denial of service from outside input is a security defect. Behaviour that is intended but surprising becomes a note that asks about it, unless it is a removed guard, resource exhaustion or a security defect. A gap the author admits is no such choice: one the PR description, a comment or a TODO calls deferred, out of scope, left open or not handled yet keeps the grade its damage earns, and only a declared placeholder or a TODO with a tracking issue lowers it. A defect in lines the PR adds is the PR's own, even when the bad state those lines mishandle existed before, so "not worse than before" is no reason for a lower cell. The defect a PR fixes in one path and leaves in a sibling path is the PR's own too: a PR that adds an auth check to `POST /items` and leaves `PUT /items/:id` open has an incomplete fix, which is never pre-existing. The judge and the verdict reader mark a finding that claims the code fails to compile, type-check or pass its tests. Such a claim blocks only when a CI annotation on the commit reports the error, unless it is a security defect. Otherwise it is posted as a warning that asks to check that it builds, since CI fails the build or the test itself. Code the judge cannot see never drops a blocker or a warning: the judge sees the diff of each file a finding sits on or cites in a proving line or an evidence line, the uses outside the diff and the code each finding cites outside it, a finding that cites one of those is graded on its merits, and the judge grades a finding that rests on code beyond that as a doubt, so a blocker it cannot follow becomes a warning. A note that rests on code the judge cannot see is the exception: the judge drops it, since a missed note costs less than a false one. A doubt that the failure is reached, such as no caller in the code shown, is graded the same way, and a path through a library's public API counts as reached without a caller in the repository. So does a function, method or handler the PR adds: it is there to be called, so a missing caller is no doubt. A value the code shown proves the code's own logic keeps valid is evidence, not a doubt, so the rules for rare internal edge cases and trusted internal values still apply to it. For every finding the judge states the row its consequence would earn if every premise it doubts holds, such as unseen code, reachability or whether the PR causes it, and lists each doubted premise as a fact the code can confirm or disprove. A premise its reasoning settles from cited lines is no doubt and is not listed. A premise that lowers or caps the grade, such as callers probably validating a value, counts as a doubt too unless the code proves it. Each premise decides either whether the defect exists at all or only which cell it earns. Manki grades a blocker cell with an open doubt as a warning until the refuter confirms every doubt, except on a security finding or a tool alert. Next to the doubts of such a finding the judge also states the grade the finding earns once every doubt holds, `blocker` or `warning`. The refuter is asked whether the premises are true and never how serious the damage is, so this is where that question is answered. With `warning`, the judge names the blocker test that still fails, and the finding stays a warning when the refuter confirms every doubt. Example: a status line counts one retry too many while every result is right. A doubt the judge listed, a rare state and "not worse than before" are no reason for `warning`. With `blocker`, or no answer, a confirmation of every doubt gives the cell's grade only to a finding a finder filed as a blocker. A doubt means the judge named the blocker cell for code it had not seen, and the refuter's confirmation says the premises are true, not that the damage is serious. So a blocker that only the judge's cell makes needs a cell with no doubt behind it. Any other finding of this kind is a warning from the refuter's step on, whatever its check answers. It takes one of the eight checks of warnings described below, and it is posted with the status that check gives it, also when the check settles nothing or the eight do not reach it. A memory suppression, a thread the author resolved or an earlier agreement hides it like any warning. Example: a finder files a warning that a Python CSV export writes dates in the server's time zone, the judge states wrong behaviour and doubts that any export runs outside UTC, and the refuter finds a scheduled export for an office in another zone. The finding is posted as a warning confirmed with tools, and the round can approve. The highest grade any finder gave the finding or a duplicate merged into it counts. Two kinds of finding rise whatever their finders filed: a security finding, and a finding that restates a blocker of an earlier round or sits in the file of an open thread that blocks. Manki reads the judge's answer nowhere else: a blocker cell without a doubt blocks at once, and a security finding and a tool alert keep the grade of their cell. A doubt about the cell alone counts only on the wrong behaviour row, where the column decides whether the finding blocks. On every other row Manki drops it, so only a doubt whether the defect exists holds a severe finding down. A doubt alone never drops a finding that would earn a warning or a blocker. A finding is a warning only when the PR causes it, the failure can be named and cited lines show it. A warning the judge cannot prove from the code shown or its own tools names its doubt, and Manki posts it only once it is proven, as described below. The finders, the judge, the refuter and the verdict reader treat everything they are told about the code as a claim to check: the PR description, code comments, linked issues, author replies, another model's finding or reasoning and an earlier round's verdict. A claim the code confirms is evidence. One they cannot check is noted but never raises or lowers a grade on its own. The exceptions are an author's statement that behaviour the code shows working is intended, a declared placeholder or a TODO with a tracking issue, and a PR description that says a change breaks no consumer. A statement of the author that a finding does no harm, such as that a value is checked elsewhere, a path cannot be reached or other code guarantees it, is no exception: the judge lowers or drops the finding only with the line that shows it, and otherwise lists the premise the statement denies as a doubt. Review memory is the maintainers' recorded decision, not a claim to check, and so are the rules in the repository's instruction files, which the judge sees as the finders do. A finding that says the change breaks one of those rules is checked against the rule's text, and a convention such as naming or import placement is graded a note. The judge grades a finding on its central claim: a wrong side detail, such as an off line number or a misnamed helper, is corrected in its reasoning and never drops the finding on its own. A later round keeps a finding's cell unless the code or the evidence changed, but only a cell with no doubt behind it anchors. For a finding from a record that stored only a grade, the judge states a cell that gives that grade. It does the same for a finding an earlier round kept at a warning in a blocker cell, by the judge's own answer or because no finder had filed a blocker: the later judge is shown its grade without that cell, so a settled doubt never turns it into the blocker the earlier round did not give. A grade an earlier round kept below its conditional grade is regraded from the code, and when the judge keeps it without naming a doubt while no check settled the earlier one, Manki sends the earlier doubts to the refuter.

With `judge.tool_steps` above 0, a judge with repository tools also reads the code a finding rests on while it grades, up to that many calls, so code it read counts as code shown and only a doubt its calls left open goes on to the refuter. It is off by default, since it makes the judge call longer. When the judge has repository tools, it also tries to refute each blocker, each open lead graded `blocker` or `warning`, each blocker posted as a warning for want of proving lines or of a CI result, each finding that would earn a higher grade if a premise the judge doubts holds, such as code it could not see or a path it doubts is reached, each finding the judge placed in the rare column of the wrong behaviour row, and up to eight warnings a round that nothing proves yet: a warning the judge keeps while doubting the defect exists, and a warning that cites no proving lines. A finding kept below `warning` with such a doubt is not checked. These checks run before Manki hides a finding that repeats one the author agreed with or resolved, so that step sees each finding's settled grade and never hides one a check raised to a blocker. A finding that step hides is checked only when a confirmation can raise it, so it takes none of the eight checks. The refuter names the general rule the finding relies on, such as a language or library behaviour, and searches the unchanged code for code that relies on the same rule. One such counterexample that already builds or runs disproves the finding. For a reachability doubt the refuter searches for a path from an entry point. A public function, method or field is one when the repository is a library or its `review.outside_input`, which the refuter is given, names that API. In an application an exported function needs a caller. For a finding with such a doubt the refuter also sees the PR's change to the files the finding cites. It confirms a doubt that the PR causes the defect only when a changed line does, and never disproves a finding only because the change shown does not cause it. The refuter answers each premise the judge listed on its own, and besides them whether the defect itself exists, whoever or whatever produces the state it needs. The premises decide the grade: a finding with such a doubt gets the higher grade its cell gives only when every premise is confirmed. A blocker cell gives its blocker then only to a finding a finder filed as a blocker, a security finding or one that restates an earlier blocker, and never when the judge stated `warning` as the grade it earns then. A finding in the rare column of the wrong behaviour row is the exception. The refuter is asked whether normal use or outside input can produce the state the failure needs, and whatever it answers, the finding keeps its grade and its column: only the judge places a finding in the normal column. The answer about the defect decides whether the finding counts as confirmed. A disproved premise that the defect rests on drops a finding below blocker, and a disproved premise that only the grade rests on keeps the judge's grade. A check that disproves a premise the defect rests on while it confirms the defect itself contradicts itself, so it settles nothing: the finding keeps the grade it had before the check. An answer that the defect does not exist counts as a disproof in the same way, whatever the premises of that check add up to. So no finding gets a higher grade while a refuter says its defect does not exist, also when every premise is confirmed, and a finding below blocker is dropped. A confirmation makes an unproven blocker a blocker again, but a claimed build failure stays a warning, since reading code is not compiling it. The verdict reader's blockers get the same build claim check, and when every one of them was such a claim, the change stays ready. For an open lead the refuter is told to start with what the finder left to check, so its tool steps go to the open point first, and to treat what the finder says it checked as a claim. A lead it confirms is posted at its grade, one it disproves is dropped, and one below `blocker` it cannot settle is listed in the review body under "Not finished checking". A disproved lead that breaks a [rule the judge confirmed](#rules-from-instruction-files) is posted as a finding, since the check finished it and no disproof drops a confirmed rule break. A lead still unsettled carries over to the next round's judge as an earlier lead, matched by file and title, instead of coming up as new, and the review body lists it once with the round it first came up in. It carries over while its file is in the PR and known to be unchanged since the last round, for at most three rounds. A security lead the tools do not confirm stays posted. Each round records how each lead ended under `leads`, with the refuters' answers. One refuter's answer never clears a blocker: a disproved blocker keeps its grade, whether it came in as a finding or an open lead, and is posted with the reason the refuter gave, so a maintainer can weigh it. Text in the PR could steer the refuter, so only a person can let such a blocker go, or two refuters in the one case described below. A disproof still drops a finding graded below blocker, such as an open lead or a finding capped at warning for want of proof, when it cites a line of the finding's own file or of the diff. The one exception is a finding that breaks a [rule the judge confirmed](#rules-from-instruction-files), which no disproof drops. See [security](security.md) for the tools.

The refuter runs on the judge's model (`models.judge`). With `models.refuter_pair` set, a second refuter on that model checks the same findings at the same time, with the same prompt and tool budget. Models of one family can share a blind spot, so pick one from another provider. Unset, there is no second refuter and no extra call. An unsettled answer, or a call that fails, counts as no vote, and the other answer decides as it would alone. When one refuter disproves a finding and the other backs it, the finding keeps the judge's grade. Where it is posted, it shows both reasons and is marked not confirmed. A refuter backs a finding when it does not disprove it and confirms the defect or at least one of the premises the judge doubted. A refuter that disproves a premise only the grade rests on stops a higher grade in the same way. Two disproofs lower a blocker in one case only: no finder graded the finding a blocker, the judge alone raised it to one, and both refuters disprove it on two different models. It then goes back to the highest grade a finder gave it and is posted with both reasons, and every rule for that grade applies to it. A finding that breaks a confirmed rule of the instruction files goes no lower than the grade `review.rules` gives, so with `block` it stays a blocker. Every other blocker that both refuters disprove stays a blocker and is posted with both reasons, since text in the PR could steer both alike: a blocker a finder filed, also as a duplicate the judge merged into another finding, a security finding, a tool alert, an open lead, a blocker the verdict reader adds, and a finding that restates a blocker of an earlier round or an open thread that blocks, or sits in the file of such a thread. The blocker also stays when the second refuter fails, is unsure or confirms, when `models.refuter_pair` is unset, and when both answers come from one model. The round record keeps the model with each answer and the judge's cell as `judgeCell`. The next round's judge sees the finding at its finders' grade with no cell, so it has no blocker cell to restate. For a finding below blocker it works as one refuter does: one confirmation with no disproof raises it, and one disproof with no confirmation drops it. A security finding still changes only when confirmed. The round record stores the second answer as `pairRefutation` beside `refutation`, and the model as `models.refuterPair` on rounds where it checked a finding or an earlier answer of it was reused. Its calls are recorded under the `refute_pair` agent. The second refuter needs repository tools, so the Claude or Codex CLI, and runs only when the judge's refuter does. Otherwise the run logs a warning. A later round reuses a refuter's answer for the same finding while the files it rests on are unchanged, and makes no new call for it. An unsettled answer whose call ended on its step budget is not reused: the refuter was told to finish or took its last step, so it may only have run out of steps, and the finding is checked again.

Only `blocker` findings block, in every round. A `warning` does not block, in its thread or in the review body, so the round can approve. The one finding that blocks without serious damage is a confirmed [rule finding](#rules-from-instruction-files) in a repository that sets `review.rules: block`. A blocker from the verdict reader blocks too. A security finding blocks only as a blocker. Manki grades it in the normal column of the row the judge states, since an attacker chooses the input, and no doubt holds it down. So a security defect with severe damage or wrong behaviour is a blocker, while one that only degrades behaviour, or one that cites no proving lines, is a `warning`, which does not block.

A warning is posted only when it is proven. It is proven when it cites the lines that show the failure and the judge does not doubt that the defect exists, or when a refuter confirms it. With repository tools, the refuter checks each warning the judge doubts and each one that cites no proving lines, up to eight a round. The findings of a `review.sweep` share those eight. A warning is confirmed when the refuter answers that the defect exists, not when it confirms a premise. A warning the check confirms is posted, and one it disproves is dropped. A warning the check cannot settle, or that the eight checks did not reach, is not posted. Without repository tools no check runs, so the cited lines decide: a warning that cites them is posted, and one that cites none is not. The cited lines also decide whenever no check could run on a warning for another reason, such as a refuter call that failed or a file the refuter cannot read, like one the PR deletes. Such a warning takes none of the eight checks. Neither does a warning a later step keeps out of the review whatever a check says: one the author already agreed to or resolved in its thread, and one a memory suppression matches. A warning in the rare column of the wrong behaviour row gets no check in those cases either, although its check is outside the eight, since no answer raises it. The same holds for a finding the judge keeps at a warning in a blocker cell: no answer raises it, so those steps hide it like any other warning. A tool alert takes none either. A warning that restates a finding an earlier round still shows is checked after the other warnings whose posting a check decides, and not left out, since that match is settled only after the checks. A security finding is posted whatever a check says, so a check of one the judge doubts only settles the status it shows. A finding that breaks a [rule the judge confirmed](#rules-from-instruction-files) is posted without proof too, and no check of one the judge doubts drops it. Both come last among the eight, after every check that decides whether the review shows a warning. A round can judge findings in more than one call, since the judge grades the findings of a `review.sweep` in a call of their own. Each call checks only its own unproven warnings on changed code that restate no earlier finding. Every other check of the eight runs once, after the round's last judge call, so those never take a check from a warning a later call brings. The round record keeps each warning left out under `findings.unposted`, with `unpostedReason` set to `unsettled_check`, `not_checked` or `no_proof`. The review body names each warning it leaves out for this reason, with the reason, in its "Checked and left out" section. The progress comment keeps the judge's reasoning for each one under "Judge decisions". An incomplete round has no such log, so its review has no such section, and the round record still keeps the warnings. This rule never leaves out a finding that would be a blocker if true: one whose cell would block if the judge's doubts hold, whatever grade the judge stated for that case, one the judge placed in the rare column of the wrong behaviour row, or one a finder or the judge graded a blocker at any point, such as a blocker posted as a warning for want of proving lines or of a CI result. It is posted as a warning that says Manki could not confirm it. The rule also never leaves out a security finding, a tool alert, or a finding that restates one an earlier round still shows, so no open thread and no "Still open" entry changes because of it. A link the judge names to an earlier finding the review no longer shows keeps nothing. A later round that finds the same warning again checks it again.

Each blocker and warning a round posts says how it was checked: proven from the cited lines, confirmed with tools, or not confirmed. A thread names it in the title of its collapsed section, and a finding listed in the review body in a line "How this was checked" inside its fold. Code works this out from the finding, and the judge returns no confidence. A finding is not confirmed unless one of two things holds. It is confirmed with tools when a refuter answered that the defect itself exists. The refuter gives that answer for every finding it checks, apart from its answers to the premises the judge doubts, so a confirmed premise, such as that normal use reaches the code, never gives this status. It is proven from the cited lines when no refuter checked it, it cites proving lines, the finder finished checking it, so it is no open lead and no finding the finder ran out of tool steps on, and the judge names no doubt whether the defect exists. Neither holds for a finding a refuter disproved, whether in a premise the defect rests on or in its answer about the defect. A check that confirms the defect itself while it disproves such a premise contradicts itself and disproves nothing, so it confirms the finding with tools unless another check disproves it. So a finding a refuter checked is confirmed with tools or not confirmed, whatever lines the check added, and a finding that fits neither description is not confirmed without a rule of its own. Such a finding says "Manki could not confirm this, so please check it." under its title. That includes a warning the judge doubts and the cited lines keep because no check could run on it: on a round without tools, after a refuter call that failed, or in a file the refuter cannot read. It also includes two findings a check cannot confirm, whatever the refuter answered: a claimed build, type or test failure that no CI result reports, since reading code is not compiling it, and a finding still posted as a warning for want of proof. A tool alert has no status, since the tool is its source. The round record keeps the status as `checkStatus` on each finding entry. Under "Checked in the code" the same section lists what was read: the reviewer's checks with a preview of the code, the proving lines, and the lines a refuter's confirmation added. A confirmation that rests on a [related repository](#related-repositories) lists each of its lines there as `owner/name:path:line`, linked to that line at the commit the round fetched. Only the location is shown, never the line's text. A check that did not confirm names the lines it read in its own sentence, related lines included.

Every round reviews the whole diff as thoroughly as the first. From the second round, the finders and the verdict reader also get the files the author changed since the last reviewed round, listed ahead of everything else, and check that new code first. A rebase onto the base branch changes no file, and when the change since the last round is unknown, the list is left out. The finders also get each earlier blocker a judge confirmed fixed, and each open blocker whose file changed since the last round. A fix often closes only the route the blocker named, so they check the other routes to the same outcome.

A finding about code the PR did not touch is tagged `pre-existing`. It counts as one only when all of these hold: the reviewer marks it pre-existing with a reason the defect exists without this PR's change, its line is not one the PR adds, the judge keeps that mark, it sits outside every hunk of the PR's diff, none of the lines it cites as proof is in the diff, and the PR neither deletes its file nor leaves the file out through `exclude_paths`. So an unchanged caller that breaks because the PR changed a function keeps blocking. Reviewers report such defects too, so they are not lost. Manki posts only the pre-existing findings worth an author's time: blockers, warnings a tool check confirmed, and security findings. It keeps the others in the round record only. With repository tools, the refuter checks each such warning after the unproven warnings on changed code of every judge call and inside the same eight checks a round, those with a doubt first. A warning the check confirms is posted and one it disproves is dropped. That holds for a warning in the rare column too: when the refuter confirms the defect, the warning is posted, whatever it answers about whether normal use reaches it. One the check cannot settle or does not reach is not posted, and neither is any such warning on a round without repository tools. The review body names each of them in its "Checked and left out" section, and the round record keeps it. A posted one shows "Pre-existing" in its header and is listed under "Pre-existing" in the review body. It never blocks: a blocker there is posted as a warning, and the round record keeps its original grade. A security finding is the exception. It keeps its grade and blocks wherever it sits. A blocker from the verdict reader is never pre-existing, since no judge checks its mark.

From the second round, each finding is tagged as new, previously missed or still open: new when it sits within a few lines of code the PR changed since the last reviewed round, previously missed when an earlier round already reviewed that code. Manki compares the PR's own change at both rounds by line text, so a rebase or shifted line numbers do not make reviewed code new. A blocker blocks wherever it sits. A warning on reviewed code is posted like one on new code: in a thread when its line is in the PR's diff, and under "Missed by an earlier review" in the review body when no line comment can hold it or the review already opens five such threads. Its thread says in one sentence that an earlier round reviewed those lines and missed it, and that it does not block. On a repository that requires resolved conversations, the thread has to be resolved before the merge like any other. A security finding below a warning on reviewed code stays listed under "Missed by an earlier review". A note on reviewed code is not posted at all. The round record keeps it under `findings.unposted` with the reason `reviewed_code`. Manki leaves one out only where it compared the lines with the earlier round. A round that could not read the PR's change at the last reviewed commit, or the diff since that commit, leaves out none of them, and neither is a note in a file outside the PR's diff. A finding that restates an earlier finding still open gets no thread of its own either. The judge links each finding to the earlier one that names the same defect, from every earlier blocker and every other earlier finding still open, in a thread or in a review body. A finding it does not link is matched by the rules that fold a finding into a verdict reader blocker, and the dedup model checks a nearby pair those rules leave apart. An open thread is matched by its own finding and by every finding an earlier round took into it. A restatement of an open thread is not posted, and a blocker among them, the verdict reader's included, is listed under a link to that thread. When the restatement is graded above the thread, Manki replies there with it, and for a blocker the round record makes the thread block from then on. A security finding is never carried by a thread that is not a security thread, since only a thread's first comment guards it. It joins the security thread that says the same, or is posted on its own, and keeps no link to another thread, so that thread stays among the open ones in the verdict. A blocker that raises a thread which did not block before counts as a new blocker in the verdict line. When the judge calls a finding another instance of the same mistake, such as another field the same check misses, Manki replies with it in that thread, unless the thread took it already, and a blocker among them makes the thread block. These replies go out before the review, and a finding whose reply fails is posted on its own instead. When the review then does not post at all, Manki deletes the replies again. A thread the judge finds addressed this round takes nothing. When the review threads cannot be read, no finding is matched to an earlier one that round, since every finding of a thread would look like one listed in a review body. A restatement of a finding an earlier round listed in its review body is listed under "Still open from round N", whatever code it sits on, unless it is pre-existing, which stays under "Pre-existing". A note among them is not listed again, and the round record keeps it with the reason `listed_earlier`. Neither rule leaves out a security finding, a tool alert, or a finding that goes into an earlier thread, and a "Review again" run leaves out nothing. Each finding's `origin` in the round record says which it is, and `raisedIn` the round that first listed it. Manki also does not object to a change it asked for: a smaller finding on code that applies a fix an earlier round suggested is dropped, unless the judge finds the new code worse. A security finding or a tool alert there is never dropped. A finding that repeats a problem Manki already answered in a thread, with Fixed, Withdrawn, Agreed, Kept or Unverified, never gets a new thread. It is dropped when its title matches the thread's and its file did not change since the last round. Otherwise the judge keeps it only when the code there got worse, and Manki then replies in that thread and reopens it if it was closed. When the finding is now a blocker, that thread blocks approval from then on, whatever its first comment's severity. Findings Manki agreed to leave for later work are listed in every later review body under a "follow-ups agreed for later" heading.

A warning that an earlier round listed only in its review body has no thread to keep it visible, so Manki carries it forward without a model call. When a round lists a warning in the body, its record keeps a hash of the line the warning points at together with the line before and the line after it, as the file reads at that commit and without the whitespace around each line, and how many places of the file read the same (`citedLine`). Each later round reads the file at its own head. While the file still has that many places reading the same, the review lists the warning again in one line under "Earlier warnings, code unchanged", with the round that listed it first, and an approval counts it in its first line. The line shown is the one that place is on at the round's head, which the carried entry records as `currentLine`, and a finding of the round is compared with that line. When several places of the file read the same, the list shows the file without a line. It never blocks and never holds an approval. The warning leaves the list when the file has fewer such places or is gone, and from then on the finders and the judge see the code as in any round. Line numbers and the history between the two commits play no part in whether it stays, so a rebase, code moved within the file and an edit elsewhere in the file change nothing, and a line the PR never changed or a file outside its diff is treated the same way. An edit to the line right before or after the cited one counts as a change, so a guard added above the line ends the warning, and so does an unrelated edit to a direct neighbour. When the file cannot be read, the warning stays listed. A warning without a line, or on a line the round could not read, has no place to compare and is not carried, and a file that was renamed or moved reads as gone. A carried warning also leaves the list when a finding the judge graded this round names the same problem, which then stands in its place whatever became of that finding. The reason is taken after the last step that leaves a finding out, so a note that names the warning and goes over `review.notes` ends it as `hidden_note`. A warning that names it and is left out because nothing proves it does not end it, so the carried warning stays listed. Neither does a warning on code the PR did not change that no check confirmed. Notes are never carried. The round record keeps the carried warnings under `findings.carried`, apart from the round's own findings, and the ones that left the list under `findings.carriedEnded`, each with its reason: `line_changed`, `restated`, `hidden_note`, `judge_dropped` or `left_out`.

The review body leads with the verdict, which counts the findings this round posted. A finding posted as a thread is only counted there, since its thread sits right below the review. The judge's summary follows under "What blocks:" when changes are requested. The review of an approval leaves the judge's summary out. When an approval is withheld because an earlier round record could not be read, the summary follows under "Summary:". The judge writes it before later steps can take a finding out of the round, such as a disproof or a note the review leaves out. So when the judge kept a finding and the round lists none of the findings it kept, the summary is left out. Later steps can also make a blocker the summary never saw, so the summary is left out as well when a finding blocks that the judge did not grade a blocker in the call that wrote it: the judge named a doubt on it, the cell the judge stated gives a lower grade than the column Manki graded it in, the judge stated no cell for it, or the sweep found it. A blocker that was lowered for citing no proving lines and that the refuter then confirmed still counts as the judge's, since the cell the judge stated gives a blocker. A later step can also lower a blocker the judge graded, and the summary may still call it one. So the summary is left out too when such a finding no longer blocks: it was posted as a warning for citing no proving lines or for claiming a build failure no CI result reports, it sits in code the PR left alone, two refuters disproved it, or a later step dropped it. A round that requests changes then says what blocks with the first two sentences of the top blocker's description, as it does when the verdict reader found the blockers. The `Manki` check and the command line output show the same sentence as the review. On an approval they show the judge's summary, which the review leaves out. A round that approves without the judge's summary has no sentence, so the check shows only its title and the command line output only its heading. When only earlier threads block, the review lists them under "Still open from earlier reviews", and the check and the command line output show that list. On an approval, "What this does" follows in at most two sentences. An approval held for files no model read says so in the verdict. The findings listed in the body come next, grouped by where they sit, each group headed by its counts per severity: "Found this round" ("Findings" on a first round), "Still open from round N", "Missed by an earlier review" and "Pre-existing". Files no model read get their own group, "Not read by any model". Each finding is a collapsed fold with its whole description, most severe first. A note is an optional improvement, never a defect. A note never gets a thread or an inline comment. The body lists the notes after the other findings in one collapsed section, a fold per note with its code fix as a code block. The judge orders the notes by how much the author gains from acting on each, and a note it did not rank follows the ranked ones, as does a note from the sweep's own judge call. A review lists at most `review.notes` notes, 3 by default, and `0` lists none. A line under the notes says how many more notes are not listed, and the round record keeps those under `findings.unposted`, with `unpostedReason: note_cap`. A note that an open thread from an earlier round already carries is not listed again and takes none of the places. A security finding is never a note, so it keeps its thread. A tool alert below a warning is listed with the notes, takes none of the places and is never left out. "What to test" follows, collapsed, and a rule sets each section apart. A collapsed "Checked and left out" comes last when the round has anything for it, and its summary line gives the count. Inside, it lists up to three kinds, each under a heading with its own count: each finding a tool check disproved, with the start of the check's reason, each warning not listed because nothing proves it, with the reason, and each lead not finished checking, with the round it first came up in when that was an earlier round. Every entry links to its line, and each kind shows at most ten. The progress comment keeps the facts about the run, and under "Judge decisions" in its "Review metadata" section the judge's full reasoning for each finding. An incomplete round has no such section. A collapsed "About this review" closes the body with the reviewed commit, the round, the lines read, the review time, the models that found and judged the findings, and the tokens the round used with its cost estimated at public API prices. The cost is marked "partly priced" when some calls had no known price, and left out when none had one. On a subscription account it still shows how heavy the round was. When the round recorded its runner, the fold also shows whether it was GitHub-hosted or self-hosted, the time from the start of the workflow run until Manki started, and the most memory the run held against the memory it may use, such as "Runner: self-hosted · started after 11m 3s · peak memory 1.5 GiB of 2.0 GiB". That time covers the wait for a runner and the job's steps before Manki, such as a checkout or a build. Every finding opens with one line: its severity, then the category and the effort the judge set, such as **Blocker** · Concurrency · Moderate. A finding that does not block says so, as in **Warning, not blocking**. The categories are correctness, security, reliability, data integrity, concurrency, performance, compatibility, testing, maintainability, documentation and style. The effort is a quick fix, moderate or a larger change. An inline finding then shows its title and up to three sentences of what goes wrong, about 700 characters at most. A short code fix GitHub can commit shows right below as a suggestion, in a thread on the finding's own line. Everything else sits in one collapsed section, in this order: how to fix it, why it matters (the rest of the description), how it was checked (what was read or searched, with code previews of the lines that prove it), and last, for a finding a refuter checked, the outcome of that check. A finding in the review body lists the same parts inside its own fold. It never shows raw tool output. Up to five warnings and security findings below a warning on changed lines get inline threads, and the rest are listed in the body. Each review's round record stores `output.bodyLength` and `output.commentLengths`, the length of the body and of each comment as Manki composed them, before GitHub accepted or refused any comment.

The PR author cannot dismiss a blocker, or a security finding of any severity. Their own "agree" reply, a reply that gets Manki to answer Fixed, Withdrawn or Agreed, or resolving the thread leaves it blocking, and auto-approve waits for it. When the author resolves the thread, Manki reopens it right away, without waiting for a push, and replies to say why. When the author also replied in the thread, the reason is part of Manki's answer to that reply. An answer that confirms the fix does not ask for a maintainer or a fix: it says that the thread stays open until the next review confirms the fix. Manki reopens a thread only once. When the author resolves it again, it stays closed and keeps blocking. It is cleared when someone else with write access resolves the thread, replies in agreement or comments `@manki dismiss` in it, or when the judge marks the thread addressed. A reply in agreement or a dismissal also clears a thread the author had resolved: Manki reopens it and resolves it itself. Manki's own resolve of such a thread counts only when something backs it: the latest round that checked the thread marked it addressed, or the latest reply by a person in the thread comes from someone other than the PR author with write access, as when Manki withdraws the finding on a maintainer's reply. Review rounds and the approval check read the same rule. Whoever resolves the thread or writes that reply counts only when GitHub's permission lookup confirms a person with write access, so a resolve by a bot, an app or a workflow token clears nothing, and a comment by another bot is not a reply. The round record backs only Manki's own resolve. When the judge confirms a fix in a thread someone else resolved, Manki reopens the thread and resolves it itself, so GitHub names Manki as the resolver. When the PR author later reopens such a thread and resolves it, it blocks again until a round confirms the fix once more. A thread backed this way stays cleared on later pushes, and a blocker found there again pauses automatic review for a person. A thread Manki resolved with nothing to back it keeps blocking: the next review lists it under "Still open from earlier reviews" and checks it again, and the approval check names it with the reason. A later reply from the PR author, or from someone without write access, takes the backing of a maintainer's reply away until a maintainer replies again, or reopens the thread and resolves it. A later round never drops a new blocker as a repeat of a thread that was not cleared this way. A later round leaves a security finding out as already settled only when its earlier thread was a blocker or security thread that was cleared this way. A thread the author could resolve alone hides a repeat of an ordinary finding, never a security finding. These rules also cover threads resolved before an upgrade to 7.5. So on a PR that was open at the upgrade, a blocker or security thread that was not cleared this way blocks again.

A PR author with a high enough repository role may clear such a finding on their own PR, so a repo with a single maintainer is not stuck. They resolve the thread in the GitHub UI, or comment `@manki dismiss` in the thread. `author_clear_role` sets the lowest role that may: `admin`, `maintain` or `write`. The default is `maintain`, so a maintainer and an admin may, and a contributor who can only push may not. A repository owned by a user account has no `maintain` role, so with the default only its owner may. With `write`, everyone who can push may clear the blockers on their own PRs, so a blocker no longer holds their PR and only tells them what Manki found. The setting is read from the base branch only, so a PR that changes it cannot lower the role for itself. It changes nothing for anyone else: someone other than the author still needs write access. Manki reads the author's role and everyone's write access through the GitHub API, because comments show an org owner, and an org member with read access, as a plain member. Only a role GitHub confirms counts. An author with a custom role, a role the API does not return or a lookup that fails may not clear. While the base branch's config cannot be read or loaded, only an author with the `admin` role may clear, since that role may under every value of the setting, and Manki approves nothing: a review round holds its approval, a resolved thread starts no approval check, and `@manki check` answers that the approval is held. Every such override is recorded: Manki replies once in the thread with "Finding dismissed by @<login>, the PR author, who has the `<role>` role on this repository.", the round context lists it with the role under `recap.securityOverrides`, and an approval that relies on it names it and the role in the review body. When Manki answers Fixed, Agreed or Withdrawn on a blocking or security thread that the replier may not clear, the answer says that the thread stays open and who can close it. On a thread the author resolved again, the answer says that the finding keeps blocking, and so does the answer to the author's `@manki dismiss` there.

Every blocker gets a thread, so a later round can evaluate it as fixed and a person can resolve it. GitHub only allows comments on changed files, so a blocker in a file outside the diff, or one tied to no file, gets its thread on the first changed file. That thread says in its first lines where the blocker is, and the review body names the blocker and the file its thread is on. A push never clears a thread that is tied to no file. Only a person does. A blocker whose line comment GitHub refuses gets a thread on its file instead. When GitHub refuses that thread too, the blocker is listed in the review body, and the next round posts it as a thread again without asking a model about it. A finding of that round that restates the blocker at a lower grade lifts nothing: the blocker is listed again and stands for it, and the record keeps the finding without posting it.

Before auto-approve approves, it reads the record of the review that covers the head. Resolving threads lifts that review's block only when a thread on the PR carries every blocker the record names. The record alone never proves a thread. A blocker the round posted as a thread counts only while a thread that the round posted for it is on the PR, so a thread that is not posted yet, that GitHub refused or that someone deleted holds the approval. A thread posted later carries its blocker from then on, and resolving it runs the check again. A blocker GitHub refused as a thread is listed only in the review body, so no thread stands for it. In those cases, and when the record cannot be read or does not say what the review blocked on, Manki does not approve and the next review round decides. A review that a version before 7.5 posted names no thread for its blockers, so resolving its threads approves nothing until a new round. To start one, tick **Review again** in the settings block, or push a commit. If the push starts no review, as while automatic review is off or paused, comment `@manki review`. An approval that Manki posts again after a push that changed nothing has no record and blocks on nothing, since it only restates the approval of the same change. `@manki check` runs the same check and replies with the reason it found: the threads that block and that someone allowed to has to resolve them, the blocker no thread carries, a head no review covers, a draft, a conflict with the base or an approval held for a person. Marking a draft ready runs the check too, on the review that covers the head, so a draft whose review found nothing to block is approved without another round.

Every finding ends with a `Create an issue for this` box: at the end of its thread, and in the review body right under each finding listed there, the Pre-existing section included. When someone with write access ticks it, Manki files the finding as an issue, with the finding as posted, a permalink to its line at the reviewed commit and a link back to where it was posted, and replaces only that box line with "Issue #N created by @login". In a thread, it also replies with the link and resolves a thread the PR author may clear. The thread of a blocker, or of a security finding of any severity, stays open, since only someone other than the PR author clears it. When an open issue Manki filed for the same finding exists, the tick links it instead of filing another. When no issue is filed, because GitHub refuses it or Manki cannot find the box's finding in the review, Manki says so in the thread or in a PR comment and clears the box. A tick by someone without write access does nothing.

Each round checks the open Manki threads against the push. For a thread whose line is gone, the judge sees the code it named on the commit it was posted on, and where that code sits now, found by several of its lines lining up again. When the code left its file and exactly one other changed file holds it unchanged, the judge sees it there, with the file named. In every other case the judge is told that it is not found, and sees the head's code near the same line. An unchanged file never reads as proof that the problem remains. When Manki itself answered in the thread, such as "Fixed." with the lines it cites, the judge must confirm that evidence or say which part is wrong before it keeps the thread open. On a blocker or security thread the judge also sees the latest reply there, when the PR author or someone with write access wrote it. Anyone can comment on a PR, so a reply by anyone else is not shown. The reply is a claim to check, never evidence: the verdict says why it does or does not settle the finding, and no reply makes a thread count as fixed. A fix on such a thread counts only when the push changed the thread's file. The judge is told which threads stay open for that reason, so its summary does not call them fixed. The push counts only for what it changed in the PR's own change, so a rebase onto the base branch changes no file. When it confirms a fix in a file the push changed, it resolves the thread with a short "Fixed in" reply and the thread stops blocking. The reply names a commit only when it is certain which one fixed the thread: the only commit since the last reviewed one that changed the thread's file, editing it in place. In every other case, such as two commits changing the file, a commit that renamed, added or deleted it, a rebase, a merge from another branch or more than 20 new commits, the reply says "Fixed by the commits up to" the head, which is always true. A thread counts as fixed only when every failure it names is gone. When the push fixes only part, the thread stays open and gets a "Partly fixed" reply that says what still goes wrong, and it keeps the grade that remaining damage earns: its own grade when the damage is the same, never a higher one, and one below the grade it carries only when the push changed the thread's file. The judge states the severity table cell of what remains, and Manki works out that grade from the cell. Nothing checks a rare claim on a thread, so on the wrong behaviour row what remains is graded in the normal column and a partly fixed blocker keeps blocking. A partial fix never lowers a security thread. A partly fixed blocker thread blocks only while what remains is a blocker, in later rounds too. It gets back the highest grade it had, with an "Open again" reply, when a later round names its blocker again, repeats its problem as a blocker, or finds it not fixed after a push to its file. The round record keeps each thread's grade under `judge.threadEvaluations`, and Manki reads it from the latest record that set one, so the grade holds exactly while the review that decided it stands. The record keeps the cell the judge stated as `cell` when that cell gives the thread's grade. When the thread keeps another grade, the record keeps the cell as `judgeCell`, and the next round's judge sees only the grade. A reply that fails to post loses only the note. A blocker a later round carries on the thread, by naming it, folding into it or repeating its answered problem, raises it to blocker the same way, and outranks a lower grade in the same round. No reply that Manki posts decides whether a thread blocks. When a round record cannot be read, a grade it held is unknown: the approval check counts every Manki thread as blocking, the review round requests changes while a Manki thread stays open, and the PR author cannot clear a Manki thread by resolving it, though an author with a role that `author_clear_role` allows still can. The review leads with an "Approval withheld" line that links each review whose record it could not read, in place of the usual count of blockers, and shows the judge's summary under "Summary". The check summary does the same, so a person sees why, and no open thread is called a blocker it may not be. The hold lasts until a maintainer has resolved the open threads. A round that requests changes for another reason does not name the unread record. A thread the round resolves, or one someone with write access agreed away, does not count as open for this hold. The judge also checks that each finding's fix removes every failure the finding names, and a fix that removes only part says what it leaves. A thread gets one Manki fix confirmation per head commit: when Manki already answered a reply there with "Fixed." on that commit, the round resolves the thread without its own line, and a reply answered after the round's line gets no second "Fixed.". A blocker that a round names again while its thread is still open stays in that thread instead of getting a new one.

When a blocker comes back after a fix was claimed for it, the review keeps requesting changes, lists the blocker under "Needs a human", and pauses automatic review. A fix is claimed when Manki confirmed it in an earlier round, when the thread counts as resolved or is gone, as after someone with write access other than the PR author resolved it, or when such a person agreed the thread away or dismissed it. No other reply in the thread claims a fix, whoever wrote it and whatever it says. Neither does the PR author resolving a blocker thread, which keeps blocking. So a blocker named again while its thread still counts as open just stays open, as after a rebase or after the author answered that the change is intended and resolved the thread: the round requests changes, and automatic review goes on. The last automatic round, round `convergence.max_auto_rounds` (default 10) counted from Manki's last approval, approves when nothing blocks, or stops the same way when a blocker is still open. Rounds after an approval, such as on rebases, start the count again. An approval held because the PR conflicts with its base counts as an approval here, and so does auto-approve after the last blocking thread is resolved. That approval also ends a pause from a blocker that came back. Only rounds that reviewed a new change count, so another round on a change Manki already reviewed, such as Review again on the same commit, does not. While automatic review is paused, its notice lists the blocking threads still open, with links. A pause by the round cap also asks the author to step back and reconsider the approach, since rounds that keep finding problems usually mean the design needs another look. A push starts no review, but replies in threads, auto-approve after the last blocking thread is resolved and the Review again and Deeper review boxes in the settings block still work. `@manki review` reviews the head commit unless Manki's newest review of it is complete, so during a pause it starts a round only after a push or after a round that did not finish. A review started by a box or the command also turns automatic review back on for the next `convergence.rounds_after_restart` automatic rounds (default 3), or for the rounds the cap still allows after the restarted round if that is more. After a restart, the notice counts the rounds since the last approval and how many came after the last review started by hand. When they pass without an approval, automatic review pauses again with the same notice, and the next review started by hand turns it back on again.

Use the `models` config section to choose different models for the finders and the judge (e.g., a faster model for the finders and a more precise model for the judge).

The judge treats two finders reporting the same defect as strong evidence that it is real, and one finder's silence as no evidence against the other's finding. Agreement never raises a finding's severity.

To give the second finder its own model, set `models.reviewer_pair`, or name models in a review group.

## Replies in a review thread

A reply in one of Manki's threads gets one answer that starts with Fixed, Withdrawn, Agreed, Kept or Unverified. The [README](../README.md#talk-to-manki) says what each means and who gets a thread resolved by it.

Before it answers, Manki checks what the reply says about code. It lists up to 5 statements below its answer, each in the developer's own words, with what Manki checked. Each line says only what was checked, never that the statement is right:

- **Line cited for it exists at** or **Line cited against it exists at** a place, such as `src/retry.ts:48`, or `owner/name:path:line` in a [related repository](#related-repositories). The review model cites the line for or against the statement, and Manki checks only that it exists: in the checkout of the PR head, or in a related repository this reply fetched. Without a checkout, only a line inside the PR's diff counts. Manki posts the place, never the text of a related repository's line.
- **No line holds** a text, for a statement that something exists nowhere, such as "nothing calls `backup`". The model names the text to look for and Manki runs the search itself, as plain text of 3 to 200 characters on one line, ignoring case, in the PR's checkout or in one fetched related repository. When no line holds the text, the list names the text and the repository searched, and what the search did not cover: the `paths` a related repository is limited to, and how many binary files or files over 1 MB it left out. A longer name that contains the text counts as a line found.
- **Not checked**, with the reason: the review model says code cannot show it or could not read the code, no cited line was found in the code that was read, the run had no checkout to read a cited line or to search, the search term is not one line of 3 to 200 characters, the search found a line, failed or did not reach every file, or the repository is not a configured related repository or was not fetched.

Manki checks the list in code. A quote that is not in the developer's reply, whitespace aside, is dropped, and a long quote is cut with an ellipsis after that check. A reply with more than 5 statements gets the first 5 checked and the count of the rest.

The list never decides a thread. No statement's status is read by the code that resolves or clears one, so a reply with a cited line for every statement clears nothing for the PR author, and a blocker or security finding still needs a person with the role. The sentence below the list says what was checked and, for a finding that keeps blocking, that the decision is a maintainer's and that the thread stays open.

Three rules can turn an answer into Unverified, and nothing turns one into anything else:

- **Withdrawn** needs a line of the PR's own repository that exists. Lines of a related repository alone never withdraw a finding.
- **Fixed** that cites a related repository needs a line of the PR's own repository too. A Fixed that cites no line is as before.
- An answer that is not in the form Manki asks the model for.

A reply is one model call with 15 tool steps and 5 minutes. A reply without repository tools, or whose checkout failed, checks lines against the diff and searches nothing. The reply record stores each statement's status, its lines and the reason it was not checked, without the developer's words and without the search text.

## Rules from instruction files

Manki reads the repository's instruction files from the PR's base branch only, so a PR cannot relax a rule for itself: the nearest `AGENTS.md` and `CLAUDE.md` above each changed file, the root `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md` and `CONTRIBUTING.md`, and the `.md` files these link to. A PR that edits one of them is reviewed against the base branch's text, and the edit applies after merge.

The files are printed in that order, up to 30,000 characters in total. The file that crosses the limit is cut and the files after it are left out, so the review does not see their rules. The run then logs a warning that names the cut file. The round record lists the files the round read under `instructions.files` and the cut one under `instructions.cut`.

The finders use these files in two ways. They check each added line against the rules. They also go through the rules about the change as a whole: what a change must include, such as a test, a migration or a documentation update, and how it must be scoped. Example: a Django project's `CONTRIBUTING.md` says every model change needs a migration, and a PR adds a model field without one. For the change as a whole, only a rule stated as a requirement counts ("must", "needs", "never", "always"). Advice ("prefer", "try to", "consider") is not reported there. An `AGENTS.md` or `CLAUDE.md` in a subdirectory covers only changes under that directory.

A finding about a rule for the change as a whole names the instruction file and quotes the rule. Manki looks the quote up in the files it loaded, ignoring case, line wraps and Markdown emphasis, and marks the finding as a rule finding only when the named file holds it. A rule a finder read anywhere else, such as in the PR's own edit of an instruction file, gives no mark. A rule that holds a Markdown link or image matches when the finder quotes it as plain text. Manki keeps the text of a link in the quote and never its target, which is not compared with the file. The round record keeps the mark as `rule` on the finding, with the `file` and the `quote`, also on a finding the judge dropped.

The mark alone changes no grade. The judge first answers two questions about each marked finding, each in its own field of its reply: whether the quote states a requirement, and whether this PR breaks it. Advice, an example, a description of how the project works and a fragment that states no rule on its own are no requirement. When the rule requires a companion for something the PR newly defines, such as a documentation entry for a new flag, the list of changed files settles it: a file the PR leaves unchanged cannot cover what did not exist before. For a round with a rule finding, the list also names the changed files no model reads: the ones `exclude_paths` leaves out, and the ones with no text to read, such as a binary or a file that was only renamed. Past 200 such files the judge gets a count of the rest and treats each as one that could hold the companion. A break that rests on code the judge cannot see is not shown. That is a changed file it cannot read that could hold the companion, such as an excluded `docs/api.md`, or a file outside the diff that may already list a name the PR only uses. The judge then names, in a third field, the one fact that would make the rule broken. Manki works the answers into `rule.verdict` on the finding: `no_requirement`, `not_broken`, or `confirmed` when both answers are yes, the judge keeps the finding, and the finder or the judge cites a line that proves the break. The verdict is `unproven` when the judge names such a fact, kept as `rule.unseen`, or when both answers are yes but one of the other conditions is missing. A doubt the judge names about the damage, such as whether a rollback fails at run time, decides the grade the damage gives and not the verdict. Only a `confirmed` rule finding counts in the grade. Any other is graded by its damage alone, like a finding without a mark.

An `unproven` rule can still be confirmed in the same round, when the review has repository tools. The fact the judge could not see becomes a doubt of the finding, and the refuter checks it, for example whether `.env.example` lists a variable. Only its answer about that fact settles the rule. When the refuter confirms the fact, the rule is `confirmed` and the finding gets the grade `review.rules` sets, recorded as a `rule` step, whatever it answers about a doubt the judge has about the damage. When it disproves the fact with a line of the finding's own file or of the diff, the finding is dropped, also when the refuter confirms the defect, since that answer is about the damage. A disproof that cites only another file settles nothing, like any disproof, so PR text cannot point the refuter at a file that drops a finding. When the refuter cannot settle the fact, or two refuters disagree about it, the rule stays `unproven` and the finding never blocks. After that check the note keeps the fact under `rule.unseen` only, without the doubt and the grade the rule would have given. So no later step of the round, such as a memory suppression, and no later round takes them for a grade the damage earned. The next round's judge answers the rule again from its own questions. No other confirmed doubt stands in for the fact the judge named. The refuter's own answer that the defect does not exist confirms no rule either, since that answer can be about the rule. The fact is added as a doubt only to a finding graded a note, so a finding graded by its own damage is never dropped over a rule. The other way round, no refuter disproof drops a finding whose rule the judge confirmed. The refuter checks whether a failure can happen, not whether a rule is followed, and the same rule break with no damage to check is posted unchecked. Such a finding stays at its grade and is recorded without the cell and the conditional grade that stated the damage, so a later round does not raise it from them. In the posted finding the check says that the finding stays because the rule break is confirmed, and that the check disagrees about the damage or the defect. The cost: when the judge wrongly confirms a rule, the warning is posted with the refuter's contrary reason next to it.

[`review.rules`](configuration.md#reference) sets the grade of a confirmed rule finding. With `warn`, the default, it is a warning. With `block` it is a blocker, so the PR is not approved until the rule is followed. Example: a Flask project's `CONTRIBUTING.md` says every new endpoint must be listed in `docs/api.md`, and a PR adds a route without changing that file. The setting only raises a grade, so a finding whose damage already gives a higher one keeps it, and the step is recorded as `rule` in `gradePath`. A rule finding blocks only when all of this is certain: `review.rules: block` is set on the base branch, the named base-branch file holds the quote, and the judge confirmed both points or a refuter confirmed the fact the judge could not see. Like every blocker it also needs a search behind a claim that something is missing. Without one it is a warning that the refuter checks, since its check is the search the finding left out. A confirmation makes it a blocker. A disproof or a check that settles nothing leaves the warning. With `warn` no such check runs, and the warning is posted on the judge's rule verdict alone. With either setting, a confirmed rule finding that its own damage made a blocker is held at a warning in the same way, for want of a search or of a CI result for a claimed build failure, and only a confirmation gives the blocker back. The posted finding shows the rule with its checks: a line that names the instruction file and quotes the rule, and on a blocker the rule raised, that it blocks because the repository sets `review.rules: block`. A confirmed rule finding is proven by the rule's text and the cited change, so a warning of this kind is posted without a check that proves it. One the judge doubts is still checked, last among the eight checks for warnings, and that check only settles the status the warning shows. The refuter checks a blocker the rule raised like any other blocker and adds the proof it finds. Its disproof does not lower that blocker, since the refuter checks whether a failure can happen, not whether a rule is followed. So a rule blocker rests on the judge's two answers and the cited line, also when no refuter runs or its check settles nothing.

Manki proposes splitting a PR only when an instruction file requires focused changes, such as one concern per PR, and only when a finder with repository tools shows that a part is independent: the rest of the PR does not use the part, and the part does not use the rest. The finding quotes the rule, names the parts and lists what was searched. Without such a rule, or when the finder has no repository tools, Manki never proposes a split and never reports a change only for being unrelated to the PR's purpose.

## Skipping PRs

`skip_labels`, `skip_authors` and `skip_branches` name PRs that get no automatic review, such as dependency bumps from a bot. Manki reads them from `.manki.yml` on the base branch only, so a PR that edits them cannot skip itself. A PR that matches any rule gets no review, no comment and no approval. Its `Manki` check completes as skipped. A `@manki review` comment still reviews it.

A skipped check passes a required status check, so a branch protection rule that requires `Manki` lets a skipped PR merge without a review. GitHub counts a neutral check as passed too, and the `Manki` check is neutral when Manki holds its approval, so also require an approving review (see [Branch protection](getting-started.md#branch-protection)). Use rules that only trusted actors can meet. GitHub sets the author, so `skip_authors` for bot accounts is the safest. It skips an event only when its sender is a listed author too, so a person who pushes to a bot's PR still gets a review. A label or branch rule matches only PRs whose head branch is in the repo itself, never a fork's. A fork's author can name a branch freely and keep pushing after a label is added, for example by a path-based labeler. Anyone with write access can still pick a matching branch name or add a skip label.

A PR that conflicts with its base gets no review at all, also on a `@manki review` comment. The token service posts one note, "This PR conflicts with `<base>`. Rebase it, and Manki reviews it then.", and completes the `Manki` check as "Rebase needed". The next skip edits that note instead of adding another, and Manki deletes it once a review posts after the rebase. A conflict that appears while a review runs still turns its approval into "Approval held".

## Reading CI results

Manki reads what your CI already reported on the PR head commit and gives the reviewers the results that sit on lines of the diff: check-run annotations (linters, type checkers, test reporters), open code scanning alerts, and vulnerable packages from the dependency review. The tool text reaches the reviewers fenced and marked as untrusted, and only for the lines they review. When a Manki note sits on the same file and line as a tool result, Manki drops it because the author already sees the tool's result. Warnings, blockers and security findings are always kept, because they can be a different problem on the same line. The drops are listed in the `Manki context` block.

Some tool results also go to the judge as candidate findings, next to the reviewers' findings:

- A vulnerable package, or a result whose tool or rule id names a security class (such as `security`, `injection`, `xss`, `format-string` or `secret`), always does.
- A style or formatting result never does, because the linter already shows it. Manki recognises these by rule id, such as `prettier/prettier`, `@stylistic/*`, `indent` or `max-len`. A result without a rule id is judged by its tool name, such as `rustfmt`.
- Any other code scanning alert does, and a check annotation only at the `failure` level.

The judge keeps a real defect at the grade it earns and refutes a false positive with a reason. A refuted result is never posted. A kept one is posted with the tool in its label, such as `⚠️ **Warning, not blocking** (CodeQL)`.

Before the judge runs, Manki also checks each reviewer finding against the code, without running it: the file is in the diff, the line is in the file, and whether each symbol the finding names in backticks occurs in the file or the diff. Only a file outside the diff or a line past the end of the file contradicts a finding. A missing symbol is only noted, since it can live elsewhere. A claimed type or compile error is confirmed by a failing annotation near the line from a type checker or compiler, such as `tsc`, `mypy` or `rustc`. A lint error there does not confirm it. The judge sees the result as confirmed, contradicted or unchecked. Only the judge can drop a contradicted finding, and a tool that says nothing never lowers or drops a finding. Each finding in the `Manki context` block records `toolEvidence` as `confirmed`, `contradicted` or `none`.

Manki reads these results with the workflow token (`github_token`), so grant the permissions in the workflow, even when the Manki app posts the review:

| Permission | Source |
|------------|--------|
| `checks: read` | Check-run annotations |
| `security-events: read` | Code scanning alerts (needs code scanning, and GitHub Advanced Security on private repositories) |
| `contents: read` | Dependency review (needs the dependency graph, and GitHub Advanced Security on private repositories) |

A source Manki cannot read is skipped with one info line in the log. Turn a source off with `static_analysis` in `.manki.yml` (see [Configuration](configuration.md)). Manki reads that block from the base branch, so a PR cannot turn off the tool that would flag it.

Manki only sees checks that finished before it runs. Manki runs in its own workflow, so `needs:` cannot order it after your CI. List the check runs to wait for in `static_analysis.wait_for_checks` instead. Manki polls them on the PR head every 15 seconds and reads the results once each has finished. After `wait_timeout_seconds` (default 300) it stops waiting, reads what is there, and records the checks still running in the `Manki context` block. The last poll starts at that limit and may take up to 11 seconds more. If it does not answer in that time, the wait still ends as timed out: the record holds the checks the last answered poll saw running, or every listed check when no poll was answered. A poll that fails or meets a GitHub rate limit ends the wait early with a warning, and Manki reads what is there. A name is the check run's name as the PR's checks list shows it, usually the job name.

```yaml
static_analysis:
  wait_for_checks: [lint, CodeQL]
  wait_timeout_seconds: 300
```

## Running Manki's analyzers

Manki can run analyzers itself. `actionlint`, `zizmor` and `shellcheck` are on by default, but each runs only when a file it checks changes, and only when CI does not run the same tool already. Manki's Rust rules for `ast_grep` are on by default in a Cargo repository (see below). The others are off by default, for a repository without CI checks. Turn them on or off in `.manki.yml` on the base branch:

```yaml
static_analysis:
  analyzers:
    ast_grep: true
    secrets: true
    dependencies: true
    semgrep:
      rules: [.semgrep/manki.yml]
    shellcheck: false
```

`analyzers: all` turns on every analyzer that needs no rules from you, including ones later releases add. Semgrep only runs when you list rule files.

| Analyzer | Tool | What it checks |
|----------|------|----------------|
| `ast_grep` | [ast-grep](https://ast-grep.github.io) 0.51.1 | Manki's own rules in [`rules/ast-grep`](../rules/ast-grep) (MIT licensed): code and shell injection, HTML sinks, disabled TLS checks and unsafe deserialization, plus error-prone patterns such as an async `forEach` callback, a comparison with `NaN` or a mutable default argument. Runs on the changed JavaScript, TypeScript and Python files. The Rust rules also run on a changed Rust file that has a `Cargo.toml` in its directory or one above it on the base branch, even without `ast_grep: true`: a narrowing `as` cast of a length, count or index, `unwrap` or `expect` on decoded input, `with_capacity` sized by a decoded length, a new `unsafe` block, and `==` on secret bytes. They report hints on added lines only, skip tests, benchmarks, examples and build scripts, and stop with `ast_grep: false`. |
| `secrets` | [gitleaks](https://github.com/gitleaks/gitleaks) 8.30.1 | Secrets on the lines the PR adds in any changed file, with gitleaks' default rules through Manki's [`rules/gitleaks.toml`](../rules/gitleaks.toml). `gitleaks:allow` comments are ignored. |
| `dependencies` | [OSV-Scanner](https://github.com/google/osv-scanner) 2.7.0 | Known vulnerabilities in the packages of the changed lockfiles, such as `package-lock.json`, `pnpm-lock.yaml`, `go.mod` or `requirements.txt`, with Manki's [`rules/osv-scanner.toml`](../rules/osv-scanner.toml). A result sits on the line that adds the package. |
| `semgrep` | [Opengrep](https://github.com/opengrep/opengrep) 1.33.1 | Your Semgrep rules on the changed files. List rule files in the repository, read from the base branch. Manki ships no Semgrep rules and never fetches registry rules such as `p/default`. `nosemgrep` comments are ignored. |
| `actionlint` | [actionlint](https://github.com/rhysd/actionlint) 1.7.12 | Mistakes in the changed workflow files under `.github/workflows`, such as invalid syntax, expression type errors or untrusted input in a `run` script. Uses `.github/actionlint.yaml` from the base branch when there is one, so self-hosted runner labels are known. Its shellcheck and pyflakes checks stay off. |
| `zizmor` | [zizmor](https://github.com/zizmorcore/zizmor) 1.32.0 | Security problems in the changed workflow files, such as template injection, dangerous triggers or excessive permissions. Runs offline, without the repository's zizmor config, and ignores `zizmor: ignore` comments. |
| `shellcheck` | [ShellCheck](https://github.com/koalaman/shellcheck) 0.11.0 | Bugs in the changed shell scripts: `.sh` and `.bash` files, and files without an extension, that start with a `sh`, `bash`, `dash` or `ksh` shebang. A `.sh` or `.bash` file without a shebang counts too. Reports down to `info`, without the repository's `.shellcheckrc`. |

The analyzers never run code from the PR. Manki reads the changed files through the API at the head commit and gives the tools the files, never a checkout. It never uses rules or config from the PR: each tool gets Manki's config or the rule files from the base branch, and the files a tool would read as its own config or ignore list, such as `.gitleaksignore` or `.semgrepignore`, are left out of what it scans. The tools run without the action's environment, so they never see a token.

Manki downloads each tool at the pinned version, checks it against its pinned digest (SHA-512 for the ast-grep packages from npm, SHA-256 for the release binaries), and caches it for the run. The ast-grep native module and its Go, Python and Rust grammars load in process. ncc can only bundle the native module for the platform that builds `dist/`, so they load at run time. Builds are pinned for Linux and macOS (x64 and arm64) and Windows (x64). A download that fails or delivers no data for 20 seconds is tried again, three times at most. If it still fails, the platform has no pinned build or a tool fails, that analyzer is skipped with a warning and the review goes on.

A self-hosted runner also keeps each download for later runs, in the `manki-pinned` folder of its tool cache (`RUNNER_TOOL_CACHE`). A later run checks the kept file against the pinned digest and unpacks it again, so it downloads nothing. This holds for the Claude CLI too, which Manki downloads the same way. [Security](security.md) says what is checked.

`exclude_paths` keeps files away from the reviewers, and `ast_grep` and `semgrep` follow it. `dependencies` checks every lockfile the PR changes, including the ones the default `exclude_paths` names, such as `yarn.lock` or `Cargo.lock`, within 10 MB per lockfile and 40 MB in all. `secrets` checks every changed file, since a PR can add its own `exclude_paths`, and for the same reason `actionlint`, `zizmor` and `shellcheck` check every changed workflow or shell script. A result on an excluded file has no inline thread, so it is listed in the review body. A blocker there gets its thread on the first file the reviewers read. A PR whose every changed file is excluded or has no code to read is never approved. No code to read means a binary, a rename, a mode change, an empty file, a Git LFS pointer, whose lines only name the content by hash, or a submodule bump, whose line only names a commit. Manki posts a comment that lists each skipped file and why, with what the analyzers found on them, and the `Manki` check waits for a person. When the PR also changes files the models read, a clean round still holds its approval: Manki posts its review as a comment that lists the skipped files, the `Manki` check reports the approval held, and a person approves. Auto-approve after the last blocking thread is resolved never gives that approval either. A deleted binary, LFS file or submodule leaves nothing unread, so it holds no approval.

Manki reads a changed `Cargo.lock`, `package-lock.json` (or `npm-shrinkwrap.json`) from npm 7 on, `yarn.lock` from Yarn 1 or later, or `pnpm-lock.yaml` into a package list, whatever `exclude_paths` says: each package the PR adds, with its source and fields, each package it removes, and each package it updates, with its old and new version and the changes to its source, checksum and other fields. The legacy `dependencies` map of a version 2 `package-lock.json`, which only npm 6 installs from, must name the same artifacts as its `packages` map, and the list then leaves it out. The finders, the judge and the verdict reader read that list, and the judge reads it in place of the lockfile's hunks. A local review and the benchmark read lockfiles the same way. The planner and the review groups count the lockfile as changed, so a lockfile change gets two finders on the supply chain floor. Such a lockfile holds no approval, and a PR that only bumps a lockfile can be approved. Manki adds a `lockfile-change` alert, which the judge triages like any tool result, for a package whose source moved to another registry or repository, an added one from a registry the lockfile did not use before (in a new lockfile, from another registry than most of its packages), one that comes from a git repository or a path, one whose checksum changed without a version change, one that moved to a lower version, and one whose tarball URL names another package or version. Manki reads the lockfile at the PR head and undoes the diff to get the version before it. A lockfile it cannot read or parse, one whose diff does not match the file, one in another format such as `poetry.lock`, or one past 100,000 characters of package lists in all, stays unread and holds the approval as before.

Analyzer results follow the path of the CI results above, limited to lines of the diff. `actionlint`, `zizmor` and `shellcheck` keep only results on the lines the PR adds or changes, so a problem the PR did not touch is never raised.

Manki also looks for hidden characters on the lines the PR adds in any changed file, whatever `static_analysis` or `exclude_paths` says: control characters other than tab and newline, format characters such as zero-width spaces and bidi controls, the line and paragraph separators U+2028 and U+2029, the invisible Hangul filler letters, and variation selectors other than U+FE0F, the one that follows most emoji. A file that adds any gets one `hidden-characters` alert from Manki at the first such line. A bidi embedding, override or isolate, which can make code display differently than it runs, makes the alert an error. Any other hidden character makes it a warning. A suggested fix that holds a hidden character is never offered as a `suggestion` block, and no text a model wrote can open a `suggestion` block. Manki rebuilds every code block in that text with its own fence, which nothing inside can close, keeps a plain language name at most, and escapes any other run of three backticks or tildes.

Manki skips `actionlint`, `zizmor` or `shellcheck` when CI already runs it: when a workflow on the base branch names the tool outside a comment line, or a check run on the base branch's head commit has the tool's name in its name. The PR can change neither, so a job it adds cannot turn a tool off. The `Manki context` block records the skip. Since no CI shows them to the author, every result goes to the judge as a candidate finding, and a reviewer finding on the same line is never dropped for it. A result the judge keeps is posted with the tool in its label, such as `⚠️ **Warning, not blocking** (gitleaks)`. A clean run posts nothing. The `Manki context` block records each analyzer that had a file to check under `staticAnalysis.analyzers`, with how many results it found or why it was skipped.

## Uses outside the diff

When the PR head is checked out for the repository tools, Manki lists where the code the PR changes is used elsewhere, before any finder runs. It takes the changed types, struct fields, enum variants, functions, constants and config keys from the hunks: through ast-grep for Rust, TypeScript, JavaScript, Python and Go, and from keyword declarations (`func`, `class`, `struct` and similar) and config keys with an underscore in other files. When a type's body changes, its other fields and variants are searched too, after the changed symbols. The search takes at most 80 changed symbols, 20 fields the changed lines read and 8 fields they look an item up in, and lists at most 6 types. When it does not search every changed symbol, because there are more than 80 or because a name is too common, too short or too long to search for, the section says how many of how many it searched. The types list shows at most 3 types per read field, the likeliest first, and none for a field that more than 6 types declare. A list that was cut says how many of the types found it shows, how many of the read fields it looked up, and for how many read fields it lists no type, so it never reads as complete. The log names each limit on size (80 symbols, 20 read fields, 8 looked-up fields, 6 types) that a change went past. Manki searches the head commit for each name as a whole word, outside the changed lines and `exclude_paths`. Code comes first, then comments, then documents. Within each, a package that depends on the changed one comes first, then other files of the same package, then the same file, and last a package that does not depend on it, which can only hold a namesake. A package whose manifest is not read, because it is larger than 1 MB or resolves outside the checkout, counts as one that may depend on it, and the log says why it was not read. One round reads and searches at most 64 MB of manifest text, and a package past that counts the same way. Each symbol shows at most 4 uses and the list at most 60, and the section says how many it left out. Among a symbol's code uses in packages that can reach it, production code comes first, then lines that only call `.name()`, then test files. Within each, one file shows at most 3 while another file still has one to show. A name as common as `new`, `len` or `from`, shorter than 4 characters or longer than 160, is not searched at all. The names are searched together in one pattern of at most 15 KB, which fits the command line of every platform Manki runs on. A name that no longer fits it is not searched, and the section names it as not searched. A name with more than 80 uses is named but not listed, except a field or variant that existed before the PR and whose own lines the diff changes, such as its type, even on a line after its name, or its doc: its readers are what the change can break, so they are listed however many there are, up to 12, and its uses outside test files take their place before other symbols' uses fill the 60 lines, up to 30 shared in turn by all redefined fields, so changed functions and types keep room however many fields a PR redefines. Among each file's first 3 uses, and again among the rest, its uses in files that also name its type come first, and uses in files that never name it come last, since they likely read a field of the same name on another type. Within those, a read of the field as `.name` comes before other code that names it, such as a struct literal. The note on the uses left out says how many of them are in files that name the type. A new field has no readers yet, so its matches are namesakes and the cutoff applies. A line that only declares a field of the same name on another type, or reads it as `self.name`, `this.name` or through a Go receiver in a method of such a type, is likely a field of the same name on another type, so it ranks after every other use of the symbol. It is never left out, since the guess can be wrong, and it counts in the uses not shown when the list is full. A function inside that method that binds the name again reads another value, so its reads rank as usual: a TypeScript `function`, object literal method or class, or a nested Python function or Go func literal with a parameter of that name. A method whose body binds the name again in a statement, such as Go `for _, v := range` or a `select` case, or a Python assignment to `self`, ranks all its reads as usual. A field of the same name that the diff also changes on another type is no namesake. A type that may derive from the changed type counts as that type: a subclass, an interface that extends it or a TypeScript type alias that names it, directly or through other types the same file declares, and a type with a base declared in another file or named through a module, such as `other.Base`. A read Manki cannot place on a type, such as `x.name` on a local, ranks as usual. The list also shows the types whose fields the changed lines read or change, each with all its fields, so the finders see state kept next to the field the PR touches.

The finders, the judge and the refuter all get the list, so a finding that cites one of its lines rests on code the judge can see. The round record keeps it as `usesOutsideDiff`: the location of each use shown, each type with its fields, and the names left out, with those that were not searched as `unsearched`, without the quoted code, so a missed defect can be traced to what the finders were shown. Building it takes seconds and calls no model. Without a checkout, or when the search fails, the review runs without it and the log says why. A failed search also leaves its reason in the round record as `usesOutsideDiff.failed`, such as a search that took longer than 30 seconds or found more than 64 MB of matching lines, so it can be told from a change with nothing to list.

## Sibling comparisons

Two kinds of defect hide next to the change rather than in it, and a finder that sees the clue can still miss the comparison. So Manki asks the comparison itself, from the same parse that builds the uses outside the diff, in one small call per question:

- **Sibling fields**: when a changed line looks an item up in a collection field, such as `queue.pending.get(id)` in Rust or TypeScript, `id in self.pending` or `self.pending[id]` in Python, or `q.pending[id]` or `delete(q.pending, id)` in Go, each other collection field of the same type that shares the item's type gets the question "The change looks up `id` in `pending`. Can `id` be held in `cancelled` instead? If so, does the change handle it?", with the type's definition and the changed hunks. A field of the same type comes first, then one with the same key type, then one sharing any element type. A fixed-size array such as `[u8; 32]` or `[32]byte` is a value, not a collection, so it gets no question. A Python field is one assigned in the class body or on `self` in `__init__`. Without a type annotation, its type is the kind of its first value, such as `dict` for `{}`, so it is compared only with a field of the same kind.
- **Sibling implementations**: when the change touches a function that sibling types also declare, such as the same trait method in two `impl` blocks, a method of the same name on two classes, or one on two Go types, in the changed files or the other files of their directories, up to 4 of them go side by side with "List every check, guard, version test, bound, error or event one has and another lacks." Functions that read the same are not asked about. A round compares at most 2 MB of function text, and functions past that count as different. Methods every type has, such as Python's `__init__` and other dunder methods, TypeScript's `constructor` or `toString`, Go's `String` or `Error` and a Rust `new`, are compared only between classes that share a base class or interface, together with the base class's own one, and implementations of standard Rust traits such as `Display`, `Debug`, `Clone`, `Default`, `From` or `PartialEq` are not compared, since unrelated types each have their own. Groups where the change touches more of the functions come first, then trait methods, then more changed lines, then more functions. A group whose functions all sit in one group already asked, such as two subclasses that share two bases, is not asked again.

Each call runs on `models.reviewer` at the finders' effort, at the same time as the finders, and with repository tools when the finders have them, at most 12 steps. A round asks at most 6 questions of each kind, and cuts the lowest ranked first. The findings go through dedup and the judge like any finder's, named after their question, such as `Sibling field: pending vs cancelled`. Each call follows the finders' rules for a claim that something is missing, which needs the search that came back empty, and for a defect in code the PR did not change, which is marked pre-existing. A question whose call fails goes unanswered, and the round still completes, since the finders read the whole change. Once the finders are done, the round waits at most one more minute for the comparisons, then stops the calls still running. The round record lists each question under `comparisons`, with where it points, whether it was answered, failed, cut by the cap or timed out, and how many findings it gave, and `usage.llmCalls` records each call under the `compare` stage.

## Claims of the PR text

A PR often says why it is safe: "the upload service already rejects files over 10 MB", "every caller passes a sorted list", "no behaviour change for existing configs". A reader that has taken in a well argued description tends to review the diff through it, and the code that would test the statement is never opened. So Manki checks such statements itself, each in a call that never reads the description, so only code can argue for the statement.

**Listing the claims.** While the planner runs, one call to the `dedup` model reads the PR title and description, cut to 20,000 characters, and the comments on added lines, at most 200 lines of 300 characters. It lists the statements the change relies on: that something is safe, cannot happen, is already checked elsewhere, is always done by callers, behaves as before, or is guaranteed by other code. What the change does, why it was written and how it was tested are no claims. The call takes at most 45 seconds and shows in `usage` as the `claims` stage. A PR without a title, description or added comment gets no such call.

Manki keeps a statement only when the PR text holds it word for word, whatever its case, markup and line breaks, so the model cannot add a statement of its own. A quote is cut to 300 characters, and one under 20 is dropped. A round checks the first 5 statements listed and counts the others.

**Checking a claim.** Each claim gets one call on `models.reviewer` at the finders' effort, at the same time as the finders, with read-only repository tools and at most 12 steps, 4 calls at a time. The call sees the statement, where the author wrote it and the diff. It answers `proven`, `disproven` or `unchecked`, and reports a defect only for a statement the code disproves. Manki keeps `proven` and `disproven` only with a cited `file:line` that exists in the head commit, or a cited line of a [related repository](#related-repositories) the round fetched, and keeps a defect only from a check whose `disproven` stands. A claim check reads the related repositories with the same tools, so a statement about another component, such as "the ledger service already rounds every amount", is checked in that component's code. A line of a related repository alone can decide either answer, since neither lifts a finding: `proven` is only recorded, and `disproven` reports a defect that the judge and the refuter then check like any other. Every other answer is `unchecked`. The defects go through dedup, the judge and the refuter like any finder's, named `Claim check 1`, `Claim check 2` and so on, and their grade is the severity table cell of the damage. A false statement in a code comment that breaks nothing is a note, and one in the description alone is no finding.

**Lines to start from.** When [related repositories](#related-repositories) are configured and the reviewer model has repository tools, each check also gets lines of them to start from. One more call to the `dedup` model, made beside the one that guesses names for the related repository search, reads the claims and each repository's kind and most common file types. It names, for each claim and repository, the identifiers that code most likely uses where it does what the claim says: at most 3, each a single identifier. Every kind of repository is searched for them, `dependency` too, and they are matched like guessed names. A term that more than 20 lines hold is too common to point anywhere and shows none. A term shows at most 3 lines, a declaration in the repository's own code first, and the claims of a round share at most 15 lines, which they take in turns. A check is shown only the lines of its own claim, after the diff, in a fence and labelled as a word search that proves nothing. No other call sees them, and a claim never points a finder to a repository's guide. A round with a claim fetches its related repositories even when the diff's names start no search. The call takes at most 45 seconds and shows in `usage` as the `claim_terms` stage. When it fails or its reply cannot be used, the checks start without lines and the round goes on. The checks wait for their lines at most 30 seconds, and never past their own deadline, one minute after the finders are done. A fetch, term call or search still running then is recorded as skipped, and the checks start without lines. No such call is made when the quick check alone reads the change.

**What a claim cannot do.** A claim can add a check and never remove, shorten or soften one:

- The finders, the sibling comparisons, the judge, the refuter and the verdict reader get the same input whatever the PR text claims and whatever the checks answer, with two exceptions. The defect a check reports for a statement it disproved joins the findings, and is graded like a finder's. And a claim fetches the related repositories, so for a finding that cites a line of one, the judge's window and the note on the citation show the fetched code where a round without a claim says the repository was not fetched. That is the repository's own code, never the author's text. The checks have their own calls and their own step budget.
- `proven` is written to the round record only. No stage is shown it and no grade depends on it, so a statement the check believed hides nothing.
- A statement no check settled is no defect. It is recorded as `unchecked`, and nothing is posted for it. That holds for a check that fails, runs out of steps, or is still running one minute after the finders are done, when the round stops it. The round still completes.
- A statement is shown to its check inside a fenced block and labelled as the author's untrusted text. One that names a file to skip or tells the model what to answer is checked like any other, against the whole diff and the whole repository.

No check runs when the quick check alone reads the change, or when the reviewer model has no repository tools or the PR head is not checked out. A trivial PR that a deeper review or `review.routing` gives finders gets its checks. The claims are then recorded as `unchecked`.

The round record lists the claims under `prClaims.claims`: the quote, its `source` (`description` or the `file:line` of the comment), the reviewer name, the `status`, the check's reason and cited lines (`proof`, and `relatedProof` for lines of a related repository), the number of defects it reported, and `call` when the check gave no answer (`failed`, `timed_out` or `skipped`). `prClaims.cut` counts the statements over the cap, and `prClaims.skipped` says why none was listed when the listing call failed. `usage.llmCalls` records each check under the `claim_check` stage. `usesOutsideDiff.claimTerms.terms` lists each term searched for the claims: the position of its claim in `prClaims.claims`, the repository, the term, how many lines hold it, how many of them its check was shown, and `notShown` when it showed none because it is too short or too generic to search for (`unsearchable`), too many lines hold it (`common`) or its search failed (`failed`). A term with fewer lines shown than found was cut by a cap. `usesOutsideDiff.claimTerms.cut` counts the terms the call gave past 3 for a claim and repository, which were not searched. `usesOutsideDiff.claimTerms.skipped` says why no term was guessed or searched.

## Sweeping for a defect class

A finder that reports one instance of a mistake often stops there, although the same kind of mistake can sit elsewhere in the PR. The first place found is not always the one that matters: a mistake noted in a test helper can be a blocker where production code makes it. With `review.sweep`, read from the base branch, a finding the judge keeps starts one more call. The value names the lowest grade that starts one:

- **`off`** (the default): no finding does.
- **`blockers`**: each blocker.
- **`warnings`**: each blocker, and each warning that its cited lines or a tool check prove.
- **`notes`**: those, and each note outside the `style` row of the severity table, so not one about wording, formatting, naming or docs.

A finding a check disproved starts none. Below blocker, neither does a tool alert, since the tool reports every place itself, nor a finding on code the PR did not change. A round runs at most three sweeps, whatever the value and however many findings it kept. The security findings go first, then the blockers, the warnings and the notes. Within a grade, those a check confirmed with tools come before those the cited lines prove, and the notes keep the judge's order. The rest are recorded as `cut`. So `notes` reaches a note only in a round with fewer than three findings above it.

The call states the finding's defect class in general terms, such as "a cache key leaves out a field the cached value depends on", never the instance, and lists every other place in the diff that makes the same mistake, each with its own proof. When it judges the class too specific to recur, such as a typo or a wrong constant, it reports nothing. Each place is graded on its own, by the judge and by what goes wrong there. It does not take the grade of the finding that started the sweep, so a note can lead to a blocker and a blocker to a note. Once found, it also stands on its own: when a later step drops or hides the finding that started the sweep, such as a memory suppression, the `review.notes` limit or a check at the round's end, the places that sweep found stay.

Each call runs on `models.reviewer` at the finders' effort, with repository tools when the finders have them, at most 15 steps, and its calls are recorded under the `sweep` stage. A place on or next to a line the starting finding cites, or exactly on a line another finding the judge kept this round cites, as its own line, proof or evidence, in any file, is dropped and logged, and so is one the judge already judged this round, or one the dedup model calls the same defect as a nearby judged finding. An evidence line counts there by the `path:line` it starts with, read like a proof line, so one that cites a related repository as `owner/name:path:line` names no line of the PR. The rest go through dedup against earlier rounds and through one more judge call, which sees no open threads, like any finding. When that judge call fails, the round ends incomplete and posts no findings, so a blocker the sweep found is never lost behind an approval. They are named `Sweep 1`, `Sweep 2` and so on, never after the starting finding's text, and one that restates an earlier open thread folds into it. Their tool checks come out of the round's eight, so the setting never raises that number. The round record lists each sweep under `sweeps`: its reviewer name, the location and grade of the finding that started it (`source` and `severity`), its status (`answered`, `too_specific`, `failed` or `cut`), the class it stated and how many places it found.

A round with sweeps costs at most three sweep calls, which run at the same time, one call of the dedup model for places near a judged finding, the usual dedup against earlier rounds, and one more judge call. With `blockers` only a round that keeps a blocker pays that. With `notes` most rounds that keep any finding do. The setting is off by default until a benchmark run decides whether the extra calls pay for themselves. `bench/variants/sweep.yml`, `sweep-warnings.yml` and `sweep-notes.yml` turn on one value each.

## Related repositories

`related_repos` lists public repositories on github.com that the review may read as context. Each entry has:

- **`repo`**: the repository as `owner/name`.
- **`kind`**: `reference` for a repository this one implements or ports, such as a protocol's reference implementation or its specifications. `consumer` for a repository that depends on this one, where a change to a public API or a wire or data format can break it. `dependency` for a repository this one depends on, such as a library it calls, where a change can rely on something the library does not guarantee.
- **`ref`** (optional): the branch, tag or full commit hash to read. The default is the repository's default branch. For a `dependency`, set it to the version this repository pins, since Manki does not read that from a lockfile or manifest. Write a branch or tag whose name looks like a short commit hash, such as `20240115`, as `refs/heads/20240115` or `refs/tags/20240115`.
- **`paths`** (optional): up to 20 paths or globs inside the repository, such as `src/` or `packages/rs-*`. Only these are fetched, along with a root `AGENTS.md` and `CLAUDE.md`. The default is the whole repository. Set it for a large dependency, so its code does not crowd out the PR's own.

```yaml
related_repos:
  - { repo: dashpay/dash, kind: reference, paths: [src/] }
  - { repo: dashpay/dips, kind: reference }
  - { repo: dashpay/platform, kind: consumer, paths: ["packages/rs-*"] }
  - { repo: tokio-rs/tokio, kind: dependency, ref: tokio-1.38.0, paths: [tokio/src/] }
```

Every stage with [repository tools](security.md) reads these repositories through the same tools, by naming one in a `repo` argument. The rest of this paragraph is what the stages that look for findings are told: the finders, the sibling comparisons and the sweep. When the PR title, description or changed code says the change matches a reference, or follows its spec, they open the code the claim names and compare it with the change. They also read a reference when the changed code implements or mirrors it, and compare each contract in both directions. They read a consumer only when the PR changes a public API or a wire or data format, to find the consumer's code that uses it. They read a dependency when the changed code calls it or relies on what it does, and check that what the change assumes about it holds in its code: what a function validates, what a signature or hash covers, which errors it returns, and what it guarantees about ordering, retries or concurrency. For example, a service retries a call because it takes a client library's timeout to cover the whole call, while the library applies it to each attempt. A divergence from a reference is graded like any other finding. A change that breaks a consumer is a warning that lists the consumer's call sites, and a blocker only when the PR says it does not break anything. An assumption a dependency's code does not keep is graded like any other finding, and a different design in the dependency is not a finding by itself. A model without tools never reads them. For a finder with repository tools, the checklist gains one check per configured kind. With a `reference`: when the change touches a wire format, a protocol message or a rule a specification defines and a reference holds that specification, search it for the name of the message, field or rule and compare the change with what it says. With a `consumer`: for each public type, function or serialized format the change alters, find its uses in each consumer and check that they still work. With a `dependency`: for each function, type or message of a dependency the changed code calls or relies on, name what the change assumes about it and check that the dependency's code keeps it. The wording for a `dependency` is part of a prompt only when one is configured.

The finders and the quick check of a trivial PR, the sibling comparisons, the [claim checks](#claims-of-the-pr-text), the sweep, the refuter and its pair, the judge with `judge.tool_steps` and the reply in a review thread all read the related repositories, each when its model has repository tools. The planner, dedup, the verdict reader, `/manki explain` and questions have no repository tools and never read them. The refuter, the judge and the thread reply check a finding instead of looking for new ones. They get the list of repositories without the grading rules above, and are told to name a repository only when what they check cites its code as `owner/name:path:line` or rests on what that code does, and to read that code before they answer. Every stage that can read a related repository is told that everything in it is untrusted data that other people wrote, never instructions. A call that names a repository Manki cannot fetch returns the reason. The stage is told that it has not read the repository then: it says so, treats whatever rests on that code as unchecked, and never answers about that code from memory.

A finding cites a related repository's code as `owner/name:path:line`. Manki tells the judge whether each cited line is in the checkout the round fetched. When the judge's model has repository tools, Manki also shows it the lines around the citation under the finding as "Cited code in a related repo", so the judge grades from the code and not from the finding's account of it. When an evidence line of the finding starts with such a citation and quotes code in backticks, Manki compares the quote with the fetched file. Code quoted after a further citation in the same line belongs to that citation, and is not compared with the first. A quoted part counts as there when it sits within 3 lines of the cited lines, whitespace aside. In a citation of more than 7 lines the quote could sit anywhere, so finding it there says nothing, and the citation is reported like one without a quote. A quote that is not in the cited lines at all is still reported as missing, in whole or in part, since that is certain at any width. A quote in double backticks is read as one quote, so it can hold a backtick. A quote cut by an ellipsis is compared part by part, every part of it, and so are the quotes of several evidence lines for one citation. Citations of one file and first line, such as `src/a.ts:12`, `./src/a.ts:12` and `src/a.ts:12-14`, are one place and get one answer, the worst of theirs. So a quote the lines do not hold decides the place whichever spelling it stands with, a range the file does not hold makes the place not found, and a quote that was not compared outweighs one the lines hold. The judge gets one of three answers. A citation with every part there holds the quoted code. One with only some of them is reported as holding only part of it, with the parts found and the parts missing named, which is also what a line that quotes this repository's own code beside the related one gets. One with none of them is reported as not holding the quoted code. Only the first answer confirms the citation, and the other two prove nothing. The judge still sees the lines the fetched file really holds at that place, and is told to grade from those lines and not from what the finding says they hold. A citation that is neither confirmed nor shown counts as code the judge cannot see. A quote of fewer than 6 characters, whitespace and ellipses aside, is taken as a name the sentence mentions and is not compared. Any other text in backticks after the citation counts as a quote of the cited lines, also a path or the name of a caller, so such a line is reported as holding only part of the quoted code. Only the first 10 related citations of a finding are looked up. To show these windows, and the ones around a finding's proving lines of the PR outside the diff, Manki tries at most 10 cited files of the PR and 10 of related repositories for a finding, and 80 in a round, whether or not a file is there, and tries each file once a round. So a finding that cites many missing files costs no more than that. A cited file over 1 MiB is not read: the judge is told its citation is unchecked, and a refuter's answer cannot use a line of it as proof. Git allows `:` in a file name, so a PR can hold a file at the very path a citation spells, such as a file named `acme/reports:src/import.ts`. Such a file changes nothing about the citation: it is looked up in the related checkout like any other, and its note to the judge only remarks that the PR also has a file at that path. A file the PR adds can therefore never take away what a related repository's code shows.

A refuter's answer lists the lines that decide it. A line of a file over 1 MiB is not read and proves nothing, in the PR's repository or in a related one. Neither does a line its file does not hold: line 0, a range that runs backwards, or a line past the last one. A line of a related repository counts there only when it is in a checkout the round fetched, at most 10 for the answer and 10 for each premise, and the round record keeps them as `relatedProof` on the refutation and on each premise. Only the first 10 related lines a list cites are looked up. Manki writes each kept location itself, from the repository's configured name and the file's own path in the checkout. The finding shows it wherever it shows its checks: in a review thread, in the review body and in the output of `manki review`. There it is a link to the line at the commit the round fetched, or the location alone when the round recorded no commit. A blocker that a round lists again from an earlier record, because no thread carries it, shows its related lines as locations without a link, since they were read at the commit that earlier round fetched. It is listed under "Checked in the code" on the condition that makes a check's lines of the PR proof of the finding: the check confirmed the defect, or its confirmation raised the grade. The round record then keeps it as `relatedProof` in the finding's `evidence`, at most 10 lines for a finding however many checks add to it. A finding that is folded into another, as a duplicate or into a blocker of the verdict reader, brings its related lines along, under the same limit of 10. Of a check with premises the lines of its own answer are kept before the lines of its premises. A check that did not, such as one that confirmed only a premise, names the line in its own sentence. A line of a repository that is not configured or was not fetched, or that the fetched file does not hold, is neither proof nor shown. An entry of the list that reads as a line of a related repository is never read as a line of the PR as well, and a file of the PR at the path it spells does not make it one. A related line that counts can confirm a finding or a premise. It never disproves one alone: a disproof still needs a line of the finding's own file or of the diff, since a disproof can lift a finding and a related repository is code the PR's reviewers do not control. A check that rests on a related line is never reused in a later round, because the repository can change while the PR's files do not, so the next round checks the finding again. An answer from a round before that check is not reused in its place either: only the latest stored answer for a finding counts.

A reply in a review thread reads `related_repos` from the base branch like a review. It fetches nothing up front. A repository is fetched the first time the reply names it, within a minute, and the reply as a whole has 15 tool steps and 5 minutes. [Replies in a review thread](#replies-in-a-review-thread) says how a line of a related repository counts for a statement of the reply. The reply record lists each configured repository as `relatedRepos`, like a round record. A reply that keeps a finding has to cite a line the finding did not cite. A line of a related repository counts there as a location of its own, and is never taken for the line of the PR's file at the same path.

Manki reads `related_repos` from the PR's base branch only, so a PR cannot make Manki fetch another repository. A PR that changes it is reviewed with the base branch's list. Every related repository is fetched before the finders run, on a round whose finders have repository tools and whose diff names something to search for. On any other round where a model has repository tools, a repository is fetched the first time a stage names it. So a round whose finders have no tools still fetches a repository that its refuter or its judge names. Each is fetched once per round however many stages read it. When a stage is stopped in the middle of its fetch, the next stage that names the repository fetches it again, into a folder of its own that no cache keeps, since the git process of the stopped stage can still be writing the first one. The fetch is a shallow, path-limited clone of one commit (`git` with `--depth 1`, `--filter=blob:none` and a sparse checkout of `paths` and the two root guide files), run without any credentials, so a private repository cannot be read. A repository that is private, missing, or not fetched within a minute gives a warning, and the review goes on without it. So does one whose fetch was stopped with its stage when no later stage asked for it, and its reason in the round record says that. The round record lists each configured repository as `relatedRepos`: fetched, failed with the reason, unused when the round never fetched it, or skipped when no model of the round had repository tools, with how long its fetch took, how many tool calls read it (`reads`) and how many of those each stage made (`readsByStage`, with the refuters as `refute` and `refute_pair`). Each call with tools in `usage.llmCalls` counts its own reads as `relatedReads`.

Before the finders run, Manki searches each fetched related repository for the names the diff changes or reads and the names its added comments mention, such as `MAX_BODY_LENGTH` in a comment that says the change follows that limit. The search ignores case and underscores, so `retry_delay` also finds `retryDelay` and `URLInfo` finds `URLINFO`, except that an `ALL_CAPS` constant keeps its case. Names of test functions, words that do not read as code and names longer than 160 characters are left out, and so are the root `AGENTS.md` and `CLAUDE.md` of the repository. The names are searched together in one pattern of at most 15 KB, and a name that no longer fits it is not searched. The section names it as not searched, apart from the names nothing matched. When the search of one repository fails and another of the same kind is searched, the section names the repository that was not searched, and a name the others do not hold is listed as not searched there, never as a name nothing matched. A dependency is searched for a different list, which Manki collects only when a `dependency` repository is configured: the names the added comments mention, then the functions the changed lines call and the fields they read, most used first, such as `verify_chunk` in `store.verify_chunk(data)`. Calls and reads in test files and in Rust test code are left out. So is a called or read name that the change also declares, since a library does not hold it. The list for a dependency holds at most 80 names. One call to the `dedup` model first guesses what each fetched repository calls those names, from the names, the file types the change touches and each repository's most common file types: a Go server may call a Python client's `fetch_profile` `GetUserProfile`. The search then looks for the guessed names as well as the original ones, at most 2 guesses a name. No names are guessed for a dependency, since the names a change calls are the dependency's own. A line only a guessed name finds is listed under the original name, marked "also searched as", after the lines the original name finds, and the section says that such a name is a guess to check. A guess that reads as code is matched like any name, a plain word only in its exact case. The guesses are searched after the original names and apart from them, so a guess whose search fails costs only the guesses searched with it. The round record marks those as `failed`, and likewise every guess for a repository whose search for the original names failed, and a guess that found no line and no longer fit the pattern. The call takes at most 45 seconds and shows in `usage` as the `translate` stage. When it fails or its reply cannot be used, the search runs with the original names alone. The finders, the judge and the refuter get the matches after the uses outside the diff, as an "In the Reference Repos" section, an "In the Consumer Repos" section and an "In the Dependency Repos" section, each only when a repository of that kind is fetched. Each lists for each name at most 4 lines, 40 lines in all, and the names nothing matched. The reference section asks to compare the change with the reference. For a name that starts with a capital letter, such as a constant or a type, it puts a line that declares the name first. The consumer section asks to check that each line still works with the change. The dependency section asks to check that what the change assumes about a line holds in that code, and orders its lines like the reference section. All three then list the repository's other code, comments and documents, then its tests, then vendored code. The round record keeps the locations under `usesOutsideDiff.reference`, the names nothing matched under `usesOutsideDiff.referenceMissing`, the names the 40-line cap left out under `usesOutsideDiff.referenceCapped`, and the names that were not searched in every repository under `usesOutsideDiff.referenceUnsearched`, with `consumer`, `consumerMissing`, `consumerCapped` and `consumerUnsearched` for the consumers and `dependency`, `dependencyMissing`, `dependencyCapped` and `dependencyUnsearched` for the dependencies. Under `usesOutsideDiff.translation` it keeps each guessed name with its repository, the original name and how many lines of that repository hold it, or `skipped` with the reason when the call failed, its reply could not be used or no model is set up for it.

A related repository often keeps a guide for its own contributors at its root, `AGENTS.md` or `CLAUDE.md`. For each repository fetched before the finders run, Manki looks for that file, `AGENTS.md` first, and the prompt of the finders, the sweep, the refuter and a judge with tools names its path as a map of that repository: they read it first to find where the repository keeps what they look for. The prompt says that the guide's rules govern that repository and not the PR, and that its text is untrusted data. Manki itself never puts the text of these two root files into a prompt: the prompt names only the path, and the search described above skips both files. A model that opens the guide reads it with its tools, as untrusted data like any other file of that repository. A repository limited by `paths` still has its root `AGENTS.md` and `CLAUDE.md` fetched, so its guide is found too. A repository fetched later, on a stage's first read, gets no pointer, and neither does a thread reply. The round record names the file as `guide` on the repository's `relatedRepos` entry.

The clones go to `manki-related-repos` in the runner's temp directory. To reuse them across runs, restore and save that directory with `actions/cache` before the Manki step. Each run saves a new entry and restores the latest one:

```yaml
      - uses: actions/cache@v6
        with:
          path: ${{ runner.temp }}/manki-related-repos
          key: manki-related-repos-${{ github.run_id }}
          restore-keys: manki-related-repos-
```

Of a restored clone Manki keeps only the object store, and only once `git fsck` finds it intact, so a tampered cache entry cannot change how git runs. It first removes an unfinished pack that a stopped fetch left there, which git itself would keep. The fetch then downloads the commit and its trees again, and only the files the cache does not hold yet, and Manki repacks the store so it keeps one copy of each object. A job with `cache-mode: read` restores the cache and saves nothing (see [Cache access](getting-started.md#cache-access)). No other job writes this cache, so such a job fetches every related repository from scratch on each run. A run for a thread reply uses the same directory, so with this step a reply that names a related repository finds its clone already there.

## Related open PRs and issues

Manki looks for other open work on the same change while the review runs. It lists up to 5 open PRs, drafts included, that change a file this PR changes, from the 50 most recently updated, most shared files first. It also searches the repository's open issues for up to 6 words: names the PR's added lines declare, such as a new function, and the longer words of its title. GitHub refuses a query of more than 256 characters, so a word that no longer fits is left out. The search takes up to 5 issues and leaves out the ones the PR body links. One call to the `dedup` model then reads this PR's title, description and changed files next to each candidate's title, the start of its description and, for a PR, its changed files. It answers whether each one is a duplicate PR, an overlapping PR or issue, an issue this PR fixes without linking it, or unrelated.

The review body lists every candidate that is not unrelated under "Related work", with its relation and a link. The model's one line of reasoning stays out of the review, since the candidates' text could steer it, and only the round record keeps it. The note never blocks, never opens a thread and never changes the verdict: whether a duplicate PR should close is the author's call. The other PRs' and issues' text reaches the model only as untrusted data in fenced blocks, cut to 400 characters each, and their titles are sanitized before they are posted. A list that fails is skipped with a warning. Neither request is retried or held for a rate limit, and the whole lookup gives up after 15 seconds, so the review waits at most that long. A list still running then is cancelled and recorded as timed out. A local review has no GitHub to ask and skips the step. The round record keeps each candidate under `relatedWork.candidates`, with its number, how many files it shares, the classification and the reason, and names any list or call that was skipped. The model call shows in `usage` as the `related` stage.

## Round records

Each review summary on the PR embeds a `Manki context` block. The block is a hidden HTML comment holding the round's diagnostics as JSON: models and effort, timings, token use, the planner's choices, every finding the finders reported (`reviewers.rawFindings`), dedup drops, and the judge's decisions with its reasoning, including the findings it dropped (`judge.dropped`). When it would not fit in the review body, Manki stores it gzip compressed and base64 encoded in the same comment instead of cutting it. Only a record too large even compressed loses its per-file and per-finding diagnostics, and `meta.omitted` then names each field left out. While it fits, such a record still keeps every finding the finders reported with only its title, location, severity and reviewers, and the uses outside the diff with only names and locations, so a missed defect can still be traced. `meta.compacted` then names those two fields. `usage.llmCalls` lists every LLM call of the round: the stage and finder, model and effort, input, output, cache read, cache write and reasoning tokens, duration, attempt, whether a fallback model answered, and an estimated cost in USD at public API prices. A call whose model has no known price, or whose provider reports no token counts (the Codex and Gemini CLI paths), counts as unpriced, and subscription use is not billed per token, so the cost is an estimate of the same calls on the API. `usage` also holds the totals for the round, per stage (`perStage`) and per model (`perModel`), and in `limits` the newest reading of each subscription usage window the Claude and Codex CLIs reported: the account, the window, the share used and the reset time. Its `durationMs` is the time spent in model calls, and `wallClockMs` the wall-clock time of the whole run, the same time the finished progress comment shows in its headline, such as "Review complete in 4m 12s". Each call also records `promptDigest`, the first 12 hex digits of the SHA-256 of its system prompt with every number in it replaced, so calls before and after a prompt change compare and the counts a prompt quotes, such as the open threads, do not split one version (an edit that changes only a number in a prompt keeps its digest, so `meta.mankiVersion` tells such versions apart), and the judge's digest hashes its prompt with every round-dependent section on, so it changes only with the template or the repository's rules, and for a call with tools its `stepBudget`, and on a Claude call `wrapUpNoted`, set when the model used enough steps to be told to wrap up. A Claude call with tools also records `toolSteps`, each tool it called in order, and `filesRead`, each file it read once, relative to the repository root, with `owner/name:` in front of a file in a related repo, so a missed defect can be told apart from a file no finder opened. `meta.promptVersions` lists the distinct digests per stage. The record also keeps why a round paused (`meta.needsHuman`, its cause and blockers), how each static analysis source ended (`staticAnalysis.sources` for checks, code scanning and dependency review, with the reason one gave nothing, such as an HTTP 403, next to `staticAnalysis.analyzers`), the learnings and suppressions memory loaded and each finding a suppression hid with the suppression's id (`memory.loaded`, `memory.suppressed`), and each call the run made to the token service before it posted, with its status, and for a failed one the error and the service's request id (`tokenService`). `runner` describes the machine and what the run took from it before it posted: `environment` (`github-hosted` or `self-hosted`), `os`, `arch`, `cpus`, the machine's `memoryBytes`, and `memoryLimitBytes` when a container limits the memory below that. It never holds the runner's name, since the record is posted with the review and a self-hosted runner's name can be a host name. `queuedMs` is the time from the start of the workflow run until Manki started, so the wait for a runner and the job's steps before Manki. It is left out when the workflow token cannot read the run, which needs `actions: read`, and when GitHub does not answer within ten seconds. Manki reads the run while it reviews, so a review posted before the answer has no `queuedMs` either, and its footer no such time. The last line of the run log still shows it. `peakMemoryBytes` is the most resident memory Manki and its child processes held at once, such as the model CLIs, git and the analyzers. Manki samples it every two seconds on Linux and macOS, and other systems leave it out. `peakCliProcesses` is the most model CLI processes that ran at the same time. The run log ends with the same figures, also for a run that posts no review. Each reply Manki posts in a thread or to a command carries the same usage in a hidden `<!-- manki-reply-record: ... -->` comment. A review state check that approves, holds or withholds the approval puts a hidden `<!-- manki-approval-record: ... -->` on what it posts: the approval review, or the held or withheld notice while that stands. It records the decision, the reason, the head commit and how many of Manki's threads are resolved. A check that skips posts nothing, and its decision shows only in the run log and in the token service's `coordinator_finished` log line. A reply record also keeps the token service calls of its run, and for a thread reply that opens with `Fixed`, `Agreed` or `Withdrawn` what it decided for the thread (`decision`): it resolves the thread, the thread stays open for a maintainer, the replier may not resolve it, the thread was already resolved, is not found or could not be looked up, or a later round already judged the fix.

Each finding, kept or dropped, records `gradePath`: every change of its severity after the reviewer graded it, in order, with what changed it and, where the stage said, why. The steps are `judge`, `rule` (a confirmed [rule finding](#rules-from-instruction-files) raised to the grade `review.rules` sets), `unproven` (a blocker without proving lines posted as a warning), `build_claim` (a blocker that claims a build, type or test failure no CI result reports, posted as a warning), `refutation`, `in_pr_suppression`, `own_proposal`, `contradiction`, `ratchet`, `resolved_thread` and `pre_existing`. A finding the judge graded records `cell`: the row and column the grade was worked out from, with `judgeColumn` when Manki graded it in another column than the judge stated, because it is a security finding. An earlier record can hold `judgeColumn` on a finding a check moved out of the rare column. A blocker that two disproofs put back at its finders' grade records `judgeCell` in place of `cell`, and `reviewerSeverity` is the highest grade a finder gave the finding or a duplicate merged into it. A finding the judge doubted records `gradeIfConfirmed`, the grade its cell gives once every doubt holds, and its `doubts`, and its refutation records the answer to each premise under `premises`. A refutation that ended unsettled records `stepsUsedUp`: `yes` when its call ended on its step budget, so it took enough tool steps to be told to finish (12 of its 15) or took them all, which also holds for a call that was done anyway, `no` when it took fewer, and `unknown` when the client does not report the steps of a call, as the Codex CLI. An open lead's entry in `leads` holds the same refutation, so the record shows how often a lead was left unsettled by a check that may have run out of steps. A `gradeIfConfirmed` of `warning` beside a `cell` that gives a blocker marks a finding no confirmation raises: the judge stated `warning` for that case, or no finder filed a blocker, the finding is no security finding and it restates no earlier blocker. `judgeIfConfirmed` is the judge's own answer for that case, `blocker` or `warning`, and is missing when the judge stated none. For a finding in the rare column of the wrong behaviour row, `gradeIfConfirmed` is the grade of the normal column, which no check gives it. The answer to its premise tells a rare claim the code bears out (`disproved`) from one the check contradicts (`confirmed`) and one nobody could settle (`unsettled`), and a doubt with no refutation was never checked. A finding the reviewer marked pre-existing and the judge kept records `preExisting`: the reviewer's reason and how the claim was checked, `pre_existing` when it held, or the condition that failed (`no_location`, `excluded_file`, `deleted_file` or `touches_diff`). A finding memory hid is listed in `memory.suppressed`. Each entry of `findings.entries` records `posted`, where the round put the finding: `thread` for a thread of its own, `body` for the review body, or `earlier_thread` when a thread from an earlier round carries it. An entry of `findings.unposted` records `record`. `findings.originsWithoutPrior` is set on a later round that tagged its findings without the PR's change at the last reviewed round, which is a "Review again" run or a failed fetch of that change. `findings.carried` holds the warnings the round carried from an earlier round's review body, each with `raisedIn` and `citedLine`, and `findings.carriedEnded` the ones it stopped carrying, each with its reason. They do not count in `findings.count`. An entry that restates a finding an earlier review body listed records `sameAs`, the key of the entry that listed it first. A round that read the diff in slices records the number of files in each slice and the verdict reader's answer on each (`slicing`). `diff.changedSinceLastRound` is the number of changed files the push since the last round touched, `judge.fixClaimedThreads` the threads where someone claimed a fix, and `approval` on a round that approved whether the approval was held, and why. To pull the round and reply records of a PR or a whole repo into one JSON Lines file, run `npm run review-history -- <owner/repo> [<pr number>] > history.jsonl` in a manki checkout. Add `--calls` to get one line per LLM call instead, ready to sum per agent, stage, model, PR or repo. The script decodes compressed records and reads the token from `GITHUB_TOKEN` or `gh auth token`.

To see whether a change to the review helps, run `npm run review-stats -- --repo <owner/repo> [--last <n>] [--fix-rate <fix-rate.jsonl>]` in a manki checkout before and after it. It reads the round records, approval records and thread replies of the last `n` merged PRs (40 by default), only reading from GitHub, and prints a markdown report:

- rounds per PR (mean, median and max), the share that passed after one round, the share that needed 5 or more, and the rounds that ended incomplete;
- the approved rounds, and how many PRs ran more rounds after their first approval, with the number of such rounds;
- findings per round and per approved round by severity, and of the findings a later round raised for the first time, the share on code an earlier round reviewed. A finding the round put under an earlier Manki thread counts in none of these, such as another instance of a finding that went into its thread as a reply. A record from before the `posted` field does not say where a finding went. For those the script leaves out a finding that names an earlier thread, or that matches one by file, title and line. It cannot tell whether that thread was still open at that round, so it also leaves out a blocker posted again after its old thread was resolved. A round that ran without the earlier round's change, which is a "Review again" run or a failed fetch of the change at the last reviewed commit, tags every finding `new`. A record that says so (`findings.originsWithoutPrior`) is left out of the reviewed-code share. An older record does not say so, and its findings on reviewed code are missing from the share, so the share reads too low. A note on reviewed code is not posted, so it counts in none of these either, and shows under `reviewed_code` in the table of findings recorded without posting;
- with `--fix-rate`, which takes the repository's `metrics/fix-rate.jsonl` from its memory repo, the fix rate by severity and by check status for the same PRs. A finding counts as fixed when the judge marked its thread addressed or a later commit touched its lines, whether or not that commit fixed it;
- how blocker threads ended: fixed, withdrawn by Manki, or other;
- per finder model, the raw findings, the kept findings only that model raised and those it raised with another finder, and the tool steps per call;
- the verdict reader's blockers, and the refutation outcomes per severity, counting the findings a disproof dropped, unposted ones and leads left unsettled, and an answer a later round reused only once;
- for the second refuter on `models.refuter_pair`: what it cost, with the number of calls that had no known price, how often it agreed with the first refuter, how often the two split with one confirming and one disproving, and how often it changed the outcome the first refuter alone gave, with a count per pair of outcomes;
- the cost per PR and per round, and the share of follow-up rounds whose inter-round diff was cut or unknown;
- how often each finder model was told to wrap up, the files changed since the last round, the fix claims, the memory loaded and the slices per round;
